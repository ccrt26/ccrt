# 脚本轻量化 + 质量保障体系 — 团队讨论报告

> 日期：2026-05-24 | 议题发起：阿黑 | 参考：豆包质量保障体系方案

---

## 一、背景与问题

项目规模持续增长，代码文件数量已达 46 个（32 个 .ps1 + 14 个 .py），其中存在两个"重磅炸弹"：

| 文件 | 行数 | 函数数 | 问题 |
|:-----|:----:|:-----:|:-----|
| `scoring_engine_v2.py` | 2359 | 25+ | 已用 `# ====` 分 17 区，但全塞一个文件 |
| `stock_data_fetcher.ps1` | 909 | 22 | 行情/K线/财务/资金流/两融/缓存混在一起 |

其余脚本在 238-728 行之间，暂可接受，但趋势是持续膨胀。

核心诉求：脚本拆分轻量化，单一文件不堆砌冗余代码；同时引入质量卡点机制，让每段代码可追溯责任人。

## 三、团队各方意见

### 3.1 腰子（金融负责人）

**关注点**：拆分后评分/选股/风控的计算链路不能断。这是金融底线。

**具体意见**：
- 拆分后 `veto.py` 的每条否决规则必须注释引用红线条款编号，方便 流金 复核时快速对照
- 评分引擎模块间的数值精度不能因拆分而改变（浮点运算顺序等）
- 拆分是工程行为，金融逻辑本身不变——但工程执行中可能碰歪金融参数，必须设验证屏障

### 3.2 流金（风控官）

**关注点**：风控逻辑被碰歪是所有拆分风险中最致命的一类。

**具体意见**：
- `veto.py` 里 7 条绝对否决 + 6 条条件否决，只要一个阈值、一个判断符号被改错，直接漏票或错杀
- 流金 二次复核不能走形式——要逐条对照规则红线原文核验代码逻辑
- 建议拆分前后都跑同一批输入数据，diff 否决判定结果，任何不一致就是 FAIL
- L2 风控模块的代码变更必须触发 流金 复核，不可跳过

### 3.3 红结（代码工匠）

**关注点**：拆分不是切豆腐，依赖关系才是真正的雷。

**具体意见**：
- 评分引擎用了大量模块级变量和裸函数调用，拆之前需要先梳理函数间调用图
- 搞漏一个 `NameError`/`ImportError`，生产环境跑一半炸了
- 建议拆分前先跑一遍静态依赖分析，画出哪些函数调了全局常量、哪些互相引用
- PowerShell 侧风险低——dot-source 天然支持，但要注意 `$script:` 作用域变量

### 3.4 新安（质量工程师）

**关注点**：验证标准不能是"看着对"，必须是"跑了算"。

**具体意见**：
- 拆分验收标准：同一批输入数据，拆分前后各跑一遍，diff 输出——任何一只股票评分不一致、排序不一致就是 FAIL
- 红结 自查清单目前还没有具体检查项，需要先定义：语法/路径/异常/日志 四项逐条打勾
- 拆分后的验证不是一次性工作——每次后续修改都要重跑 diff 验证

### 3.5 旧影（审计官）

**关注点**：拆分过程不可追溯 = 事后问题分不清责任。

**具体意见**：
- 讨论不需要走流程，但一旦动手，每一步必须有书面记录
- 谁拆了哪个文件、谁复核了哪段逻辑、diff 结果存哪里——这些不能靠事后回忆
- 拆分过程中发现的旧 bug 要单独标记，与新引入的 bug 区分开
- 整个过程应记录在 `审计报告/` 目录下

## 五、最终方案

### 5.1 拆分方案（分两阶段）

**第一阶段：两个重磅炸弹**

**scoring_engine_v2.py → `engine/` 包**：

```
代码文件/每日荐股/分析逻辑/engine/
├── __init__.py          # 统一导出接口
├── theme.py             # 题材三分类 + PE差异化估值 (L1)
├── technical.py         # 技术指标 MA/RSI/MACD/ATR (L0)
├── sector.py            # 板块相位 + 动量 + 趋势 (L1)
├── veto.py              # 否决体系 + 市场状态 (L2) ← 最高风险
├── subscores.py         # 技术面子项评分 (L1)
├── scores.py            # 四维评分 + 相位折扣 (L1)
└── engine.py            # main() 入口 + 编排 (L1)
```

依赖方向：`engine → scores → {theme, technical, sector, veto, subscores}`，单向无环。

每个模块标注 L0/L1/L2 等级，决定后续审核路径。

**stock_data_fetcher.ps1 → `modules/` 目录**：

```
代码文件/每日荐股/scripts/modules/
├── cache.ps1            # 缓存层 (L0)
├── quotes.ps1           # 行情 (L0)
├── kline.ps1            # K线 (L0)
├── financials.ps1       # 财务 (L0)
├── fundflow.ps1         # 资金流 (L0)
└── margin.ps1           # 两融+北向 (L0)
```

原文件退化为薄入口，dot-source 各模块。

**第二阶段（后续）**：`run_full_audit.ps1`(728行)、`batch_data_collector.ps1`(505行)、`gen_daily_html.ps1`(425行)。

### 5.2 质量卡点补充（三项新增）

**新增1：需求→代码逐项核对清单**

位置：情墨设计文档末尾。情墨+腰子共同勾签。

内容：
- 选股规则是否 100% 匹配白皮书
- 风控阈值是否与红线规则一致
- 指标算法公式是否与白皮书一致
- 否决条件是否覆盖全部条款

**新增2：红结 提交前自查清单**

写入 `红结-知识库/`，编码完成后逐项打勾：
- [ ] 语法检查通过（`python -m py_compile` / PowerShell syntax check）
- [ ] 所有路径使用跨平台写法，无盘符硬编码
- [ ] 所有 API 调用/文件 IO 在异常捕获内
- [ ] 关键决策点有日志输出
- [ ] 单文件不超过 500 行

**新增3：缺陷台账**

新安 维护 `审计报告/缺陷台账.md`：
```
| ID | 日期 | 文件:行号 | 等级 | 描述 | 状态 | 修复人 | 复查结果 |
```

高频缺陷每月沉淀入 `.claude/knowledge/常见错误.md`。

### 5.3 代码三级分级审核

| 等级 | 范围 | 审核路径 | 示例 |
|:----:|:-----|:--------|:-----|
| L0 | 工具/数据/图表 | 红结自查 + 新安常规 | technical.py, cache.ps1 |
| L1 | 策略/评分/指标 | 情墨复审 + 新安全量 | theme.py, scores.py |
| L2 | 风控/否决/交易 | 全工程 + 流金二次复核 | veto.py |

标签由 情墨 在设计阶段标注，红结 不得自行变更等级。

### 5.4 验证硬标准

拆分验收不靠肉眼：

1. 同一批输入数据，拆分前后各跑 `scoring_engine_v2.py`
2. diff 输出：评分、排序、否决标记 三者完全一致
3. 任何不一致 → FAIL，打回重改，直到完全一致
4. diff 结果存入 `审计报告/`，作为拆分审计证据

### 5.5 编码强制规范

写入 红结 知识库，所有新代码强制执行：

- 路径：`os.path.join` / `Join-Path`，禁用 `C:\`、`D:\` 等盘符
- 异常：所有 I/O 和网络调用包异常捕获
- 日志：关键决策点、数据变更点强制日志
- 拆分：单文件不超过 500 行，超出须申报 情墨 评审
- 注释：veto.py 每条规则带红线条款编号引用

### 5.6 待定决策（需阿黑/用户拍板）

| 决策项 | 选项 A | 选项 B |
|:-------|:------|:------|
| 拆分启动时机 | 现在就动 | 等下次策略迭代窗口一起动 |
| 范围 | 先拆两个重磅炸弹 | 一口气全拆 |
| L0/L1/L2 标签 | 情墨 拆的时候打 | 拆完后团队评审再打 |

## 六、风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|:-----|:----:|:----:|:--------|
| 模块级变量引用断裂 | 中 | 高—引擎直接跑不起来 | 拆分前静态依赖分析 |
| 浮点精度因调用顺序变化 | 低 | 高—评分排序偏移 | diff 验证硬标准 |
| 否决阈值被误改 | 中 | 极高—漏票或错杀 | 流金 逐行复核 + 红线编号注释 |
| PowerShell 作用域变量丢失 | 低 | 中—数据拉取异常 | dot-source 测试 + API 连通验证 |
| 拆分后文档未同步更新 | 高 | 低—维护混乱 | 文件引用路径更新 + 版本号同步 |
| 拆分引入新 bug vs 暴露旧 bug | 中 | 中—责任不清 | 拆分前先跑一轮基线测试记录 |

---

> **团队结论**：拆，但必须是验证驱动的拆——先 diff 基线再下刀，先静态分析再切文件，先 流金 复核再上线。不着急，稳着来。
