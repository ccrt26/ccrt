## Context

现有系统每天对 6 只重点股票生成评分/预判/信号，并输出分析报告。但所有分析仅停留在纸面——无法验证"看多"信号是否真能赚钱、"止损价"是否真能控制回撤。证券公司都有模拟交易系统，我们也需要一套专注于重点股票的模拟交易系统，实现：

1. **信号→交易闭环**：将每日预判转化为模拟买卖操作
2. **绩效量化**：实时跟踪组合净值、胜率、最大回撤
3. **归因分析**：哪个信号/维度贡献了正收益，哪个是负贡献
4. **策略迭代**：积累实盘级交易数据，为规则优化提供依据

## 一、系统架构

### 整体设计

```
评估数据_YYYYMMDD.json  ──→  模拟交易引擎  ──→  持仓更新 + 交易流水
       ↑                          │
  每日自动触发              绩效计算模块
                                  ↓
                            每日快照 + 绩效报告
```

### 目录结构（新建 `模拟交易/`）

```
模拟交易/
├── sim_config.json                # 配置（初始资金、费率、仓位限制等）
├── ex_dividend_dates.json         # 除权除息日配置表
├── 交易引擎/
│   └── sim_trading.ps1            # 核心引擎（读预测 → 执行交易 → 更新持仓）
├── 持仓记录/
│   ├── positions.json             # 当前持仓快照
│   └── transactions.csv           # 完整交易流水（永不清除）
├── 每日快照/
│   └── snapshot_YYYYMMDD.json     # 每日组合估值快照
├── 绩效报告/
│   └── perf_summary.json          # 累计绩效指标（自动更新）
└── 模拟交易白皮书_v1.0.md         # 规则白皮书
```

## 二、交易规则

### 2.1 开仓条件（同时满足）

| 条件 | 规则 | 来源 |
|------|------|------|
| 方向 | Short预测 = "看多" 或 "偏多" | `Prediction.Short` |
| 趋势健康 | TrendHealth.Label ≠ "危险" 且 ≠ "数据不足" | `TrendHealth.Label` |
| 已持仓 | 该股票当前无持仓 | `positions.json` |
| 仓位上限 | 总持仓 ≤ 3 只股票（可控风险） | 配置项 |
| 再入场冷却期 | 该股票过去 5 个交易日内未触发止损 | `positions.json.LastStopLossDate` |
| 止盈后冷却期 | 该股票过去 3 个交易日内未触发 P4 全部止盈 | `positions.json.LastFullTakeProfitDate` |
| **未涨跌停** | **今日开盘未涨停（涨跌幅 < 9.5%）** | 腾讯行情 API 开盘价 vs 前日收盘 |

> ⚠️ **冷却期设计理由**：
> - **再入场冷却期（5 日）**：防止 whipsaw（反复打脸）。同一只股票刚止损又买入，可能连续亏损。
> - **止盈后冷却期（3 日）**：P4 全部止盈后，股价往往处于短期超买状态，立即重新入场可能追高。3 日冷却期既避免追高，又不至于错过趋势延续。

#### 2.1.1 多股选股优先级规则

当同时满足开仓条件的股票数量超过最大持仓限制（3只）时，按以下优先级依次选取：

| 优先级 | 因子 | 规则 |
|:------:|:-----|:-----|
| P1 | CompositeScore | 评分高者优先 |
| P2 | Confidence | 同分时，"高置信度" > "中" > "低" |
| P3 | ShortBull Score | 同分同置信度时，短期看多强度高者优先 |
| P4 | 先到先得 | 以上均相同的，按代码排序取前N只 |

> 设计理由：CompositeScore 是综合评分，反映整体质量；Confidence 反映信号的可靠性；ShortBull 在短线交易中提供额外区分度。
>
> **Confidence 字段解析规则**：评估数据中 Confidence 为文本格式，引擎须按以下映射转为数值用于排序：`"高(>70%)"` → 3, `"中(50-70%)"` → 2, `"低(<50%)"` → 1。无法识别或空值 → 0（排最后）。

### 2.2 仓位管理

| CompositeScore | 仓位比例 | 说明 |
|---------------|---------|------|
| ≥ 80 | 25% | 强烈关注，重点配置 |
| ≥ 65 | 20% | 关注，正常配置 |
| ≥ 45 | 10% | 观察，轻仓试探 |
| ≥ 30 | 5% | 谨慎，极轻仓 |
| < 30 | 0% | 回避，不参与 |

- 仓位比例 = 占**当前总资产**的百分比
- 买入股数向下取整到 100 股（手）
- 单一股票上限不超过总资产的 **30%**

> ⚠️ **注意**：仓位比例在阈值边界有阶梯跳跃（如 Score=64 时为 10%，Score=65 时跳至 20%）。引擎应如实执行，评估阶段再审视是否需要平滑。

### 2.3 入场价格

- **开盘价入场**：读取当日腾讯行情 API 的开盘价 `parts[5]`
- 若开盘价无法获取，使用评估数据的 `Price` 字段（昨日收盘）
- 考虑 0.1% 滑点（买卖双向均适用）

#### 2.3.1 引擎运行时序

引擎运行时机定义如下：

```
T日 15:00   → 市场收盘
T日 20:00   → 生成评估数据_T.json（已有流程）
T+1日 09:25 → 集合竞价结束，开盘价确定
T+1日 09:35 → 运行模拟交易引擎（开盘5分钟后，确保行情API已返回开盘价）
```

> ⏰ **引擎固定于每个交易日 09:35 触发**。在此时间之前，行情 API 可能未返回当日开盘价；09:35 时开盘价已确定且 API 数据稳定。
>
> 如果超过 09:45 仍未运行（如系统故障），当日跳过不开新仓，仅执行止损检查（用最新价代替开盘价）。
>
> 若因节假日/停市等原因无法运行，引擎应静默跳过，不报错中断。

### 2.4 出场规则

#### 2.4.1 出场条件与优先级

| 优先级 | 出场原因 | 条件 | 操作 |
|:------:|:---------|:------|:------|
| **P1** | **止损** | 当前价 ≤ KeyLevels.StopLoss | 全部卖出 |
| **P2** | **趋势恶化** | TrendHealth 变为 "危险" | 全部卖出 |
| **P3** | **预判转空** | Short 与入场时相比变为 "中性" 或 "看空" | 全部卖出 |
| **P4** | **全部止盈** | **当前价 ≥ R3（独立于 Short 方向）** | 全部卖出 + 进入 3 日止盈冷却期 |
| **P5** | **止盈减仓** | 当前价 ≥ R2 | 卖出 50% 持仓 |

> ⚠️ **优先级设计理由**：同一交易日可能同时触发多个出场条件（如开盘跳空既触及止盈又随后跌回止损）。止损（P1）永远优先于止盈——截断亏损比锁定利润更重要，风控是模拟交易的第一原则。
>
> ✅ **P4 条件变更说明（v1.3 → v1.5）**：v1.3 要求"当前价 ≥ R3 **且** Short 变中性"。铁律量化指出：股价到 R3（+10%）说明趋势很强，此时 Short 大概率仍是"看多"，AND 条件导致 P4 几乎永远不触发。**专家确认采纳**：P4 改为纯价格条件，去除 Short 方向依赖。同时新增"止盈后冷却期 3 日"防止在急涨行情中追高。

#### 2.4.2 "预判转空"的滞后处理机制

> ⚠️ **重要限制**："预判转空"出口存在至少 **1 个交易日** 的固有滞后。原因如下：

```
T日 收盘 → 生成评估数据_T.json（含 Short="看多"）
T+1 09:35 → 引擎运行，只能读到评估数据_T.json，Short 仍为"看多"→ 不触发
T+1 收盘 → 股价已下跌，生成评估数据_T+1.json（Short 变为"中性"）
T+2 09:35 → 引擎比对两份数据，发现 Short 变化 → 触发卖出（滞后 1 日）
```

**实现方案**：

1. 在 `positions.json` 的每个持仓记录中增加 `EntryShortPrediction` 字段，记录入场时的 Short 值
2. 每次引擎运行时，加载最近两份评估数据：
   - 用最新数据（T+1 日评估数据，如果存在）的 Short 值与 `EntryShortPrediction` 比对
   - 若 Short 变为"中性"或"看空"，触发卖出
3. 运行时若无新的评估数据（即 T+1 日评估数据尚未生成），则无法检测预判转空，跳过该检查，正常处理其他出口

> 此滞后属于系统固有局限（每日评估数据仅在收盘后生成），无法在现有架构下消除。绩效报告中应标注"预判转空出口存在 ≥1 日滞后，实际效果弱于理论设计"。

#### 2.4.3 R2 / R3 数据来源定义

当前 `评估数据_YYYYMMDD.json` 的 `KeyLevels` 仅有 `Support`、`Resistance`、`StopLoss` 三个字段，**不含 R2/R3**。为保证出场规则可执行，按以下方式补充：

**方案 A（推荐，需改分析白皮书）**：
在 `KeyLevels` 中增加 R2/R3 字段，由分析逻辑白皮书在评分阶段一同输出：

```json
"KeyLevels": {
    "Support": 64.73,
    "Resistance": 61.77,
    "StopLoss": 60.20,
    "R2": 75.00,       ← 新增
    "R3": 80.00        ← 新增
}
```

**方案 B（即插即用，不改数据源）**：
在 `sim_config.json` 中配置固定倍数，由引擎按以下公式动态计算：

```
R2 = EntryPrice × (1 + take_profit_pct_1)
R3 = EntryPrice × (1 + take_profit_pct_2)
```

默认值：`take_profit_pct_1 = 5%`, `take_profit_pct_2 = 10%`。

> ✅ **实施建议**：v1 先用**方案 B** 快速跑通，v2 改分析白皮书时再升级到方案 A。
>
> **补充：ATR 差异化止盈**：固定 5%/10% 对所有股票一刀切不合理——招商银行日均波动 ~1%，多瑞医药 ~4%，统一乘数下低波动股可能永远触不到止盈。建议 sim_config.json 中增加 ATR 倍数选项作为备选：
> ```
> R2 = EntryPrice + ATR × 2.0（替代固定 5%）
> R3 = EntryPrice + ATR × 3.0（替代固定 10%）
> ```
> v1 可在 sim_config.json 中同时保留两种模式，由配置项 `take_profit_mode = "fixed" | "atr"` 切换。

#### 2.4.4 TrendHealth 持仓期间监控

| TrendHealth 变化 | 操作 |
|:-----------------|:------|
| 健康 → **警戒** | 输出黄旗警告，标记该持仓进入关注名单，**不自动卖出** |
| 健康/警戒 → **危险** | 触发 P2 出场，全部卖出 |
| 警戒 → 健康 | 自动从关注名单移除，无操作 |

> 设计理由："警戒"不等于"危险"，不应自动卖出。但持仓期间的健康度恶化值得关注——当同一只股票连续出现多次"警戒"状态时，引擎应在绩效报告中汇总报告，辅助人工审视是否该手动调整止损位。

## 三、核心数据流

### 3.1 每日运行流程

```
① 读取评估数据_YYYYMMDD.json
② 读取当前持仓 positions.json
③ 调用腾讯行情 API 获取 6 只股票最新行情（含今日开盘价）
④ 执行出场检查（按优先级 P1→P5：止损 > 趋势恶化 > 预判转空 > 全部止盈 > 止盈减仓）
⑤ 执行开仓检查（满足条件 → 含冷却期检查 → 按优先级排序 → 计算仓位 → 买入）
⑥ 写入交易流水 transactions.csv
⑦ 更新持仓 positions.json（含 EntryShortPrediction / LastStopLossDate / LastFullTakeProfitDate）
⑧ 计算组合净值 → 写入每日快照 snapshot_YYYYMMDD.json
⑨ 更新绩效汇总 perf_summary.json
```

> 运行时序见 **§2.3.1**：固定于 T+1 日 09:35 执行。节假日自动跳过。

#### 3.1.1 行情 API 降级方案

| API 状态 | 开新仓 | 已有持仓止损检查 | 净值计算 |
|:---------|:------|:----------------|:---------|
| 正常 | 正常执行 | 正常检查 | 正常计算 |
| 降级（备API可用） | 正常执行，数据标注 `[1B]` | 正常检查 | 正常计算 |
| 全部行情API不可用 | 跳过当日开仓 | **用保守估计价检查止损 `[C]`** | 用昨日净值，标注 `[C]` |

**保守估计价定义**（三重回退）：

```
第1优先: min(昨日收盘, 前日收盘)
第2优先: 昨日收盘（前日收盘缺失时）
第3优先: StopLoss × 1.0（前日收盘也缺失时，直接触发止损）
```

> ✅ **变更说明（v1.3 → v1.5）**：铁律量化指出"昨日收盘价"在跳空低开场景下会漏止损。**专家确认采纳**，改用 `min(昨日收盘, 前日收盘)` 作为保守估计，三重回退保证在任何数据缺失程度下都有合理取值。
>
> 设计原则：API 全挂属于极端情况，止损检查宁严勿松。

### 3.2 数据格式设计

**positions.json**（v1.3 新增 `EntryShortPrediction`, `LastStopLossDate`；v1.5 新增 `LastFullTakeProfitDate`）：

## 六、验证方案

### 6.1 前置数据质量检查

每次运行引擎前，对评估数据执行以下质量检查，**检查不通过则当日跳过不开新仓**：

| 检查项 | 规则 | 失败处理 |
|:------|:-----|:---------|
| KeyLevels 完整性 | Support / Resistance / StopLoss 三个字段均存在且为正数 | 跳过当日开仓 |
| Support vs Price 合理性 | Support < Price × 1.5（允许价格已突破支撑位的情形） | 记录警告日志，仍执行已有持仓的止损检查 |
| Resistance vs Price 合理性 | Resistance > Price × 0.5（抵抗位不应远低于现价） | 记录警告日志，仍执行已有持仓的止损检查 |
| StopLoss 合理性 | StopLoss < Price（止损价低于当前价） | 跳过该股开仓 |
| CompositeScore 范围 | 0~100 之间 | 跳过该股开仓 |
| 必要字段存在 | Prediction.Short / TrendHealth.Label / Price / Code 均存在 | 跳过该股 |

> 设计理由：输入数据异常时，宁可跳过也不能让引擎基于错误数据做交易决策。已有持仓的止损保护是最高优先级，不受数据质量问题影响。

**自动预警条件**：

| 条件 | 动作 |
|:-----|:------|
| 最大回撤 > 8% | 输出红旗警告，建议暂停开仓 |
| 连续亏损交易 ≥ 5 笔 | 输出红旗警告，建议审视信号有效性 |
| 单笔亏损 > 总资产 2% | 输出黄旗警告，标记该交易 |
| 胜率 < 40% 且总交易 ≥ 10 | 输出黄旗警告，建议审视开仓条件 |

> ⚠️ **v1.6 补充意见：`ConsecutiveLosses` 计数器重置条件需明确定义**。当前文档未规定连续亏损计数在何时归零——是盈利一笔后重置？还是保本（盈亏比 ≤ 0）也视为亏损？建议定义为：**单笔交易盈亏 ≤ 0 均视为"失败"，盈利 > 0 时才重置计数器**。这笔交易在止盈减仓（P5，卖出 50%）后若剩余部分仍持有，算已实现亏损还是未实现？建议 P5 减仓不计入连续亏损统计，仅完整平仓时才结算。否则减仓动作可能干扰连续亏损预警的准确性。
>
> 🔶 **铁律量化回应**：同意专家方案。补充一细节：**"保本"交易（扣除佣金和印花税后盈亏 = 0）应计为"失败"**，因为考虑了交易成本后保本实际上是净亏损。完整方案：单笔完整平仓后，`净盈亏 > 0` 重置计数器，`净盈亏 ≤ 0` 计数 +1；P5 减仓不计入，仅完整平仓（全部卖出）才算。

#### 6.2.1 Benchmark 比较

在绩效报告中增加与沪深 300 的对比分析：

| 指标 | 说明 |
|:-----|:------|
| 组合总收益率 | 模拟交易的实际收益 |
| 基准总收益率 | 同期沪深 300 的收益 |
| 超额收益率 | 组合收益率 - 基准收益率（正数表示跑赢大盘）|
| 信息比 | 超额收益的年化 / 跟踪误差 |

> **SharpeRatio 与信息比生效条件**：两项指标均基于日频收益率计算，至少需要 20 个交易日样本才有统计意义。运行前 20 个交易日内，两字段均显示 `null`，不触发任何预警。
>
> 基准数据每天 09:35 从行情 API 获取沪深 300 指数最新值。基准的初始值为模拟交易启动当日的沪深 300 收盘价。
>
> ⚠️ **v1.6 补充意见：基准日频收益率存在时间口径错配**。组合的日收益率 = (T 日 09:35 净值) / (T-1 日 09:35 净值) - 1，但沪深 300 基准的日收益率如果按传统方式用(T 日收盘/T-1 日收盘)-1 计算，则两者的日内时间段不一致（09:35→次日 09:35 vs 收盘→收盘），遇到隔夜跳空时两者天然不可比。建议：基准日收益率统一使用 **09:35 截面数据** 计算，即基准日收益率 = (T 日 09:35 基准值) / (T-1 日 09:35 基准值) - 1。这要求引擎首次运行时记录当日的 09:35 基准值作为基准初始值，后续每天用 09:35 值环比，保持与组合净值同口径。
>
> 🔶 **铁律量化回应**：完全同意，无不同意见。建议在 sim_config.json 的 Benchmark 配置段中增加 `InitialValue` 字段，由引擎首次启动时自动填充 09:35 的沪深 300 值，后续以该值为锚点做日环比。

### 6.4 评审遗留风险点

以下问题在 v1 中不做修改，但作为已知风险记录：

| 风险 | 说明 | 影响 | 计划处理 |
|:-----|:------|:-----|:---------|
| KeyLevels 中 Support/Resistance 取值方向需确认 | 现有数据中 Support 和 Resistance 与传统技术分析定义可能不一致（实测部分股票 Support > Resistance） | 可能影响止盈/止损逻辑的有效性 | ⚠️ **v1.6 补充意见：建议在 v1 启动前修复，而非推迟到 v2**。因为 R2/R3 出自 KeyLevels，若 Support/Resistance 已反转，基于 EntryPrice 固定倍数计算的止盈位与真实支撑阻力完全脱节，v1 的出场规则实际上跑在一套不可靠的基准上。"v1 先用"意味着所有止损/止盈结果都无法作为有效参考，回测数据积累越多误导越大 |
>
> 🔶 **不同意见（铁律量化）**：前提认同——Support/Resistance 确实存在倒挂，这是个问题。但 R2/R3 用的是方案 B（EntryPrice × 固定倍数），**并不依赖 KeyLevels**，所以"止盈位脱节"这个推论不成立。止损 P1 依赖 StopLoss，这个字段独立于 Support/Resistance，不受影响。**真正受影响的是 §6.1 数据质量检查中的 Support·Price 和 Resistance·Price 合理性校验**。建议改方案：不修改数据源（涉及改动 run_keystock_analysis.ps1，立项中可以先不动），而是在 sim_trading.ps1 中加一条**前置校验**：如果 `Support ≥ Resistance`，输出 RED WARNING 要求人工确认后再继续。这样改动最小、风险可控、且达到了"不让引擎跑在错误数据上"的目的。请专家评估。
>
> ✅ **专家终审确认（v1.8）**：接受前置校验方案。细化如下：**该 RED WARNING 不阻塞引擎运行**，仅做两件事——(1) 在当日日志和绩效报告中标注 `Support/Resistance 倒挂` 警告；(2) **跳过该股的** Support/Resistance 质量检查项（§6.1 中第 2、3 项），该股其他检查正常执行。其余股票不受影响。这样既不会在无人值守时卡死，也达到了"不让引擎跑在错误数据上"的目的。 |
| 单股止损距离差异大（4%~16%） | 不同股票的止损幅度差异极大，宽止损股会拉大最大回撤 | 最大回撤可能超过预期 | v1 跟踪 MaxDrawdown 指标，触发预警后审视 |
| 闲置资金管理 | 无持仓时段全部现金闲置，无回购/货基等现金管理 | 有通胀隐形成本 | v1 不作处理，v2 可考虑加入逆回购模拟 |
| 盘中止损盲区 | 引擎每日 09:35 仅运行一次，盘中价格若跌破 StopLoss 后反弹，止损不会触发 | 实际止损效果弱于预期，最大回撤可能放大 | v1 在绩效报告中标注"日频模拟，非实时监控"；v2 可增加盘中多时段检查 |
| **涨跌停无法成交** | A 股有 ±10% 日涨跌幅限制（科创/创业板 ±20%）。若持仓股跌停，09:35 检查时 StopLoss 已触发但卖单无法成交。引擎目前假定任何出场指令都能按当前价成交 | 跌停场景下模拟交易记录虚假成交，实际无法止损 | v1 应在引擎中增加跌停检测：若触发止损当日该股跌停，记录"未成交"标记，持续跟踪直到恢复流动性能卖出。同步在绩效报告中标注"模拟滑点未含涨跌停无法成交风险" |
>
> 🔶 **铁律量化回应**：完全同意涨跌停检测方案，尤其是"跟踪直到恢复流动性"这个设计很务实。补充一点：**涨停场景下开仓也应跳过**——如果某只股票开盘涨停（涨跌幅 ≥ 9.5%），即使信号为"看多"也不应开仓，因为无法以开盘价成交，且涨停后次日大概率高开，追涨风险大。建议在开仓检查中也加一道涨停过滤。
| 初期现金闲置 | 6 只股票中满足开仓条件的可能仅 1-2 只，且仓位比例低（10%~25%），初期大量现金闲置 | 总收益曲线对少数交易高度敏感，初期波动大 | v1 接受现状，在绩效报告中标注"实际仓位比例"供参考 |
| 预判转空存在 ≥1 日滞后 | 评估数据仅在收盘后生成，引擎无法在 T+1 日 09:35 获取 T+1 日的新预判 | 预判转空的实际反应速度比理论慢 1 个交易日 | v1 在绩效报告中标注"预判转空 ≥1 日滞后"；长期方向是引入盘中信号推送机制 |
| **除权除息人工配置** | 引擎依赖 ex_dividend_dates.json 手动配置除权除息日，漏配会导致 KeyLevels 未调整 | 漏配时止损价可能永久高于现价，保护失效 | v1 每月初手动更新一次配置表（耗时约 5 分钟）；v2 可考虑接入除权除息 API |

> ✅ **分红送股处理方案变更（v1.3 → v1.5）**：v1.3 的方案是"手动暂停止损检查"，铁律量化指出暂停期间存在保护真空。**专家确认采纳**改为调整因子法：引擎在 `ex_dividend_dates.json` 中查找当日是否有持仓股除权除息，若有则自动计算调整因子（Ratio = 除权后开盘价 ÷ 除权前收盘价），将所有 KeyLevels 等比下调。此方案更系统化、零保护真空、无需人工干预。

### 8.2 Bug 记录

#### BUG-01：日志文件为空（优先级：P0 必修）

**位置**：`sim_trading.ps1` 第 57-62 行 `Write-Log` 函数

**问题**：`$logLines += $line` 在 PowerShell 函数内部会创建函数级局部变量，不会修改脚本级的 `$logLines` 变量。运行后 `sim_20260522.log` 仅 5 字节（UTF-8 BOM），全为空。

**根因**：PowerShell 变量作用域规则——`+=` 在函数内默认创建局部变量，需显式使用 `$script:` 前缀引用脚本级变量。

**修复方案**：
```
function Write-Log {
    $script:logLines += $line   # 使用 $script: 前缀
    Write-Output $line
}
```

**影响范围**：所有运行日志丢失，无法事后追溯当日交易决策过程。

---

#### BUG-02：SELL_HALF 止盈减仓被排除在交易统计之外（优先级：P0 必修）

**位置**：
- `sim_trading.ps1` 第 425 行（写入 SELL_HALF）
- 第 791 行（CSV 回读时只识别 BUY 和 SELL，漏掉 SELL_HALF）

**问题**：P5 止盈减仓产生的交易记录 Action 为 `SELL_HALF`，但在回读 CSV 计算盈亏时（第 791 行），条件判断为 `$t.Action -eq "SELL"`，`SELL_HALF` 被忽略。导致：

1. P5 减仓的卖出收入从未进入盈亏计算
2. 对触发过 P5 的股票，只算了买入成本，漏了一半卖出收入
3. 胜率、盈亏比、连续亏损计数全部失准

**修复方案**：第 791 行增加 `SELL_HALF` 识别：
```
} elseif ($t.Action -eq "SELL" -or $t.Action -eq "SELL_HALF") {
```

**影响范围**：任一股票触发 P5 止盈减仓后，交易统计数据即产生偏差。运行时间越长、P5 触发越频繁，偏差越大。

---

#### BUG-03：交易按股票聚合而非按轮次——Trade Counting 失真（优先级：P0 必修）

**位置**：`sim_trading.ps1` 第 797-804 行

**问题**：当前实现按 `(股票代码)` 分组，将该股票全部历史买卖合并计算一笔盈亏。如果一只股票被买卖多轮（买入→卖出→冷却→再买入→再卖出），多轮交易被合并成 1 笔统计。

```
示例：
601689: BUY(May1) → SELL(May3) → BUY(May10) → SELL(May12)
当前计算：1 笔交易（4 笔行为合并）
正确计算：2 笔交易（两轮独立买卖）
```

**影响**：
- `TotalTrades` 远低于实际交易次数
- `WinRate` 完全失准
- `ConsecutiveLosses` 可能被掩盖

**修复方案（最小改动）**：按时间顺序遍历交易记录，按以下逻辑配对：
1. 按 `(Code, 时间)` 排序
2. 遇到 BUY 时记录待配对买入
3. 遇到 SELL/SELL_HALF 时与最近的未配对 BUY 匹配
4. 完整平仓（全部卖出）后结算一笔完整交易

**影响范围**：全部交易统计指标。运行时间越长，累积误差越大。

### 8.3 优化建议

#### SUG-01：涨跌停阈值应区分板块（优先级：P2 建议）

**位置**：第 191-197 行 `Test-IsLimitUp / Test-IsLimitDown`

**问题**：统一使用 9.4% 阈值判断所有股票的涨跌停。但：
- 主板（600/601/603/000）限幅 ±10%，9.4% 合理
- 创业板（300/301）限幅 ±20%，9.4% 远未涨停
- 科创板（688）限幅 ±20%

当前 301075 多瑞医药（创业板）在 9.5% 涨幅时会被误判为涨停，实际离涨停还远。

**建议**：在 `codeMap` 中增加板块标记，按不同标准判断：
```powershell
$codeMap = @{
    "603019" = @{ Market="sh"; Name="中科曙光"; Board="main" }
    "301075" = @{ Market="sz"; Name="多瑞医药"; Board="chiNext" }
}
function Test-IsLimitUp {
    $limit = if ($board -eq "chiNext" -or $board -eq "star") { 19.4 } else { 9.4 }
    return $ChangePct -ge $limit
}
```

#### SUG-02：CSV 回读应使用结构化解析而非按逗号分割（优先级：P3 建议）

**位置**：第 774 行 `$fields = $line -split ','`

**问题**：按逗号分割行字段脆弱——如果未来任何字段（如股票名称、Reason）包含逗号，解析会错位。当前数据安全，但看长期维护。

**建议**：改用 `Import-Csv` 读取或至少限制分割数量。当前数据中 `Reason` 字段格式为 `开仓_看多_健康`，使用下划线而非逗号，暂安全。
