# 04 — 审计处理流程（红线规则）

> **定位**：Gauge 发现 FAIL 项后的闭环处理规程。本流程为 Gauge 红线规则，任何审计发现必须走完此闭环，不得在未修复的情况下关闭 FAIL 项。

---

## 一、闭环总览

```
 Gauge审计   →   发现FAIL    →   汇报阿黑    →   阿黑分派    →   角色修复
    ↑                                                              │
    └──────────────── 验证通过 ← 重新审计 ← 阿黑通知 ← 修复完成 ──┘
                              ↓
                         验证未通过 → 回到"汇报阿黑"
```

**铁律**：FAIL 项未经验证关闭不得从审计记录中移除。每一个 FAIL 项都必须走完整个闭环。

---

## 二、分步规程

### 第1步：Gauge 审计 → 发现 FAIL

Gauge 执行审计（日检/周检/月检），产出审计报告（JSON + PDF）。

对每一个 FAIL 项，Gauge 必须记录：
- **编号**（如 `[G-1]`）
- **描述**（什么问题）
- **根因**（哪个文件、哪行、什么偏差）
- **修复路线**（具体到文件路径+行号+改动内容）
- **责任角色**（建议由谁修复）

### 第2步：Gauge → 阿黑 汇报

Gauge 向阿黑提交「审计异常报告」，包含所有 FAIL 项的完整信息。

**汇报格式**：

```
阿黑，[日期] [模式] 审计发现 N 项 FAIL：

FAIL-1 [编号] [描述]
  - 根因：[具体文件+行号+偏差]
  - 修复路线：[具体改动]
  - 建议责任人：[角色]

FAIL-2 ...
```

Gauge 不得跳过此步骤直接找修复人——所有 FAIL 必须经过阿黑。

### 第3步：阿黑 → 分派修复

阿黑收到 Gauge 汇报后：
1. 确认 FAIL 项的真实性和优先级
2. 按协作规则（团队名册 §协作规则）分派给对应角色：
   - 金融线问题 → 腰子（金融负责人）
   - 工程线问题 → Arch（架构设计）/ Craft（代码修复）/ Proof（测试修复）
   - 版本/文档问题 → Proof（质量审查）
   - 跨线问题 → 阿黑协调
3. 明确修复时限（P0=立即, P1=24h, P2=本周, P3=下周）

### 第4步：角色执行修复

被指派的角色按修复路线执行修复。修复完成后：
1. 自验通过
2. 通知阿黑修复完成
3. 附修复证据（文件路径+改动内容）

### 第5步：阿黑 → Gauge 反馈

阿黑确认修复完成后，通知 Gauge：
```
Gauge，[编号] 已由 [角色] 修复。请重新审计验证。
```

### 第6步：Gauge 重新审计验证

Gauge 针对修复项重新审计（仅验证修复项，非全量审计）。

**验证结果**：
- **PASS** → 进入第6步bis（自检锁）
- **FAIL** → 回到第2步（重新汇报，附新发现）

### 第6步bis：自检锁（强制门禁）⛔

> **背景**：此前发生 Gauge 在 FAIL 项未完全修复时即声明"任务完成"的严重违规（2026-05-24 quick审计 G-2 仍为 FAIL 时关闭）。此步骤为防止此类事件再次发生的强制门禁。

Gauge 在声明"验证通过"并进入第7步之前，必须执行以下自检：

1. **读取审计JSON文件**：确认当前报告 `历史数据/审计报告/audit_report_*.json` 中的 `summary.fail` 字段
2. **逐项对照**：将 JSON 中每一个 `failures[]` 条目与上次汇报给阿黑的 FAIL 清单逐条比对
3. **判定**：
   - `summary.fail == 0` 且所有历史 FAIL 项均已转为 PASS → 通过，进入第7步
   - `summary.fail > 0` 或仍有 FAIL 项未解决 → **不通过**，自动回到第2步（重新汇报阿黑）

**自检失败时的标准输出**：

```
⛔ 自检锁未通过 — summary.fail = N — 以下 FAIL 项未修复：
  [编号] [描述] — 状态仍为 FAIL
自动回到第2步，重新汇报阿黑...
```

**红线**：此自检锁不得跳过、不得缩短、不得以"肉眼看了觉得没问题"代替读取JSON确认。

### 第7步：关闭 — 生成新报告并存档

Gauge 自检锁通过后：
1. 生成新的审计报告（JSON + PDF），`summary.overall_verdict` 必须为 `PASS`
2. 旧报告移入 `历史数据/审计报告/归档/`
3. 更新审计趋势记录（标记"已修复"）

## 三、优先级定义

| 优先级 | 含义 | 示例 |
|:------:|:-----|:-----|
| **P0** | 立即修复，阻塞所有操作 | 数据完整性FAIL、交易记录不一致、编码损坏 |
| **P1** | 24h内修复 | 红线合规检查FAIL、版本一致性FAIL |
| **P2** | 本周内修复 | 缓存健康WARN、日志堆积WARN |
| **P3** | 下周或下次迭代 | 文档格式WARN、空目录WARN |
| **P4** | 观察，暂不修复 | 趋势性劣化但未达阈值 |

---

## 四、禁止事项（红线）

1. **禁止跳过阿黑**：Gauge 不得直接找修复人，所有 FAIL 必须先报告阿黑
2. **禁止未验证关闭**：FAIL 项必须经 Gauge 重新审计确认 PASS 后才能关闭
3. **禁止模糊修复**：修复必须具体到文件+行号+改动，"检查了没问题"不是有效修复
4. **禁止阻塞不报**：Gauge 发现问题后必须在审计报告中列出，不得因为"修不了"而隐藏
5. **禁止阿黑绕过**：任何人不得要求 Gauge 跳过某项检查或修改审计结论
6. **禁止删除审计报告**：所有审计报告（含旧版）永久保留，不得删除（红线 §1.7 适用范围扩展至审计报告）
7. **禁止伪关闭**：Gauge 不得在 `summary.fail > 0` 时声明"任务完成"或"所有问题已解决"。必须走完自检锁（第6步bis），以 JSON 数据为准，不以主观判断为准

## 五、记录模板

### 审计异常报告模板（Gauge → 阿黑）

```
阿黑，[日期] [模式] 审计发现 N 项 FAIL，需处理：

================================================
FAIL-1 [编号] [描述]
  根因：[文件:行号] [具体偏差]
  修复路线：[具体操作]
  建议责任人：[角色]
  优先级：[P0/P1/P2/P3]

FAIL-2 ...
================================================

完整报告：历史数据/审计报告/audit_report_[日期].pdf
```

### 修复完成通知模板（阿黑 → Gauge）

```
Gauge，以下 FAIL 项已修复，请验证：

[编号] — 修复人：[角色] — 改动：[文件:行号] [改动摘要]
```

### 验证关闭记录模板（Gauge）

```
[日期] [编号] 验证通过 — 修复确认 — 新报告已存档
[日期] [编号] 验证未通过 — [新发现的问题] — 重新汇报阿黑
```
