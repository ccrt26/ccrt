### 1.2 各测试点详细规范

#### R01 -- 腾讯行情API正常返回+字段完整

```
目的：验证主行情数据源可用且返回结构完整
方法：
  1. 运行 Get-StockQuote 对至少3只正常交易的股票（如600519、000858、300750）
  2. 检查返回数据包含以下字段：当前价、涨跌幅、换手率、PE、流通市值
  3. 检查所有数值非空、非异常（如负数当前价）

通过标准：
  - 3只股票全部返回有效数据
  - 每个字段值在合理范围内（当前价>0、涨跌幅在±20%内、换手率>=0）

失败处理：
  - 如果仅1只失败：检查该股票是否停牌/退市，记录为边界用例
  - 如果全部失败：触发R02备API验证，标记为P0阻断

日志检查：
  - 确认日志中记录了主API调用（非备源）
  - 确认响应时间<3秒
```

#### R02 -- 新浪K线API降级触发+切换正常

```
目的：验证K线数据的备源降级路径实际可用
方法：
  1. 正常调用 Get-StockKLine 获取K线数据（确认主API新浪可用）
  2. 手动断网或修改hosts临时屏蔽新浪域名，再次调用
  3. 确认自动切换到腾讯K线[2B]
  4. 恢复网络，确认后续调用回到主API

通过标准：
  - 主API正常时使用主API（日志确认）
  - 主API不可用时自动切换备API（日志确认）
  - 备API返回数据包含完整的OHLCV
  - 恢复后自动回到主API

失败处理：
  - 备API未触发：检查降级逻辑代码
  - 备API也失败：触发R03缓存兜底

重要提醒：
  - 此测试必须"实际"触发备API，不能仅检查代码中的if-else分支
  - 过去曾出现"代码中有备源逻辑但从未实际触发过"的问题
```

#### R03 -- 缓存兜底-两API均不可用

```
目的：验证极端情况下缓存兜底可用
方法：
  1. 确保某只股票已有有效缓存（先正常调用一次，缓存写入）
  2. 同时屏蔽主API和备API（断网或修改hosts）
  3. 调用数据获取函数
  4. 确认返回缓存数据
  5. 确认日志标记为[C]缓存

通过标准：
  - 两API均失败时自动读取缓存
  - 缓存数据包含完整字段（与API返回结构一致）
  - 日志标记"缓存数据，可能滞后"
  - 缓存过期（超过TTL）时不再返回

失败处理：
  - 无缓存可读：标记为P0阻断，数据链路彻底中断
  - 缓存数据格式不兼容：检查缓存写入逻辑
```

#### R04 -- PE(TTM)计算-5只股票手动验算

```
目的：验证PE(TTM)计算使用正确的TTM_EPS公式
方法：
  1. 选择5只不同行业的股票（确保有对应的财务数据）
  2. 获取：当前价[1]、最新年报EPS[3]、最新季报EPS[3]、去年同季EPS[3]
  3. 手动计算：TTM_EPS = 最新年报EPS - 去年同季EPS + 最新季报EPS
  4. 手动计算：PE(TTM) = 当前价 / TTM_EPS
  5. 与代码计算结果对比

通过标准：
  - 5只股票手动计算与代码计算结果偏差<0.01
  - 不使用腾讯静态PE作为PE(TTM)

失败处理：
  - 任何偏差>0.01：检查TTM_EPS公式是否使用了错误的季报
  - 偏差规律性出现：检查是否有系统性的数据取用错误

特别注意：
  - 历史问题：曾被直接用腾讯静态PE做否决，导致错误
  - 亏损股（EPS为负）应输出"N/A"而非负数PE
```

#### R05 -- 一票否决-正常/触发边界

```
目的：验证一票否决逻辑在各类边界条件下正确
方法：
  1. 设计以下用例：
     a) ST股票 → 应触发否决
     b) 亏损股（EPS<0） → 应触发否决
     c) 正常盈利股 → 不应触发否决
     d) 停牌股 → 应跳过（不参与评分）
     e) 财务数据缺失 → 应标记"数据不足"但不报错
  2. 每个边界至少3个真实股票样本

通过标准：
  - 所有触发条件正确触发
  - 所有不触发条件正确不触发
  - 边界情况不导致崩溃

失败处理：
  - 漏触发：检查否决条件逻辑（是否遗漏了某个ST前缀或亏损判定）
  - 误触发：检查条件阈值是否过于严格
```

#### R06 -- 评分排名-同一输入3次运行一致

```
目的：验证评分引擎的确定性（无随机因素影响排名）
方法：
  1. 选取包含至少20只股票的候选池
  2. 对同一候选池运行评分引擎3次
  3. 对比3次的排名结果

通过标准：
  - 3次运行的最终排名完全一致（无顺序变化）
  - 每只股票的综合得分3次完全相同

失败处理：
  - 排名不一致：检查是否有随机数/时间戳/缓存过期等非确定性因素
  - 得分不一致：检查因子权重是否被意外修改
```

#### R07 -- HTML报告-数据源标注完整性

```
目的：验证报告中所有数据数字后都有正确的数据源标记
方法：
  1. 生成HTML报告
  2. 逐段检查报告中的数字
  3. 确认每个关键数字后跟[1]/[1B]/[2]/[2B]/[3]/[5]/[7]/[8]/[9]/[10]/[11]/[12]/[C]之一
  4. 确认使用了备源的数据标注为[B]
  5. 确认使用了缓存的数据标注为[C]

通过标准：
  - 所有行情数据后跟[1]或[1B]
  - 所有K线相关后跟[2]或[2B]
  - 所有财务数据后跟[3]
  - 所有计算指标后跟[5]
  - 独有数据(资金/北向/研报/融券)标注"仅供参考"

失败处理：
  - 缺少标注：补充模板中的标注逻辑
  - 标注错误：检查数据来源追踪机制
```

#### R08 -- DOCX报告-版本号一致性

```
目的：验证报告文件名、文档头版本声明、文档版本索引三处版本号一致
方法：
  1. 检查.md文件名中的版本号（如 _v2.4）
  2. 检查.md文档头部的版本声明（第1-3行）
  3. 检查.docx文件名版本号
  4. 文档版本索引中记录的版本号
  5. CHANGELOG最新条目版本号

通过标准：
  - 五处版本号完全一致
  - version_supervisor.ps1 检查全部通过

失败处理：
  - 不一致：更新遗漏处并重新生成.docx
```

#### R09 -- 免责声明-所有报告模板存在

```
目的：验证所有类型的报告都包含免责声明
方法：
  1. 检查所有报告生成脚本的输出模板
  2. 确认HTML模板包含免责声明段
  3. 确认DOCX生成脚本包含免责声明页
  4. 确认.md模板包含免责声明章节

通过标准：
  - 每种报告类型至少包含一条免责声明
  - 免责声明包含关键短语："仅供参考"、"不构成投资建议"、"数据来源"

失败处理：
  - 缺失：补充免责声明到对应模板
```

#### R10 -- 空数据/退市股票/停牌股票处理

```
目的：验证异常股票不会导致整个分析流程中断
方法：
  1. 候选池中加入1只已知退市股
  2. 候选池中加入1只已知停牌股
  3. 模拟某只股票API返回空数据
  4. 运行完整分析流程

通过标准：
  - 退市股被跳过（不进入评分池）
  - 停牌股被跳过（不进入评分池）
  - 空数据股票标记为"数据不可用"
  - 其他正常股票不受影响
  - 整体流程不中断、不报崩溃性错误

失败处理：
  - 流程中断：检查异常处理逻辑是否捕获了所有异常类型
  - 跳过失败：检查退市/停牌判断逻辑
```

#### R11 -- API调用间隔>=0.3s检查

```
目的：验证API调用遵守了防封禁的间隔规则
方法：
  1. 运行一次完整的批量数据获取
  2. 检查日志中的API调用时间戳
  3. 计算相邻调用的间隔

通过标准：
  - 每次API调用间隔 >= 0.3秒
  - 每10次调用后有额外 >= 2秒的休息
  - 日志中有明确的Sleep记录

失败处理：
  - 间隔不足：检查代码中Sleep位置和时长
```

#### R12 -- CHANGELOG与代码变更一致性

```
目的：验证CHANGELOG记录与实际代码改动一致
方法：
  1. 运行 version_supervisor.ps1 -CrossCheck
  2. 逐条对比CHANGELOG条目与git diff
  3. 检查每条"已修复/已修改/已新增"声明是否有对应代码变更

通过标准：
  - CrossCheck全部通过
  - CHANGELOG中每条声明都能在git diff中找到对应修改
  - 没有"计划实施"被记录为"已完成"

失败处理：
  - 虚假记录：修正CHANGELOG条目，标注更正声明
  - 遗漏记录：补充遗漏的变更记录
```

#### R13 -- Token预算合规检查

```
目的：验证Agent定义文件和核心脚本符合红线 v1.13 §2.3 Token预算门禁
方法：
  1. 遍历 .claude/agents/*.md（排除知识库子目录），检查每个文件行数≤250、大小≤12KB
  2. 检查 scoring_engine_v2.py 等核心脚本的print()数量≤8
  3. 检查 data_full.json 等>500KB文件是否有AI禁止读取声明
  4. 运行 pre-commit-check.ps1 验证Check E全部PASS

通过标准：
  - 所有Agent定义文件行数≤250行（红线§2.3警告阈值）
  - 所有Agent定义文件大小≤12KB
  - 核心脚本正常模式stdout≤20行（print≤8个）
  - 无超标Agent定义文件（>300行或>15KB将阻断提交）
  - 无新增文件匹配AI禁止读取模式

失败处理：
  - Agent定义超标：将§三知识体系内容移至对应知识库文件，Agent定义仅保留索引
  - 脚本print超标：添加--verbose标志控制输出量
  - 大文件未保护：添加保护声明标记或配置blacklist
  - 阻断项：需Arch审批豁免，72h内修复
```

### 2.3 报告生成层

#### 2.3.1 数据源标注

|:-------|:---------|:---------|:---:|

| K线数据标注[2] | 检查报告中所有K线相关数字后 | 跟[2]或[2B] | R07 |

#### 2.3.2 免责声明

## 六、回归测试执行纪律

### 6.1 执行铁律

1. **变更后必须执行**：任意代码变更（即使只改了一行），至少执行受影响模块的回归测试
2. **发布前必须全量**：任何版本发布前，必须执行R01-R12全量回归
3. **P0不过不发布**：任何P0级回归测试失败，禁止发布
4. **失败必须记录**：任何测试失败必须记录到05-缺陷分级与追踪.md
5. **执行报告必须存档**：每次回归测试的执行报告必须保存在 `临时回溯/回归测试/` 目录下

### 6.2 跳过规则

| 跳过类型 | 允许条件 | 审批要求 | 记录要求 |
|:---------|:---------|:---------|:---------|
| 跳过P0 | **永不** | — | — |
| 跳过P1 | 仅紧急hotfix且变更与此P1无关 | 人工确认 | 必须在报告中注明跳过原因 |
| 跳过P2 | 时间紧张且变更无关 | 自行决定 | 在报告中注明 |
| 跳过P3 | 任何时候 | 无需 | 无需记录 |
