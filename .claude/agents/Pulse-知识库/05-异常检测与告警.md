> Pulse知识库 v1.0 | 2026-05-23
> 所属项目：铁律量化
> 关联文件：01-数据源全景、02-数据质量维度、04-1+2架构合规检查

## 一、异常分类体系：P0-P5 六级别

Pulse使用六级异常分类体系，从"忽略"到"致命"，逐级升级。每个级别有明确的触发条件、影响范围、和响应要求。

```
P5 (忽略)  → 预期内波动，不告警，仅记录
P4 (信息)  → 值得注意但无需立即行动
P3 (注意)  → 单个字段/单次异常，需记录追踪
P2 (警告)  → 影响局部使用，需告警和后续行动
P1 (严重)  → 影响核心功能，需立即告警和降级
P0 (致命)  → 全部数据源不可用，暂停依赖操作
```

### 1.1 各等级详细定义

| 等级 | 名称 | 含义 | 响应要求 | 需暂停决策链？ | 自动/人工 |
|:---:|:----|:-----|:--------|:----------:|:------:|
| P5 | 忽略 | 预期内波动，属正常现象 | 仅记录到日志 | 否 | 自动 |
| P4 | 信息 | 值得注意的状态变化，无即时影响 | 记录并在巡检报告中注明 | 否 | 自动 |
| P3 | 注意 | 单一异常，影响范围局限 | 标注异常，持续追踪，三次后升级 | 否 | 自动 |
| P2 | 警告 | 局部数据不可用或质量显著下降 | 告警标注，启动降级路径，建议人工复核 | 局部暂停 | 自动+人工 |
| P1 | 严重 | 核心数据源或功能受影响 | 立即告警，强制执行降级，暂停受影响操作 | 是（受影响部分） | 人工确认 |
| P0 | 致命 | 全部数据源不可用，系统无法运作 | 立即告警并通知用户，暂停所有依赖数据的操作 | 是（全部） | 人工确认 |

## 二、P5 忽略级 — 预期内波动

这些事件不需要告警，但会在日志中记录，供趋势分析使用。

| 编号 | 事件 | 触发条件 | 处理 |
|:---:|:----|:--------|:----|
| P5-01 | 集合竞价价格波动 | 9:15-9:25期间价格大幅跳动 | 无需处理，集合竞价结束恢复正常 |
| P5-02 | 午休期无数据更新 | 11:30-13:00行情不更新 | 无需处理 |
| P5-03 | 节假日API返回空 | 节假日时间，API无数据 | 交叉验证holidays_2026.csv后确认 |
| P5-04 | 新上市首日涨跌超限 | 新股上市前5日不设涨跌幅 | 无需处理 |
| P5-05 | 除权除息日价格跳空 | 分红/送股/配股导致的自然价格变化 | 记录除权信息，不告警 |
| P5-06 | 微利股PE极高 | PE>500但EPS极低（<0.01） | 属于正常现象，标注"微利股高PE" |
| P5-07 | 缓存过期但API正常 | API返回正常数据时会自动刷新 | 系统自动处理 |

## 三、P4 信息级 — 值得注意

P4级事件应记录并在每日巡检报告的信息摘要中提到，但不触发告警。

| 编号 | 事件 | 触发条件 | 建议行动 |
|:---:|:----|:--------|:--------|
| P4-01 | API响应时间趋势上升 | 连续5日平均响应时间递增 | 关注，可能预示API即将故障 |
| P4-02 | 缓存新鲜度下降 | 新鲜率从>90%降至70-90% | 计划在下次盘前预热中加强 |
| P4-03 | 新增停牌股票 | 某股票首次出现全天成交量=0 | 标注停牌，纳入停牌清单 |
| P4-04 | 财务数据报告期更新 | 新季报可用（NOTICE_DATE变动） | 确认新数据已正确读取 |
| P4-05 | 板块成分股变动 | SectorConstituents成分股数变化>5% | 确认是正常调整还是数据问题 |
| P4-06 | 同花顺THS版本更新 | akshare有新版本可用 | 计划在合适时间更新 |
| P4-07 | 编码异常（中文乱码） | 部分股票名称出现乱码 | 记录，但不影响数值计算 |
| P4-08 | 单一字段缺失 | 非核心字段（如Amplitude）为null | 不阻塞，标注即可 |
| P4-09 | 缓存写入延迟 | 单次缓存写入耗时>1秒 | 关注磁盘IO |

## 四、P3 注意级 — 单点异常

P3级事件需在巡检报告中列出，并开始追踪是否重复出现。连续3次同一P3事件 → 升级为P2。

| 编号 | 事件 | 触发条件 | 影响面 | 升级条件 |
|:---:|:----|:--------|:------|:------:|
| P3-01 | 单次API超时 | 某次API调用超过TimeoutSec但后续成功 | 单次请求延迟 | 连续3次 → P2 |
| P3-02 | 单字段值域异常 | PE/市值/换手率等超出合理范围 | 该字段不可用于评分 | 同一股票3次 → P2 |
| P3-03 | 跨源微小差异 | 腾讯vs新浪价格差异0.5%-1% | 不影响主要使用 | 连续3次超阈值 → P2 |
| P3-04 | 指标突变 | PE/市值日变化>50% | 该指标的评分可能失真 | 无（财报更新是正常现象） |
| P3-05 | 数据延迟增大 | 行情延迟从<5s变为5-30s | 实时性下降但可用 | 持续>5分钟 → P2 |
| P3-06 | 涨跌停触及 | 触及涨停或跌停 | 该股票当日无法正常交易 | 无（市场正常现象） |
| P3-07 | 少量重复记录 | 重复率0%-1% | 已自动去重 | 重复率>1% → P2 |
| P3-08 | 编码部分乱码 | 部分股票中文名显示异常 | 不影响数值 | 大面积乱码 → P2 |
| P3-09 | 极低成交量 | 成交量<前5日均量的10% | 可能是流动性枯竭 | 标注即可 |
| P3-10 | PE(TTM)与静态PE差异>30% | 腾讯PE手动计算PE偏离 | 估值判断需注意 | 标注即可 |

## 五、P2 警告级 — 局部不可用

P2级事件必须在巡检报告的"警告"区域显著展示。发出后连续2次未解决 → 升级为P1。

| 编号 | 事件 | 触发条件 | 影响面 | 升级条件 |
|:---:|:----|:--------|:------|:------:|
| P2-01 | 主API连续失败 | 同一主API连续3次调用失败 | 该数据类型需切换到备源 | 连续2次巡检仍未恢复 → P1 |
| P2-02 | 备源也连续失败 | 主+备连续3次调用均失败 | 仅缓存可用，数据时效风险 | 缓存过期 → P1 |
| P2-03 | 跨源价格差异显著 | 腾讯vs新浪价格差异>1% | 价格数据可靠性存疑 | 差异>2%且持续 → P1 |
| P2-04 | 数据断档 | 交易日但有2天以上无K线数据（非节假日） | K线数据不连续，技术指标计算受影响 | 断档>5天 → P1 |
| P2-05 | 字段非空率骤降 | 必填字段非空率单次下降>10% | 数据完整性受损 | 持续下降 → P1 |
| P2-06 | 成交量=0但非停牌日 | 非已知停牌股票成交量=0 | 数据明显错误 | 确认非停牌 → P2已定 |
| P2-07 | 业务规则违反 | 收盘价不在[最低价,最高价]区间 | 单条数据完全不可用 | 大面积违反 → P1 |
| P2-08 | 缓存命中率骤降 | 从>80%降至<50% | 缓存兜底能力严重削弱 | 同时API异常 → P1 |
| P2-09 | 缓存大面积过期 | 过期率>40% | 多数数据依赖过时缓存 | 结合API状态判断 |
| P2-10 | 高频脏数据检出 | 脏数据检出率>15% | 缓存与源数据大面积不一致 | 持续 → P1 |
| P2-11 | 同花顺THS备源不可用 | akshare未安装/版本过低/调用失败 | 财务/板块/资金流向失去备源 | 主源也异常 → P1 |
| P2-12 | 盘中行情延迟>30s | 连续5分钟延迟>30s | 实时分析受影响 | 延迟>5分钟 → P1 |

## 六、P1 严重级 — 核心受影响

P1级事件必须**立即告警**，暂停受影响的数据操作，等待人工确认。P1事件必须在巡检报告的最顶部展示。

| 编号 | 事件 | 触发条件 | 强制操作 | 恢复条件 |
|:---:|:----|:--------|:--------|:--------|
| P1-01 | 主+备双源全部不可用 | 某数据类型主API和备API全部失败 | 降级到缓存，暂停生成该数据类型的报告 | 任一API恢复+连续3次成功 |
| P1-02 | 缓存兜底失败 | 主+备+缓存三级全部失败 | 该数据标注"不可获取"，相关分析暂停 | 任一级恢复 |
| P1-03 | K线数据7天以上断档 | 最近7个交易日完全无K线数据 | 暂停所有技术分析 | 数据恢复+验证连续性 |
| P1-04 | 财务数据全部过期 | 所有股票财务数据超过2个季度未更新 | 暂停估值相关评分 | 新季报数据到齐 |
| P1-05 | 跨源数据系统性偏差 | 腾讯vs新浪多只股票价格差异同时>2% | 暂停跨源数据，使用单一源 | 差异恢复至<0.5% |
| P1-06 | API反爬封禁 | 所有对某API的请求返回空或被拒绝 | 暂停该API调用2小时，使用备源 | 2小时后测试恢复 |
| P1-07 | 缓存文件大面积损坏 | >20%缓存文件JSON解析失败 | 清理损坏文件，全量重建缓存 | 预热完成+验证 |
| P1-08 | 数据完整率<80% | 多只股票多个核心字段缺失 | 暂停评分，退回给Claude诊断 | 完整率恢复>95% |

## 七、P0 致命级 — 系统失控

P0级事件意味着数据管线完全断裂，项目无法运作。**必须立即通知用户，暂停所有依赖数据的操作。**

| 编号 | 事件 | 触发条件 | 强制操作 | 恢复流程 |
|:---:|:----|:--------|:--------|:--------|
| P0-01 | 全部API不可达 | 腾讯+新浪+东方财富全部超时/连接失败 | 暂停所有自动分析任务 | 1.确认网络连接 2.逐一测试恢复 3.从缓存重建 |
| P0-02 | 本地缓存全部损坏/丢失 | data_cache目录不存在或为空 | 暂停一切，等待API恢复后全量重建 | 1.检查磁盘 2.API恢复后执行全量预热 |
| P0-03 | 数据源系统性故障超过4小时 | P1级故障时间>4小时 | 评估当日是否还能正常执行 | 人工决策 |
| P0-04 | 大盘级别数据异常 | 大盘指数数据严重异常（如上证指数显示0） | 暂停所有分析 | 数据恢复正常后再运行 |

## 八、告警升级规则引擎

### 8.1 时间维度升级

```
P5/P4 → 无时间升级（非告警级别）

P3 → P2：连续3次巡检出现同一P3事件
        （"同一"定义：同一数据类型+同一事件编号+同一股票/API源）

P2 → P1：连续2次巡检出现同一P2事件
        或同一P2事件持续超过2小时（盘中）

P1 → P0：P1事件持续超过4小时
        或同时出现3个或以上不同P1事件
```

### 8.2 关联升级

当多个低级别事件同时发生时，可能产生组合效应触发升级：

| 组合 | 升级至 | 说明 |
|:----|:----:|:-----|
| P3-01(API超时) + P4-01(延迟趋势上升) | P2 | 超时+趋势恶化=API可能即将完全故障 |
| 任意3个不同P3事件涉及同一数据源 | P2 | 该数据源存在多重问题 |
| P2-01(主API连续失败) + P2-08(缓存命中率骤降) | P1 | 无API+弱缓存=数据即将不可用 |
| 任意2个不同P2事件涉及同一数据类型 | P1 | 该数据类型完全不可靠 |

### 8.3 告警降级规则

告警级别不是只升不降的。满足以下条件时可降级或解除：

| 条件 | 操作 |
|:----|:-----|
| P3事件连续3次巡检不再出现 | 解除告警，标记为"已恢复" |
| P2事件连续3次巡检不再出现 | 降级为P3（观察中），再3次后解除 |
| P1事件恢复条件满足 | 降级为P2（已恢复，需观察24小时） |
| P0事件恢复条件满足 | 降级为P1（已恢复，需观察48小时） |

## 九、巡检调度时间表

### 9.1 每日巡检节点

```
08:00 — 盘前全量巡检（最重要）    ← Pulse巡检核心执行点
      范围：全部API连通性 + 全部缓存新鲜度 + 1+2架构合规
      输出：完整盘前巡检报告
      
09:25 — 开盘前快速确认
      范围：确认API未在盘前巡检后发生变化
      输出：简短确认（1行即可）
      
11:30 — 盘中上午巡检
      范围：行情数据延迟 + API响应时间 + 关键缓存
      输出：轻量巡检报告
      
13:00 — 下午开盘前确认
      范围：确认午休期间无异常
      
15:00 — 收盘即时检查
      范围：收盘数据完整性 + 日线数据是否生成
      输出：收盘数据状态
      
18:00 — 盘后数据到齐检查
      范围：K线日线到齐 + 资金流向更新 + 融资融券更新
      输出：盘后数据完整性报告
```

### 9.2 盘中轻量检查（30分钟间隔）

在 9:30-15:00 之间的每30分钟检查点：

```
轻量检查项目（快速，<10秒完成）：
1. 行情API响应时间（1次探测请求）
2. 当前使用的数据源是否变化（读 $script:SourceUsed）
3. 是否有此前告警的P2+事件需要追踪
4. 缓存新鲜度抽样（仅检查活跃使用的5个缓存文件）
```

### 9.3 检查频率优先级

| 时间窗口 | 频率 | 深度 | 原因 |
|:--------|:---:|:---:|:-----|
| 盘前 8:00-9:00 | 1次 | 全量 | 为全天交易做准备 |
| 盘中 9:30-11:30 | 4次(每30分) | 轻量 | 确保实时数据可用 |
| 午休 11:30-13:00 | 0次 | 不检查 | 午休无数据更新 |
| 盘中 13:00-15:00 | 4次(每30分) | 轻量 | 确保实时数据可用 |
| 盘后 15:00-18:00 | 2次(15:00,18:00) | 中量/全量 | 确认日终数据到齐 |

## 十、异常事件响应流程

### 10.1 一般流程

```
发现异常
  → 判定异常等级（P0-P5）
    → 记录到异常日志（时间/类型/等级/详情）
      → P0/P1：暂停受影响操作 + 通知用户
        P2：标记降级路径 + 巡检报告显著展示
        P3：记录追踪 + 巡检报告信息区展示
        P4：记录 + 巡检报告信息摘要
        P5：静默记录
      → 写入修复指令（P2及以上）
        → 持续监控直至恢复/升级
```

### 10.2 Pulse的操作边界

```
Pulse可以做的（诊断）：
✅ 检测异常
✅ 判定等级
✅ 记录日志
✅ 生成告警
✅ 给出修复指令
✅ 追踪异常趋势

Pulse不能做的（交由Claude/其他角色）：
❌ 修复API调用代码
❌ 重启API连接
❌ 清理磁盘空间
❌ 更新akshare版本
❌ 修改缓存TTL配置
❌ 重新运行数据采集脚本
```

### 10.3 典型修复指令模板

**P2-01: 主API连续失败**
```
问题：[P2] 腾讯行情API连续3次调用超时(>5s)
影响面：所有实时行情数据切换到新浪备源，缺少PE/换手率/市值
诊断建议：检查网络到 qt.gtimg.cn 的连通性，检查是否被限流
修复指令：
  1. 运行 Test-NetConnection qt.gtimg.cn -Port 80 检查网络
  2. 等待10分钟后重试（可能被腾讯限流）
  3. 如果持续故障，通知项目负责人评估是否需要增加第三行情源
```

**P1-02: 缓存兜底失败**
```
问题：[P1] Financial_600036 的财务数据三级链路全部失败
      主源：东方财富API超时
      备源：同花顺THS akshare版本不匹配
      缓存：缓存文件不存在（从未成功获取过）
影响面：招商银行财报数据不可用，V2否决和F1-F4评分将缺失
修复指令：
  1. 升级 akshare 至 >=1.18.63
  2. 重新运行 Get-StockFinancial -Code "600036"
  3. 确认缓存成功写入后，重新触发评分流程
```

## 十一、异常日志格式

### 11.1 单条异常记录

```json
{
  "EventID": "P3-01",
  "Timestamp": "2026-05-23T09:35:12+08:00",
  "Level": "P3",
  "LevelName": "注意",
  "DataType": "Quote",
  "Source": "腾讯",
  "StockCode": "600036",
  "Description": "腾讯行情API单次超时(6.2s)，已切换到新浪备源",
  "ConsecutiveCount": 1,
  "UpgradeThreshold": 3,
  "Actions": ["记录日志", "追踪后续调用"],
  "Resolved": false
}
```

### 11.2 日志时序聚合

巡检报告中按以下顺序展示异常：
1. P0（致命 — 红色高亮）
2. P1（严重 — 红色）
3. P2（警告 — 橙色）
4. P3（注意 — 黄色）
5. P4（信息 — 灰色）
