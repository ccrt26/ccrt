## 一、缓存体系架构

铁律量化项目的缓存系统设计为**三层级**，按数据变化频率分区管理。缓存位于 `代码文件/每日荐股/data_cache/` 目录，所有缓存文件均为JSON格式。

```
┌──────────────────────────────────────────────────┐
│                  L1 热缓存（内存层）                │
│  当日实时行情 / 板块排行 / 盘中温度计             │
│  TTL: 5分钟    │  存储: $script:SourceUsed       │
├──────────────────────────────────────────────────┤
│                  L2 温缓存（磁盘层-短TTL）          │
│  近期K线 / 资金流向 / 板块成分股                   │
│  TTL: 1-6小时  │  存储: data_cache/*.json        │
├──────────────────────────────────────────────────┤
│                  L3 冷缓存（磁盘层-长TTL）          │
│  历史K线 / 财务季报 / 北向资金 / PE百分位          │
│  TTL: 1-7天    │  存储: data_cache/*.json        │
└──────────────────────────────────────────────────┘
```

### 1.1 三层级的定位差异

| 层级 | 定位 | 访问速度 | 数据量 | 场景 |
|:---:|:----|:------:|:-----:|:-----|
| L1 热缓存 | 盘中的第一选择（若API不可用） | 毫秒级 | 小（当前会话） | 实时交易/评分 |
| L2 温缓存 | 短TTL数据的主要缓存 | 秒级 | 中等 | 日内的多次调用 |
| L3 冷缓存 | 低频变化数据的长期存储 | 秒级 | 最大 | 跨日/跨周的复用 |

## 二、缓存TTL精确配置表

以下配置来自 `stock_data_fetcher.psm1` 的 `$script:CacheTTL` 定义：

| 缓存键类型 | TTL（小时） | 等效 | L层级 | 过期处理 |
|:---------|:--------:|:----|:---:|:--------|
| Quote | 1 | 1小时 | L2 | 需刷新，行情1小时前完全过时 |
| KLine | 24 | 1天 | L3 | 日线数据收盘后不变，24小时内仍有效 |
| Financial | 168 | 7天 | L3 | 季报数据低频更新，7天内有效 |
| Sector | 6 | 6小时 | L2 | 盘中更新频繁，半日刷新 |
| FundFlow | 6 | 6小时 | L2 | 资金流向盘中变化，半日有效 |
| SectorFundFlow | 6 | 6小时 | L2 | 同上 |
| Northbound | 168 | 7天 | L3 | 北向资金季度+日频更新，长TTL |
| Research | 24 | 1天 | L3 | 研报每日可能有新发布 |
| Margin | 24 | 1天 | L3 | 融资融券每日盘后更新 |
| PEPercentile | 168 | 7天 | L3 | PE百分位变化缓慢 |
| SectorConstituents | 6 | 6小时 | L2 | 成分股可能调整，半日刷新 |

### 2.1 TTL设置原理

```
TTL设置公式：
  TTL = max(数据更新周期 × 安全系数, 业务最小容忍时长)

示例：
  - 行情(Quote) TTL=1h：行情每3-5秒更新，但缓存是为API失败时兜底，1小时内仍可接受
  - K线 TTL=24h：日线每天只产生一条，收盘后不变，24小时合理
  - 财务 TTL=168h(7d)：季报每3个月才更新一次，7天是财务数据的不变窗口
  - 资金流向 TTL=6h：半日内变化显著，超过半天需要刷新
```

## 四、缓存存储格式

### 4.1 标准缓存JSON结构

```json
{
  "Timestamp": "2026-05-23T09:35:00.0000000+08:00",
  "Data": { ... }
}
```

- `Timestamp`：缓存写入时间，ISO 8601格式，含时区
- `Data`：实际数据体，结构取决于数据类型

### 4.2 缓存写入流程（Save-DataCache）

```
1. 接收 Key（缓存键）和 Data（数据体）
2. 如果 Data 为 null → 跳过，不写入（防止空数据覆盖有效缓存）
3. 构建缓存对象：{ Timestamp: Now, Data: $Data }
4. 序列化为JSON（Compressed，Depth=5，UTF8编码）
5. 写入到 data_cache/$Key.json
6. 如果写入失败 → Write-Debug 记录（不中断主流程）
```

### 4.3 缓存读取流程（Load-DataCache）

```
1. 接收 Key（缓存键）和 TTLHours（有效期，默认24）
2. 检查文件是否存在 → 不存在返回 null
3. 读取JSON文件内容
4. 解析Timestamp并计算年龄：Age = Now - Timestamp
5. 如果 Age.TotalHours > TTLHours → 返回 null（过期）
6. 如果未过期 → 返回 Data 字段
7. 读取失败（损坏/格式错误）→ 返回 null
```

### 4.4 缓存读写错误处理矩阵

| 场景 | 写入行为 | 读取行为 |
|:----|:--------|:--------|
| 文件被占用 | 静默失败，不中断 | 返回null，写入日志 |
| JSON格式损坏 | — | 返回null（catch捕获） |
| 磁盘空间不足 | 静默失败 | — |
| 目录不存在 | 自动创建目录 | 返回null |
| 权限不足 | 静默失败 | 返回null |

## 五、缓存新鲜度审计

Pulse执行缓存审计的核心任务：检查每个缓存文件是否在TTL内，判断数据降级链路的健康状态。

### 5.1 审计触发时机

| 触发类型 | 时机 | 审计范围 |
|:--------|:----|:-------:|
| 盘前全量审计 | 每日8:00-9:00 | 全部缓存文件 |
| 盘中抽样审计 | 每30分钟 | 活跃使用的缓存文件（抽样） |
| 事件触发审计 | API失败切换到缓存时 | 单个被使用的缓存文件 |
| 用户请求审计 | 用户主动要求检查 | 按需指定范围 |

### 5.2 审计流程（单文件）

```
1. 列出目标缓存文件
2. 读取 Timestamp 字段
3. 解析数据类型（从文件名推断 DataType）
4. 查询该类型的TTL（从CacheTTL表）
5. 计算：Age = Now - Timestamp
6. 判断新鲜度等级：

   ┌──────────────────────────────────────────────────────┐
   │ Age < TTL × 0.5           → ✅ 新鲜                  │
   │ TTL × 0.5 <= Age < TTL    → ⚠️ 将过期，建议预刷新     │
   │ TTL <= Age < TTL × 2      → 🔶 已过期，需标注时效风险  │
   │ TTL × 2 <= Age < TTL × 5  → 🔴 严重过期，不可依赖      │
   │ Age >= TTL × 5            → ❌ 失效，必须丢弃           │
   └──────────────────────────────────────────────────────┘

7. 记录到审计日志
8. 汇总生成审计报告
```

### 5.3 审计流程（批量）

```
1. 遍历 data_cache/ 目录下所有 .json 文件
2. 对每个文件执行单文件审计流程
3. 按数据类型分组统计：
   - 新鲜文件数 / 将过期文件数 / 已过期文件数 / 失效文件数
4. 计算缓存新鲜度比率：
   新鲜率 = (新鲜 + 将过期) / 总文件数 × 100%
5. 评级：
   - 新鲜率 >= 90%：A 优秀
   - 75% <= 新鲜率 < 90%：B 良好
   - 50% <= 新鲜率 < 75%：C 警告（建议批量刷新）
   - 新鲜率 < 50%：D 严重（缓存体系可能失效）
```

### 5.4 审计报告模板

```
## Pulse 缓存新鲜度审计 [日期 时间]

### 一、总体状态
| 指标 | 值 |
|:-----|:--|
| 缓存文件总数 | XX |
| 新鲜文件数 | XX (XX%) |
| 将过期文件数 | XX (XX%) |
| 已过期文件数 | XX (XX%) |
| 失效文件数 | XX (XX%) |
| 新鲜度评级 | A/B/C/D |

### 二、按类型分组
| 数据类型 | 总数 | 新鲜 | 将过期 | 已过期 | 失效 | 新鲜率 |
|:--------|:---:|:---:|:-----:|:-----:|:---:|:-----:|

### 三、已过期/失效文件清单
| 文件名 | 时间戳 | TTL | 年龄 | 状态 | 操作建议 |
|:------|:------|:---:|:---:|:---:|:--------|

### 四、修复指令（如有）
- [ ] 刷新 XX 类型缓存（N个文件）
- [ ] 清理失效文件（N个文件）
- [ ] 检查API连通性（XX类型缓存已连续N天过期）
```

## 六、缓存失效策略

### 6.1 被动失效（TTL到期）

系统默认的主要失效方式。缓存过期后，下一次读取时 `Load-DataCache` 返回null，触发重新从API获取并写入新缓存。

**优点**：实现简单，无需额外维护。**缺点**：首次过期后的请求会经历API延迟。

### 6.2 主动失效（事件触发）

在以下事件发生时，主动标记缓存为失效或直接刷新：

| 触发事件 | 失效范围 | 触发时机 |
|:--------|:--------|:--------|
| 收盘（15:00） | 全部Quote缓存 | 15:05自动执行 |
| 财报公告日 | 对应股票的Financial缓存 | 公告发布后 |
| 板块成分股调整 | 对应SectorConstituents缓存 | 调整公告后 |
| 数据源升级/维护 | 受影响的全部缓存 | 维护窗口内 |
| 缓存文件损坏检测 | 单个文件 | 读取时自动检测 |

### 6.3 主动刷新策略

```
预刷新（Pre-refresh）：
  当 Age > TTL × 0.5 时，在下次使用前主动调用API刷新缓存
  实现：在盘前审计中检查"将过期"列表，触发批量预刷新

写穿（Write-through）：
  每次API成功获取数据后，立即写入缓存（当前实现方式）

延迟写（Write-back）：
  暂不适用此项目（数据量小，不需要）
```

## 七、脏数据检测

### 7.1 定义

脏数据是指**缓存内容与API最新数据不一致**的情况——缓存尚未过期，但源数据已经发生变化。

### 7.2 脏数据产生场景

| 场景 | 举例 | 风险 |
|:----|:----|:---:|
| 盘中行情变化 | Quote缓存TTL=1h，但价格每秒在变 | 低（缓存主要用于API失败兜底） |
| 除权除息 | K线的前收盘价与实际不同 | 中（影响涨跌幅计算） |
| 财报修正 | 财务数据有更正公告 | 高（影响PE/评分） |
| 成分股调整 | 板块成分股已变更但缓存未更新 | 中（影响板块分析） |
| 分红/送股 | 股价除权后缓存仍用旧价格 | 高（价格不可比） |

### 7.3 脏数据检测方法

```
方法一：抽样对比法
1. 随机抽3-5只股票
2. 对每只股票，同时读取缓存和调用API
3. 对比缓存数据和API数据的关键字段
4. 差异超过阈值 → 该类型缓存可能存在脏数据
5. 扩大到该类型的全量检查

方法二：元数据校验法
1. 缓存Timestamp与API中Time字段对比
2. 如果API返回的数据时间晚于缓存Timestamp → 缓存已过时

方法三：逻辑一致法
1. 检查缓存中相邻K线的收盘价是否存在巨大的非涨跌停跳空
2. 如果存在且非除权日 → 可能数据异常
```

### 7.4 脏数据处置

```
发现脏数据后：
1. 立即标记该缓存文件为"不可信"
2. 记录到脏数据日志（时间、文件、差异字段、差异量）
3. 如果API当前可用 → 立即刷新该缓存
4. 如果API不可用 → 标注"[C]-脏数据嫌疑"，降级使用或放弃
5. 连续3次发现同一类型缓存脏数据 → 缩短该类型TTL 50%
```

## 八、缓存预热方案

### 8.1 盘前预热（推荐日常执行）

在每日盘前（8:30-9:00）执行：

```
预热目标：
  - 关注池中所有股票（约70-80只）的Quote
  - 关注池中所有股票的KLine (240日线, 120条)
  - 板块排行TOP30 (Sector_30)
  - 行业资金流向TOP20 (SectorFundFlow_20)
  - PE百分位（关注池股票）

预热流程：
1. 先检查各API连通性
2. 对Quote数据：腾讯批量行情一次性拉取关注池（约80只，在限制内）
3. 对KLine数据：逐只获取（新浪K线不支持批量），间隔>=0.3s
4. 对板块/资金流向：单次API调用
5. 预热完成后记录：成功数/失败数/耗时
```

### 8.2 预热效果检查

| 检查项 | 期望标准 | 不达标处理 |
|:------|:------|:---------|
| Quote覆盖率 | >=95% | 对失败项使用新浪备源重试 |
| KLine覆盖率 | >=90% | 对失败项使用腾讯备源重试 |
| 板块数据 | 100% | 使用同花顺THS备源 |
| 总耗時 | <3分钟 | 不严格执行 |

## 九、缓存监控指标

Pulse应持续追踪以下缓存健康指标：

| 指标 | 计算方式 | 健康范围 | 告警触发 |
|:----|:--------|:------:|:------:|
| 缓存命中率 | API失败时缓存可用的次数/API总失败次数 | >80% | <50% → P2 |
| 平均缓存年龄 | 所有缓存Age的平均值 | < TTL×0.5 | > TTL×0.8 → P3 |
| 过期率 | 已过期文件数/总文件数 | <20% | >40% → P2 |
| 脏数据检出率 | 脏数据检出次数/抽样次数 | <5% | >15% → P2 |
| 预热成功率 | 盘前预热成功的文件数/目标文件数 | >90% | <80% → P2 |
| 缓存写入失败率 | 写入失败次数/总写入次数 | <1% | >5% → P1 |

## 十、缓存文件磁盘管理

### 10.1 文件大小参考

| 缓存类型 | 单文件典型大小 | 70只股票总计 |
|:--------|:----------:|:---------:|
| Quote | ~320 B | ~22 KB |
| KLine (120条) | ~5.5 KB | ~385 KB |
| Financial | ~3.8 KB | ~266 KB |
| FundFlow | ~175 B | ~12 KB |
| Sector/SectorFundFlow | ~7-8 KB | ~8 KB |
| 其它 | ~1-4 KB | ~50 KB |
| **合计** | | **~750 KB** |

### 10.2 磁盘清理规则

```
1. 每日审计后，识别失效缓存（Age > TTL × 5）
2. 失效缓存可以直接删除（下次需要时自动从API重建）
3. 不删除已过期但未失效的缓存（作为API双源失败后的最后兜底）
4. 磁盘总占用超过10MB → 清理最老的已过期缓存
5. 被标记为"脏数据"的缓存 → 立即删除
```

### 10.3 缓存备份

当前项目不要求缓存备份（数据量小，从API重建成本低）。但如果未来数据量增大，可考虑每日做一次 `data_cache/` 的zip归档。
