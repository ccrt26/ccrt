## 一、接口契约总览

铁律量化项目采用**文件传递松耦合**架构。模块间不通过函数调用或RPC通信，而是通过标准化的缓存文件（JSON/CSV）传递数据。每个接口有明确的输入契约（文件路径+格式+schema）和输出契约。

### 1.1 接口契约全景图

```
┌─────────┐  契约I1: 缓存文件    ┌─────────┐  契约I2: 评分JSON   ┌─────────┐
│ 数据层  │ ──────────────────→ │ 计算层  │ ────────────────→ │ 展示层  │
│ (PS模块)│   JSON/CSV           │ (Python)│   标准化评分输出    │ (PS)    │
└────┬────┘                     └────┬────┘                    └─────────┘
     │                               │
     │ 契约I3: 缓存文件              │ 契约I4: 评分JSON
     ▼                               ▼
┌─────────┐                    ┌──────────────┐
│ 服务层  │                    │ 模拟交易层    │
│ MCP     │                    │ sim_trading  │
└─────────┘                    └──────────────┘
```

### 1.2 契约编号体系

| 契约编号 | 生产方 | 消费方 | 传递方式 | 格式 |
|:--------:|:------|:------|:---------|:----:|
| I1 | 数据层 | 计算层 | 代码文件/data_cache/*.json | JSON |
| I2 | 计算层 | 展示层 | 评分结果JSON文件 | JSON |
| I3 | 数据层 | 服务层(MCP) | 代码文件/data_cache/*.json | JSON |
| I4 | 计算层 | 模拟交易层 | 评分结果JSON文件 | JSON |
| I5 | 数据层 | 模拟交易层 | 代码文件/data_cache/*.csv | CSV |
| I6 | 模拟交易层 | 计算层(反馈) | 交易记录JSON | JSON |
| I7 | 各层 | 监督层 | 文件系统中的输出文件 | 多种 |
| I8 | 计算层 | 后评估 | 评分结果JSON + 实际收益JSON | JSON |

## 二、契约I1：数据层 → 计算层

### 2.1 传递机制

- **传递方式**：本地JSON/CSV文件
- **存储位置**：`代码文件/data_cache/`（L1热缓存）
- **命名规范**：`{数据类型}_{日期}.json` 或 `{数据类型}_{日期}.csv`
- **编码**：UTF-8 with BOM（兼容PowerShell和Python双端读取）

### 2.7 字段命名约定

| 约定 | 示例 | 说明 |
|:-----|:-----|:-----|
| snake_case | `pe_ttm`, `change_pct` | Python端友好，PS端通过ConvertFrom-Json自动转为PSCustomObject |
| 日期格式 | `2026-05-23` | ISO 8601日期格式 |
| 金额单位 | 元（不除10000） | `amount: 625000000`而非`6.25亿` |
| 百分比单位 | 原始百分比值 | `change_pct: 1.25`表示1.25%，不存储为0.0125 |
| 缺失值 | `null` | 不写入0或空字符串 |
| 必填字段 | 在metadata中标注 | 消费端先检查metadata完整性 |

## 三、契约I2：计算层 → 展示层

### 3.1 传递机制

- **传递方式**：评分引擎输出标准化JSON文件
- **文件路径**：由调用方通过命令行参数指定（通常为`每日荐股/`或临时目录）
- **编码**：UTF-8（Python原生）

### 3.2 评分结果契约（scoring_result.json）

```json
{
  "metadata": {
```

### 3.3 评分JSON Schema约束

| 字段 | 类型 | 必填 | 约束 |
|:-----|:----:|:----:|:-----|
| `metadata.engine_version` | string | 是 | 格式`vX.Y`，与白皮书版本一致 |
| `metadata.scoring_date` | string | 是 | ISO 8601日期，YYYY-MM-DD |
| `metadata.factor_weights` | object | 是 | 所有权重合计必须为1.0（容差0.01） |
| `rankings[].rank` | integer | 是 | 从1开始连续递增，无跳号 |
| `rankings[].total_score` | float | 是 | 0-100范围 |
| `rankings[].factor_scores` | object | 是 | 各因子分之和必须在total_score的0.95-1.05范围内 |
| `rankings[].key_metrics.pe_ttm` | float\|null | 否 | >0，null表示数据不可获取 |
| `sector_summary[].avg_score` | float | 是 | 该板块所有股票的平均分 |
| `risk_metrics.sector_hhi` | integer | 是 | 0-10000，赫芬达尔指数 |

### 3.4 升级兼容性规则

1. **新增字段**（无breaking）：消费端忽略未知字段，生产端可自由新增
2. **删除字段**（breaking）：必须先确认所有消费端不再使用，至少保留一个版本过渡期
3. **修改字段类型**（breaking）：必须走新版本号，旧格式由适配层转换
4. **修改枚举值**（breaking）：需要所有消费端同步更新

## 四、契约I3-I8：其他关键契约

### 4.1 契约I5：数据层 → 模拟交易层

传递K线CSV文件，格式：

```
date,open,close,high,low,volume,amount
2026-05-22,12.30,12.35,12.45,12.20,48000000,592000000
```

- **分隔符**：逗号
- **表头**：必需
- **排序**：日期升序
- **空行**：不允许

### 4.2 契约I6：模拟交易层 → 计算层（反馈）

```json
{
  "metadata": {
    "feedback_period": "2026-05-01_2026-05-23",
    "trade_count": 45,
    "win_rate": 0.62

  "score_performance_correlation": {
    "total_score_vs_return": 0.68,

    "quality_factor_vs_return": 0.38,
    "capital_flow_vs_return": 0.58,
    "sector_factor_vs_return": 0.22
  },
  "factor_efficiency": {
    "value": {"ic": 0.08, "ir": 0.55},
    "momentum": {"ic": 0.05, "ir": 0.32},
    "quality": {"ic": 0.03, "ir": 0.18},
    "capital_flow": {"ic": 0.07, "ir": 0.48},
    "sector": {"ic": 0.02, "ir": 0.10}
  }

```

### 4.3 契约I7：各层 → 监督层

监督层通过只读方式访问各模块的输出文件：
- `version_supervisor.ps1`：读取白皮书文件头部的版本声明
- `check_redlines.ps1`：读取报告文件检查红线合规
- `verify_report_output.ps1`：读取报告输出检查完整性

### 4.4 契约I8：计算层 → 后评估

后评估需要两份数据：
1. 评分结果JSON（与I2相同格式）
2. 实际收益JSON：
```json
{
  "code": "000001",
  "score_date": "2026-05-22",
  "score": 85.50,
  "next_day_return": 1.25,
  "next_5d_return": 3.80,
  "next_20d_return": 5.50,
  "benchmark_relative": 2.15
}
```

## 五、完整数据契约链

### 5.1 每日荐股数据链路

```
外部API(腾讯/新浪/东财)
  → [stock_data_fetcher.psm1] → 缓存JSON/CSV (契约I1)
    → [scoring_engine_v2.py] → 评分结果JSON (契约I2)
      → [gen_daily_html.ps1 / gen_doc_v2.ps1] → HTML/DOCX报告
      → [sim_trading.ps1] → 交易决策 (契约I4/I5)
        → [trade_to_score_feedback.py] → 反馈优化 (契约I6)
      → [后评估] → 评估报告 (契约I8)
```

### 5.2 各环节的生产/消费关系

| 环节 | 生产方 | 契约输出 | 消费方 | 传递延迟 |
|:-----|:------|:--------|:------|:--------|
| 数据采集 | stock_data_fetcher.psm1 | I1 | 评分引擎+模拟交易+MCP | 实时（写文件=可用） |
| 评分计算 | scoring_engine_v2.py | I2 | 报告生成+模拟交易+后评估 | 实时（写文件=可用） |
| 报告生成 | gen_daily_html.ps1/gen_doc_v2.ps1 | I2消费 | 用户 | 无（最终输出） |
| 交易执行 | sim_trading.ps1 | I6 | 反馈分析 | T+1（次日） |
| 后评估 | eval脚本 | I8消费 | 用户/Alpha | T+1 |

## 六、接口变更的影响传播规则

### 6.1 变更影响传播矩阵

| 变更层级 | 影响范围 | 传播延迟 | 需要通知的角色 |
|:---------|:---------|:---------|:--------------|
| 缓存文件格式变更 | 所有数据消费者（评分/交易/MCP） | 立即 | Pulse + Forge + Alpha |
| 评分结果JSON新增字段 | 报告生成 + 模拟交易 + 后评估 | 消费端适配前不影响 | Forge + Proof |
| 评分结果JSON删除/修改字段 | 同上 | 立即 | 所有关联角色 |
| 因子权重调整 | 评分结果→报告→交易→后评估 | 下次运行生效 | Alpha + Vega + 腰子 |
| 数据源API变更 | 数据层→缓存→所有下游 | 立即 | Pulse + Forge |
| 工作流编排变更 | 整个调度链路 | 下次调度生效 | Forge + Dock + Proof |
| 命令行接口变更 | 调度层所有调用方 | 立即 | Forge |

### 6.2 变更通知模板

```
## 接口变更通知

- **变更契约**：I2（评分结果JSON）
- **变更类型**：[新增字段 / 删除字段 / 修改类型 / 其他]
- **变更内容**：在rankings[]中新增`sector_rank`字段
- **影响范围**：
  - gen_daily_html.ps1（需在报告中展示板块排名）
  - gen_doc_v2.ps1（同上）
  - sim_trading.ps1（不受影响，忽略新字段即可）
- **兼容性**：向后兼容（新增字段）
- **消费端适配截止**：2026-05-30
- **审批人**：阿黑
```

## 七、向后兼容性约定

### 7.1 版本号策略

- **Major（X.0）**：不兼容的接口变更（删除字段、修改类型、修改契约结构）
- **Minor（0.X）**：向后兼容的新增（新增字段、新增接口契约）
- **Patch（0.0.X）**：bug修复，不影响接口契约

### 7.2 过渡期策略

1. Major版本变更需保留1个版本的旧接口适配层
2. 所有消费端完成迁移后，方可移除适配层
3. 适配层代码标注`@deprecated`注释和计划移除日期

### 7.3 契约文档化要求

- 每个接口契约必须有对应的JSON Schema定义
- 字段变更必须在CHANGELOG中记录
- 契约文档存储在对应模块目录下

```
### 错误处理
```
