## 一、架构设计自我审查清单（12项）

在进行任何架构相关决策、模块设计、重构方案输出前，逐项审查：

### 审查清单

| 编号 | 审查项 | 检查方法 | 通过标准 |
|:----:|:-------|:---------|:---------|
| CH1 | **模块边界是否清晰？** | 能否用一句话描述模块的核心职责？职责是否唯一？ | 一句话描述不含"和"字（或最多1个"和"），职责不超过2个动词 |
| CH2 | **接口输入/输出/错误码是否定义完整？** | 检查接口契约（参考02-接口契约设计），是否有字段定义表、错误处理规则？ | 所有字段有类型+必填+约束定义，异常情况有明确处理方式 |
| CH3 | **数据流是否符合1+2主备架构？** | 检查每个数据字段是否有主源[1-12]→备源[B]→缓存[C]的降级路径 | 每个数据字段可追溯来源编号，有备源降级逻辑 |
| CH4 | **是否引入新的第三方依赖？** | 检查是否新增了pip/库/dll依赖 | 如果引入，必须通过03-技术选型决策§5的评审流程 |
| CH5 | **是否产生循环依赖？** | 检查模块间的import/invoke关系是否形成环 | 依赖关系图是DAG（有向无环图） |
| CH6 | **是否有单点故障风险？** | 如果一个文件/API/脚本不可用，整个链路是否中断？ | 关键路径有降级方案，单点不会导致全链路中断 |
| CH7 | **是否违反已知反模式？** | 对照04-反模式库的7个反模式逐项检查 | 不触发AP-01到AP-07中的任何一个 |
| CH8 | **变更影响范围是否评估？** | 列出所有受影响的下游模块和角色 | 影响清单完整覆盖所有消费者（参考01-模块全景的依赖关系） |
| CH9 | **是否考虑了API超时/限流/节假日？** | 数据获取层是否有超时设置、重试策略、交易日历？ | 超时>0、重试<=3次、节假日跳过逻辑存在 |
| CH10 | **是否有回退方案？** | 如果新设计/变更失败，能否恢复到旧方案？ | 回退方案可执行（不是"理论上可以"），有具体的回退步骤 |
| CH11 | **是否通知了受影响的下游模块/角色？** | 检查变更通知是否发给了所有影响范围内的角色 | 通知列表完整（参考02§6.2变更通知模板） |
| CH12 | **是否符合项目红线规则？** | 对照规则红线文档逐项检查 | 不触发任何红线违规（特别是§1.3禁止编造、§1.7禁止删除PDF、§2.1文档同步） |

## 二、重构决策矩阵

### 2.1 决策框架

```
发现代码问题
    │
    ▼
┌─────────────────────┐
│ 这是什么性质的问题？  │
└───┬──────┬──────┬───┘
    │      │      │
    ▼      ▼      ▼
  Bug   设计缺陷 性能问题
    │      │      │
    ▼      ▼      ▼
  修Bug  评估重构  评估优化
```

### 2.2 重构决策矩阵

| 维度 | 权重 | 评分标准 |
|:-----|:----:|:---------|
| **问题严重度** | 35% | 5=导致数据错误/红线违规；4=影响核心功能；3=影响效率；2=影响可读性；1=仅美观 |
| **发生频率** | 25% | 5=每次运行都触发；4=每日触发；3=每周触发；2=每月触发；1=几乎不触发 |
| **扩散风险** | 20% | 5=可能污染所有下游数据；4=影响3+模块；3=影响1-2模块；2=仅影响当前文件；1=自包含 |
| **修复成本** | 15% | 5=<1h；4=1-2h；3=半天；2=1天；1=>2天 |
| **验证难度** | 5% | 5=自动验证；4=一行命令验证；3=手动验证但简单；2=需要多步骤验证；1=需要全量回归 |

### 2.3 评分公式与决策

**重构优先级分** = 问题严重度×0.35 + 发生频率×0.25 + 扩散风险×0.20 + 修复成本×0.15 + 验证难度×0.05

| 总分 | 决策 | 行动 |
|:----:|:-----|:-----|
| >= 4.0 | 立即重构 | 当务之急，停止其他非紧急任务 |
| 3.0-3.9 | 当前迭代重构 | 排入当前迭代，在迭代结束前完成 |
| 2.0-2.9 | 下个迭代重构 | 记录为技术债，排入下个迭代 |
| < 2.0 | 仅记录 | 记录到技术债清单，不主动排期 |

### 2.4 重构决策示例

**示例1：合并重复的`md_to_docx.py`（5副本）**

| 维度 | 评分 | 理由 |
|:-----|:----:|:-----|
| 问题严重度 | 4 | 修改bug需要到5处同步修复，但未直接影响核心功能 |
| 发生频率 | 5 | 每次生成DOCX都用到 |
| 扩散风险 | 4 | 5个副本各自演化，可能出现行为不一致 |
| 修复成本 | 4 | 约1h（合并+验证） |
| 验证难度 | 3 | 手动对比5个副本的输出一致性 |

**总分** = 4×0.35 + 5×0.25 + 4×0.20 + 4×0.15 + 3×0.05 = 1.40 + 1.25 + 0.80 + 0.60 + 0.15 = **4.20**

**决策**：>=4.0 → **立即重构**

---

**示例2：升级PowerShell 5.1 → 7.x**

| 维度 | 评分 | 理由 |
|:-----|:----:|:-----|
| 问题严重度 | 1 | 当前5.1运行稳定，无功能障碍 |
| 发生频率 | 1 | 不使用新特性就完全不触发 |
| 扩散风险 | 2 | 影响所有PowerShell脚本但可通过兼容模式过渡 |
| 修复成本 | 1 | 需要全量测试所有脚本 |
| 验证难度 | 1 | 需要逐脚本验证行为一致性 |

**总分** = 1×0.35 + 1×0.25 + 2×0.20 + 1×0.15 + 1×0.05 = 0.35 + 0.25 + 0.40 + 0.15 + 0.05 = **1.20**

**决策**：<2.0 → **仅记录**

---

### 2.5 重构的风险-收益对照

| 重构类型 | 典型收益 | 典型风险 | 本项目中重点关注 |
|:---------|:---------|:---------|:----------------|
| 提取公共模块 | 减少重复，统一行为 | 接口设计不当导致耦合更紧 | `md_to_docx.py`合并 |
| 拆分上帝模块 | 提高可读性和可测性 | 拆得太散导致文件过多 | `sim_trading.ps1`、`gen_doc_v2.ps1` |
| 统一配置管理 | 修改一处生效全局 | 配置格式设计不当 | API endpoints集中管理 |
| 统一错误处理 | 问题可追溯、可降级 | 过度抽象导致理解困难 | 所有PS脚本增加`$ErrorActionPreference` |
| 接口契约规范化 | 解耦模块 | 过度约束限制灵活性 | 评分结果JSON Schema |
| 升级技术栈 | 获得新能力 | 兼容性破坏 | PS 5.1→7.0 |

## 三、新增功能架构评估清单

当项目需要新增功能时，使用此清单进行架构评估。

### 3.1 评估流程

```
需求 → 模块归属判断 → 影响评估 → 接口设计 → 反模式检查 → 审查报告
```

### 3.2 评估清单

| 编号 | 评估项 | 问题 | 完成标准 |
|:----:|:-------|:-----|:---------|
| A1 | 模块归属 | 这个功能属于哪个层？（数据/计算/展示/工具/监督/服务） | 明确归属的层和具体模块 |
| A2 | 文件策略 | 需要新增文件还是修改现有文件？ | 列表：新增x个文件，修改y个文件 |
| A3 | 接口定义 | 输入什么数据格式？输出什么数据格式？ | 有完整的字段定义表（参考02§8模板） |
| A4 | 下游影响 | 影响哪些下游模块/消费者？ | 列出完整的下游模块清单 |
| A5 | 数据源 | 是否需要变更数据源（1+2架构）？ | 新数据源有主源+备源+缓存兜底 |
| A6 | 第三方依赖 | 是否需要新的第三方库依赖？ | 如果引入，需要经过03§5评审 |
| A7 | 反模式检查 | 是否违反7个反模式（04-反模式库）中的任何一个？ | 逐一检查，不触发任何反模式 |
| A8 | 循环依赖 | 新增/修改的依赖关系是否形成环？ | 依赖图是DAG |
| A9 | 红线合规 | 是否符合项目规则红线？ | 逐一对照红线 |
| A10 | 回退方案 | 如果新功能导致问题，如何回退？ | 有具体的回退步骤 |

### 3.3 评估报告模板


## 四、日常架构自检速查

Arch在每次被召唤时，快速扫描以下5个关键信号：

| 信号 | 如果出现 | 行动 |
|:-----|:---------|:-----|
| 新脚本被直接放在根目录 | 目录约定可能在退化 | 检查是否应该放入`代码文件/`对应子目录 |
| 某目录下有3+个同名或高度相似的文件 | 重复代码模式 | 启动AP-07分析，评估合并 |
| 新增文件超过300行 | 上帝模块风险 | 检查是否符合单一职责 |
| 有文件引用了不在其层级以下的模块 | 跨层调用 | 审计是否绕过接口 |
| `md_to_docx.py`或`build_docx.ps1`出现新副本 | 重复扩散 | 立即阻止，统一到一处 |
