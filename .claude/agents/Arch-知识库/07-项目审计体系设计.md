# 07 — 项目四级审计体系设计

> **定位**：Arch（系统架构师）本地知识库 —— 项目不会自己告诉你它跑偏了，审计就是倒车镜
> **更新**：2026-05-23 | **触发背景**：2026-05-22 手动审计发现编码bug、字段缺失、目录蔓延等12个问题
> **关联**：05-设计检查清单 → 06-数据持久化架构设计 → **07-项目审计体系**

---

## 一、为什么需要审计体系

### 1.1 背景

2026-05-22 手动审计发现：

| 问题 | 根因 | 积累时间 |
|:-----|:-----|:-------|
| Research "无研报" 误报（4/6只股票） | PowerShell `.Count` 对单项数据返回 `$null` | 从系统上线就存在 |
| 评估数据缺 v3.0 字段 (ADX/OBV/Wyckoff) | 暂无字段完整性校验 | 白皮书 v3.0 升级后 |
| transactions.csv 15条重复记录 | sim_trading.ps1 无幂等性保护 | 每次重跑积累 |
| 临时报告/ 12个文件混入根目录 | 无输出路径规范 | 数周 |
| 历史数据/ 18个子目录新旧并存 | 无目录生命周期管理 | 架构演进中 |

**共同特征**：都不是一次性事故，而是在无人检查的情况下悄悄积累。等到发现时，已经需要大规模整改。

### 1.2 核心命题

审计要回答四个问题：

1. **方向对吗？** — 项目产出是否在服务核心目标？有没有跑偏？
2. **规矩守了吗？** — 红线规则的每一条是否被真正执行？
3. **成本可控吗？** — Token、API调用、磁盘、人力是否被浪费？
4. **系统健康吗？** — 数据、缓存、编码、文件、流水线是否运转正常？

## 三、第一级：目标对齐审计（月度）

> **执行者**：阿黑（工程总监）+ 腰子（金融负责人）
> **方式**：`/审计 --深度` 触发，AI审视 + 人工判断

### 3.1 检查清单

| # | 检查项 | 问什么 | 红线信号 |
|:--|:------|:------|:--------|
| A1 | 产出-目标一致性 | 每日荐股报告、重点股票报告、模拟交易、后评估，这四类产出是否直接服务"验证选股信号→优化策略"这个目标？ | 有产出连续5个交易日未被任何人查看 |
| A2 | 白皮书演进验证 | 白皮书每次版本升级后，是否有对应的回测数据支持？还是只改文档不改逻辑？ | 白皮书版本号升了但对应脚本未改动 |
| A3 | 范围蔓延检测 | 新增了不在原计划中的子目录/脚本/数据源？有没有"顺手加的功能"一直留着？ | 根目录出现不在基线列表中的新目录 |
| A4 | 重点股票池健康 | 6只股票是否定期审视？有没有连续10个交易日评分垫底(<30分)还占着位置的？ | 股票连续10天综合分<30且无调出记录 |
| A5 | 交易→评分反馈闭环 | 模拟交易的胜率/回撤/归因数据，有没有反馈到评分引擎的参数调整中？ | 模拟交易运行≥20笔后评分引擎权重无任何调整 |
| A6 | 后评估→荐股反馈闭环 | 后评估发现的误判模式（如"看多但次日大跌"），有没有进入荐股逻辑的修正？ | 连续3次同类误判无对应规则调整 |
| A7 | 知识库利用率 | `.claude/agents/` 下62+个知识文件，有多少在最近30天被实际引用过？ | 知识库文件>30天未被任何session引用 |

### 3.2 判定标准

- ✅ **目标对齐**：7项全部绿灯
- ⚠ **轻度偏离**：1-2项黄灯，需在下月审计前修正
- ❌ **严重跑偏**：任何红线信号触发，需立即调整优先级

## 五、第三级：成本审计（每周）

> **执行者**：run_full_audit.ps1 Section H（待实现）
> **当前状态**：设计完成，Phase 2 实现

### 5.1 检查清单

| # | 检查项 | 指标 | 告警阈值 |
|:--|:------|:----|:-------|
| B1 | API调用量趋势 | 每日API调用总次数 | 日环比增长>50% |
| B2 | 单源调用频率 | 每个数据源[1]-[12]的调用次数 | 任一源的调用量占比>60% |
| B3 | 缓存命中率 | Load-DataCache命中次数 vs API调用次数 | 命中率<60% |
| B4 | 缓存文件增长 | data_cache/文件数趋势 | 周环比增长>20% |
| B5 | Agent spawn频率 | Claude Code session中Agent调用次数 | 单session Agent spawn>5次 |
| B6 | 脚本重复拉取 | 同一数据(如K线)被多个脚本各自调API | 同一code+scale的API调用>2次/天 |
| B7 | 报告文件膨胀 | 单个PDF报告大小 | 任意PDF>2MB 或 HTML>100KB |
| B8 | 日志文件增长 | 日志文件总大小 | workflow日志>5MB |

### 5.2 成本归因

审计报告中将成本浪费分为三类：

| 类型 | 举例 | 修正方式 |
|:----|:-----|:--------|
| **缓存策略缺陷** | TTL设置太短导致频繁重拉 | 调整CacheTTL |
| **脚本冗余调用** | 两个脚本各自调同一API | 合并到共享数据拉取阶段 |
| **架构浪费** | 不必要的Agent spawn | 使用角色切换而非Agent |

## 六、第四级：技术健康审计（每日+每周）

> **执行者**：run_full_audit.ps1 Section A~G
> **当前状态**：设计完成，Phase 1 实现

### 6.1 七大板块（覆盖12个盲区）

| Section | 名称 | 频率 | 检查项数 | 填补的盲区 |
|:--------|:-----|:---:|:------:|:----------|
| **A** | 数据完整性 | 每日 | ~8 | #1跨文件校验, #9API健康, #11数据新鲜度 |
| **B** | 缓存健康 | 每周 | ~5 | #2缓存健康 |
| **C** | 编码健康 | 每周 | ~6 | #3编码+bom+乱码+.Count模式 |
| **D** | Schema完整性 | 每日 | ~4 | #4 v3.0字段验证 |
| **E** | 文件系统卫生 | 每周 | ~12 | #5重复, #6孤儿, #8路径, #10备份, #12蔓延 |
| **F** | 流水线健康 | 每日 | ~6 | #7流水线日志+输出 |
| **G** | 集成已有检查 | 每日 | ~4 | 聚合check_redlines+version_supervisor等 |

### 6.2 判定标准

每个检查有确定性 pass/warn/fail（无AI判断）：

- **PASS**: 全部通过
- **WARN**: 有异常但不阻塞（空缓存目录、BOM不一致）
- **FAIL**: 需立即处理（数据不一致、编码损坏、输出缺失）

综合判定：`0 fail + ≤5 warn = ✅PASS` / `≤2 fail = ⚠WARN` / `>2 fail = ❌FAIL`

### 6.3 输出格式

JSON报告写入 `历史数据/audit_report_YYYYMMDD.json`：

```json

      "A_data_integrity": { "pass": 7, "warn": 1, "fail": 0 },

      "C_encoding_health": { "pass": 14, "warn": 4, "fail": 1 },
```
