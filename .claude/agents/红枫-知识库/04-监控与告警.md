### 1.2 API 可用性专项监控

#### 腾讯 API（qt.gtimg.cn）

| 监控项 | 端点 | 超时 | 预期响应 | 检查频率 |
|:-------|:-----|:----|:--------|:-------:|
| 实时行情 | `qt.gtimg.cn/q=sh000001` | 5s | JSON 含 name/cur 字段 | 每 30 分钟 |
| K 线数据 | K 线接口 | 5s | 返回有效 K 线数据 | 每日盘前 |
| 响应延迟 | 全部端点 | — | P50 < 500ms, P99 < 2s | 每次调用记录 |

#### 新浪 API（sina.com.cn）

| 监控项 | 端点 | 超时 | 预期响应 | 检查频率 |
|:-------|:-----|:----|:--------|:-------:|
| 实时行情 | 新浪行情接口 | 5s | 有效数据 | 每 30 分钟 |
| 响应延迟 | 全部端点 | — | P50 < 1s, P99 < 3s | 每次调用记录 |

#### 东方财富 API（eastmoney.com）

| 监控项 | 端点 | 超时 | 预期响应 | 检查频率 |
|:-------|:-----|:----|:--------|:-------:|
| 板块动量 | 东财板块接口 | 8s | 有效板块数据 | 每日盘前 |
| 响应延迟 | 全部端点 | — | P50 < 1.5s, P99 < 5s | 每次调用记录 |

### 1.3 缓存新鲜度监控

```
监控对象：L1/L2/L3 三级缓存
检查内容：
  - 各缓存条目的最后更新时间
  - 与 TTL 对比，标记过期条目
  - 计算 TTL 合规率 = 未过期条目数 / 总条目数

告警条件：
  - L1 缓存 TTL 合规率 < 90% → P2 警告
  - L2 缓存 TTL 合规率 < 80% → P2 警告
  - L3 缓存 TTL 合规率 < 70% → P1 严重（L3 是兜底）
  - 任何缓存条目过期超过 2x TTL → P1 严重
```

### 1.4 缓存目录增长趋势监控

| 时间 | 正常增长速度 | 告警触发 | 处理方式 |
|:-----|:-----------|:--------|:--------|
| 每日 | < 10MB | > 20MB/天连续 3 天 | 检查缓存策略 |
| 每周 | < 50MB | > 100MB/周 | 手动清理+优化 |

## 二、告警规则设计

### 2.1 告警级别定义

```
P0 致命（Critical）— 立即通知，需要现在爬起来修
  系统核心功能中断，影响交易决策或报告产出

P1 严重（Major）— 15 分钟内响应
  重要功能降级，但系统核心链路仍在运转

P2 警告（Warning）— 1 小时内关注
  功能正常但有异常迹象，需要主动检查

P3 提示（Info）— 下次发布迭代时处理
  优化建议或非紧急问题
```

### 2.2 P0 致命告警规则（立即通知）

| 编号 | 触发条件 | 影响 | 通知方式 |
|:----:|:--------|:-----|:--------|
| P0-1 | 所有 3 个 API 源（腾讯+新浪+东财）同时不可用 | 无法获取任何行情数据 | 弹窗 + 日志 ERROR + 终端告警 |
| P0-2 | 评分引擎进程崩溃 | 无法生成评分/排名 | 弹窗 + 日志 ERROR |
| P0-3 | 报告生成完全失败（DOCX+HTML 均未产出） | 无法产出荐股报告 | 弹窗 + 日志 ERROR |
| P0-4 | 关键数据文件损坏或丢失 | 历史数据不可用 | 弹窗 + 日志 ERROR |
| P0-5 | 磁盘空间耗尽（< 100MB） | 所有写入操作失败 | 弹窗 + 日志 CRITICAL |

### 2.3 P1 严重告警规则（15 分钟内）

| 编号 | 触发条件 | 影响 | 通知方式 |
|:----:|:--------|:-----|:--------|
| P1-1 | 任意 2 个 API 源同时不可用 | 降级到唯一可用源 | 日志 ERROR + 终端标黄 |
| P1-2 | L1+L2+L3 三级缓存全部过期 | 无缓存数据可用 | 日志 ERROR |
| P1-3 | 评分引擎连续 3 次超时 | 评分不可靠 | 日志 WARNING |
| P1-4 | DOCX 或 HTML 报告任一格式未产出 | 报告不完整 | 日志 ERROR |
| P1-5 | 缓存在过去 1 小时内无任何更新 | 数据可能停滞 | 日志 WARNING |
| P1-6 | 定时任务连续 2 次执行失败 | 自动化中断 | 日志 ERROR |

### 2.4 P2 警告告警规则（1 小时内）

| 编号 | 触发条件 | 影响 | 通知方式 |
|:----:|:--------|:-----|:--------|
| P2-1 | 单个 API 源不可用超过 1 小时 | 降级到另两个源 | 日志 WARNING |
| P2-2 | 缓存部分条目过期（30%-50%） | 部分数据需重新获取 | 日志 WARNING |
| P2-3 | 报告生成耗时超过正常值 2 倍 | 效率下降 | 日志 WARNING |
| P2-4 | 任务执行超时但最终完成 | 延迟但未丢失 | 日志 WARNING |
| P2-5 | 缓存目录超过 500MB | 磁盘压力增大 | 日志 WARNING |
| P2-6 | API 响应延迟超过 P99 阈值 2 倍 | 数据获取变慢 | 日志 WARNING |

### 2.5 P3 提示级别（下次迭代处理）

| 编号 | 触发条件 | 建议 |
|:----:|:--------|:-----|
| P3-1 | 缓存命中率持续下降趋势 | 优化缓存策略 |
| P3-2 | 日志文件增长过快 | 增加日志轮转 |
| P3-3 | 某个 API 端点延迟稳定偏高 | 考虑切换优先级 |
| P3-4 | 报告生成时间逐渐增长 | 优化报告生成逻辑 |

### 2.6 告警升级规则

```
持续时长 + 严重程度 → 告警升级：

P2 持续超过 2 小时  →  升级为 P1
P1 持续超过 1 小时  →  升级为 P0
P1 + 新 P1 出现    →  升级为 P0
P2 + P2 + P2 (3个不同警告同时存在) → 升级为 P1
```

## 三、监控数据收集与日志聚合

### 3.1 日志分类与目录结构

```
项目根目录/logs/
├── api/                    ← API 调用日志
│   ├── tencent_YYYYMMDD.log
│   ├── sina_YYYYMMDD.log
│   └── eastmoney_YYYYMMDD.log
├── engine/                 ← 引擎运行日志
│   ├── scoring_YYYYMMDD.log
│   └── report_YYYYMMDD.log
├── system/                 ← 系统健康日志
│   ├── health_YYYYMMDD.log
│   └── disk_YYYYMMDD.log
├── task/                   ← 定时任务执行日志
│   └── scheduler_YYYYMMDD.log
└── error/                  ← 错误汇总
    └── error_YYYYMMDD.log
```

### 3.2 日志格式规范

```
统一日志格式：
[YYYY-MM-DD HH:MM:SS.sss] [LEVEL] [MODULE] [SUBJECT] message

示例：
[2026-05-23 14:30:00.123] [INFO] [API.TENCENT] [SH000001] 获取行情成功, 延迟=320ms
[2026-05-23 14:30:05.456] [WARNING] [API.SINA] [SH000001] 请求超时, 重试第2次
[2026-05-23 14:30:10.789] [ERROR] [CACHE.L2] [SH000001] TTL 过期, 已超过 1.5x

日志级别含义：
  DEBUG   — 调试信息（生产环境默认关闭）
  INFO    — 正常操作记录
  WARNING — 需要关注的异常但系统能自行处理
  ERROR   — 错误，需要人工介入
  CRITICAL — 致命错误，系统可能无法继续运行
```

### 3.3 日志聚合方案

```
每日凌晨自动执行：
  1. 收集前一天的日志文件
  2. 按模块聚合统计：
     - 各 API 调用次数、成功率、P50/P99 延迟
     - 各引擎运行次数、成功率、耗时
     - 各级别告警次数
  3. 生成每日健康摘要日志
  4. 归档超过 30 天的日志（压缩存储）
```

## 四、故障回溯

### 4.1 故障回溯目的

当系统出现异常后，需要完整重建"什么时间发生了什么"，以便：
- 确定根因
- 评估影响范围
- 防止再次发生
- 优化告警规则

### 4.2 故障回溯信息收集清单

```
必须收集的信息：
  1. 故障时间窗口（开始→发现→处理→恢复）
  2. 时间线：
     - 故障前 30 分钟内所有系统事件
     - 故障期间所有 ERROR/CRITICAL 日志
     - 故障后首次恢复正常的事件
  3. 受影响的数据：
     - 哪些股票的评分受影响
     - 是否影响了最终荐股结论
     - 缓存数据是否被污染
  4. 环境快照：
     - 当时的 Python/PowerShell 版本
     - 当时的系统资源状态（CPU/内存/磁盘）
     - 当时的 API 连通状态
```

### 4.3 故障时间线重建模板


## 五、健康检查脚本设计

### 5.1 健康检查脚本架构

```powershell
# health_check.ps1 — 铁律量化系统健康检查
[CmdletBinding()]
param(
    [ValidateSet('quick', 'full', 'pre-release')]
    [string]$Mode = 'quick',

    [switch]$JsonOutput,  # 输出 JSON 格式（方便程序化处理）

    [string]$LogDir = "logs/system/"
)

# 检查结果收集
$results = @{
    timestamp = (Get-Date -Format 'yyyy-MM-dd HH:mm:ss')
    mode = $Mode
    checks = @()
    summary = @{
        total = 0
        passed = 0
        failed = 0
        warning = 0
    }
}

# 各检查模块
# Check-APIConnectivity
# Check-CacheHealth
# Check-EngineStatus
# Check-ReportIntegrity
# Check-SystemResources
# Check-TaskScheduler

# 输出结果
# ...
```

### 5.2 快速健康检查（quick 模式）

适合每次操作前的快速诊断，耗时 < 5 秒：

| 检查项 | 方法 |
|:-------|:-----|
| Python 可用 | `python --version` |
| 关键包可导入 | `python -c "import numpy, pandas, docx"` |
| PS 可用 | `powershell -Command "Get-Date"` |
| 至少 1 个 API 连通 | 快速 ping 腾讯 API |
| 磁盘 > 100MB | `Get-PSDrive C` |

### 5.3 全量健康检查（full 模式）

适合每日盘前/盘后执行，耗时 < 60 秒：

包含 quick 模式的所有检查，外加：
- 全部 3 个 API 源连通性
- 三级缓存 TTL 合规率
- 评分引擎冒烟测试
- 报告生成冒烟测试
- 磁盘空间详细报告
- 日志异常扫描

### 5.4 发布前健康检查（pre-release 模式）

包含 full 模式 + 发布检查清单的全部项（参考 03-发布与回滚 §1.1）。

## 六、告警通知方式

### 6.1 通知方式矩阵

| 通知方式 | 适用级别 | 优点 | 缺点 |
|:--------|:--------|:-----|:-----|
| 终端彩色输出 | P0-P2 | 实时、无依赖 | 人不看就看不到 |
| 日志文件 | 全部 | 完整记录、可检索 | 被动，需主动查看 |
| Windows 弹窗 | P0 | 醒目、无法忽略 | 仅 Windows |
| 健康摘要文件 | P2-P3 | 可定期查看 | 非实时 |
| 任务栏通知 | P0-P1 | 低干扰 | 可能被忽略 |

### 6.2 当前项目推荐通知方案

```
P0 致命：
  1. 终端输出红色高亮 + 蜂鸣（如果有）
  2. 写入 error/ 目录下的独立告警文件
  3. 健康检查脚本退出码为非零

P1 严重：
  1. 终端输出黄色警告
  2. 写入当前运行日志 WARNING 级别
  3. 汇总到健康摘要

P2 警告：
  1. 写入运行日志 WARNING 级别
  2. 汇总到每日健康摘要

P3 提示：
  1. 写入运行日志 INFO 级别
  2. 汇总到每周健康摘要
```

### 6.3 告警静默规则

| 静默条件 | 时长 | 说明 |
|:--------|:----:|:-----|
| 同类型告警已触发 | 30 分钟 | 避免告警风暴 |
| 已知维护窗口 | 维护期间 | 计划内操作不应告警 |
| 用户手动静默 | 自定义 | 紧急处理时减少干扰 |
| 非交易时段 | — | 降低通知级别但不静默 |
