## 一、发布前检查清单

### 1.1 完整检查清单（14项）

发布前必须逐项确认，任何一项未通过 → 不能发布。

| 编号 | 检查项 | 检查方法 | 责任人 | 通过标准 |
|:----:|:------|:--------|:-----|:--------|
| P01 | 所有测试通过 | 新安 确认回归测试结果 | 新安 | 0 失败 |
| P02 | 红线检查通过 | `check_redlines.ps1` | Claude + 红枫 | 全部 PASS |
| P03 | CHANGELOG 已更新 | 人工确认 CHANGELOG.md | 红枫 | 有本次版本条目 |
| P04 | 版本号一致性 | `version_supervisor.ps1 -CrossCheck` | 红枫 | 无差异 |
| P05 | .md → .docx 同步 | 检查所有白皮书/规则对应 docx | 红枫 | .md 修改时间 <= .docx 修改时间 |
| P06 | 文档版本索引更新 | 检查 规则红线/文档版本索引.md | 红枫 | 含本次版本 |
| P07 | 备份已创建 | 确认备份操作完成 | 红枫 | 备份文件存在且完整 |
| P08 | 回滚路径已验证 | 模拟回滚操作 | 红枫 | 回滚后系统可正常运行 |
| P09 | API 连通性正常 | 分别测试腾讯/新浪/东财 | 红枫 | 至少 2/3 连通 |
| P10 | 报告生成验证 | 完整跑一次生成流程 | 红枫 | 产出完整 DOCX+HTML |
| P11 | 依赖版本锁定 | `pip check` 通过 | 红枫 | No broken requirements |
| P12 | 环境变量正确 | 检查当前会话环境 | 红枫 | 关键变量全部设置 |
| P13 | Git 状态干净 | `git status` | 红枫 | 无未提交变更 |
| P14 | 冒烟测试通过 | 数据获取→评分→报告→输出 | 红枫 + 新安 | 全链路正常 |

### 1.2 发布检查执行顺序

```
阶段 1：代码和文档完整性（5 分钟）
  P01(测试) → P02(红线) → P03(CHANGELOG) → P04(版本) → P06(索引)

阶段 2：环境就绪（3 分钟）
  P09(API) → P11(依赖) → P12(环境变量) → P13(Git)

阶段 3：安全与验证（10 分钟）
  P05(docx) → P07(备份) → P08(回滚) → P10(报告) → P14(冒烟)

全部通过 → 可以发布
任一失败 → 停止发布，修复后重新检查
```

### 1.3 快速发布检查（紧急修复时用，但不能替代完整检查）

| 快速项 | 说明 |
|:-------|:-----|
| P02 红线 | 不可跳过 |
| P04 版本 | 不可跳过 |
| P07 备份 | 不可跳过 |
| P14 冒烟 | 不可跳过 |

## 二、发布流程

### 2.1 标准发布流程

```
第 1 步：发布准备
  ├─ 从 master 分支创建 release/vX.Y 分支
  ├─ 执行完整检查清单（§1.1）
  ├─ 修复检查中发现的问题
  └─ 在 release 分支上完成最终修改

第 2 步：发布验证
  ├─ 执行冒烟测试
  ├─ 生成一份完整的测试报告（作为本次发布的证据）
  └─ 新安 确认验证通过

第 3 步：执行发布
  ├─ 标记版本标签：git tag -a vX.Y -m "Release vX.Y"
  ├─ 合并到 main 分支
  ├─ 合并回 master 分支
  └─ 推送到远程仓库

第 4 步：发布后验证
  ├─ 确认远程仓库标签存在
  ├─ 在干净环境中克隆并验证可运行
  └─ 记录发布日志

第 5 步：通知团队
  ├─ 发布摘要：版本号、变更范围、回滚方式
  └─ 通知 千光（如有 CI/CD 联动）
```

### 2.2 紧急发布流程（Hotfix）

```
与标准发布相比的区别：
  - 从 main 分支创建 hotfix/vX.Y.Z 分支
  - 仅修复目标问题，不做额外改动
  - 快速检查清单替代完整检查（但 P02/P04/P07/P14 不可跳过）
  - 合并到 main 和 master
  - 事后补充完整检查
```

## 三、灰度发布策略

### 3.1 适用场景

当前项目为单机环境，灰度发布的核心思路是：
**先出报告 → 验证结果 → 全量推广**

### 3.2 铁律量化灰度发布三步法

```
第 1 步：影子模式（Shadow Mode）
  - 新版本在后台运行，产生的输出不进入决策链
  - 比较新旧版本的输出差异
  - 持续时间：至少 1 个完整交易日周期
  - 退出条件：差异在预期范围内

第 2 步：单报告验证
  - 用新版本生成一份完整报告
  - 与旧版本相同输入下的产出进行对比
  - 验证点数：评分一致性、数据完整性、格式合规
  - 退出条件：全项验证通过

第 3 步：全量切换
  - 将新版本设为默认版本
  - 持续监控 3 个交易日
  - 随时准备回滚
```

### 3.3 灰度发布检查点

| 检查点 | 阶段 | 检查内容 | 通过标准 |
|:-------|:----:|:--------|:--------|
| G1 | 影子 | API 调用成功率 | >= 旧版本 |
| G2 | 影子 | 数据降级频率 | <= 旧版本 |
| G3 | 影子 | 运行时错误率 | 0 |
| G4 | 验证 | 评分分布一致性 | 差异 < 5% |
| G5 | 验证 | 报告格式完整性 | 无异常 |
| G6 | 全量 | 3 日稳定性 | 零异常 |

## 四、蓝绿部署概念

### 4.1 概念（适应当前单机环境）

```
传统蓝绿部署（服务器级别）：
  Blue（当前生产）+ Green（新版本） → 切换流量 → Green 成为生产

单机环境适配：
  Blue（当前运行版本目录）+ Green（新版本目录）
  → 通过配置或软链接切换 → Green 成为当前版本
```

### 4.2 铁律量化单机蓝绿方案

```
目录结构：
  项目根目录/
  ├── _releases/
  │   ├── blue/      ← 当前生产版本（实际运行位置）
  │   └── green/     ← 待切换的新版本
  └── 当前版本链接/   ← 指向 blue 或 green 的软链接

切换操作（PowerShell）：
  # 1. 准备 Green（新版本）
  Copy-Item -Path "项目根目录/" -Destination "_releases/green/" -Recurse
  
  # 2. 在 Green 中完成配置和验证
  
  # 3. 切换（原子操作）
  # 更新配置指向 green
  
  # 4. 验证 Green 正常工作
  
  # 5. 旧 Blue 保留 7 天作为回滚备份
```

### 4.3 蓝绿部署风险控制

| 风险 | 缓解措施 |
|:-----|:--------|
| 切换过程中数据不一致 | 切换窗口选在非交易时段 |
| Green 有隐藏问题 | 保留 Blue 7 天 |
| 磁盘空间不足 | 蓝绿双份最多占用 2x 空间，提前检查 |
| 配置文件路径不一致 | 使用相对路径和配置变量 |

## 五、回滚策略

### 5.1 回滚触发条件

| 级别 | 触发条件 | 响应时间 | 决策人 |
|:----:|:--------|:--------|:-----|
| 🔴 强制回滚 | 评分引擎崩溃、报告无法生成、数据全挂 | 立即 | 红枫 自主决策 |
| 🟠 强烈建议回滚 | 核心输出数据异常、2/3 API 不可用 | 15 分钟内 | 红枫 提议，团队确认 |
| 🟡 考虑回滚 | 性能显著下降、部分格式异常 | 1 小时内 | 团队讨论决定 |
| 🟢 不需要回滚 | 仅日志/监控层面的轻微异常 | — | — |

### 5.2 回滚操作流程

```
第 1 步：确认回滚决策
  ├─ 记录回滚原因
  ├─ 评估回滚影响范围
  └─ 通知受影响方（情墨/千光/新安）

第 2 步：数据恢复
  ├─ 如有数据库变更 → 执行数据回滚脚本
  ├─ 如缓存数据被污染 → 清空并重建缓存
  └─ 验证数据完整性

第 3 步：代码回退
  ├─ 方法 A：git revert <commit-range>
  │   适用于：需要保留回滚历史
  ├─ 方法 B：git reset --hard <last_good_commit>
  │   适用于：需要完全抹除问题版本（慎用！）
  ├─ 方法 C：切换蓝绿目录
  │   适用于：使用蓝绿部署时
  └─ 确认代码版本正确

第 4 步：配置还原
  ├─ 恢复备份的配置文件
  └─ 验证配置项正确

第 5 步：依赖还原
  ├─ pip install -r requirements.txt.backup
  └─ 或重建虚拟环境

第 6 步：回滚验证
  ├─ 冒烟测试
  ├─ API 连通性
  └─ 报告生成

第 7 步：记录回滚
  ├─ 更新 CHANGELOG（标注回滚）
  ├─ Git 记录回滚 commit
  └─ 团队通报
```

### 5.3 回滚后分析（Post-Mortem）

回滚完成后 24 小时内完成以下分析：
- 根因分析：为什么需要回滚
- 为什么在发布前检查中没有发现
- 检查清单是否需要增加检查项
- 是否需要增加自动化验证

```powershell

param(
    [switch]$Quick  # 快速模式
)

$errors = @()
$warnings = @()

# P01：测试通过（需 新安 确认，此处检查上一次测试结果）
# P02：红线检查
# ...
# P14：冒烟测试

if ($errors.Count -eq 0) {
    Write-Host "✓ 发布检查全部通过" -ForegroundColor Green
} else {
    Write-Host "✗ $($errors.Count) 项未通过" -ForegroundColor Red
    $errors | ForEach-Object { Write-Host "  ✗ $_" -ForegroundColor Red }
}
```

## 八、附录：发布决策矩阵

### 8.1 "能不能发"快速判断

| 场景 | 判断 | 条件 |
|:-----|:----:|:-----|
| 所有检查通过 | ✅ 发 | 正常发布流程 |
| 1-2 个非关键检查未通过 | ⚠️ 评估 | 记录豁免，团队确认 |
| 关键检查未通过（P01/P02/P14） | ❌ 不发 | 修复后重新检查 |
| 交易时段内 | ❌ 不发 | 等盘后 |
| 重要经济数据发布日 | ⚠️ 谨慎 | 评估风险后决定 |

### 8.2 发布窗口建议

| 窗口 | 时间 | 适用场景 |
|:-----|:-----|:--------|
| 最佳窗口 | 周五 15:30 - 周日 18:00 | 常规发布 |
| 次佳窗口 | 交易日 15:30 - 次日 09:00 | 需要次日验证 |
| 禁止窗口 | 交易日 09:00 - 15:30 | 影响交易 |
