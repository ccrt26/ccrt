## 一、pip 依赖版本锁定

### 1.1 锁定策略

```
原则：精确版本锁定（Exact Version Pinning）
不推荐：范围版本（>=x.y.z）—— 不确定性高，难以复现
不推荐：latest —— 每次安装可能不同

文件方案：
  requirements.txt        —— 用于新环境搭建（精确版本）
  requirements-dev.txt    —— 开发额外依赖（linter/测试工具）
```

### 1.2 requirements.txt 格式规范

```text
# ==== 铁律量化 vX.Y 依赖清单 ====
# 生成日期：YYYY-MM-DD
# 生成方式：pip freeze > requirements.txt（手动精简）
# 更新规则：仅记录直接依赖，不记录传递依赖

# 核心计算
numpy==1.26.4
pandas==2.1.4

# HTTP 请求
requests==2.31.0
urllib3==2.1.0

# 文档生成
python-docx==1.1.0
openpyxl==3.1.2

# 外部查询
mcp==1.x.x

# SSL/TLS
certifi==2024.x.x
```

### 1.3 版本锁定更新流程

```
触发条件：
  - 安全漏洞公告（CVE）→ 立即评估
  - 功能需求（新API）→ 评审后决定
  - 每季度定期检查 → 评估不强制升级

更新步骤：
  1. 在独立分支创建测试环境
  2. pip install --upgrade <package>==<new_version>
  3. 运行全量回归测试（Proof 确认）
  4. 更新 requirements.txt
  5. 记录到 CHANGELOG
  6. 合并到主分支
```

## 二、版本冲突诊断流程

### 2.1 冲突检测

```bash
# 检查当前环境是否有冲突
pip check

# 查看某个包的依赖树
pip show <package> | grep Requires

# 查看完整依赖关系
pipdeptree                    # 需安装 pipdeptree
```

### 2.2 常见冲突场景与诊断

| 冲突场景 | 症状 | 诊断命令 | 典型解决方案 |
|:--------|:-----|:--------|:----------|
| numpy 版本不兼容 | ValueError: numpy.ndarray size changed | `pip show numpy` 检查版本 | 锁定 numpy 版本 |
| pandas API 变更 | AttributeError: module 'pandas' has no attribute | `pip show pandas` 对比文档 | 降级到已知兼容版本 |
| openpyxl 样式兼容 | 样式丢失/报错 | 检查 openpyxl 版本 | 锁定到 3.1.x |
| python-docx 格式异常 | DOCX 格式损坏 | `pip show python-docx` | 锁定版本并报告上游 |
| 传递依赖冲突 | pip check 报错 | `pipdeptree` 查看冲突链 | 手动指定兼容版本 |

### 2.3 冲突诊断决策树

```
发现异常
  │
  ├─ pip check 是否通过？
  │   ├─ 否 → 使用 pipdeptree 定位冲突的传递依赖
  │   │       ├─ 能通过固定版本解决 → 更新 requirements.txt
  │   │       └─ 无法解决 → 评估是否可移除某个直接依赖
  │   │
  │   └─ 是 → 检查运行时行为
  │           ├─ 行为正常 → 可能是 API 用法问题（非依赖问题）
  │           └─ 行为异常 → 查看包的 CHANGELOG/Release Notes
  │
  ├─ 最近是否升级了某个包？
  │   ├─ 是 → 降级该包到之前版本，看问题是否消失
  │   └─ 否 → 检查是否有新安装的包引入了版本冲突
  │
  └─ 所有方法无效 → 创建全新 venv，从零安装排查
```

## 三、第三方库更新策略

### 3.1 更新分类

| 更新类型 | 定义 | 响应策略 | 响应时间 |
|:--------|:-----|:--------|:--------|
| 🔴 安全更新 | CVE 漏洞修补 | 立即评估→24小时内升级 | 24小时 |
| 🟠 紧急修复 | 严重影响功能的 Bug 修复 | 评估→3天内升级 | 3天 |
| 🟡 功能更新 | 新增 API/功能 | 灰度测试→评审后决定 | 按需 |
| 🟢 大版本升级 | 主版本号变更（破坏性） | 完整评审→独立分支验证→团队讨论 | 按需 |
| ⚪ 常规维护 | 小版本/补丁 | 随下次发布周期 | 每季度 |

### 3.2 更新评估矩阵

对每次更新，评估以下维度（每项 1-5 分）：

| 评估维度 | 权重 | 说明 |
|:--------|:----:|:-----|
| 安全影响 | 30% | 是否修复已知漏洞 |
| 功能需求 | 20% | 项目是否实际需要新功能 |
| 兼容风险 | 25% | 与现有代码的兼容概率 |
| 社区活跃度 | 10% | 包的维护活跃程度 |
| 替代成本 | 15% | 如果这个包坏了，有没有替代方案 |

**评估公式**：总分 = 安全*0.3 + 功能*0.2 + (6-兼容风险)*0.25 + 社区*0.1 + (6-替代成本)*0.15

阈值：总分 >= 3.5 → 建议升级；2.5-3.5 → 灰度测试；< 2.5 → 暂不升级

## 四、Python 库依赖树可视化

### 4.1 依赖树结构

```
铁律量化项目依赖树（简化）：
├── numpy (1.26.x)
│   └── (无传递依赖)
├── pandas (2.1.x)
│   ├── numpy (共享)
│   ├── python-dateutil
│   └── pytz
├── requests (2.31.x)
│   ├── urllib3
│   ├── certifi
│   ├── charset-normalizer
│   └── idna
├── python-docx (1.1.x)
│   └── lxml
├── openpyxl (3.1.x)
│   └── et-xmlfile
└── mcp
    ├── pydantic
    └── httpx
```

### 4.2 传递依赖管理原则

- requirements.txt 只记录**直接依赖**（项目直接 import 的包）
- 传递依赖版本由 pip 解析器自动管理
- 如某个传递依赖需要固定版本，显式添加到 requirements.txt 并注释原因
- 依赖树定期用 `pipdeptree` 导出存档

## 五、PowerShell 模块依赖管理

### 5.1 当前策略

```
核心理念：零外部 PowerShell 模块依赖

除非绝对必要，所有脚本使用 Windows 内置 cmdlet：
  - Invoke-WebRequest   → HTTP 请求
  - ConvertFrom-Json     → JSON 解析
  - Export-Csv           → CSV 生成
  - Get-ChildItem        → 文件遍历
  - ...
```

### 5.2 例外管理

如果确实需要外部 PS 模块：

| 步骤 | 操作 |
|:----:|:-----|
| 1 | 在 Arch 团队会议上提出并论证必要性 |
| 2 | 确认该模块在 PSGallery 上的维护状态（最近 6 个月有更新） |
| 3 | 固定在特定版本：`Install-Module -Name X -RequiredVersion Y.Y.Y` |
| 4 | 在环境配置文档中记录 |
| 5 | 在 `#Requires` 声明中注明 |

## 六、依赖安全审计

### 6.1 审计方法

```bash
# 使用 pip-audit 检查已知漏洞
pip install pip-audit
pip-audit

# 使用 safety 检查
pip install safety
safety check

# 手动检查
# 定期查看 https://nvd.nist.gov 和 GitHub Security Advisories
```

### 6.2 漏洞响应流程

```
发现漏洞
  │
  ├─ 评估严重性（CVSS 评分）
  │   ├─ Critical (9.0+)  → 立即升级，24小时内
  │   ├─ High (7.0-8.9)   → 3天内评估并处理
  │   ├─ Medium (4.0-6.9) → 下次发布周期处理
  │   └─ Low (<4.0)       → 记录，不紧急处理
  │
  ├─ 检查漏洞是否影响本项目
  │   ├─ 是 → 升级到修复版本
  │   └─ 否（不使用的功能）→ 记录豁免，不升级
  │
  └─ 升级后运行全量回归测试
```

## 七、降级和回滚策略

### 7.1 回滚触发条件

| 条件 | 自动/手动 | 说明 |
|:-----|:--------|:-----|
| 升级后核心功能失败 | 手动 | 评分引擎报错、报告生成失败 |
| 测试套件不通过 | 手动 | Proof 验证失败 |
| 数据产出异常 | 手动 | 输出数据与预期严重偏离 |
| 性能严重下降 | 手动 | 耗时增加 50%+ |

### 7.2 依赖回滚操作

```bash
# 方法 1：通过 requirements.txt 回滚
pip install -r requirements.txt.rollback

# 方法 2：手动降级单个包
pip install <package>==<previous_version>

# 方法 3：重建虚拟环境
deactivate
Remove-Item -Recurse .venv
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

### 7.3 回滚验证清单

回滚完成后必须验证：
- [ ] 所有核心包版本回到升级前的状态
- [ ] `pip check` 无冲突
- [ ] 关键脚本可正常运行
- [ ] API 调用正常（腾讯/新浪/东财至少 2/3）
- [ ] 报告生成正常
- [ ] 回滚操作已记录

## 八、依赖更新日志规范

### 8.1 格式模板

每次依赖变更必须记录：

```markdown
### 依赖变更 — YYYY-MM-DD

| 字段 | 值 |
|:-----|:---|
| 操作类型 | [升级/降级/新增/移除] |
| 包名 | xxx |
| 旧版本 | x.x.x |
| 新版本 | y.y.y |
| 变更原因 | 安全修复/功能需求/冲突解决/... |
```

## 九、依赖管理最佳实践

### 9.1 黄金规则

1. **不追新**：稳定 > 新功能，不盲目升级
2. **有回滚**：每次升级前记录回滚命令
3. **有测试**：升级后跑全量回归
4. **有记录**：每次变更都有日志
5. **有备份**：升级前 `pip freeze > requirements.txt.backup`
6. **隔离验证**：在独立分支/环境测试后才合并

### 9.2 反模式（不要做的事）

- ❌ `pip install --upgrade` 不加包名（批量升级所有包）
- ❌ 跳过测试就合并依赖变更
- ❌ 在 requirements.txt 中使用 `>=` 不设上限
- ❌ 不记录变更原因（"不知道为什么升级了"）
- ❌ 忽略安全审计告警
- ❌ 在生产环境直接 pip install 测试
