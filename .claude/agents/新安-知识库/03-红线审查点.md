# 03 -- 红线审查点

> **定位**：新安（质量工程师）本地知识库 -- 将规则红线逐条翻译为可执行的代码级审查点
> **更新**：2026-05-23 | **基础文档**：规则红线v1.10 | **关联文件**：01-测试策略分层、02-回归测试检查清单

---

## 一、审查总则

### 1.1 红线审查的基本原则

红线审查是新安对代码变更的"合规性审查"：不评判"代码写得好不好"，只检查"代码是否违反了不可触碰的红线规则"。

### 1.2 审查范围

所有代码变更、文档变更、配置变更，只要触及以下任一红线条款，就必须通过对应审查点的验证。

### 1.3 审查执行时机

| 时机 | 审查深度 | 触发条件 |
|:-----|:---------|:---------|
| **提交前自查** | 快速审查（受影响条款） | 每次git commit前 |
| **代码审查时** | 完整审查（全部条款） | Pull Request / 变更审查请求 |
| **发布前检查** | 完整审查 + 历史缺陷复查 | 版本发布前 |
| **定期审计** | 完整审查 + 随机抽查 | 每2周 |

## 二、红线条款→代码审查点映射

### 2.1 红线 §1.1 数据真实性 — 禁止编造数据

**红线原文**：所有出现在报告中的数字，必须来自真实数据源。禁止在没有数据时凭空赋值或编造任何数字。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL1.1-1 | 代码中无硬编码的数字数据 | grep搜索代码中的硬编码数值（非配置常量，如直接赋值EPS=1.5） | B0 |
| RL1.1-2 | 所有数据赋值来自API调用或计算 | 检查每个数据变量是否有明确的API来源或计算公式 | B0 |
| RL1.1-3 | 缺失字段返回null而非默认值 | 检查异常处理：API字段缺失时是否返回$null而非填充默认值 | B1 |

**常见违规模式**：

```
违规1: 硬编码兜底值
  $EPS = 0.85  # 当API获取失败时直接用固定值 —— B0违规
正确做法:
  $EPS = Get-FinancialEPS -Code $code  # 失败时返回$null并标注不可用

违规2: 填充推断值
  if ($PE -eq $null) { $PE = $IndustryAvgPE }  # 用行业均值推断 —— B1违规
正确做法:
  if ($PE -eq $null) { $PE = "数据不可用" }

违规3: 删除异常值
  if ($price -lt 0) { return }  # 静默丢弃 —— 应记录告警
正确做法:
  if ($price -lt 0) { Write-Warning "异常价格: $price"; return $null }
```

### 2.2 红线 §1.2 数据源1+2主备架构

**红线原文**：每个数据字段按主API→备API→缓存获取。双源数据(行情/K线)必须实际尝试主和备两个API。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL1.2-1 | 行情数据获取函数实现了主备双API调用 | 检查Get-StockQuote：是否尝试腾讯[1]→失败后尝试新浪[1B] | B0 |
| RL1.2-2 | K线数据获取函数实现了主备双API调用 | 检查Get-StockKLine：是否尝试新浪[2]→失败后尝试腾讯[2B] | B0 |
| RL1.2-3 | 备API不是"伪尝试" | 确认代码中备API的调用路径可达（不是被注释掉的代码，不是永远不会执行的分支） | B0 |
| RL1.2-4 | 缓存兜底在所有降级路径末端 | 检查每个数据获取函数：主+备都失败后是否读取缓存 | B1 |
| RL1.2-5 | 缓存读取有TTL检查 | 检查Load-DataCache调用：是否传入TTL参数 | B1 |
| RL1.2-6 | 独有数据标注"仅供参考" | 检查报告模板：[8][9][10][11][12]后是否有"仅供参考"标注 | B1 |
| RL1.2-7 | 数据源编号与标注规则一致 | 对照规则红线§1.2表格，确认代码中使用的数据源编号正确 | B2 |

**常见违规模式**：

```
违规1: 伪降级路径
  # 代码中有备API的if分支，但条件永远不会为真
  if ($false) { Invoke-SinaAPI }  # 被硬编码跳过 —— B0违规

违规2: 声明了备源但从未调用
  # 文档写了"[1B]新浪行情"但代码中没有新浪API的实际HTTP调用 —— B0违规
  
违规3: 缓存无TTL检查
  Load-DataCache -Key "Quote_600519"  # 缺少TTL参数，可能返回过期数据 —— B1违规

违规4: 独有数据未标注
  报告中出现"北向资金净流入8.2亿[8]"但没有"仅供参考"说明 —— B1违规
```

### 2.3 红线 §1.2 PE(TTM)公式

**红线原文**：PE(TTM) = 当前价[1] / TTM_EPS[3]，TTM_EPS = 最新年报EPS - 去年同季EPS + 最新季报EPS。禁止直接用腾讯静态PE做否决。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL1.2-PE1 | PE(TTM)使用正确公式 | 检查评分引擎代码：PE(TTM)是否使用 当前价/TTM_EPS | B0 |
| RL1.2-PE2 | TTM_EPS使用正确公式 | 检查TTM_EPS计算：最新年报EPS - 去年同季EPS + 最新季报EPS | B0 |
| RL1.2-PE3 | 未使用腾讯静态PE做否决 | 搜索代码中是否直接用腾讯API返回的PE字段做一票否决依据 | B0 |
| RL1.2-PE4 | 亏损股EPS为负时返回"N/A" | 检查PE(TTM)计算：EPS<=0时是否返回"N/A"或null而非负数 | B1 |
| RL1.2-PE5 | 当前价=0时跳过 | 检查PE(TTM)计算：停牌股(价格为0或不变)是否被正确跳过 | B1 |

**常见违规模式**：

```
违规1: 直接使用腾讯静态PE
  $ttmPE = $tencentData.PE  # 腾讯PE是静态PE，不是TTM —— B0违规
正确做法:
  $ttmEPS = $annualEPS - $lastYearSameQEPS + $latestQEPS
  $ttmPE = $price / $ttmEPS

违规2: TTM_EPS用了错误的季报
  $ttmEPS = $annualEPS + $Q1 + $Q2 + $Q3  # 这是前滚EPS，不是TTM —— B0违规
正确做法:
  $ttmEPS = $annualEPS - $lastYearSameQuarterEPS + $latestQuarterEPS

违规3: 亏损股返回负数PE
  PE(TTM) = 10.5 / (-0.85) = -12.35  # 负数PE无意义 —— B1违规
正确做法:
  当EPS<=0时，PE(TTM) = "N/A（亏损）"
```

### 2.4 红线 §1.3 禁止编造数据（扩展审查）

**红线原文**：禁止用AI模型推断缺失的财务指标；不可获取的指标不得输出具体数值。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL1.3-1 | 代码中无AI推断逻辑 | 搜索代码中是否有让AI估算数据值的逻辑 | B0 |
| RL1.3-2 | 不可获取指标不输出 | 对照规则红线§1.5.1，确认EV/EBITDA/筹码分布/社交情绪/大宗交易等不可获取指标未在报告中输出具体数值 | B0 |
| RL1.3-3 | 不可获取指标标注说明 | 如果模板中留有不可获取指标的占位符，确认标注了"数据不可获取" | B2 |

**常见违规模式**：

```
违规1: 让AI估算DCF
  # 在prompt中: "请根据行业平均增长率估算DCF估值" —— B0违规

违规2: 输出不可获取指标
  # 报告中: "筹码集中度85%[5]" —— 实际[5]是本地计算，筹码分布无数据源
正确做法: 删除该指标，或标注"数据不可获取"

违规3: 灰色地带
  # 用简单公式代理复杂指标，如用"20日涨幅波动率"代理"筹码分布"
正确做法: 标注"代理指标：20日涨幅波动率（非筹码分布，仅供参考）"
```

### 2.5 红线 §1.6 CHANGELOG真实性

**红线原文**：CHANGELOG只记录已完成且已验证的改动。禁止先写CHANGELOG再补代码。"已修复"声明必须附带证据链。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL1.6-1 | CHANGELOG条目有对应代码变更 | 逐条对比CHANGELOG与git diff | B0 |
| RL1.6-2 | "已修复"声明有证据链 | 检查commit message和diff是否包含具体的修改位置+内容 | B1 |
| RL1.6-3 | 不存在"计划实施"被记录为"已完成" | 搜索CHANGELOG中的"将"/"计划"/"待"等未来时关键词 | B1 |
| RL1.6-4 | CrossCheck通过 | 运行 version_supervisor.ps1 -CrossCheck | B0 |
| RL1.6-5 | 每个版本有责任人+审批人 | 检查CHANGELOG条目是否包含修改人和审批人字段 | B2 |

**常见违规模式**：

```
违规1: 虚假记录
  CHANGELOG记录: "## Fixed - 已移除VetoedStocks"
  实际代码中: VetoedStocks变量仍然存在 —— B0违规

违规2: 先写CHANGELOG再补代码
  先提交CHANGELOG记录"新增数据源[13]"，但数据源[13]的代码提交在之后 —— B1违规

违规3: 计划当完成
  CHANGELOG记录: "### Security - 将增加API签名认证" —— 这是计划，不是已完成 —— B1违规

违规4: 缺少证据链
  说"已修复编码问题"但commit中看不到任何编码相关改动 —— B1违规
```

### 2.6 红线 §1.7 PDF删除禁止

**红线原文**：未经用户明确书面许可，AI禁止删除项目中任何已生成的PDF文件。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL1.7-1 | 代码中无自动删除PDF的逻辑 | 搜索代码中的Remove-Item/DEL/rm等删除命令，确认目标不是PDF | B0 |
| RL1.7-2 | 清理脚本不含PDF删除 | 检查所有清理/维护脚本（如clean_cache.ps1）不包含PDF删除 | B0 |
| RL1.7-3 | 构建脚本不自动覆盖旧版PDF | 检查构建脚本：生成新PDF时是否直接覆盖旧文件（应重命名保留旧版） | B1 |
| RL1.7-4 | Git历史中无PDF删除记录 | 检查git log是否有意外删除PDF的记录 | B2 |

**常见违规模式**：

```
违规1: 清理脚本删除PDF
  Remove-Item "*.pdf" -Recurse  # 在清理脚本中 —— B0违规

违规2: 报告生成脚本直接覆盖
  gen_daily_html.ps1 中: "每日股票推荐_20260523.pdf" 直接覆盖同名文件 —— B1违规
正确做法: 先检查文件是否存在，如存在则保留（或重命名为旧版），再生成新版

违规3: 以"清理旧文件"为由删除
  "删除所有2025年的旧报告" —— 需要用户明确指令
```

### 2.7 红线 §2 Token纪律

**红线原文**：能用代码完成的绝不消耗Token。禁止把原始数据全文喂给AI阅读。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL2-1 | 数据获取层无AI参与 | 检查代码：数据获取是否完全由代码执行（无LLM调用） | B0 |
| RL2-2 | 无原始数据喂AI | 检查prompt/logic：评分/分析的输入是否为计算结果而非原始JSON/CSV | B1 |
| RL2-3 | 批量数据处理使用代码 | 检查是否存在让AI"遍历100只股票"的prompt（应使用代码循环） | B1 |
| RL2-4 | AI调用有明确边界 | 检查每个AI调用是否只做分析判断而非数据处理 | B2 |

**常见违规模式**：

```
违规1: 把K线JSON喂给AI
  "请阅读以下120日K线数据，计算移动均线..." —— B1违规
正确做法: 代码计算均线→AI基于计算结果做分析判断

违规2: 让AI过滤股票
  "以下500只股票中请筛选出符合条件的前20只" —— B1违规
正确做法: 代码按条件筛选→AI评估筛选结果

违规3: 重复调用
  同一个数据被多次读取给AI（未使用缓存或变量保存） —— B2违规
```

### 2.8 红线 §3 API调用间隔>=0.3s

**红线原文**：每次API调用后强制间隔>=0.3秒，每10次调用后额外休息>=2秒。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL3-1 | 每次API调用后有Sleep | 检查每个Invoke-WebRequest/Invoke-RestMethod后是否有Start-Sleep | B1 |
| RL3-2 | Sleep时长>=0.3秒 | 检查Start-Sleep -Milliseconds的值是否>=300 | B1 |
| RL3-3 | 批量调用有额外休息 | 检查批量循环中：每10次调用后是否有>=2秒的额外Sleep | B1 |
| RL3-4 | 财务数据仅在TTL过期时拉取 | 检查财务数据获取：是否有TTL检查避免短期内重复拉取 | B2 |

**常见违规模式**：

```
违规1: 无间隔
  foreach ($stock in $stocks) { Invoke-API $stock }  # 无Sleep —— B1违规

违规2: 间隔太短
  Start-Sleep -Milliseconds 100  # 只有0.1秒 —— B1违规

违规3: 间隔只在最后
  # 循环内无Sleep，循环结束后才Sleep一次 —— B1违规
```

### 2.9 红线 §5.4 版本管理

**红线原文**：白皮书版本管理——版本号、CHANGELOG、归档策略、双格式同步。

**审查点**：

| 编号 | 检查项 | 检查方法 | 严重级别 |
|:----:|:-------|:---------|:------:|
| RL5.4-1 | 白皮书版本号符合SemVer | 检查所有白皮书文件名：vMAJOR.MINOR.PATCH | B1 |
| RL5.4-2 | .md→.docx同步生成 | 检查.md修改后是否重新生成了.docx | B1 |
| RL5.4-3 | 旧版本保留不删 | 检查白皮书目录：旧版本文件是否存在 | B1 |
| RL5.4-4 | 文档版本索引同步更新 | 检查版本变更后索引是否更新 | B1 |
| RL5.4-5 | 团队名册.md和.xlsx版本一致 | 检查项目成员目录：.md和.xlsx版本号是否一致 | B2 |

## 三、审查执行流程

### 3.1 标准审查流程

```
1. 确定审查范围
   ├─ 收到变更内容（git diff / 变更摘要）
   ├─ 确定变更类型（代码/文档/配置）
   └─ 确定受影响的红线条款
   
2. 逐条款审查
   ├─ 对照§二的审查点表格逐项检查
   ├─ 使用grep/diff/代码阅读验证
   └─ 记录审查结果（通过/发现问题）
   
3. 分级报告
   ├─ B0问题：立即阻断，禁止继续
   ├─ B1问题：必须修复才能通过审查
   ├─ B2问题：建议修复，可记录跟进
   └─ B3问题：可选优化，不必阻塞
   
4. 输出审查报告
   └─ 使用§五的红线审查报告模板
```

### 3.2 快速审查 vs 完整审查

| 审查类型 | 适用场景 | 检查范围 | 预计耗时 |
|:---------|:---------|:---------|:-------:|
| 快速审查 | 日常commit前自查 | 仅检查变更涉及的红线条款（如只改了数据获取→仅查§1.1/1.2/3） | 3-5分钟 |
| 完整审查 | 发布前/PR审查/定期审计 | 逐条检查所有§一~§六的红线条款 | 10-15分钟 |

### 3.3 审查辅助工具

| 工具 | 用途 | 命令 |
|:-----|:-----|:-----|
| check_redlines.ps1 | 自动化红线合规检查 | `powershell -File 代码文件/规则红线/check_redlines.ps1` |
| version_supervisor.ps1 | 版本一致性检查 | `powershell -File 代码文件/监督机制/version_supervisor.ps1 -CrossCheck` |
| check_report_style.ps1 | 报告样式合规检查 | `powershell -File 代码文件/规则红线/check_report_style.ps1` |

## 四、模块→红线条款速查

### 4.1 按代码模块查红线

| 代码模块 | 核心红线条款 | 次要红线条款 |
|:---------|:-----------|:-----------|
| 数据获取（Get-StockQuote等） | §1.1, §1.2(1+2架构), §3(API间隔) | §2(Token) |
| 评分引擎（评分计算、一票否决） | §1.2(PE公式), §1.3(不编造) | §2(Token) |
| 报告生成（HTML/DOCX/MD） | §1.2(标注), §1.3(不输出不可获取), §6(样式) | §1.7(PDF) |
| 白皮书/文档 | §1.6(CHANGELOG), §5.4(版本管理) | — |
| 脚本/工具 | §1.7(PDF删除), §3(API间隔) | — |
| 基础设施/配置 | §2(Token) | §3(API间隔) |

### 4.2 按变更类型查红线

| 变更类型 | 必查红线条款 |
|:---------|:-----------|
| 新增数据获取函数 | §1.1, §1.2(1+2架构), §3.1-3.3 |
| 修改评分逻辑 | §1.2(PE公式), §1.3 |
| 修改报告模板 | §1.2(标注), §1.3, §6 |
| 新增/修改白皮书 | §1.6, §5.4 |
| 修改脚本工具 | §1.7, §3 |
| 新增配置项 | §2, §3 |

## 六、红线审查决策矩阵

### 6.1 发现问题后的处理流程

```
发现红线问题
├─ B0 阻断级
│   ├─ 立即停止当前任务
│   ├─ 通知阿黑
│   ├─ 修复后重新审查
│   └─ 未修复前禁止任何发布/提交
│
├─ B1 严重级
│   ├─ 记录到缺陷追踪
│   ├─ 必须在本次变更中修复
│   ├─ 修复后重新审查对应条款
│   └─ 全部B1修复后方可通过审查
│
├─ B2 一般级
│   ├─ 记录到缺陷追踪
│   ├─ 可在本次变更中修复或记录跟进
│   └─ 不阻塞审查通过
│
└─ B3 建议级
    ├─ 记录到改进日志
    └─ 不阻塞审查通过
```

### 6.2 审查通过/不通过标准

| 条件 | 结论 |
|:-----|:-----|
| 无B0且无B1 | **通过** |
| 无B0，B1≤3且有修复计划 | **有条件通过**（B1修复后自动转通过） |
| 无B0，B1>3 | **暂缓通过**（需先修复部分B1） |
| 有B0 | **不通过**（禁止继续） |
