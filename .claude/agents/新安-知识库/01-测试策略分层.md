## 一、测试金字塔：四层模型

### 1.1 金字塔结构

```
            /\
           /  \        端到端(E2E)：全链路验证
          /    \       频率：每次发布前
         /------\      责任人：新安设计 + Claude执行
        /        \     覆盖目标：核心用户场景100%
       / 回归测试  \    
      /   (R01-R12) \  回归测试：变更后验证已有功能
     /--------------\  频率：每次变更后
    /                \ 责任人：新安设计 + Claude执行
   /   集成测试       \ 覆盖目标：模块间接口100%
  /   (数据→评分→报告)  \ 
 /--------------------\ 
/    单元测试          \ 单元测试：函数/模块级别
/  (公式/计算/边界)     \ 频率：每日/每次代码变更
------------------------  责任人：新安设计 + Claude实现
                          覆盖目标：关键计算函数100%
```

### 1.2 各层详细定义

| 层级 | 定位 | 覆盖目标 | 执行频率 | 责任人 | 实现方式 |
|:-----|:-----|:---------|:---------|:------|:---------|
| **L1 单元测试** | 函数/模块级正确性验证 | 关键计算函数100% | 每次代码变更 | 新安设计，Claude实现 | PowerShell Pester / Python pytest |
| **L2 集成测试** | 模块间接口契约验证 | 模块间接口100% | 每次接口变更 | 新安设计，Claude执行 | 手动+脚本混合 |
| **L3 回归测试** | 已有功能无损验证 | 核心链路100%、R01-R12全通过 | 每次变更后 | 新安设计+执行 | 对照检查清单逐项验证 |
| **L4 端到端** | 全链路真实数据验证 | 核心用户场景100% | 每次发布前 | 新安设计+执行 | 完整运行+对比基线 |

## 二、各层详细规范

### 2.1 L1 单元测试

**单元测试的"单元"定义**：本项目中最小的可独立测试的计算单元。

**必测单元清单**：

| 编号 | 测试单元 | 所属模块 | 测试内容 | 覆盖要求 |
|:----:|:---------|:---------|:---------|:---------|
| U01 | PE(TTM)计算 | 评分引擎 | TTM_EPS公式正确性、边界值(N/A/亏损/0) | 正常+边界全覆盖 |
| U02 | 一票否决判定 | 评分引擎 | 否决条件触发/不触发边界 | 每个否决条件至少3个用例 |
| U03 | 评分加权计算 | 评分引擎 | 因子权重应用正确性 | 排名一致性验证 |
| U04 | 缓存读写 | 数据获取 | TTL过期判定、缓存命中/未命中 | 过期/未过期/不存在 三态 |
| U05 | 降级路径 | 数据获取 | 主→备→缓存 三级降级 | 每级成功/失败全组合 |
| U06 | API调用间隔控制 | 数据获取 | >=0.3s间隔、>=2s/10次 | 时序验证 |
| U07 | 数据源标注 | 报告生成 | [1]/[B]/[C]标记正确性 | 每种标记类型至少1例 |
| U08 | 版本号一致性 | 报告生成 | 文件名vs文档头vs索引 | 三处比对 |

### 2.2 L2 集成测试

**集成测试焦点**：模块间的数据传递和接口契约。

**必测集成链路**：

| 编号 | 集成链路 | 验证点 | 优先级 |
|:----:|:---------|:------|:-----:|
| I01 | 数据获取→评分引擎 | 数据格式正确传递、缺失字段不导致崩溃 | P0 |
| I02 | 评分引擎→一票否决 | 否决结果正确传递给评分汇总 | P0 |
| I03 | 评分引擎→报告生成 | 评分排名完整传递、无数据丢失 | P0 |
| I04 | 数据获取→缓存层 | 写入后立即可读、TTL过期不返回 | P1 |
| I05 | 缓存层→数据获取 | 缓存数据结构与API返回结构一致 | P1 |
| I06 | 报告生成→DOCX生成 | Markdown渲染为DOCX无丢失 | P1 |
| I07 | 报告生成→HTML生成 | HTML模板数据填充完整 | P1 |
| I08 | 所有模块→日志 | 异常/降级/超时均有日志记录 | P2 |

### 2.3 L3 回归测试 (R01-R12)

详见 `02-回归测试检查清单.md`。核心链路回归测试套件必须在每次变更后完整执行。

### 2.4 L4 端到端测试

**端到端测试等于一次完整的"真实"运行**：从数据获取到报告产出，使用真实API（非mock），输出完整报告。

**E2E测试检查点**：

| 阶段 | 检查项 | 通过标准 |
|:-----|:------|:---------|
| 数据获取 | 所有数据源尝试主API | 主API被实际调用（日志确认） |
| 数据获取 | 备API在需要时触发 | 备API降级路径可触发（日志确认） |
| 数据获取 | 缓存正常读写 | 缓存文件存在且结构正确 |
| 评分引擎 | 至少5只股票完成评分 | 评分输出不为空 |
| 评分引擎 | PE(TTM)值可验证 | 至少1只可手动验算 |
| 评分引擎 | 一票否决有触发 | 实际市场中有ST/亏损股触发否决 |
| 报告生成 | HTML报告可打开 | 浏览器打开无异常 |
| 报告生成 | DOCX报告可打开 | Word打开无异常 |
| 报告生成 | 免责声明存在 | 所有报告模板含免责声明 |
| 报告生成 | 数据源标注完整 | 每个数据数字后跟来源标记 |

## 三、核心链路必测原则

### 3.1 什么是核心链路

```
数据获取层 → 数据完整性验证 → 评分引擎 → 评分准确性验证 → 报告生成 → 报告内容验证
    ↓              ↓                ↓              ↓              ↓            ↓
 API连通性    缓存TTL检查      PE(TTM)计算     评分排名一致性   HTML/CSS规范  免责声明
 1+2架构      数据不缺失        因子权重       一票否决触发     DOCX格式    版本号正确
```

### 3.2 核心链路必测规则

1. **每次变更后必跑**：无论变更多大或多小，核心链路的L3回归测试(R01-R12)必须全部通过
2. **数据获取必验**：R01(行情API)、R02(K线降级)、R03(缓存兜底) -- 三项中至少通过两项方可继续
3. **评分引擎必验**：R04(PE(TTM)验算)、R05(一票否决) -- 两项全部通过方可继续
4. **报告生成必验**：R07(数据源标注)、R09(免责声明) -- 两项全部通过方可发布报告
5. **阻断规则**：核心链路中任何P0测试失败，禁止发布报告或提交变更

### 3.3 核心链路测试的时间预算

| 测试层级 | 预计耗时 | 自动化程度 |
|:---------|:---------|:-----------|
| L1 单元测试 | 1-2分钟 | 高（脚本可自动运行） |
| L2 集成测试 | 3-5分钟 | 中（部分需手动检查） |
| L3 回归测试 | 5-10分钟 | 中（检查清单逐项确认） |
| L4 端到端 | 10-15分钟 | 低（需人工判断报告质量） |
| **完整测试周期** | **20-30分钟** | — |

## 四、测试优先级判定矩阵

### 4.1 优先级定义

| 优先级 | 定义 | 跳过后果 | 可跳过场景 |
|:------:|:-----|:---------|:-----------|
| **P0 阻断级** | 不通过则禁止继续 | 可能导致错误报告发布 | 永不跳过 |
| **P1 核心级** | 不通过必须记录+跟进 | 降低报告可信度 | 仅紧急hotfix可跳过（需标注） |
| **P2 常规级** | 不通过应记录 | 不影响核心功能 | 时间紧张时可延后 |
| **P3 增强级** | 通过则更放心 | 细节改进 | 任何时候可延后 |

### 4.2 优先级判定矩阵

| 测试对象 | 变更频率 | 影响范围 | 历史出问题次数 | → 优先级 |
|:---------|:--------:|:--------:|:-------------:|:-------:|
| PE(TTM)计算 | 低 | 广泛(影响所有评分) | 高(曾用错公式) | **P0** |
| 一票否决逻辑 | 低 | 广泛(影响选股结果) | 中(边界曾遗漏) | **P0** |
| 数据源1+2架构 | 低 | 广泛(影响所有数据) | 高(曾只声明未实现) | **P0** |
| API调用间隔 | 低 | 窄(仅影响API稳定性) | 低 | **P1** |
| 评分因子权重 | 中 | 广泛(影响排名) | 中 | **P1** |
| 报告数据源标注 | 中 | 中(影响合规性) | 高(曾遗漏标注) | **P1** |
| 报告版本号一致性 | 高 | 窄(影响管理) | 中(曾不一致) | **P1** |
| CHANGELOG一致性 | 高 | 中(影响可信度) | 高(曾有虚假记录) | **P1** |
| 缓存TTL | 低 | 中(影响数据新鲜度) | 低 | **P2** |
| 日志格式 | 中 | 窄(影响调试) | 低 | **P2** |
| HTML样式合规 | 高 | 窄(影响美观) | 低 | **P2** |
| 变量命名规范 | 中 | 窄(影响可读性) | 低 | **P3** |

### 4.3 优先级判定公式

```
测试优先级 = max(影响范围分, 历史出问题分) + 变更频率调整

影响范围分: 广泛=3, 中等=2, 窄=1
历史出问题分: 高=3, 中=2, 低=1, 无=0
变更频率调整: 高=+1, 低=-1, 中=0

总分 >= 4 → P0
总分 = 3 → P1
总分 = 2 → P2
总分 <= 1 → P3
```

## 五、冒烟测试 vs 深度测试

### 5.1 冒烟测试（Smoke Test）

**定义**：快速验证核心功能是否"能跑"的最小测试集。不追求覆盖面，只求确认没有"起火"。

**触发条件**：
- 每次CI构建完成后
- 每次代码提交后（自动化触发）
- 部署到新环境后
- 快速修复(hotfix)后需要立即确认

**冒烟测试清单（最小集，预计3-5分钟）**：

| 编号 | 测试点 | 通过标准 | 耗时 |
|:----:|:------|:---------|:---:|
| S01 | 腾讯行情API连通 | 返回有效数据（至少1只股票） | ~10s |
| S02 | PE(TTM)计算不报错 | 至少1只股票计算成功 | ~5s |
| S03 | 一票否决有输出 | 至少1只股票被否决或跳过 | ~5s |
| S04 | HTML报告可生成 | 生成文件大小>0 | ~30s |
| S05 | 报告含免责声明 | 关键文本存在 | ~5s |

### 5.2 深度测试（Deep Test）

**定义**：完整执行所有测试层(L1→L2→L3→L4)，覆盖所有边界和异常场景。

**触发条件**：
- 重大版本发布前（MAJOR/MINOR）
- 核心算法变更后（评分公式、一票否决逻辑）
- 数据源切换或新增后
- 项目重构后
- 定期质量审计（建议每2周一次）

**深度测试扩展清单（在冒烟基础上增加）**：

| 编号 | 测试点 | 通过标准 | 耗时 |
|:----:|:------|:---------|:---:|
| D01 | 所有数据源主备切换验证 | 每个有备源的数据源均实际触发降级 | ~2min |
| D02 | 缓存过期+重新拉取验证 | TTL过期后自动拉取新数据 | ~1min |
| D03 | 10只股票PE(TTM)验算 | 与手动计算结果偏差<0.01 | ~3min |
| D04 | 所有一票否决条件边界 | 每条件至少触发+不触发各3例 | ~3min |
| D05 | 三份报告(DOCX+HTML+MD)格式检查 | 样式基线文档全部合规 | ~2min |
| D06 | 版本号三处一致性 | 文件名=文档头=索引 | ~1min |
| D07 | CHANGELOG与代码diff对应 | version_supervisor.ps1 CrossCheck通过 | ~1min |
| D08 | 边界用例库全部执行 | 见04-边界用例库.md | ~5min |

### 5.3 冒烟→深度 决策树

```
收到测试任务
├─ 是hotfix修复？ → 冒烟测试即可
├─ 是文档格式修改？ → 仅L4端到端报告检查
├─ 是数据源变更？ → 深度测试（重点D01+D02）
├─ 是评分逻辑变更？ → 深度测试（重点D03+D04）
├─ 是报告模板变更？ → 深度测试（重点D05+D06）
├─ 是发布前检查？ → 完整深度测试
└─ 其他变更 → 冒烟测试 + 受影响模块的深度测试
```

## 七、测试数据管理

### 7.1 测试数据原则

1. **不使用生产数据做测试**：使用样本数据或历史快照
2. **测试数据可重复**：同一输入始终产生同一输出
3. **测试数据覆盖边界**：正常+异常+边界 三类必须齐全
4. **测试数据独立**：不依赖外部API状态

### 7.2 测试数据样本池

| 股票类型 | 代码示例 | 特征 | 用途 |
|:--------|:--------|:-----|:-----|
| 正常大盘股 | 600519(贵州茅台) | 数据齐全、成交活跃、PE可计算 | 正常流程验证 |
| 正常中小盘 | 000858(五粮液) | 数据齐全、中等波动 | 评分排名验证 |
| 亏损股 | — | EPS为负 | PE(TTM)="N/A"验证 |
| ST股票 | — | 风险警示 | 一票否决触发验证 |
| 停牌股 | — | 当前价不变 | 跳过逻辑验证 |
| 次新股 | — | 上市<1年 | 财务数据可能不完整 |
| 退市股 | — | 已退市/即将退市 | 异常处理验证 |

## 八、快速参考

### 8.1 测试决策速查

| 场景 | 做哪个测试 | 参考章节 |
|:-----|:----------|:---------|
| 刚改了一行代码 | 冒烟测试(S01-S05) | §5.1 |
| 改了评分公式 | 深度测试(重点D03+D04) | §5.2 |
| 换了数据源 | 深度测试(重点D01+D02) | §5.2 |
| 要发布新版本了 | 完整深度测试(D01-D08) | §5.2 |
| 不确定改了什么影响 | 变更影响分析 + L3回归 | §3 + 02号文件 |
| 发现了一个bug | 边界用例库对应场景 | 04号文件 |
| 想确认红线合规 | 红线审查点逐项检查 | 03号文件 |

### 8.2 关键原则速记

1. **核心链路必测**：数据→评分→报告，每次变更后
2. **边界比正常更重要**：bug都在边界里
3. **P0不过不发布**：阻断级测试失败禁止继续
4. **先冒烟再深度**：快速确认→全面验证，不浪费时间
5. **可复现是底线**：不能复现=不存在
