### 1.2 daily_workflow.ps1 调度模式

当前master调度脚本 `daily_workflow.ps1` 支持三种模式：

| 模式 | 用途 | 触发方式 | 阶段数 | 关键操作 |
|:-----|:----|:--------|:-----:|:--------|
| `daily` | 首次运行（Day N） | 手动 | 6 | 建池→采集→评分→报告→重点股→归档 |
| `eval` | 后评估（Day N+1） | scheduler 19:00 | 5 | 评估→归档→重点评估→优化检查→CHANGELOG |
| `daily_latest` | 日常运行（Day N+1起） | scheduler 20:00 | 7 | 建池→采集→评分→报告→重点股→归档→模拟交易 |

### 1.3 模式内阶段详细

**daily 模式（手动首次运行）**：
```
Phase 1: build_dynamic_pool.ps1    → 构建动态股票池
Phase 2: batch_data_collector.ps1  → 批量采集数据
Phase 3: scoring_engine_v2.py      → 评分引擎（否决+评分）
Phase 4: gen_daily_html.ps1        → 生成HTML报告
Phase 5: run_keystock_analysis.ps1 → 重点股票分析
Phase 6: archive_data.ps1          → 归档数据
```

**daily_latest 模式（每日定时）**：Phase 1-6 + Phase 7（模拟交易引擎）：
```
Phase 7: sim_trading.ps1 -DryRun   → 模拟交易（安全模式）
```

**eval 模式（盘后评估）**：
```
Phase 1: run_daily_eval.ps1        → 每日荐股后评估
Phase 2: archive_data.ps1          → 归档评估数据
Phase 3: run_keystock_evaluation.ps1 → 重点股票后评估
Phase 4: 自动优化检查              → 胜率/盈亏比/区分度/误判率
Phase 5: CHANGELOG更新             → 记录评估执行
```

### 2.2 可并行与不可并行的任务

**可并行执行（无资源冲突）**：
- 盘前巡检 + 宏观简报（不同数据源、不同脚本）
- 数据预热 + 集合竞价快照（预热用热点池，竞价用全市场，无交集）
- 收盘数据拉取 + 盘中最后一轮巡检（同时进行不冲突）
- 后评估 + 重点股票评估（不同脚本、不同数据文件）
- 模拟交易结算 + 自动优化检查（无依赖关系）

**必须串行执行（有依赖）**：
- 交易日检测 → 所有后续任务（非交易日全跳过）
- 盘前巡检 → 评分引擎（巡检不过则评分不可信）
- 数据预热/集合竞价 → 评分引擎（数据必须就绪）
- 评分引擎 → 报告生成（报告依赖评分结果）
- 后评估 → 自动优化检查 → CHANGELOG更新（链条依赖）

## 三、失败重试策略

### 3.1 指数退避重试

| 重试次数 | 退避延迟 | 总等待 | 适用级别 |
|:-------:|:--------|:------|:--------|
| 第1次 | 3s | 3s | P3-P5 |
| 第2次 | 9s | 12s | P2-P3 |
| 第3次 | 27s | 39s | P1-P2 |
| 第4次 | 81s | 120s | P0-P1 |
| 第5次 | — | — | 放弃，进入降级路径 |

### 3.2 按任务类型的重试配置

| 任务 | 最大重试 | 退避策略 | 失败后 |
|:-----|:-------:|:--------|:------|
| API调用（单源） | 3 | 指数退避 1s→3s→9s | 切换备源 |
| API调用（全源挂） | 5 | 指数退避 3s→9s→27s→81s | 使用缓存兜底 |
| 评分引擎 | 2 | 固定间隔 10s | 人工介入 |
| 报告生成 | 2 | 固定间隔 5s | 使用上一日报告模板 |
| 数据归档 | 3 | 指数退避 1s→5s→25s | 跳过，次日补归档 |
| 模拟交易 | 1 | — | 记录失败，不做交易 |

### 3.3 降级路径

```
任务失败
├── API调用失败
│   ├── 主源 [1] 不可用 → 自动切换到备源 [B]
│   ├── 备源 [B] 不可用 → 使用缓存 [C]
│   └── 缓存 [C] 过期 → 标记 P1 异常 → 该字段使用 "N/A"
│
├── 评分引擎失败
│   ├── 第1次失败 → 重试(10s后)
│   ├── 第2次失败 → 使用上一日评分结果 + 标记 P1
│   └── 上一日无结果 → 人工接管
│
├── 报告生成失败
│   ├── HTML生成失败 → 检查模板/数据
│   ├── DOCX转换失败 → 仅输出HTML + 标记 P2
│   └── 全失败 → 使用上一日报告模板 + 标记 P1
│
└── 定时任务整体失败
    └── 写workflow record FAILED → 人工次日检查
```

## 四、节假日/非交易日处理

### 4.1 交易日历检测机制

```
daily_workflow.ps1 入口
├── param([switch]$SkipMarketCheck)  → 测试用，跳过检测
├── -SkipMarketCheck 未设置
│   ├── 调用 is_market_open.ps1 -Date $Date -HolidayFile $holidayFile
│   ├── exit code != 0 → 非交易日
│   │   ├── Write-Log SKIP
│   │   └── exit 0（优雅退出，不报错）
│   └── exit code == 0 → 交易日，继续执行
└── 结果记录到 workflow_records.csv（状态=SKIPPED）
```

### 4.2 交易日历文件

文件路径：`每日荐股/运营记录/holidays_2026.csv`

格式：
```csv
Date,Reason
2026-01-01,元旦
2026-01-26,春节假期
2026-01-27,春节假期
...
```

### 4.3 节假日行为矩阵

| 时间 | 动作 | 说明 |
|:-----|:----|:-----|
| 周末（周六/周日） | 全部定时任务跳过 | is_market_open 返回 false |
| 法定节假日 | 全部定时任务跳过 | 依赖 holidays_2026.csv |
| 节前最后一个交易日 | 正常执行+额外提示 | "明日起休市N天，注意数据时效" |
| 节后第一个交易日 | 数据预热量加大 | 缓存可能全过期，需全量刷新 |
| 长假（>3天）后 | 新增数据完整性深度检查 | 确认无假期数据断层 |

### 4.4 跳过日志规范

```
[2026-05-23 19:00:01][SKIP] 2026-05-24 is not a trading day, skip
[2026-05-23 19:00:01][SKIP] Reason: Weekend (Saturday)
```

## 五、任务锁机制

### 5.1 防止重复执行

```
任务启动
├── 检查锁文件是否存在
│   ├── 存在 + 未超时 → 退出（已有实例在运行）
│   └── 不存在 / 已超时 → 创建锁文件 → 继续执行
├── 执行任务
└── 任务结束（无论成功/失败）→ 删除锁文件
```

### 5.2 锁文件规范

| 属性 | 值 |
|:-----|:---|
| 存储路径 | `每日荐股/运营记录/.locks/` |
| 命名规则 | `{task_name}.lock` |
| 文件内容 | `pid={PID}\ntimestamp={ISO8601}` |
| 锁超时 | 任务最大执行时间 x 2（例如评分引擎超时5分钟→锁超时10分钟） |
| 清理策略 | 每次任务启动时检查并清理超时锁 |

### 5.3 实现伪代码

```powershell
$lockDir = "每日荐股/运营记录/.locks"
$lockFile = "$lockDir/daily_workflow_eval.lock"
$lockTimeout = 3600  # 1小时

if (Test-Path $lockFile) {
    $lockAge = (Get-Date) - (Get-Item $lockFile).LastWriteTime
    if ($lockAge.TotalSeconds -lt $lockTimeout) {
        Write-Log "Task already running (lock age: $lockAge), exit" -Level "SKIP"
        exit 0
    }
    Write-Log "Stale lock detected (age: $lockAge), removing and continuing" -Level "WARN"
    Remove-Item $lockFile
}

# 创建锁
"pid=$PID`ntimestamp=$(Get-Date -Format 'o')" | Out-File $lockFile -Encoding UTF8

try {
    # 执行任务
} finally {
    Remove-Item $lockFile -ErrorAction SilentlyContinue
}
```

## 六、超时控制

### 6.1 每步最大执行时间

| 步骤 | 正常耗时 | 最大超时 | 超时后动作 |
|:-----|:-------:|:-------:|:----------|
| 盘前巡检 | 30-120s | 300s (5min) | 标记P1，人工确认是否继续 |
| 数据预热 | 60-120s | 300s (5min) | 跳过预热，使用冷缓存（性能劣化） |
| 集合竞价快照 | 10-20s | 60s | 跳过竞价数据，使用昨日收盘价 |
| 评分引擎 | 30-90s | 300s (5min) | 使用上一日评分 |
| 报告生成 | 10-30s | 120s (2min) | 使用上一日报告模板 |
| 后评估 | 10-30s | 120s (2min) | 推迟到次日合并评估 |
| 数据归档 | 5-10s | 60s | 跳过，次日补归档 |
| 模拟交易 | 5-20s | 60s | 跳过，不做交易 |
| daily_workflow整体 | 60-180s | 600s (10min) | 标记FAILED |

### 6.2 超时实现方式

**PowerShell**：使用 `Wait-Process` + `Start-Job` 或 `[System.Diagnostics.Stopwatch]`

```powershell
$timeout = 300  # 5分钟
$stopwatch = [System.Diagnostics.Stopwatch]::StartNew()
$job = Start-Job -ScriptBlock { & $scriptPath @args }
$completed = Wait-Job $job -Timeout $timeout
if (-not $completed) {
    Stop-Job $job
    Write-Log "Task timed out after ${timeout}s" -Level "ERROR"
    throw "Timeout"
}
$result = Receive-Job $job
```

**Python**：使用 `subprocess.run(timeout=...)` 或 `signal.alarm`

### 6.3 超时监控链

```
daily_workflow.ps1
├── 自身超时监控：Windows Task Scheduler ExecutionTimeLimit = 2h
├── 阶段超时监控：每个Phase用 Stopwatch 计时
│   ├── Phase 1: build_dynamic_pool → 超时120s
│   ├── Phase 2: batch_data_collector → 超时300s
│   ├── Phase 3: scoring_engine_v2 → 超时300s
│   ├── Phase 4: gen_daily_html → 超时120s
│   ├── Phase 5: keystock_analysis → 超时180s
│   ├── Phase 6: archive_data → 超时60s
│   └── Phase 7: sim_trading → 超时60s
└── 总超时：Task Scheduler 2h硬限制
```

## 七、调度器配置参考

### 7.1 Windows Task Scheduler（当前方案）

已在 `setup_scheduler.ps1` 和 `register_tasks.ps1` 中定义：

| 任务名 | 时间 | 脚本 | 模式 |
|:-------|:----:|:-----|:----:|
| TieLv-Evaluation | 19:00 | daily_workflow.ps1 | -Mode eval |
| TieLv-DailyStock | 20:00 | daily_workflow.ps1 | -Mode daily_latest |
| TieLv-MonthlySummary | 09:00 (1号) | monthly_summary.ps1 | — |

### 7.2 调度器配置要求

- 执行策略：`-NoProfile -ExecutionPolicy Bypass`
- 权限级别：`HIGHEST`
- 执行时间限制：2小时（`-ExecutionTimeLimit (New-TimeSpan -Hours 2)`）
- 电池策略：允许电池运行、不因电池停止
- 用户登录：无需用户登录（LogonType S4U 或 Password）

### 7.3 调度器健康检查

每周一检查一次调度器状态：
```
schtasks /QUERY /TN "TieLv-*" /FO LIST
```
- 所有任务状态=Ready → OK
- 任一任务=Disabled → 告警
- 上次运行结果≠0 → 检查日志

## 八、与Pulse定时巡检的协调

Pulse的巡检时间表与Forge的任务编排需要精确对齐：

| 时间 | Forge任务 | Pulse巡检 | 协调点 |
|:-----|:---------|:---------|:------|
| 08:00 | — | 盘前全量巡检 | Forge等待Pulse的PASS信号 |
| 08:30 | 数据预热 | — | Pulse确认缓存状态OK后Forge开始预热 |
| 09:00 | 最终确认 | 二次确认 | 双方确认绿灯 → Forge触发评分 |
| 09:30-15:00 | 盘中监控 | 每30分钟轻量巡检 | Forge触发时先检查Pulse最近一次结果 |
| 15:00 | 收盘数据拉取 | 收盘后巡检 | Pulse确认收盘数据到齐后Forge触发收盘评分 |
| 17:00后 | 盘后流程 | 盘后缓存审计 | 互不阻塞 |
