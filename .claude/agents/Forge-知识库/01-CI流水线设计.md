## 一、项目当前的自动化触发点

铁律量化目前有四个级别的自动化触发点，从提交前到每日盘后全覆盖。

### 1.1 触发点总览

| 触发点 | 触发条件 | 执行时间 | 耗时 | 关键脚本 |
|:-------|:--------|:-------|:-----|:--------|
| pre-commit hook | git commit | 提交前 | 1-3s | `.claude/hooks/pre-commit-check.ps1` |
| 盘前巡检 | 手动/Pulse触发 | 08:00-09:00 | 30-120s | Pulse巡检框架 |
| 盘中轻量巡检 | 定时器（每30分钟） | 09:30-15:00 | 5-15s | 轻量API探测 |
| 盘后数据到齐检查 | 手动/定时 | 15:00-18:00 | 10-60s | 数据完整性检查 |

### 1.2 pre-commit hook 详细设计

当前pre-commit hook（`pre-commit-check.ps1`）执行4项检查：

```
pre-commit hook 执行流程
├── 入口：git commit 命令触发
│   └── 无staged文件 → 跳过，exit 0
├── Check A：版本一致性
│   ├── 遍历staged中的 .md/.ps1 文件
│   ├── 从文件名提取版本号（_vX.Y）
│   ├── 从文件内容提取内部版本声明
│   ├── 比对：文件名版本 vs 内部版本 → 不一致则ERROR
│   └── 无内部版本声明 → WARN
├── Check B：垃圾文件检测
│   ├── 匹配模式：^null$ / \.tmp$ / \.temp$ / ^~\$ / /data_cache/
│   └── 命中 → WARN
├── Check C：文档完整性
│   ├── 遍历staged中的 .md 文件
│   ├── 检查是否存在同名 .docx
│   ├── .md staged 但 .docx 未staged → WARN（提示同步）
│   └── 无 .docx 对应文件 → PASS（跳过）
├── Check D：Commit Message格式
│   ├── 读取 .git/COMMIT_EDITMSG
│   ├── 正则匹配：^(feat|fix|docs|chore|refactor|test):
│   ├── 匹配成功 → PASS
│   └── 不匹配/为空 → WARN
└── 汇总：任一ERROR → exit 1（阻塞提交）；仅WARN → exit 0（允许提交但警告）
```

### 1.3 盘前巡检触发机制

盘前巡检由Pulse（数据监理）负责触发，非交易日自动跳过：

```
盘前巡检流程（08:00-09:00）
├── 交易日检测 → 非交易日则 skip
├── API连通性检查（全部12个端点）
│   ├── 腾讯行情API [1]
│   ├── 新浪K线API [2]
│   ├── 东方财富财务API [3]
│   ├── 东方财富板块API [7]/[7b]
│   ├── 东方财富北向资金API [8]
│   ├── 东方财富资金流向API [9]/[10]
│   ├── 东方财富研报API [11]
│   ├── 东方财富融资融券API [12]
│   └── 同花顺THS备源API
├── 缓存新鲜度检查
│   ├── L1热缓存 TTL检查（≤5分钟）
│   ├── L2温缓存 TTL检查（≤1小时）
│   └── L3冷缓存 TTL检查（≤24小时）
├── 数据完整性验证
│   ├── 昨日收盘数据已入库
│   ├── 财务数据日期不早于上一报告期
│   └── K线数据覆盖最近20个交易日
└── 巡检报告输出 → 有P0/P1异常则告警，阻塞后续评分
```

## 二、CI流水线完整设计

### 2.1 流水线总图

```
代码提交 → 红线检查 → 评分验证 → 报告生成 → 结果对比 → 通过/驳回
 (git)     (pre-commit)  (smoke test)  (冒烟)     (diff)      (gate)
```

### 2.2 各阶段详细设计

#### Stage 0：代码提交（触发源）

| 属性 | 值 |
|:-----|:---|
| 触发方式 | git commit |
| 输入 | staged files + commit message |
| 前置条件 | 无（任意提交均可触发） |
| 超时 | N/A（等待用户操作） |
| 输出 | 提交进入流水线 |

#### Stage 1：红线检查

| 属性 | 值 |
|:-----|:---|
| 触发方式 | pre-commit hook 自动 |
| 执行脚本 | `pre-commit-check.ps1` + `check_redlines.ps1` + `version_supervisor.ps1` |
| 输入 | staged files 列表 |
| 检查项 | 版本一致性 / 垃圾文件 / .md↔.docx同步 / commit message格式 |
| 超时 | 5s（轻量级，不进网络） |
| 成功输出 | PASS → 进入Stage 2 |
| 失败处理 | ERROR → 阻塞提交，exit 1；WARN → 继续但记录 |

**失败降级策略**：
- 版本不一致 → 必须修复后才能提交（不可跳过）
- 垃圾文件 → 从staging移除后重新提交
- .docx未同步 → 运行对应 `build_docx.ps1` 生成后重新提交
- commit message格式 → 修改message后重新提交

#### Stage 2：评分验证（冒烟测试）

| 属性 | 值 |
|:-----|:---|
| 触发方式 | Stage 1 PASS 后自动（可选，后台异步） |
| 执行脚本 | `scoring_engine_v2.py`（仅1-2只股票） |
| 输入 | 选2只代表性股票（1只大盘蓝筹+1只中小盘） |
| 检查项 | 评分引擎可运行 / 输出JSON格式正确 / 评分范围合理(0-100) |
| 超时 | 30s |
| 成功输出 | PASS → 评分引擎健康 |
| 失败处理 | WARN → 不影响提交，但标记"评分引擎异常" |

**为什么不是ERROR**：评分引擎故障不应阻塞代码提交（代码改动可能和评分无关），但应记录以便盘前修复。

#### Stage 3：报告生成（冒烟测试）

| 属性 | 值 |
|:-----|:---|
| 触发方式 | Stage 2 PASS 后自动（可选） |
| 执行脚本 | `gen_daily_html.ps1`（仅生成简化版） |
| 输入 | Stage 2的评分结果 |
| 检查项 | HTML可生成 / 文件大小>0 / 核心元素存在 |
| 超时 | 15s |
| 成功输出 | PASS → 报告生成链完整 |
| 失败处理 | WARN → 标记"报告生成异常" |

#### Stage 4：结果对比（回归检测）

| 属性 | 值 |
|:-----|:---|
| 触发方式 | Stage 3 PASS 后自动 |
| 执行方式 | 对比本次评分输出与baseline（上次运行的金标准结果） |
| 检查项 | 评分偏差<5分 / 推荐股票列表重合度>70% / 无一票否决被绕过 |
| 超时 | 10s |
| 成功输出 | PASS / WARN + diff报告 |
| 失败处理 | 偏差>10分 → ERROR，需人工确认是否合理；5-10分 → WARN |

**baseline管理**：baseline存储在 `每日荐股/运营记录/ci_baseline.json`，每次通过完整CI后更新。

### 2.3 流水线状态定义

| 状态 | 符号 | 含义 | 后续动作 |
|:-----|:----:|:-----|:--------|
| PASS | ✅ | 正常通过 | 进入下一阶段 |
| WARN | ⚠️ | 通过但有关注项 | 继续执行但记录告警 |
| SKIP | ⏭️ | 条件不满足跳过 | 跳过，不影响后续 |
| FAIL | ❌ | 阶段失败 | 根据级别决定：阻塞/告警/跳过 |
| RETRY | 🔄 | 重试中 | 等待重试结果 |
| BLOCKED | 🚫 | 被前置依赖阻塞 | 等待上游恢复 |

### 2.4 失败告警和回退策略

#### 告警等级体系

| 等级 | 触发条件 | 告警方式 | 响应时间 |
|:----:|:--------|:--------|:--------|
| P0-致命 | pre-commit阻塞 + 数据全不可用 | 终端红色醒目 + 日志标记 | 立即 |
| P1-严重 | API主备全挂 / 评分引擎崩溃 | 终端黄色警告 + 日志 | 盘前必须修复 |
| P2-警告 | 单源不可用（备源工作） / 冒烟WARN | 日志记录 | 24小时内 |
| P3-注意 | 缓存接近过期 / 性能劣化 | 日志记录 | 本周内 |

#### 回退策略

```
流水线失败回退决策树
├── pre-commit FAIL
│   └── 阻塞提交 → 修复问题 → 重新提交
├── 评分冒烟 FAIL
│   ├── 代码改动涉及评分逻辑 → ERROR，要求修复
│   └── 代码改动不涉及评分 → WARN，标记待盘前修复
├── 报告生成 FAIL
│   ├── 模板改动 → ERROR，要求修复
│   └── 数据缺失 → WARN，可能是环境问题
├── 结果对比 FAIL（偏差>10分）
│   └── ERROR → 人工确认：如果是预期变化则更新baseline；如果是bug则回退
└── 盘前巡检 P0/P1
    └── 阻塞当日自动评分 → 通知人工接管 → 修复后手动触发
```

## 四、与Proof（质量工程师）的集成点

### 4.1 集成架构

```
Proof测试套件 ←→ CI流水线
     │                │
     ├── 单元测试 ────→ Stage 2.5（可选嵌入）
     ├── 集成测试 ────→ Stage 3.5（可选嵌入）
     ├── 回归测试 ────→ Stage 4（结果对比=轻量回归）
     └── 红线合规测试 → Stage 1（红线检查）
```

### 4.2 具体集成点

| CI阶段 | Proof测试类型 | 集成方式 | 触发条件 |
|:-------|:------------|:--------|:--------|
| Stage 1 红线检查 | 红线合规测试 | pre-commit hook已集成 | 每次commit |
| Stage 2 评分验证 | 评分引擎单元测试 | 可选：`pytest scoring_engine_v2_test.py` | 评分相关文件变更时 |
| Stage 3 报告生成 | 报告快照测试 | 可选：HTML结构验证 | 模板/样式变更时 |
| Stage 4 结果对比 | 回归测试（轻量） | 自动执行 | 每次CI |
| 独立 | 全量回归测试 | 手动触发：`run_regression.ps1` | 重大版本发布前 |

### 4.3 Proof反馈到CI的闭环

```
Proof发现问题
    ↓
分类：代码bug / 数据问题 / 逻辑缺陷
    ↓
代码bug → 修复 → CI重新验证 → Proof确认
数据问题 → 通知Pulse → 数据修复 → 回归验证
逻辑缺陷 → 通知Alpha → 策略调整 → 冒烟验证
```

## 六、与其他角色的协作

| 场景 | Forge | 其他角色 |
|:-----|:------|:--------|
| pre-commit扩展 | 设计新增检查项的位置和顺序 | Arch：确认检查项是否冗余；Proof：编写测试用例 |
| CI失败处理 | 设计降级/回退路径 | Dock：确认环境不是问题根因；Pulse：确认数据源正常 |
| 评分冒烟 | 设计冒烟用例选择策略 | Alpha：指定代表性股票；Proof：验证冒烟覆盖率 |
| 基线管理 | 设计baseline存储格式和更新策略 | Proof：确认baseline有效性；Alpha：确认评分变化合理性 |
| 告警 | 设计告警等级和路由 | Dock：配置通知渠道；Pulse：对接数据异常告警 |
