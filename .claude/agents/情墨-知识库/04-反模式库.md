## 一、反模式总览

以下7个反模式是铁律量化项目中已识别或需要警惕的架构问题。每个反模式包含：定义、识别方法、真实案例（如有）、危害等级、修复方案。

### 反模式严重程度分级

| 级别 | 标识 | 含义 | 修复时限 |
|:----:|:----:|:-----|:---------|
| **致命** | 🔴 | 导致数据错误、红线违规或系统不可用 | 必须立即修复 |
| **严重** | 🟠 | 显著增加维护成本，高概率导致bug | 当前迭代修复 |
| **中等** | 🟡 | 降低代码质量，增加理解和修改成本 | 排入下个迭代 |
| **轻微** | 🟢 | 不够优雅但不影响功能 | 顺手修，不专门排期 |

## 二、反模式清单

### 2.1 AP-01：循环依赖

**定义**：模块A引用模块B，模块B又引用模块A，形成依赖环。

**识别方法**：
- 两个文件互相 import/include
- 修改一个文件迫使同时修改另一个文件
- 无法独立测试任一模块

**在本项目中的表现**：
- PowerShell脚本A调用脚本B，脚本B又 dot-source 脚本A
- Python模块A import B，模块B又 from A import something
- 两个JSON配置文件互相引用对方的输出路径

**真实案例**：暂无已确认的循环依赖（项目通过文件松耦合有效规避），但需警惕以下场景：
- `scoring_engine_v2.py` 和 `trade_to_score_feedback.py` 之间：评分引擎输出→交易决策→反馈分析→评分参数调整→评分引擎。这形成了逻辑循环但非代码级循环依赖（通过文件异步传递，周期为T+1），属于**设计级别的闭环反馈**，不是反模式。

**危害等级**：🔴 致命
**危害说明**：代码级循环依赖导致模块无法独立测试、修改一处级联崩溃、初始化顺序问题。

**修复方案**：
1. **打破循环**：提取共享接口到第三个独立模块
2. **依赖倒置**：A和B都依赖抽象接口C，而非互相依赖
3. **合并模块**：如果A和B确实紧密耦合，合并为一个模块
4. **事件驱动**：A发布事件，B订阅事件（通过文件系统）

### 2.2 AP-02：上帝模块（God Module）

**定义**：一个脚本/模块承担了过多职责（数据获取+评分+报告+调度+监督），违反单一职责原则。

**识别方法**：
- 单个文件超过500行且功能不聚焦
- 文件头部的"功能说明"包含"和"字超过3个（如"获取数据并评分并生成报告并发送通知"）
- 修改一个功能时必须理解不相关的其他功能
- 函数的参数列表超过8个

**真实案例（已识别）**：

| 文件 | 嫌疑等级 | 分析 |
|:-----|:--------|:-----|
| `代码文件/每日荐股/分析逻辑/gen_doc_v2.ps1` | 🟡 中等 | 同时承担DOCX生成、数据读取、模板渲染、样式应用，约400行。建议：拆分为数据读取+模板渲染+样式应用三个函数至少（即使在同一文件内） |
| `daily_workflow.ps1` | 🟠 严重 | 编排所有模块，虽然是工作流编排器（允许），但需要警惕不要在其中嵌入具体业务逻辑 |
| `模拟交易/交易引擎/sim_trading.ps1` | 🟡 中等 | 买卖决策、仓位管理、冷却期管理、风控检查、记录日志多项职责。建议：拆分为决策引擎+仓位管理器+风控检查器 |

**危害等级**：🟠 严重
**危害说明**：修改任何功能都需理解全部代码，测试困难，复用不可能。

**修复方案**：
1. **按职责拆分**：一个文件对应一个核心职责
2. **提取函数**：大型脚本内部至少按功能块拆分为独立函数
3. **提取模块**：当一个"方面"超过200行时，考虑提取为独立文件
4. **编排器模式**：保留编排器（如daily_workflow.ps1），但确保它只协调调度，不包含具体业务逻辑

**修复优先级**：
1. `sim_trading.ps1` → 拆分内部函数（不改外部接口）
2. `gen_doc_v2.ps1` → 内部函数化
3. `daily_workflow.ps1` → 审计是否有业务逻辑内嵌

### 2.3 AP-03：硬编码路径

**定义**：文件路径以字符串形式直接写死在代码中，而非通过配置或相对路径。

**识别方法**：
- 代码中出现 `C:\Users\xxx\Documents\...` 这样的绝对路径
- 路径字符串不包含任何变量（如`$PSScriptRoot`、`os.path.dirname(__file__)`）
- 在同事的电脑上运行脚本会因路径不存在而失败

**真实案例（已识别）**：

```powershell
# ❌ 反模式：硬编码绝对路径
$dataPath = "C:\Users\34269\Documents\Claude\股票分析\代码文件\data_cache\"

# ✅ 正确：基于脚本位置的相对路径
$dataPath = Join-Path $PSScriptRoot "..\data_cache"
```

```python
# ❌ 反模式：硬编码绝对路径
DATA_DIR = "C:/Users/34269/Documents/Claude/股票分析/代码文件/data_cache/"

# ✅ 正确：基于文件位置的相对路径
import os
DATA_DIR = os.path.join(os.path.dirname(__file__), "..", "data_cache")
```

**危害等级**：🟠 严重
**危害说明**：
1. 项目目录迁移后所有硬编码路径失效
2. 不同用户/环境路径不同
3. 在Git中clone到不同位置后无法运行
4. GPT/AI在编辑代码时如果看到硬编码路径，会沿袭这个模式

**修复方案**：
1. **PowerShell**：统一使用 `$PSScriptRoot` 构建相对路径
2. **Python**：统一使用 `os.path.dirname(__file__)` 或 `pathlib.Path(__file__).parent`
3. **配置文件**：所有可变路径写入配置文件，代码仅读取配置
4. **入口约定**：所有脚本从项目根目录运行，路径统一为 `代码文件/xxx/`

**检查命令**：
```powershell
# 查找所有硬编码的绝对路径
Select-String -Path "**/*.ps1","**/*.py" -Pattern "C:\\Users" | Where {$_ -notmatch "CLAUDE\.md"}
```

### 2.4 AP-04：配置散落

**定义**：API Key、超时时间、路径配置、阈值参数分散在多个文件中，修改一处遗漏多处的风险。

**识别方法**：
- 同一个API endpoint出现在2个以上文件中
- 修改一个超时值需要在3个文件中找
- 因子权重同时出现在评分引擎和报告中

**真实案例（已识别）**：

| 配置项 | 散落位置 | 风险 |
|:-------|:---------|:-----|
| 东方财富API endpoint | `stock_data_fetcher.psm1` + `stock_data_fetcher_ths.py` | 改一个忘另一个 |
| 因子权重 | `scoring_engine_v2.py` + HTML报告模板 + DOCX报告模板 | 权重改了但报告仍显示旧权重 |
| 数据源超时设置 | 至少3个文件中独立定义 | 超时不一致导致行为异常 |
| 报告样式（品牌色） | 多个gen_*.ps1中独立定义 | 样式不一致（已被红线§6样式基线冻结规避） |

**危害等级**：🟠 严重
**危害说明**：修改配置容易遗漏，导致各模块行为不一致。调试时耗费大量时间排查"明明改了啊"的问题。

**修复方案**：
1. **集中配置**：创建 `config.json` 或 `config.psd1`，所有模块从中读取
2. **单一来源**：每个配置项只在一个地方定义
3. **配置验证**：version_supervisor.ps1 扩展为检查配置一致性
4. **立即行动**：
   - 将API endpoints 集中到一个 `api_config.json`
   - 将因子权重集中到 `factor_config.json`
   - 将超时/重试参数集中到 `timeout_config.json`

**渐进式迁移策略**：
- 阶段1：新建 `代码文件/配置/api_endpoints.json`，先写后读
- 阶段2：逐模块迁移，从数据层开始（影响最广）
- 阶段3：废弃旧的内嵌配置，统一从配置文件读取

### 2.5 AP-05：静默失败

**定义**：脚本出错但没有退出码、没有日志、没有异常传播，调用方无法感知失败。

**识别方法**：
- `try { ... } catch { }` 空catch块
- PowerShell脚本没有 `$ErrorActionPreference = "Stop"`
- Python函数返回 `None` 而不抛出异常
- 脚本执行后 `$LASTEXITCODE` 为0但实际数据未更新
- 没有日志输出的脚本

**真实案例（已识别）**：

```powershell
# ❌ 反模式：静默失败
try {
    $data = Invoke-RestMethod -Uri $url
} catch {
    # 什么都不做，$data保持为null
}
# 后续代码使用$data可能出错，但不知道根本原因是API调用失败

# ✅ 正确：明确错误处理
try {
    $data = Invoke-RestMethod -Uri $url -TimeoutSec 30
} catch {
    Write-Error "API调用失败: $_"
    # 按1+2架构降级到备源
    return $false  # 或 throw
}
```

```python
# ❌ 反模式：静默返回None
def load_cache(filepath):
    try:
        with open(filepath) as f:
            return json.load(f)
    except:
        return None  # 调用方不知道失败原因

# ✅ 正确：明确异常或使用Result类型
def load_cache(filepath):
    try:
        with open(filepath) as f:
            return json.load(f)
    except FileNotFoundError:
        raise CacheNotFoundError(f"缓存文件不存在: {filepath}")
    except json.JSONDecodeError as e:
        raise CacheCorruptError(f"缓存文件格式错误: {filepath}, {e}")
```

**危害等级**：🔴 致命
**危害说明**：
1. 数据获取失败但报告照常生成（可能用旧数据或空数据）
2. 模拟交易实际未执行但无感知
3. 评分引擎静默失败→报告显示0分→用户误判
4. 错误积累，排查时已错过最佳时机

**修复方案**：
1. **PowerShell脚本头部必须包含**：
   ```powershell
   $ErrorActionPreference = "Stop"
   # 或至少在脚本开头声明
   ```
2. **所有API调用必须有超时和错误处理**
3. **每个关键步骤输出状态日志**（到文件，不污染stdout）
4. **支持 `-Verbose` 和 `-Debug` 参数**
5. **定义统一的退出码约定**：
   - 0 = 成功
   - 1 = 数据源不可用（已降级到备源）
   - 2 = 数据全部不可用（仅缓存可用）
   - 3 = 致命错误（无数据可用，停止下游）

### 2.6 AP-06：跨层直接调用

**定义**：高层模块跳过中间层的接口，直接调用底层模块的内部实现。

**识别方法**：
- 展示层脚本直接调用数据层的API而不是通过缓存
- 报告生成脚本直接 import 数据获取模块
- 调度脚本修改底层模块的内部状态变量

**真实案例（已识别）**：

| 跨层调用 | 描述 | 是否应修复 |
|:---------|:-----|:----------|
| `gen_daily_html.ps1` 可能直接调用 `stock_data_fetcher.psm1` 的函数（而非读缓存） | 如果存在，展示层绕过了计算层 | 需要审计 |
| 多个脚本直接读写同一缓存文件但没有约定谁负责写入 | 写入权散乱 | 需要明确 |
| 临时回溯脚本直接操作数据层缓存（合理，因为是回溯） | 专用场景 | 不需要 |

**危害等级**：🟡 中等
**危害说明**：破坏模块边界，修改内部实现需要同时改多处。调用方无意中依赖了不应依赖的实现细节。

**修复方案**：
1. **明确中间层接口**（已在02-接口契约设计中定义）
2. **代码审查时重点检查**：是否绕过已有接口
3. **在模块头部注释中声明public API**：
   ```powershell
   # PUBLIC FUNCTIONS: Get-StockQuote, Get-KLineData
   # INTERNAL ONLY: _ParseResponse, _BuildUrl
   ```

### 2.7 AP-07：重复代码 > 3处

**定义**：同样或高度相似的代码块在3个及以上位置出现。

**识别方法**：
- 复制粘贴后只改了少量参数
- 修改一个逻辑需要同步修改多个文件
- 函数签名几乎相同但散落在不同文件中

**真实案例（已识别）**：

| 重复内容 | 出现位置 | 建议 |
|:---------|:---------|:-----|
| `md_to_docx.py` | `代码文件/tools/` + `代码文件/每日荐股/分析逻辑/` + `代码文件/每日荐股/事后评估/` 等至少5个目录有副本 | **严重**：应该统一引用一处 |
| build_docx.ps1 | 多个业务目录各自一份 | **严重**：应该只保留一份通用版 + 各目录用参数调用 |
| 编码处理逻辑（GBK→UTF-8） | 多个PS脚本中独立实现 | 提取为通用函数 |
| 报告样式定义 | 多个gen_*.ps1中重复 | 已被红线§6样式基线冻结 |
| 日期格式化/市场状态判断 | 多文件中独立实现 | 提取到通用工具模块 |

**危害等级**：🟠 严重
**危害说明**：
1. 修改一个bug需要到N处同步修复
2. 各副本逐渐产生差异，行为不一致
3. 新人不知道哪个是"正宗"版本

**修复方案**：
1. **提取公共模块**：创建 `代码文件/模块/` 目录存放共享代码
2. **统一入口**：`md_to_docx.py` 只保留 `代码文件/tools/` 下的一份，其他目录用相对路径引用
3. **通用函数库**：提取日期处理、编码处理、配置读取等通用函数

**新工具提议**：
```powershell
# 创建 代码文件/模块/common_utils.ps1 (PowerShell通用函数)
# 创建 代码文件/模块/common_utils.py (Python通用函数)
```

### 2.8 AP-08：校验降级（Verification Downgrading）

**定义**：数据完整性校验结果只写WARN日志，不阻止引擎继续运行。导致引擎在数据层已损坏的情况下继续产出"看起来正常"的结果。

**识别方法**：
- 数据加载返回空结果 → 仅 `log(WARN)`，不 `sys.exit(1)`
- 格式不兼容导致匹配数为0 → 继续运行（使用默认值或空值）
- 必需字段缺失 → 使用默认值替代，无 FATAL 级日志
- 数据覆盖率不足（如预期50只仅匹配到2只）→ 仅警告

**在本项目中的表现**：
- 评估数据格式不兼容→返回空列表→10条WARN→引擎继续运行
- sim_trading 读到空评估数据→回退到昨日收盘价→产生看似正常的交易记录

**危害等级**：🔴 致命
**危害说明**：
1. 数据层已损坏但引擎继续产出结果——比直接报错退出更危险
2. 静默降级到旧数据跑一整天，产生不可靠的交易记录
3. 排查时已错过最佳时机，错误可能已扩散到下游

**修复方案**：
```python
# ✅ 正确：数据加载层加硬闸门
matched = len(stocks_eval)
if matched == 0:
    log("FATAL: 评估数据格式不兼容或为空，引擎终止", "FATAL")
    sys.exit(1)
elif matched < len(CODE_MAP) * 0.5:
    log(f"FATAL: 评估数据覆盖率过低({matched}/{len(CODE_MAP)})，可能格式变更", "FATAL")
    sys.exit(1)
```

**与AP-05的区别**：AP-05是"出错但无日志/无异常"，AP-08是"有WARN但故意不阻塞"。AP-08更隐蔽——它看起来像做了错误处理，实际上是在纵容数据损坏。

## 三、反模式检测清单

在进行代码审查或架构审查时，按此清单逐项检查：

### 日常自查（每次提交前）

- [ ] 是否有循环依赖？（AP-01）
  - 检查：import/include/dot-source是否形成环
- [ ] 新增文件是否超过500行且职责混杂？（AP-02）
  - 检查：文件描述中"和"字超过3个
- [ ] 是否使用了绝对路径？（AP-03）
  - 检查：`C:\Users\` 或 `/home/` 出现在代码中
- [ ] 是否有空catch块或 `return None`？（AP-05）
  - 检查：`catch {}` 或 `except: return None`
- [ ] 是否有数据校验只WARN不阻塞？（AP-08）
  - 检查：数据加载失败后是否仍继续执行？WARN后是否有exit？

### 架构审计（每迭代）

- [ ] 同一配置值是否在3+文件中重复？（AP-04）
  - 检查：用grep搜索关键配置值（API endpoint、超时时间、权重等）
- [ ] 是否存在跨层直接调用？（AP-06）
  - 检查：展示层是否直接调用数据层API
- [ ] 是否有相同代码块在3+位置出现？（AP-07）
  - 检查：`md_to_docx.py`、`build_docx.ps1` 的副本数量

## 五、反模式预防机制

### 5.1 代码审查聚焦点

审查代码时，优先关注以下信号：
1. 函数体超过50行 → 检查是否违反单一职责
2. 参数超过5个 → 检查是否需要重构为对象传递
3. import/include超过5个 → 检查是否依赖过多
4. 文件超过300行 → 检查是否可以拆分
5. 有4+个函数不在头部声明 → 检查函数管理是否混乱

### 5.2 Pre-commit Hook增强建议

在现有 `pre-commit-check.ps1` 中增加：
- 检查绝对路径（AP-03）
- 检查空catch块（AP-05）
- 检查`$ErrorActionPreference`声明（AP-05）
- 检查重复`md_to_docx.py`文件（AP-07）
