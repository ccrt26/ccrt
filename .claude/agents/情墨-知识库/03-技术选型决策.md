## 一、当前技术栈决策记录（ADR）

### 1.1 ADR-001：PowerShell作为数据获取主语言

| 属性 | 值 |
|:-----|:---|
| **决策编号** | ADR-001 |
| **决策日期** | 2026-05（项目启动） |
| **状态** | ✅ 已接受，运行中 |
| **背景** | 需要从腾讯/新浪/东方财富API获取A股数据，数据获取脚本需与Windows环境深度集成 |
| **决策** | 使用PowerShell 5.1编写数据获取模块（.psm1），利用Invoke-WebRequest/Invoke-RestMethod的Windows原生TLS支持 |
| **备选方案** | Python (requests库) |
| **选择原因** | 1) Windows原生，无额外运行时依赖 2) PowerShell字符串处理和JSON转换原生支持 3) 与Windows Task Scheduler深度集成 4) 编码处理（GBK/UTF-8）对A股数据源兼容好 |
| **代价/风险** | 1) Linux/macOS不可运行（已知限制） 2) PS 5.1不支持现代语法特性 3) 错误处理不如Python try/except直观 |
| **复审周期** | 每6个月 |

## 三、不应引入的技术清单

### 3.1 黑名单（绝不应引入）

| 技术 | 原因 | 严重程度 |
|:-----|:-----|:--------|
| Docker/LXC容器 | Windows环境不支持原生Docker，WSL2过于复杂，与项目约束冲突 | ⛔ 硬性 |
| Kubernetes (k8s) | 单机项目，无分布式需求，引入k8s是严重的过度工程 | ⛔ 硬性 |
| MongoDB | 项目数据规模（单日<10MB）不需要NoSQL，JSON文件足够 | ⛔ 硬性 |
| Redis | 单进程运行，不需要进程间共享缓存，文件系统足够 | ⛔ 硬性 |
| Kafka/RabbitMQ | 无消息队列需求，模块间文件传递已经是最佳方案 | ⛔ 硬性 |
| GraphQL | 无API对外暴露需求（MCP Server用标准HTTP），增加无谓复杂度 | ⛔ 硬性 |
| TypeScript | 项目中无JavaScript需求，引入TS运行环境是额外负担 | ⛔ 硬性 |
| React/Vue/Angular | 无Web前端，HTML报告是静态生成 | ⛔ 硬性 |
| Rust/Go | 项目无性能瓶颈需要重写底层，引入会大幅提升维护成本 | ⛔ 硬性 |

## 五、第三方库引入评审流程

### 5.1 评审流程图

```
提出需求 → 技术选型评估 → 备选方案对比 → 情墨评审 → 用户审批 → 红枫集成
   │            │               │              │           │           │
   │      填写评估矩阵     至少2个备选     输出ADR    阿黑决策    pip/环境配置
   │      （见§2.2）       方案对比                      ← 最终 ←
   └─────────────────────────────────────────────────────────────┘
```

### 5.2 评审检查清单

**引入新第三方库前，逐项确认：**

- [ ] **必要性**：现有技术栈能否满足？不引入新技术能否实现？
- [ ] **许可证**：许可证是否与项目兼容？（优先MIT/Apache/BSD）
- [ ] **安全**：是否有已知CVE？是否依赖了过量的传递依赖？
- [ ] **维护状态**：最近6个月有提交？不是放弃的项目？
- [ ] **兼容性**：支持Python 3.9+？Windows兼容？
- [ ] **体积**：包大小是否合理？（<50MB）
- [ ] **替代方案**：是否评估了至少2个替代方案？
- [ ] **项目约束**：是否与Windows环境、DeepSeek代理兼容？
- [ ] **团队负担**：红枫是否确认可以安装和维护？
- [ ] **锁定版本**：生产环境必须锁定版本（禁止`>=`）

### 5.3 紧急引入简化流程

在以下情况下可跳过完整评审：
- 纯工具类库（如`json`、`csv`替代实现）且体积<1MB
- 修复已知安全漏洞的补丁版本升级

简化流程：情墨快速评估 → 用户1句话确认 → 引入

### 5.4 依赖版本管理规范（`requirements.txt`约定）

```txt
# === 核心依赖（锁定版本） ===
numpy==1.24.3
pandas==2.0.3

# === 工具依赖（锁定版本） ===
python-docx==0.8.11
openpyxl==3.1.2

# === 备源依赖（锁定版本） ===
akshare==1.12.0

# === 可选依赖（锁定版本） ===
# scipy==1.10.1  # 仅在评分引擎中使用
```

**规则**：
1. 所有依赖必须锁定大版本+小版本（`==X.Y.Z`），禁止使用`>=`或`~=`
2. `requirements.txt` 按用途分组注释
3. 删除不再使用的依赖时，同步更新注释
4. 红枫负责维护虚拟环境和`requirements.txt`

## 六、关键决策规则

### 6.1 什么时候应该引入新技术？

1. 现有技术在**性能上成为瓶颈**（如评分从2分钟→10分钟且无法通过算法优化）
2. 现有技术在**功能上无法实现**（如需要交互式图表但matplotlib不支持）
3. 现有技术在**维护上成为负担**（如Python库已被废弃无替代）
4. 新的业务需求需要**根本性的新能力**（如实时推送→需要WebSocket支持）

### 6.2 什么时候不应该引入新技术？

1. "这个技术很火" — 不是理由
2. "这样写更优雅" — 在混合架构项目中，一致性 > 优雅
3. "以后可能会用到" — YAGNI原则（You Aren't Gonna Need It）
4. "重构顺便换技术栈" — 重构和技术栈替换是两件事，分开做
5. 评价矩阵综合评分 < 3.0 — 不引入

### 6.3 技术决策的"先问5个问题"

1. 不引入新技术能不能解决？
2. 引入后的维护成本谁承担？
3. 现有模块需要多少改动来适配？
4. 如果这个技术3年后停止维护怎么办？
5. 团队（AI+人）能在30分钟内理解这个技术吗？
