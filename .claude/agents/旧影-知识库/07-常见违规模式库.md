> 版本 v1.0 | 生效日期 2026-05-24

> 关联：`.claude/knowledge/常见错误.md`（操作层面错误，本库为审计层面违规模式）

## 一、违规模式分类

| 类别 | 代码 | 说明 |
|:-----|:----:|:-----|
| 红线违规 | RED | 违反规则红线明确条款 |
| 架构违规 | ARC | 违反模块依赖/接口契约/代码分级 |
| 流程违规 | PRC | 跳过管线环节/未经闸门放行 |
| 角色越界 | BND | 违反角色边界宪章C/X边界 |
| 数据违规 | DAT | 违反1+2架构/数据真实性铁律 |
| 文档违规 | DOC | 违反文档同步红线/CHANGELOG规范 |

## 二、常见违规模式

### RED-001：PE(TTM)未自行计算
```
模式：直接使用腾讯API返回的静态PE做否决
红线：红线§1.2
正确做法：PE(TTM) = 当前价[1] / TTM_EPS[3]
检查方法：搜索代码中是否直接用接口PE字段做判断
```

### RED-002：缺少数据来源标注
```
模式：报告/分析中引用数据但未标注来源编号[1]~[12]
红线：红线§4
正确做法：所有数据标注来源，如"当前价[1] 10.50元"
检查方法：检查报告输出中数字是否有[编号]标注
```

### RED-003：删除PDF文件
```
模式：AI或脚本删除项目中生成的PDF文件
红线：红线§1.7
正确做法：PDF文件只增不删，旧版本保留
检查方法：Git历史中是否有PDF删除记录
```

### RED-004：编造/推测数据
```
模式：输出不可获取的指标具体数值
红线：红线§1.3
正确做法：不可获取→"数据不可获取"或"N/A"
检查方法：检查输出中如"筹码分布"/"社交情绪"等是否有具体数值
```

### RED-005：API调用间隔<0.3s
```
模式：脚本中API请求间隔不足300ms
红线：红线§1
正确做法：Start-Sleep -Milliseconds 300 (PowerShell) 或 time.sleep(0.3) (Python)
检查方法：搜索脚本中的sleep/delay设置值
```

### RED-006：双源数据未实际尝试备源
```
模式：行情/K线数据只调了主源，未尝试备源
红线：红线§1.2
正确做法：主源失败→实际调用备源→缓存兜底
检查方法：检查API调用的try/except中是否有备源调用
```

### RED-007：报告缺少免责声明
```
模式：生成的报告不含免责声明
红线：红线§4
正确做法：每份报告开头含"仅供参考，不构成投资建议"
检查方法：检查报告模板/生成脚本中是否有免责声明行
```

### ARC-001：单文件超过500行
```
模式：代码文件超过500行未经情墨评审
规范：轻量化规范§9.2
正确做法：拆分或申报情墨拆分评审
检查方法：wc -l *.ps1 *.py | sort -rn
```

### ARC-002：跨层直接调用
```
模式：上层模块跳过中间层直接调更下层(如L5→L2)
规范：模块依赖关系图(情墨-知识库/10)
正确做法：经过中间层中转
检查方法：检查import/调用链是否跳过中间层
```

### ARC-003：接口契约未声明变更
```
模式：修改了模块间数据格式但未通知下游
规范：接口契约设计(情墨-知识库/02)
正确做法：变更前通知情墨→情墨评估→通知所有下游消费者
检查方法：对比commit前后的接口字段定义
```

### ARC-004：L2模块无流金复核记录
```
模式：L2风控模块变更后未经过流金逐条红线复核
规范：代码分级审核制度(情墨-知识库/08)
正确做法：L2变更→流金逐条复核红线→记录留档
检查方法：检查L2模块变更commit是否有关联的流金复核记录
```

### PRC-001：跳过情墨设计直接编码
```
模式：无情墨设计文档就开始写代码
规范：管线§7.3 环节①→③
正确做法：腰子提需求→情墨出设计→闸门1→红结编码
检查方法：检查新功能是否有对应情墨设计文档
```

### PRC-002：跳过闸门直接上线
```
模式：未经新安验证/红枫灰度直接部署
规范：管线§7.4 闸门2+3
正确做法：闸门2 PASS→闸门3 PASS→灰度→全量
检查方法：检查发布记录的闸门状态
```

### PRC-003：未经腰子确认的金融逻辑落地
```
模式：红结自行调整评分公式/否决阈值/因子权重
规范：管线§7.3 金融确认
正确做法：任何金融参数变更→腰子确认→情墨更新设计→红结实现
检查方法：检查参数变更commit是否有腰子确认记录
```

---

### BND-001：金融角色写代码
```
模式：腰子/山猫/玉夜/流金/青山执行了代码编写
规范：角色边界宪章 金融线 C/X
正确做法：金融角色→阿黑→红结
检查方法：检查是否有金融角色产出的代码文件
```

### BND-002：工程角色做金融判断
```
模式：情墨/红结/新安等做策略/评分/风控决策
规范：角色边界宪章 工程线 C/X
正确做法：工程角色→阿黑→腰子
检查方法：检查工程角色输出中是否有金融决策内容
```

### BND-003：旧影动手修代码
```
模式：旧影在审计发现FAIL后自己动手修复
规范：角色边界宪章 旧影: 只审计不执行
正确做法：旧影→修复指令→红结执行→新安验证
检查方法：检查旧影产生的commit是否包含代码修改
```

---

### DAT-001：财务数据高频拉取
```
模式：每日拉取[3]东财财务数据
规范：红线§1 财务数据每7天拉取1次
正确做法：每7天刷新，财报季(3-4月/8-10月)可缩短至3天
检查方法：检查数据采集脚本中财务API的调用频率
```

### DAT-002：缓存过期未标注
```
模式：使用缓存数据但未标注[C]和过期时间
规范：数据字典§六
正确做法：缓存数据必须标注[C]和过期时间
检查方法：检查报告/分析中数据来源标注
```

### DAT-003：独有数据未标注"仅供参考"
```
模式：[8]北向/[9]资金流等独有数据未标注
规范：红线§4
正确做法：无备源的数据标注"仅供参考"
检查方法：检查使用[8][9][10][11][12]数据的地方是否有免责标注
```

### DOC-001：.md修改后未同步.docx
```
模式：修改了.md文件但未重新生成.docx
规范：红线§5.4
正确做法：python md_to_docx.py input.md output.docx
检查方法：检查.md和.docx的最后修改时间差
```

### DOC-002：CHANGELOG虚假陈述
```
模式：CHANGELOG写"已修复"但实际未修复
规范：红线§1.6
正确做法：CHANGELOG只记已完成改动，"已修复"带文件路径+行号
检查方法：逐条核对CHANGELOG中的修复声明与实际代码
```

### DOC-003：版本号不一致
```
模式：文件名版本≠文档内部声明版本≠CHANGELOG版本
规范：红线§5.4
正确做法：提交前运行version_supervisor.ps1 -CrossCheck
检查方法：version_supervisor.ps1 -CrossCheck
```

## 三、审计时优先检查

旧影在每次审计时，用以下优先级扫描：

1. **先查RED类**（红线违规→最高优先级）
2. **再查ARC+PRC类**（架构+流程违规）
3. **再查DAT+DOC类**（数据+文档合规）
4. **最后查BND类**（角色越界→需对话日志回溯）

## 四、违规模式更新

- 新违规模式发现→登记本库+标注类别代码
- 同一违规模式月内≥3次→升级为P0审计事件
- 每季度汇总TOP违规模式→提出预防方案
- 与 `常见错误.md` 联动：本库中的违规模式若可追溯到操作层面错误→同步更新常见错误案例库
