## 一、阶段命名规则

### 1.1 阶段前缀

| 前缀 | 含义 | 示例 |
|:-----|:-----|:------|
| **第-X** | 启动和审计阶段（X=负数或0） | 第-1（目录治理审计）、第0（地基审计） |
| **P0-X** | 最小强制地基闸门包，只检测不修复 | P0-A（baseline权威闸门） |
| **第X** | 正式重构阶段，逐步接入流程并固化 | 第1（baseline权威体系接入） |

### 1.2 双轨关系

P0 包与正式阶段存在一一对应关系，但不是同一个阶段：

```
P0-A (检测) → 第1阶段 (检测+接入+修复+固化)
P0-B (检测) → 第2阶段 (检测+接入+修复+固化)
P0-C (检测) → 第3阶段 (检测+接入+修复+固化)
P0-D (检测) → 第4阶段 (检测+接入+修复+固化)
```

P0 包先行建立**检测能力**，正式阶段在检测能力基础上进一步**接入流程、修复发现问题、固化到报告生成链路**。

### 1.3 执行顺序要求

1. 第-1 → 第-1.5 → 第0 → 第0.5（启动审计序列）
2. P0-A → P0-B → P0-C → P0-D（强制地基闸门包序列）
3. 第1 → 第2 → 第3 → 第4（一一对应接入序列）
4. 第5 → 第6（canonical报告迁移序列）
5. 第7 → 第8 → 第9（统一解读+后评估+知识进化序列）
6. 第10（最终验收）

## 三、P0包与正式阶段的关系

### 3.1 核心区别

| 维度 | P0包（检测闸门） | 正式阶段（重构接入） |
|:-----|:----------------|:-------------------|
| 目标 | 发现问题，拦截错误产出 | 修复问题，固化到流程 |
| 新增文件 | 只新增脚本+配置+验收记录 | 可修改报告生成器和流程配置 |
| 修改旧报告 | ❌ 严禁 | ❌ 仍不修改历史报告 |
| 修改报告生成逻辑 | ❌ 严禁 | ✅ 允许（第6阶段） |
| 修改流程定义 | ❌ 严禁 | ✅ 允许（第10阶段） |
| 停止条件 | P0完成+验收通过 | 修复+固化+验收通过 |
| 输出 | 问题列表+闸门脚本 | 闸门接入流程+修复数据 |

### 3.2 映射关系

```
P0-A（检测 baseline_id 不一致）→ 第1阶段（修复 baseline_id + 固化到日报生成）
P0-B（检测 数值不一致/板块相位）→ 第2阶段（修复数值源 + 固化）
P0-C（检测 日期新鲜度/降级路径）→ 第3阶段（修复日期标注 + 固化）
P0-D（检测 MD/sidecar 不一致）   → 第4阶段（修复生成逻辑 + 固化）
```

### 3.3 为什么不能合并

1. **P0包是防御性的**——先立"不做什么"的边界，后面"要做什么"才有安全区
2. **拆开检测和修复**——检测阶段不改文件，风险最低；修复阶段涉及改动，需单独验收
3. **P0包产出是正式阶段的输入**——P0-B发现的N-01（600114板块相位错误）是第2阶段的具体修复目标
