## 1. 前置检查结论

知识库进化重构不得做成“大一统重构”。本轮执行只做最小闭环：

1. 建立 `07_知识进化` 的总账和候选 schema。
2. 建立第一个场景适配器：深度周报。
3. 建立反例库和参数库的索引骨架。
4. 定义东睦后评估必须如何产出 `KnowledgeUpdateCandidate`。

本轮不改生产入口，不改报告生成脚本，不改 `.claude/agents/*-知识库/` 核心规则，不自动入库。

## 7. 字段设计

`KnowledgeUpdateCandidate` 必须至少包含：

| 字段 | 说明 |
|:-----|:-----|
| candidate_id | 全局唯一 ID |
| source_type | weekly_report / daily_report / stock_pick / sim_trade / eval |
| source_ref | 来源报告、baseline、EvalHook 或后评估路径 |
| scenario | 周报、日报、荐股、模拟交易、后评估 |
| owner_role | 首要确认角色 |
| related_roles | 联审角色 |
| attribution_type | 数据、参数、权重、证据等级、分析逻辑、展示、执行、策略环境变化 |
| observed_failure | 后评估观察到的问题 |
| proposed_update | 建议更新内容 |
| target_layer | core / adapter / evolution / counterexample / parameter |
| evidence_refs | 证据引用 |
| risk_if_applied | 采纳风险 |
| risk_if_ignored | 忽略风险 |
| decision_status | proposed / role_review / approved / rejected / parked / superseded |

## 8. 执行顺序

### STEP 0：阿黑路由

阿黑确认：

1. 本阶段按 F-KNOW 主流程执行。
2. 只做文档骨架和契约，不改生产。
3. 拆成 G3-1、G3-2、G3-3 三个小包。

### STEP 1：G1/G2 角色确认

金融团队确认上游 G1/G2 方案中的五层结构：

1. 角色核心知识库。
2. 场景适配器。
3. 后评估进化库。
4. 反例库。
5. 参数库。

未确认前不得进入 G3。

### STEP 2：G3-1 先建总账与 schema

先做总账和候选 schema，完成后暂停自检。

通过条件：

1. 五层目录关系清楚。
2. Candidate 字段完整。
3. 状态机明确。
4. 禁止自动入库写清楚。

### STEP 3：G3-2 再建深度周报适配器

只建深度周报，不同时扩展日报、荐股、模拟交易。

通过条件：

1. A/B/C 三层对应角色知识。
2. 周报如何生成后评估问题写清楚。
3. 周报如何引用候选状态写清楚。

### STEP 4：G3-3 建反例库、参数库、东睦样例要求

最后补反例库、参数库和东睦样例要求。

通过条件：

1. 反例库能防止单次失败硬改规则。
2. 参数库能区分修参数和修逻辑。
3. 东睦后评估必须产出知识候选，而不是只写对错。

### STEP 5：G4 自检

执行模型提交自检报告，至少包括：

1. 新增文件清单。
2. 未修改禁止范围证明。
3. 验收命令输出摘要。
4. 未代签角色证明。
5. 遗留 WARN。

### STEP 6：G5 旧影复查

旧影复查：

1. 文件范围是否合规。
2. 是否跳过角色确认。
3. 是否把单次报告结论写成规则。
4. 是否存在 formal pipeline PASS 伪称。
5. 是否触碰生产入口。

### STEP 7：Codex 复查

用户把执行产物交给 Codex 后，Codex 按 review 姿态复查：

1. 先给 BLOCK/WARN/PASS。
2. 逐文件列出问题和行号。
3. 检查 schema 字段是否能支撑后评估闭环。
4. 检查东睦样例是否真的产出候选，而不是写成报告补丁。
5. 检查是否可以进入下一步日报/荐股/模拟交易适配器。
