## 1. 前置检查结论

本轮要解决的问题不是“东睦股份这份报告还缺哪条规则”，而是：

> 金融团队的每次分析、日报执行、后评估、错误归因和参数修正，应该如何变成角色知识库的可治理进化素材。

结论如下：

1. 不建立“每个分析逻辑一个知识库补丁”的模式。
2. 不把单次报告结论直接写入角色核心知识库。
3. 不让周报、日报、荐股、模拟交易各自临时背一套规则。
4. 建立“角色核心知识库 + 场景适配器 + 后评估进化库 + 反例库 + 参数库”的五层结构。
5. 后评估只产出知识更新候选，不直接修改规则资产或角色知识库。
6. 角色知识更新必须区分：自动建议、角色确认、腰子终审、旧影审计。
7. 东睦股份本轮周报重构作为首个强制样例，后评估时必须产出知识更新候选。

一句话原则：

> 周报定逻辑，日报验状态，后评估做归因，知识库只吸收经过确认的可复用经验。

## 6. 五层知识库结构

### 6.1 总体分层

| 层级 | 名称 | 回答的问题 | 稳定性 | 典型落点 |
|:-----|:-----|:-----------|:-------|:---------|
| L-K1 | 角色核心知识库 | 这个角色本来应该懂什么 | 高 | `.claude/agents/*-知识库/` |
| L-K2 | 场景适配器 | 角色知识在周报、日报、荐股、模拟交易中怎么输出 | 中 | `00_项目地基/07_知识进化/scenario_adapters/` |
| L-K3 | 后评估进化库 | 这次判断错了，应该生成什么更新候选 | 中 | `00_项目地基/07_知识进化/evolution_candidates/` |
| L-K4 | 反例库 | 哪些失败样本证明规则不能泛化 | 中高 | `00_项目地基/07_知识进化/counterexamples/` |
| L-K5 | 参数库 | 哪些阈值、窗口、权重需要版本化校准 | 中 | `00_项目地基/07_知识进化/parameters/` |

### 6.2 核心原则

| 原则 | 说明 |
|:-----|:-----|
| 稳定层不频繁改 | 东睦、周报、日报的单次变化不得直接冲击角色核心知识库 |
| 应用层可多场景适配 | 同一角色知识可以在周报、日报、荐股、模拟交易中有不同输出格式 |
| 学习层先收候选 | 后评估只能生成候选，不能直接写入核心规则 |
| 反例优先于硬改规则 | 单次失败先进入反例库；多次重复、跨样本成立，才考虑改规则 |
| 参数优先于逻辑重写 | 若问题是阈值过紧/过松，先修参数，不重写分析逻辑 |

## 7. 角色核心知识库：稳定层

角色核心知识库回答“这个角色本来应该懂什么”。这层只吸收跨场景、跨标的、可复用、经过确认的知识。

| 角色 | 核心知识范围 | 可自动建议更新 | 必须人工确认 |
|:-----|:-------------|:---------------|:-------------|
| 玉夜 | 数据质量、字段口径、数据可用等级、TTL、新鲜度、缺失处理 | 字段可信等级候选、数据源故障模式、moneyflow/财务字段口径疑点 | 数据可用等级变更、字段权威源变更、TTL 红线变更 |
| 青山 | 信号有效性、因子胜率、样本约束、策略退化、后评估方法 | 信号胜率候选、低样本标记、因子失效疑点、策略环境归因候选 | 信号升降权、样本门槛、因子有效性规则 |
| 流金 | 风险边界、否决项、回撤、动作审计、风控表达 | 风险触发滞后样本、动作表达过激样本、否决/恢复异常样本 | 否决项新增/删除、动作红线、仓位边界 |
| 信鸽 | 事件分级、公告证据、催化窗口、事件标签 | 催化兑现/落空样本、公告证据等级疑点、事件窗口偏差 | 事件等级规则、P0/P1/P2 标准、公告证据采信规则 |
| 山猫 | 宏观覆写、行业相位、市场环境、风格切换 | M 层触发候选、行业相位错配样本、宏观覆写有效性统计 | M 层覆写阈值、批量暂停/降级条件 |
| 腰子 | 整合裁决、状态机、结论强度、用户摘要边界 | 结论强度偏差、状态切换误判、摘要返工模式 | 状态机规则、结论强度口径、正式金融规则入库 |

### 7.1 核心知识入库门槛

满足以下任一条件，才允许从候选进入核心知识库评审：

1. 同类问题连续出现 3 次及以上，且跨至少 2 个标的或 2 个周期。
2. 单次问题造成重大风险误判，且角色复盘确认是规则缺陷而非执行失误。
3. 后评估量化指标连续 2 个周期触发修正规则。
4. 腰子判定该规则属于金融团队通用口径，不能只留在场景适配器或反例库。

### 7.2 知识来源治理

角色核心知识库的能力来源分为四类，权威等级和使用边界不同。

| 来源 | 含义 | 能做什么 | 不能做什么 | 入库等级 |
|:-----|:-----|:---------|:-----------|:---------|
| 外部权威资料 | 监管规则、交易所规则、财务准则、经典教材、学术论文、机构方法论、公司公告和财报说明 | 提供角色稳定知识的专业底座 | 不能不加验证地照搬到本项目参数 | 最高 |
| 项目已验证经验 | 周报、日报、荐股、模拟交易、后评估、反例、参数校准形成的复盘经验 | 提供本系统自己的经验进化 | 不能用单次成败直接改核心规则 | 高 |
| 角色共识规则 | 多角色在项目流程内确认过的职责边界、协作口径、裁决原则 | 提供团队内部执行一致性 | 不能替代外部事实和后评估验证 | 中高 |
| 大模型临时推理 | 执行模型基于上下文做出的归纳、比较、推理和表达 | 提出候选、生成草案、辅助归因 | 不能单独成为稳定规则来源 | 低 |

结论：

> 大模型提供推理和组织能力；外部权威资料提供可审计专业底座；项目已验证经验提供本系统自己的进化；角色共识规则提供团队执行一致性。

#### 7.2.1 外部权威资料如何获得

外部权威资料不是随手搜索几篇文章，而是建立“来源分级 + 采集责任 + 质量审查 + 更新周期”的来源治理。

| 资料类型 | 主要来源 | 适用角色 | 用途 |
|:---------|:---------|:---------|:-----|
| 监管与交易规则 | 证监会、交易所、结算机构、会计准则、上市公司监管规则 | 腰子、流金、玉夜、信鸽 | 交易边界、公告证据、财务口径、风控红线 |
| 公司硬事实 | 上市公司公告、年报、半年报、季报、问询函、投资者关系记录 | 信鸽、玉夜、腰子 | L1 证据、财务字段、催化验证 |
| 财务与估值方法 | 财务分析教材、估值教材、会计准则解释、审计方法论 | 腰子、玉夜 | 财务质量、估值框架、字段解释 |
| 因子与策略研究 | 学术论文、交易所研究、券商/基金公开方法论、可复现实证材料 | 青山、流金 | 因子有效性、样本约束、过拟合防范 |
| 风险管理方法 | 风控教材、组合管理方法、压力测试框架、交易纪律案例 | 流金、腰子 | 否决项、动作边界、回撤处理 |
| 宏观与行业框架 | 官方统计、央行/财政/产业政策文件、行业协会、公开研究框架 | 山猫、信鸽、腰子 | 宏观覆写、行业相位、事件窗口 |
| 数据工程与质量 | 数据质量标准、API 文档、供应商口径说明、项目数据契约 | 玉夜、情墨 | 字段可用等级、新鲜度、缓存策略 |

获得逻辑：

1. 先定义角色缺口：这个角色当前稳定知识缺哪类底座。
2. 再确定来源等级：优先监管、交易所、公司公告、准则、可复现实证；再考虑公开研究和教材。
3. 再抽取可复用知识：只沉淀原则、定义、适用边界、禁用条件，不沉淀大段原文。
4. 再绑定项目场景：说明该知识用于周报、日报、荐股、模拟交易还是后评估。
5. 最后进入角色评审：对应角色确认，腰子终审金融口径，旧影审计来源与越界。

#### 7.2.2 外部资料质量如何确保

外部资料入库前必须做质量分级。

| 等级 | 标准 | 可进入哪里 |
|:-----|:-----|:-----------|
| S | 官方规则、交易所规则、上市公司正式公告、财报、会计准则 | 核心知识库、证据规则、数据口径 |
| A | 有明确作者、方法、样本、可复核过程的教材、论文、机构方法论 | 核心知识库候选、参数库候选 |
| B | 公开研究报告、行业协会资料、可交叉验证的媒体资料 | 场景适配器、反例库、候选说明 |
| C | 单一媒体、论坛、二手转述、未给出处的观点 | 不进核心知识库，只能作为待核查线索 |

质量审查必须检查：

1. 来源是否可追溯。
2. 发布时间是否明确。
3. 适用市场是否匹配 A 股。
4. 样本与方法是否透明。
5. 结论是否被过度外推。
6. 是否与监管规则或公司公告冲突。
7. 是否有更新版本或废止版本。
8. 是否只适合某类市场环境。

#### 7.2.3 外部资料是否需要定期更新

需要。稳定层不是永远不变，而是不能被单次报告随意冲击。

| 知识类型 | 更新周期 | 触发条件 |
|:---------|:---------|:---------|
| 监管、交易、会计规则 | 事件触发 + 季度巡检 | 新规、废止、交易制度变化、会计准则变化 |
| 公司公告证据规则 | 事件触发 | 信息披露规则变化、公告类型变化 |
| 因子与策略方法 | 月度/季度复核 | 胜率退化、样本扩大、市场风格变化 |
| 风控规则 | 月度复核 + 重大风险事件触发 | 回撤异常、否决误杀、风险滞后 |
| 宏观与行业框架 | 月度复核 + 政策事件触发 | 宏观环境变化、行业相位切换 |
| 数据质量口径 | 周度/月度复核 | API 口径变化、字段缺失、延迟、数据源替换 |

资料会过时，因此每条外部知识入库时必须记录：

| 字段 | 说明 |
|:-----|:-----|
| source_ref | 来源链接、文件、书名、公告编号或本地路径 |
| source_level | S/A/B/C |
| published_at | 发布时间或版本日期 |
| reviewed_at | 最近复核日期 |
| owner_role | 负责复核角色 |
| applicable_scope | 适用市场、场景、标的范围 |
| expiry_or_review_cycle | 过期条件或复核周期 |
| superseded_by | 若被新资料替代，记录新来源 |

#### 7.2.4 项目已验证经验如何沉淀

项目经验的来源是“事实闭环”，不是人的感觉。最小链路为：

```
报告判断
  -> 日报执行记录
  -> 后评估回填
  -> 偏差归因
  -> KnowledgeUpdateCandidate
  -> 角色确认
  -> 反例库 / 参数库 / 场景适配器
  -> 多次验证后进入核心知识库候选
```

项目经验沉淀标准：

| 标准 | 说明 |
|:-----|:-----|
| 有来源 | 必须能追溯到报告、日报、baseline、EvalHook 或后评估记录 |
| 有结果 | 必须知道当初判断后来命中、偏离还是无法判断 |
| 有归因 | 必须区分数据、参数、证据等级、分析逻辑、执行、展示或策略环境变化 |
| 有复用性 | 必须说明下次在哪类场景可复用 |
| 有边界 | 必须说明什么情况下不适用 |
| 有角色确认 | 对应角色确认，金融口径由腰子终审 |
| 有审计记录 | 旧影检查是否单次结论硬升规则 |

落地路径：

| 后评估结论 | 首选落点 | 何时升级 |
|:-----------|:---------|:---------|
| 单次失败、原因未稳 | 反例库 | 等更多样本 |
| 阈值偏差明确 | 参数库 | 连续复核后进入参数规则 |
| 报告结构误导动作 | 场景适配器 | 多次返工后固化模板规则 |
| 数据字段误导 | 玉夜候选 + 反例库 | 字段口径确认后改核心数据知识 |
| 信号有效性变化 | 青山候选 + 参数库 | 样本足够且后评估支持后更新 |
| 风控滞后或过严 | 流金候选 + 参数库 | 腰子终审后改风控规则 |
| 通用因果链条错误 | 反例库 + 核心知识候选 | 跨样本确认后进入核心知识 |

#### 7.2.5 角色共识规则如何理解

角色共识规则不是角色职责定义本身，也不是外部知识。它是项目内部为了协作一致而形成的“共同操作口径”。

三者区别：

| 概念 | 回答的问题 | 示例 |
|:-----|:-----------|:-----|
| 角色职责 | 谁负责什么 | 玉夜管数据质量，青山管信号有效性，流金管风控边界 |
| 角色核心知识 | 这个角色专业上应该懂什么 | 数据可用等级、因子样本门槛、否决项设计 |
| 角色共识规则 | 多个角色发生交叉时怎么裁决 | 数据缺失时不得强行给结论；技术信号不能覆盖 L1 风险；C 层摘要不得越过流金动作红线 |

角色共识规则通常来自：

1. 多角色协作中反复出现的冲突。
2. G1/G2 方案中冻结的裁决口径。
3. 腰子对金融结论强度的统一裁决。
4. 旧影审计发现的越界模式。
5. 后评估证明某类协作边界反复出问题。

角色共识规则的落点优先是：

1. 流程与角色文件。
2. 场景适配器。
3. 角色知识库的“协作边界”章节。

只有当共识规则已经稳定、跨场景复用、并通过角色确认后，才进入角色核心知识库。

#### 7.2.6 大模型临时推理如何理解

大模型临时推理可以理解为执行模型自身的能力，包括：

1. 阅读和摘要。
2. 归纳和分类。
3. 比较多个证据。
4. 生成候选规则。
5. 提出失败归因假设。
6. 起草场景适配器或候选条目。

但它的权威性最低。原因是：

1. 推理过程不可完全审计。
2. 内部知识不可版本化。
3. 可能混入过时信息。
4. 可能产生看似合理但没有证据的归因。

因此大模型临时推理的正确位置是：

| 用途 | 是否允许 |
|:-----|:--------:|
| 起草 KnowledgeUpdateCandidate | 允许 |
| 汇总后评估发现 | 允许 |
| 提出外部资料检索方向 | 允许 |
| 改写场景适配器草案 | 允许 |
| 直接修改核心知识库 | 禁止 |
| 单独决定参数修正 | 禁止 |
| 代替角色签字 | 禁止 |
| 把模型常识当外部权威资料 | 禁止 |

## 8. 场景适配器：应用层

场景适配器回答“这些角色知识用在具体场景时，应该怎么输出”。它不是补丁，而是说明书。

| 场景 | 适配目标 | 需要引用的角色知识 | 输出形态 |
|:-----|:---------|:-------------------|:---------|
| 深度分析周报 | 冻结中期逻辑、给日报下指令、给后评估留基准 | 腰子、玉夜、青山、流金、信鸽、山猫 | A/B/C 三层、状态机、参数快照、后评估问题 |
| 每日分析 | 执行周报指令、识别状态变化、不重新发明中期逻辑 | 周报适配器、玉夜、青山、流金、信鸽 | 指令执行记录、触发项、状态更新、异常回报 |
| 每日荐股 | 排序、否决、降级、候选池治理 | 青山、流金、山猫、信鸽、玉夜、腰子 | 候选排序、否决链、降级原因、择时边界 |
| 模拟交易 | 把判断转成动作边界，不让报告语言越界 | 流金、腰子、青山 | 试探、加仓、减仓、退出的触发条件 |
| 后评估 | 验证判断、归因偏差、生成知识更新候选 | 青山、玉夜、流金、信鸽、山猫、腰子 | 命中记录、归因、参数偏差、KnowledgeUpdateCandidate |

### 8.1 场景适配器不做的事

1. 不新增角色核心知识。
2. 不直接修改参数库。
3. 不把用户摘要当作金融规则。
4. 不在日报中重写周报中期逻辑。
5. 不因单次东睦样例固定所有标的模板。

## 9. 后评估进化库：学习层

后评估进化库回答“这次判断错了，是知识错、参数错、数据错，还是市场环境变了”。

### 9.1 从 B 层后评估到知识候选

```
周报判断
  -> 日报执行
  -> B 层后评估
  -> 失败归因
  -> 生成 KnowledgeUpdateCandidate
  -> 分派到对应角色
  -> 角色确认
  -> 腰子终审
  -> 旧影审计
  -> 写入核心知识库 / 场景适配器 / 反例库 / 参数库
  -> 下次报告按版本引用
```

### 9.2 KnowledgeUpdateCandidate 最小字段

| 字段 | 必填 | 说明 |
|:-----|:----:|:-----|
| candidate_id | 是 | 全局唯一 ID，建议 `KUC-YYYYMMDD-ROLE-XXXX` |
| source_type | 是 | weekly_report / daily_report / stock_pick / sim_trade / eval |
| source_ref | 是 | 来源文件、baseline、EvalHook 或报告路径 |
| stock_code | 否 | 涉及单一标的时填写 |
| scenario | 是 | 周报/日报/荐股/模拟交易/后评估 |
| owner_role | 是 | 首要确认角色 |
| related_roles | 否 | 需要联审的角色 |
| attribution_type | 是 | 数据/参数/权重/证据等级/分析逻辑/展示/执行/策略环境变化 |
| observed_failure | 是 | 后评估观察到的问题 |
| proposed_update | 是 | 建议更新内容 |
| target_layer | 是 | core / adapter / evolution / counterexample / parameter |
| confidence | 是 | low / medium / high |
| evidence_refs | 是 | 数据、公告、报告、后评估记录 |
| risk_if_applied | 是 | 若采纳可能造成的副作用 |
| risk_if_ignored | 是 | 若忽略可能重复发生的问题 |
| decision_status | 是 | proposed / role_review / approved / rejected / parked / superseded |
| final_decision_ref | 否 | 角色确认或审计记录 |

### 9.3 归因到落库路径

| 归因类型 | 优先落点 | 何时升级到核心知识 |
|:---------|:---------|:-------------------|
| 数据问题 | 玉夜候选 + 反例库 + 数据参数库 | 字段口径或可用等级被确认需要通用修正 |
| 参数问题 | 参数库 | 同类阈值连续偏离，或跨标的稳定失效 |
| 权重问题 | 参数库 + 青山候选 | 后评估证明权重长期偏误 |
| 证据等级问题 | 信鸽/玉夜候选 + 反例库 | L1/L2a/L2b/L3 判定规则需要通用修正 |
| 分析逻辑问题 | 反例库 + 腰子/青山候选 | 因果链条被确认不成立，且不只是一只标的 |
| 展示问题 | 场景适配器 | 用户摘要或报告结构反复误导动作 |
| 执行问题 | 场景适配器 + 审计清单 | 日报/荐股未按指令执行，属于流程接口缺陷 |
| 策略环境变化 | 山猫/青山候选 + 参数库 | M 层覆写或因子环境阈值需稳定化 |

## 10. 反例库

反例库用于保存“证明某条规则不能直接泛化”的失败样本。反例不是羞耻墙，而是防止团队把一次成功经验升级成万能规则。

### 10.1 进入反例库的条件

| 条件 | 说明 |
|:-----|:-----|
| 单次失败但归因未充分确认 | 先收反例，不改核心规则 |
| 规则在特殊环境中失效 | 标记适用边界，不立即废弃规则 |
| 数据口径误导结论 | 记录当时数据快照和误导路径 |
| 动作表达过激或过保守 | 记录报告语言如何影响动作边界 |
| 证据等级错配 | 记录把预期、传闻、叙事误当强证据的链条 |

### 10.2 反例库最小字段

| 字段 | 说明 |
|:-----|:-----|
| case_id | 反例 ID |
| source_ref | 来源报告/后评估/EvalHook |
| failed_rule_or_assumption | 失败的规则或假设 |
| context | 市场环境、行业相位、标的状态 |
| failure_path | 从判断到失败的路径 |
| confirmed_cause | 已确认原因；未确认时填 `unknown` |
| reusable_lesson | 可复用教训 |
| linked_candidates | 关联 KnowledgeUpdateCandidate |
| review_status | proposed / confirmed / archived |

## 11. 参数库

参数库管理“可校准但不应写死在报告里的阈值、窗口、权重”。

### 11.1 参数类别

| 参数类别 | 示例 | 负责角色 | 修正依据 |
|:---------|:-----|:---------|:---------|
| 技术阈值 | 支撑位偏差、突破确认天数、量能倍数 | 青山 + 流金 | 后评估命中率、回撤、误触发率 |
| 证据窗口 | L2a 催化有效期、公告后观察期 | 信鸽 + 腰子 | 催化兑现/落空统计 |
| 数据可信等级 | moneyflow、融资融券、主营构成、公告全文 | 玉夜 | 字段缺失、延迟、口径误导记录 |
| 风控边界 | 否决项阈值、降级触发、恢复条件 | 流金 + 腰子 | 风险事件、回撤、动作审计 |
| 宏观覆写 | M 层触发阈值、行业暂停条件 | 山猫 + 青山 + 腰子 | 风格切换、行业相位、宏观事件 |
| 结论强度 | 强跟踪、等待、降级、移出所需证据 | 腰子 | 状态切换准确率、摘要返工率 |

### 11.2 修参数还是修逻辑

| 情况 | 优先动作 |
|:-----|:---------|
| 阈值偏差大，但因果链条仍成立 | 修参数 |
| 样本不足导致信号不稳 | 降低置信度或增加样本门槛 |
| 证据等级被误判 | 修证据等级规则或字段可信等级 |
| 事件窗口过短/过长 | 修窗口参数 |
| 规则方向反复错误 | 修分析逻辑 |
| 逻辑正确但市场风格变化 | 修 M 层/策略环境参数，不否定原逻辑 |
| 日报没执行周报指令 | 修场景适配器或执行流程，不修金融逻辑 |

## 12. 自动建议、人工确认与禁止自动写入

### 12.1 自动建议允许范围

系统或执行模型可以自动生成：

1. KnowledgeUpdateCandidate 草案。
2. 反例库候选条目。
3. 参数偏差统计。
4. 字段缺失、延迟、口径冲突提示。
5. 日报指令执行率统计。
6. 用户摘要返工模式统计。

### 12.2 必须人工确认范围

以下内容必须由对应角色确认，金融相关内容最终由腰子终审：

1. 核心知识库新增、删除、改写。
2. 状态机规则变化。
3. 否决项、降级项、恢复条件变化。
4. 信号升权、降权或移除。
5. 数据可用等级或权威源变化。
6. M 层宏观覆写阈值变化。
7. 场景适配器影响用户摘要或动作边界的变化。

### 12.3 禁止自动写入

任何自动流程都不得直接写入：

1. `.claude/agents/*-知识库/` 的核心知识文件。
2. 正式报告模板。
3. 正式风控规则。
4. 评分权重。
5. 否决项红线。
6. 生产调度入口。

## 13. 东睦股份作为首个样例

东睦股份不作为永久规则来源，但必须作为知识进化机制的首个验证样例。

### 13.1 后评估必须产出的候选

东睦周报后评估时，至少生成以下候选检查项；是否采纳由角色评审决定。

| 可能发现 | 首要角色 | 候选落点 | 初始处理 |
|:---------|:---------|:---------|:---------|
| 技术修复后没有延续 | 青山 | 反例库 / 参数库 / 青山候选 | 检查技术信号有效性和样本门槛 |
| moneyflow 口径误导 | 玉夜 | 反例库 / 数据可信等级候选 | 检查资金字段可信等级和使用限制 |
| C 层动作太激进 | 流金 + 腰子 | 场景适配器 / 反例库 | 修动作表达红线，不直接改核心逻辑 |
| 中期逻辑判断过强 | 腰子 | 结论强度参数 / 反例库 | 检查证据等级与状态机升级条件 |
| 催化窗口落空 | 信鸽 | 催化窗口参数 / 反例库 | 检查 L2a 有效期和公告证据等级 |
| 市场风格压制成长线索 | 山猫 + 青山 | M 层参数 / 策略环境候选 | 判断是否属于策略环境变化 |

### 13.2 东睦样例验收要求

东睦后评估不能只输出“判断对/错”。至少要回答：

1. 周报核心假设是否命中。
2. 日报是否执行周报指令。
3. 哪些字段被证明有用。
4. 哪些字段被证明误导。
5. 哪些参数需要候选修正。
6. 哪些失败只进入反例库。
7. 哪些问题需要角色核心知识库评审。
8. 下次周报是否自动引用本次候选的处理状态。

## 15. 脚本、函数与字段设计

本阶段不写脚本，只冻结后续字段与状态。

### 15.1 Candidate 状态机

| 状态 | 含义 | 允许下一步 |
|:-----|:-----|:-----------|
| proposed | 后评估或人工提出候选 | role_review / rejected |
| role_review | 对应角色评审中 | approved / rejected / parked |
| approved | 角色确认可更新 | final_review |
| final_review | 腰子终审或非金融由阿黑终审 | applied / rejected / parked |
| applied | 已写入目标库并记录版本 | closed |
| rejected | 明确不采纳 | closed |
| parked | 暂存，等待更多样本 | role_review / superseded |
| superseded | 被新候选替代 | closed |
| closed | 流程关闭 | 不再流转 |

### 15.2 审计检查点

| 检查点 | 规则 |
|:-------|:-----|
| 来源检查 | 每个候选必须有 source_ref 和 evidence_refs |
| 分层检查 | target_layer 必须是五层之一 |
| 角色检查 | owner_role 必须与归因类型匹配 |
| 单次入库检查 | 单次报告结论不得直接进入核心知识库 |
| 签字检查 | 不得用执行模型代签角色确认 |
| 版本检查 | applied 后必须记录 final_decision_ref |
| 回溯检查 | 下次报告引用时必须能追到候选来源 |
