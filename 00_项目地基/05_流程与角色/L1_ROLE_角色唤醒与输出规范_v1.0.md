# ROLE：角色唤醒与输出规范 v1.0

> **定位：** 承接文件，整合 `角色唤醒协议.md` + `角色实唤醒与输出证据协议.md` + `角色输出矩阵.md`
> **用途：** 任务需要角色唤醒判定或输出规范时读取
> **维护人：** 阿黑

---

## 1. 核心原则

1. **执行模型（DeepSeek/Claude/Codex）不是项目角色。** 不得以角色身份签字。
2. **阿黑**是调度者，负责流程路由和阶段调度，**不得代签**其他角色结论。
3. **腰子**是金融口径裁决者。
4. **旧影**负责独立审计和阶段复查。
5. **玉夜**负责数据事实审查。
6. **情墨**负责流程制度和文档秩序。
7. **"列出角色 ≠ 实际唤醒"** — 只写"唤醒角色：阿黑、情墨、旧影"不算角色已参与。

## 4. 角色唤醒时序

```
G0: 阿黑（路由）
  ↓
G1: 金融团队（腰子+山猫+信鸽+玉夜+流金+青山）
  ↓  （若涉及报告也引入情墨）
G2: 情墨（架构设计）+ 玉夜（数据方案）
  ↓
G3: 执行模型（编码/改文档）
  ↓
G4: 执行模型（自检）
  ↓
G5: 旧影（独立复查）
  ↓
G6: 阿黑（放行）+ 腰子（签字）
```

> **签署证据规则引用：** 角色输出 PASS 必须满足 `04_一致性闸门/role_evidence_signature_schema.json` 字段定义。缺 evidence、执行模型代签、G5/G6 缺失均按 `stage_acceptance_policy.json` 判定 BLOCK。详见 `04_一致性闸门/check_role_evidence.py`。此规则为程序化强制执行，不接受口头 PASS。

## 5. 角色输出格式

每个被唤醒角色输出必须包含：

```text
角色名：【】
参与阶段门：【G0/G1/G2/G3/G4/G5/G6】
本阶段职责：【一句话说明】
检查对象：【路径/文件/范围】
结论：【PASS / BLOCK / WARN】
依据：【文件/命令/规则编号】
遗留问题：【如有】
```

## 6. 角色输出通过规则

| 情况 | 处理 |
|:-----|:------|
| 必唤醒角色未输出结论 | ⛔ BLOCK |
| 阿黑代签角色结论 | ⛔ BLOCK |
| 执行模型以角色身份签结论 | ⛔ BLOCK |
| G5 复查缺失 | ⛔ BLOCK |
| 角色输出 BLOCK | ⛔ 转化为阶段 BLOCK |
| 角色输出 PASS/WARN | ✅ 汇总到验收报告 |

## 7. G5 独立复查格式

```text
复查角色：旧影
复查范围：【验收报告+命令+文件】
复查结果：【命令通过率 / 文件范围合规 / 角色输出完备性】
总体结论：【建议通过 / 需补修 / 不通过】
遗留问题：【如有】
```

## 8. 跳过角色必须说明

跳过必唤醒角色时，必须在验收报告中逐条说明：跳过角色、跳过原因、是否影响阶段结论。

## 9. 角色启动完成条件

角色被列入唤醒名单，不等于角色已经完成启动。

角色完成启动必须同时满足：

1. ✅ 已读取自身角色入口 `.md`。
2. ✅ 已确认当前任务流程编号与阶段门（FLOW / ROLE / TASK）。
3. ✅ 已生成或接收 KRM 知识库读取清单。
4. ✅ 已声明本次实际读取范围。
5. ✅ 已声明本次明确不读范围及原因。
6. ✅ 未发生全量读取知识库、历史归档或外部原文的风险。

## 10. 角色输出知识读取声明格式

所有角色输出格式追加以下知识读取声明区块：

```text
知识读取声明：
- 角色入口文件：
- 必读启动层：
- 场景必读层：
- 角色按需层：
- 按需引用层：
- 本次明确不读：
- 未读原因：
- 是否存在全量读取风险：是/否
```
