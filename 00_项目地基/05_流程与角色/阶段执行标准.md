# 阶段执行标准

> 版本: 1.0 | 创建: 2026-06-02 | 维护人: 阿黑+情墨

---

## 一、阶段编号规则

| 前缀 | 含义 | 示例 |
|:-----|:------|:------|
| **第-X** | 启动和审计阶段（X=负数或0） | 第-1（目录治理审计） |
| **第0.X** | 固化/标准化阶段 | 第0.5（固化第0阶段报告） |
| **P0-X** | 最小强制地基闸门包，只检测不修复 | P0-A（baseline权威闸门） |
| **P0-FIX** | P0 级问题定点修复 | P0-FIX |
| **第X** | 正式重构阶段 | 第1（baseline权威体系接入） |
| **第X.5** | 流程标准化/制度固化 | 第1.5（流程标准化） |

---

## 二、阶段生命周期

每个阶段按以下顺序执行，不允许跳过：

```
设计 → 路由 → 阶段门判断 → 角色唤醒 → 派单 → 执行 → 自检 → 报告 → 复查 → 通过/补修 → 下一阶段
```

| 步骤 | 说明 | 负责人 |
|:-----|:------|:------|
| 设计 | 先设计方案，后编码 | 阿黑/情墨 |
| 路由 | 确定流程编号和阶段门 | 阿黑 |
| 阶段门判断 | 判断需要启用哪些阶段门 | 阿黑 |
| 角色唤醒 | 按流程编号唤醒对应角色 | 阿黑 |
| 派单 | 按阶段派单模板生成执行指令 | 阿黑 |
| 执行 | 执行模型（G3）或角色鉴定（G1/G2） | 执行模型/角色 |
| 自检 | G4：执行者跑验收命令 | 执行模型 |
| 报告 | 输出阶段执行报告 | 执行模型 |
| 复查 | G5：独立复查，不通过则补修 | 旧影/阿黑 |
| 通过/补修 | 补修不得扩大范围 | 旧影/阿黑 |

---

## 三、阶段边界规则

每个阶段必须明确以下七类边界：

| 边界 | 说明 |
|:-----|:------|
| **允许新增** | 可以创建哪些类型的新文件 |
| **允许修改** | 可以修改哪些现有文件 |
| **禁止修改** | 绝对不能碰的文件类型 |
| **是否可碰旧文件** | 历史日报、历史 sidecar、历史 baseline 等 |
| **是否可修数据** | kline_cache、fund_flow_cache、data_scored 等 |
| **是否可改脚本** | check_*.py、scripts/*.py、代码文件/*.py 等 |
| **是否可改业务配置** | pigeon_config.json、schema 等 |

---

## 四、文件操作分类

| 代码 | 含义 | 说明 |
|:----:|:------|:------|
| **N** | 新增（New） | 本阶段新创建的文件 |
| **M** | 修改（Modified） | 本阶段修改的现有文件 |
| **D** | 删除（Deleted） | 本阶段删除的文件 |
| **R** | 移动（Renamed/Moved） | 本阶段迁移的文件 |
| **??** | 未跟踪（Untracked） | git 未跟踪但存在于工作区的文件 |

---

## 五、既有未跟踪文件处理

`git status` 中出现的 `??`（untracked）文件，必须说明：
1. 是否为本阶段产生
2. 若否，是哪个阶段/来源产生的
3. 本阶段是否触碰该文件

---

## 六、验收命令规则

| 文件类型 | 必跑命令 |
|:---------|:---------|
| **JSON 文件** | `python3 -m json.tool <路径>` |
| **Python 文件** | `python3 -c "import py_compile; py_compile.compile('<路径>', cfile='/private/tmp/<临时文件>.pyc', doraise=True); print('PASS')"` |
| **闸门脚本** | 单票 + `--all` +（如支持）`--json` 可解析 |
| **git status** | 必须 path-limited（`git status --short <关注范围>`） |

---

## 七、git status 解释规则

1. 所有 `M`（modified）文件必须说明修改原因
2. 所有 `??`（untracked）文件必须说明来源
3. 允许范围外的文件变更必须停止并通过/回滚
4. 多个阶段间的累积 `M` 需要区分“本阶段修改”和“前阶段未提交”

---

## 八、通过条件

阶段通过必须同时满足：
1. ✅ 所有允许范围内的文件已创建/修改完成
2. ✅ 所有验收命令通过
3. ✅ 未修改允许范围之外的文件
4. ✅ git status 已解释
5. ✅ 无静默失败（报告说 PASS 但命令实际失败）
6. ✅ 未跳过必需的阶段门
7. ✅ 验收报告已提交

---

## 九、补修规则

| 规则 | 内容 |
|:-----|:------|
| 补修必须在同一阶段 | 不得另开新阶段 |
| 补修不得扩大范围 | 只能修已暴露的问题 |
| 补修同样需要验收 | 补修后重跑全部验收命令 |
| 补修记录必须写入验收报告 | 说明问题、修复方式、验收结果 |

---

## 十、阶段冻结规则

1. 阶段通过后不得追加修改
2. 如需追加修改，应走 F-FIX 流程
3. 重大项目修复前阶段可被“解冻”，但必须由阿黑+腰子+旧影三方签字
4. 解冻不得改变已完成阶段的验收结论
