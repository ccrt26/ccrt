## 0. 启动协议

本文件是本协作组被唤醒时的唯一启动入口。

本协作组参与正式任务时，必须先完成以下启动动作：

1. 确认协作组成员身份、职责、能力边界与禁止事项。
2. 读取项目级 FLOW / ROLE / TASK，确认当前任务流程编号与阶段门。
3. 根据当前任务生成或接收 KRM 知识库读取清单。
4. 只读取 KRM 指定的场景文件、schema、参数、反例和角色知识。
5. 输出时声明：已读文件、未读文件、未读原因、结论依据。

禁止默认全量读取角色知识库、项目地基、历史归档、G4/G5/G6 过程文件或外部原文。

若本文件与 FLOW / ROLE / TASK / KRM 冲突，以项目级规则和 KRM 为准。

## 二、交接标准

### 2.1 情墨 → 新安（闸门1 设计审查）

情墨交付物：
- 架构设计文档（含模块划分/接口契约/数据流）
- 代码分级标注（L0/L1/L2）
- 需求→代码核对清单（文末附）
- 闸门判定：`PASS` / `FAIL`

新安接收标准：
- 设计文档格式完整，所有必填项已填
- 接口契约与现有契约无冲突
- 代码分级标注合理
- 核对清单可逐项验证
- **时限**：收到设计文档后2轮对话内完成审查

### 2.2 新安 → 红结（闸门1通过后）

新安交付物：
- 架构合规审查报告
- 闸门1判定：`PASS`

红结接收标准：
- 闸门1必须为PASS状态
- 情墨设计文档必须已获腰子金融确认
- 无此二者，红结拒绝开工

### 2.3 红结 → 新安（闸门2 代码审查）

红结交付物：
- 代码实现（Git分支/commit）
- 自查清单（红结-知识库/06-提交前自查清单.md 逐项打勾完成）
- CHANGELOG更新

新安接收标准：
- 自查清单全部打勾
- 代码文件路径与情墨设计文档一致
- 单文件不超过500行（或附情墨拆分许可）
- L2模块代码中每条风控规则注释引用红线条款
- **时限**：收到代码后2轮对话内完成四层验证

### 2.4 新安 → 红枫（闸门3 上线闸）

新安交付物：
- 四层验证报告（变更影响→测试→回归→红线），全部PASS
- Golden Master diff报告（涉及引擎变更时）
- 闸门2判定：`PASS`

红枫接收标准：
- 四层验证全部PASS
- 无未关闭的B0/B1缺陷
- 缺陷台账已更新
- **时限**：收到放行单后1轮对话内确认灰度方案

### 2.5 红枫 → 上线

红枫交付物：
- 灰度部署方案（含灰度范围/时长/监控指标）
- 回滚方案（含触发条件/操作步骤/回滚验证）
- 闸门3判定：`PASS`

## 三、角色间SLA

| 交接 | 响应时限 | 阻塞升级条件 |
|:-----|:--------|:-----------|
| 情墨出设计 | 1轮对话内启动 | 超2轮未出→阿黑介入 |
| 新安架构审查 | 2轮对话内完成 | 超3轮→阿黑介入 |
| 红结编码 | 视需求复杂度 | 超4轮未完成→阿黑检查是否卡在设计问题 |
| 新安四层验证 | 2轮对话内完成 | 超3轮→阿黑介入 |
| 红枫灰度部署 | 1轮对话内出方案 | 超2轮→阿黑介入 |
| 旧影审计 | 日检1轮/周检3轮 | 超时→阿黑催促 |

## 四、升级链（工程线内部）

```
角色间交接超时/争议
  ↓
L1：情墨协调（工程线负责人）
  ↓
L2：阿黑仲裁
  ↓
L3：用户(创始人)裁决
```

升级条件：
- 角色间对接口契约有争议
- 代码分级(L0/L1/L2)判定有分歧
- SLA超时未响应
- 闸门FAIL后对修复方案有分歧

## 六、沟通纪律

- 角色间反馈默认在同一次对话上下文中完成（顺序接力，不另起Agent）
- 跨角色反馈格式：`[角色A→角色B]：具体问题+文件路径+建议`
- 打回必须带具体原因+修复指引，禁止仅说"不通过"
- 旧影审计结果对所有工程角色可见，被审计角色须在1轮内确认收到
- 紧急问题（B0缺陷/数据源全挂）可越级直接通知阿黑
