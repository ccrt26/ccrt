# 02 — 数据质量维度

> 玉夜知识库 v1.0 | 2026-05-23
> 所属项目：铁律量化
> 关联文件：01-数据源全景、05-异常检测与告警

---

## 一、六大维度总览

玉夜的数据质量审计围绕六个维度展开。每次巡检必须覆盖全部六个维度，每个维度有明确的定量阈值和判定规则。

| 维度 | 核心问题 | 不可用阈值 | 警告阈值 | 巡检频率 |
|:----:|:--------|:--------:|:-------:|:------:|
| 完整性 | 该有的字段都有吗？ | 单字段非空率<80% | <95% | 每次 |
| 准确性 | 数值在合理范围内吗？ | 关键字段错误率>5% | >1% | 每次 |
| 时效性 | 数据是最新的吗？ | 延迟>1小时（实时数据） | >30s | 每次 |
| 一致性 | 跨源数据一致吗？ | 价格差异>2% | >0.5% | 抽样 |
| 唯一性 | 有没有重复记录？ | 重复率>5% | >0% | 每日 |
| 有效性 | 符合业务规则吗？ | 业务规则违反率>5% | >1% | 每次 |

## 二、维度1：完整性（Completeness）

### 2.1 定义

数据完整性衡量所有**预期应有**的字段和记录是否实际存在。缺失可以是字段级别的（某个单元格为null），也可以是记录级别的（某一天的整行缺失）。

### 2.2 检查对象与预期记录数

| 数据类型 | 预期记录数 | 计算依据 |
|:--------|:--------|:---------|
| 行情Quote | 每日1条/股 | 交易日每天一条 |
| K线日线 | 最近120条（按参数） | 不含停牌日和非交易日 |
| K线日线（完整） | 最近N个交易日，N=自然日*0.69 | 约69%自然日为交易日 |
| 财务数据 | 最近4季度 | 4个报告期 |
| 板块排行 | TOP N（10/20/30） | 按参数pz值 |
| 资金流向 | 最近N天 | 按参数Days值 |
| 融资融券 | 最近N天 | 按参数Days值 |

### 2.3 字段级完整性阈值

**行情Quote字段必须非空**（如为空则数据不可用）：

| 字段 | 允许为空？ | 备注 |
|:----|:--------:|:-----|
| Code | 否 | 无代码无法关联 |
| Name | 否 | 无名称无法识别 |
| Price | 否 | 核心字段 |
| PrevClose | 否 | 涨跌幅计算基础 |
| Open | 否 | 技术分析基础 |
| High | 否 | 有效性校验依赖 |
| Low | 否 | 有效性校验依赖 |
| Volume | 否 | 非停牌日必须>0 |
| ChangePct | 否 | 核心展示字段 |
| PE | 是（仅腾讯提供） | 新浪备源不提供PE |
| TurnoverRate | 是（仅腾讯提供） | 新浪备源不提供 |
| MktCap | 是（仅腾讯提供） | 新浪备源不提供 |
| Amplitude | 是（仅腾讯提供） | 新浪备源不提供 |

### 2.4 完整性检查流程

```
1. 确认检查目标（如某只股票的行情数据）
2. 对比预期交易日历，列出应有交易日列表
3. 检查实际返回的记录数
4. 对于K线数据，逐条检测是否有跳空日期（非节假日间隔>1天）
5. 对于每一条记录，检查必填字段是否非空
6. 计算：非空率 = 非空字段数 / 预期字段总数 × 100%
7. 判定：
   - 非空率 >= 95%：正常
   - 80% <= 非空率 < 95%：警告（标注缺失字段）
   - 非空率 < 80%：不可用（该数据不得用于决策链）
```

### 2.5 缺失日期检测（K线专用）

K线数据的日期连续性检查：

```
1. 取得K线数据，按日期升序排列
2. 对相邻两条记录，计算日期差（自然日）
3. 如果日期差 > 1 天：
   a. 检查中间日期是否为节假日（查 holidays_2026.csv）
   b. 若是节假日 → 正常跳过
   c. 若不是节假日 → 缺失告警
4. 计算：缺失率 = 实际缺失非节假日天数 / 预期交易日天数 × 100%
   - 缺失率 = 0%：正常
   - 0% < 缺失率 <= 3%：警告（少量缺失）
   - 缺失率 > 3%：严重（可能API分页截断或数据损坏）
```

### 2.6 板块成分股完整性

```
预期成分股数 = 东方财富板块定义中的成分股总数
实际返回数 = API返回的diff数组长度
覆盖率 = 实际返回数 / 预期成分股数 × 100%
- 覆盖率 >= 95%：正常
- 80% <= 覆盖率 < 95%：警告（部分成分股缺失）
- 覆盖率 < 80%：不可用（板块数据可能不具代表性）
```

## 三、维度2：准确性（Accuracy）

### 3.1 定义

数据准确性衡量数值是否在合理范围内，是否与真实值一致。包括：值域检查、逻辑校验、跨源交叉验证。

### 3.2 通用值域范围

| 字段 | 合理范围 | 异常判定 | 说明 |
|:----|:--------|:--------|:-----|
| Price | 0.01 ~ 3000 | 超出即P3异常 | 贵州茅台最高约3000元作为上界 |
| ChangePct（主板） | -10.5% ~ +10.5% | 超出即P2异常 | 留0.5%浮点误差余量 |
| ChangePct（创业板/科创） | -21% ~ +21% | 超出即P2异常 | 留1%浮点误差余量 |
| ChangePct（北交所） | -31% ~ +31% | 超出即P2异常 | |
| PE（静态） | 0 ~ 500 | 超出即P3注意 | PE>500可能为微利股，标注"极高PE" |
| PE(TTM) | 0 ~ 500 | 超出即P3注意 | 负PE不在范围内，单独标注"亏损" |
| PE（负值） | < 0 | P3注意 | 正常现象（亏损公司），标注"亏损"不告警 |
| 成交量 | >= 0 | =0 且非停牌日 → P2 | 成交量=0但非停牌=数据缺失 |
| 成交额 | >= 0 | =0 且成交量>0 → P2 | 逻辑矛盾 |
| 换手率 | 0 ~ 100% | >50% → P3注意 | 妖股特征，标注"异常高换手" |
| 总市值 | > 0 且 < 100万亿 | 0或负数 → P2 | 不可能为0或负 |
| 振幅 | 0 ~ 震幅上限 | >20% → P3注意 | 极端波动，但不一定是数据错误 |
| 涨跌额 | = Price - PrevClose | 偏差>0.02元 → P2 | 计算值与声明值不一致 |

### 3.3 板块特异性涨跌幅上限判断

```
函数 GetChangePctUpperBound(code):
  如果 code 以 "8" 或 "4" 开头（北交所）:
    上限 = 30%
  否则 如果 code 以 "300" 或 "301" 开头（创业板）或 以 "688" 开头（科创板）:
    上限 = 20%
  否则 如果 名称中包含 "ST":
    上限 = 5%
  否则:
    上限 = 10%
  
  实际误差容忍 = 上限 + 1%（浮点计算误差）
```

### 3.4 数据突变检测

当同一只股票的某个指标发生大幅变动时，需区分"真变化"和"数据错误"：

| 指标 | 日变化阈值 | 超过后判定 |
|:----|:--------:|:--------:|
| PE | >50% | P3注意（可能财报更新导致EPS变化） |
| 市值 | >20% | P2警告（除非是除权除息日） |
| 换手率 | 从<5%跳至>30% | P3注意（可能有利好/利空事件） |
| 成交量 | >5倍前5日均量 | P3注意（标注"巨量"，不一定是数据错误） |

### 3.5 准确性的玉夜诊断指令

```
当检测到数值异常时，玉夜不应直接判定为数据错误，而应：
1. 记录异常值
2. 标注可能的解释（财报更新/除权/事件驱动等）
3. 归类到对应告警等级
4. 如果无法排除数据错误，在报告中使用"疑似数据异常"措辞
5. 建议Claude运行二次验证（用备源重新获取同一数据）
```

## 四、维度3：时效性（Timeliness）

### 4.1 定义

时效性衡量数据的时间戳是否在可用时间窗口内。过期数据可能仍有参考价值，但必须在报告中明确标注时滞。

### 4.2 时效性分类

| 类别 | 定义 | 期望延迟 | 不可用阈值 |
|:----|:----|:-------:|:--------:|
| 实时 | 数据反映当前市场状态 | <5s | >30s |
| 准实时 | 有轻微滞后但可用 | 5-30s | >5min |
| 日内有效 | 当日有效 | 当日收盘前 | 收盘后但使用当日数据 |
| 日终 | 每日收盘后更新 | 当日18:00前 | 次日开盘前未更新 |
| 季频 | 每季报公告后更新 | 公告日+5工作日 | 超过15工作日未更新 |
| 历史 | 不可变数据 | 无时效要求 | 无 |

### 4.3 各数据类别的时效标准

| 数据类别 | 时效类别 | TTL | 过期后行为 |
|:--------|:------:|:---:|:----------|
| 实时行情Quote | 实时 | 5分钟 | 不可用于交易决策 |
| K线日线 | 日终 | 1天 | 当日收盘后旧缓存仍可用 |
| K线盘中 | 准实时 | 5分钟 | 仅盘中有效 |
| 财务季报 | 季频 | 7天 | 标注"基于上一季度数据" |
| 板块排行 | 盘中实时 | 5分钟 | 不可用于当日板块判断 |
| 板块成分股 | 日内有效 | 6小时 | 次日开盘前刷新 |
| 资金流向(个) | 日终 | 6小时 | 次日需刷新 |
| 资金流向(行) | 日终 | 6小时 | 次日需刷新 |
| 北向资金 | 季频 | 7天 | 标注"季度数据，时滞1-2周" |
| 研报 | 不定时 | 24小时 | 标注"截至X月X日" |
| 融资融券 | 日终 | 24小时 | 标注"T-1日数据" |

### 4.4 数据时效性按频率分档

不同数据类型的时效性要求不应一刀切。以下按底层数据的更新频率分档，明确各频率的"新鲜"与"过期"判定标准。

#### 4.4.1 频率分档表

| 更新频率 | 新鲜标准 | 容忍阈值 | 过期判定 | 典型数据 |
|:-------:|:------|:------:|:------|:-----|
| 盘中实时 | 延迟 < 30s | 30s | 延迟 > 5min | Quote实时行情 |
| 每日收盘后 | 数据日期 = 最近交易日 | 最近交易日 | 数据日期 < 最近交易日-1 | KLine日线、Margin、FundFlow |
| 每周 | 数据日期在本周内 | 本周一前 | 数据日期 < 上周一 | 北向资金周报 |
| 每月 | 数据日期在本月内 | 本月1日前 | 数据日期 < 上月1日 | PE百分位 |
| 每季 | 报告期 >= 最近完整季度 | 上季末+30天 | 报告期 < 上季末 | Financial季报 |
| 每年 | 报告期年份 >= 当前年份-1 | 年报披露截止日 | 报告期 < 当前年份-1 | Financial年报 |

#### 4.4.2 日频数据的时效性判定

日频数据（KLine/Margin/FundFlow等）的核心审计点是**最新数据日期**：

```
1. 读取数据最后一条的Date字段
2. 获取最近交易日（考虑节假日）
3. 判定：
   - Date == 最近交易日：✅ 新鲜
   - Date == 最近交易日-1：⚠️ 可用，标注"T-1数据"
   - Date < 最近交易日-2：🔴 过期，检查API/缓存链路
```

对于盘后（15:00后）检查日线数据：
- 如果最新Date不是当日：检查是否当日为交易日且API尚未完成收盘更新（通常18:00前完成）
- 非交易日不要求Date为当日

#### 4.4.3 季频数据的时效性判定

季频数据（Financial）的核心审计点是**报告期覆盖**：

```
1. 读取Financial数据中的REPORT_DATE
2. 确定最近应披露的完整季度：
   - 当前月份在1-4月：最近完整季度为上年Q3（上年9月30日）
   - 当前月份在5-8月：最近完整季度为当年Q1（当年3月31日）
   - 当前月份在9-10月：最近完整季度为当年Q2（当年6月30日）
   - 当前月份在11-12月：最近完整季度为当年Q3（当年9月30日）
3. 判定：
   - REPORT_DATE >= 最近完整季度截止日：✅ 新鲜
   - REPORT_DATE == 上上个季度：⚠️ 可用但可能即将过时
   - REPORT_DATE < 上上个季度：🔴 过期，需重新获取
4. 特殊窗口：
   - 季报公告截止日（季末+30天）前，上一季度数据仍视为新鲜
   - 年报公告截止日（年末+4个月）前，上一年度数据仍视为新鲜
```

#### 4.4.4 频率分档与TTL的关系

频率分档审计**不替代**缓存TTL机制，两者互补：

| 审计维度 | TTL审计 | 频率审计 |
|:----|:----|:----|
| 关注点 | 缓存写入时间戳 | 数据本身的业务日期 |
| 检查对象 | 缓存的Timestamp字段 | 数据的Date/REPORT_DATE字段 |
| 适用场景 | API失败时缓存兜底的可用性判断 | 数据是否反映最新市场/财报状态 |
| 告警逻辑 | Age > TTL → 过期 | Date落后 → 过时 |
| 互补关系 | TTL保证不读损坏/极旧缓存 | 频率审计保证数据内容时效 |

**玉夜审计时两者都需要检查**：先通过频率审计判断数据内容是否过时，再通过TTL判断缓存结构是否需清理。

### 4.5 时效性检查流程

```
1. 读取数据的时间戳（缓存的Timestamp字段，或API返回的时间字段）
2. 计算：延迟 = 当前时间 - 数据时间戳
3. 查询CacheTTL配置，获取该数据类型的TTL
4. 对比：
   - 延迟 < TTL：数据新鲜，正常使用
   - TTL <= 延迟 < TTL×2：数据稍旧，可用但标注"[C]-过期X分钟"
   - TTL×2 <= 延迟 < TTL×5：数据显著过期，标注"[C]-过期X小时，建议刷新"
   - 延迟 >= TTL×5：数据严重过期，标注"[C]-严重过期，不可依赖"
5. 如果是盘中（9:30-15:00），行情数据延迟>30s → 触发P2告警
6. 如果是盘后（18:00后），日线数据最后更新日期非当日 → 触发P2告警
```

### 4.6 时效性特殊规则

- **盘中11:30-13:00**：午休期间行情数据不更新属于正常，不算延迟
- **收盘后15:00-15:05**：收盘价刚确定，部分数据源可能有5分钟延迟，放宽至15分钟
- **财报空窗期**：季报截止日到下一个季报公告日之间，最新财务数据还是上一季度，不算过期
- **周末/节假日**：所有行情类数据不更新，不应告警

## 五、维度4：一致性（Consistency）

### 5.1 定义

一致性衡量同一数据在不同数据源中的差异程度。差异过大（超过阈值）可能表明某个数据源存在质量问题。

### 5.2 跨源一致性阈值

| 数据字段 | 对比源 | 正常阈值 | 警告阈值 | 严重阈值 |
|:--------|:------|:------:|:------:|:------:|
| 最新价 | 腾讯 vs 新浪 | <=0.1% | 0.1%-0.5% | >0.5% |
| 涨跌幅 | 腾讯 vs 新浪 | <=0.2% | 0.2%-1% | >1% |
| 成交量 | 腾讯 vs 新浪 | <=5% | 5%-15% | >15% |
| PE | 腾讯静态PE vs 计算PE(TTM) | — | — | — |
| K线收盘价 | 新浪K线 vs 腾讯K线 | <=0.1% | 0.1%-0.5% | >0.5% |

**PE特例说明**：腾讯返回的是**静态PE**（基于上年年报），而PE(TTM)是基于最近4个季度EPS滚动计算。两者差异可能是本质性的（不是数据错误），因此PE跨源对比的阈值不做硬性规定，只做信息标注：
- 如果`|腾讯静态PE - 计算PE(TTM)| / 计算PE(TTM) > 30%`：标注"静态PE与TTM PE差异显著，建议使用PE(TTM)"

### 5.3 一致性检查触发时机

- **常规触发**：盘前巡检时，对关注池中的3-5只代表性股票做跨源抽样
- **事件触发**：当评分/否决结果出现异常时，对涉及股票做全源数据一致性检查
- **异常触发**：当某个数据源连续2次异常时，对其返回数据做一次跨源验证

### 5.4 一致性差异的处理逻辑

```
1. 获取主源和备源的数据
2. 对关键字段计算差异率 = |主源值 - 备源值| / max(|主源值|, |备源值|, 0.01) × 100%
3. 分类：
   - 差异率 <= 正常阈值：正常，使用主源
   - 正常阈值 < 差异率 <= 警告阈值：记录差异，仍使用主源，标注"跨源微小差异"
   - 警告阈值 < 差异率 <= 严重阈值：P3告警，标注差异，建议用第三方源验证
   - 差异率 > 严重阈值：P2告警，"跨源数据严重不一致"，需人工审查
4. 连续3次差异>警告阈值 → 升级为P2，并审查数据源可靠性
```

### 5.5 内部一致性

同一数据源内部的字段之间应满足数学关系：

| 关系 | 公式 | 允许偏差 |
|:----|:----|:------:|
| 涨跌额 vs 涨跌幅 | ChangePct ≈ (Change/PrevClose) × 100 | <=0.05% |
| 成交额 vs 成交量×均价 | Turnover ≈ Volume × (High+Low+Close)/3 / 100 | <=10% |
| 市值 vs 价格×总股本 | MktCap ≈ Price × TotalShares | 允许差异（因总股本可能未及时更新） |

## 六、维度5：唯一性（Uniqueness）

### 6.1 定义

数据集中不应存在重复记录。重复记录定义为：同一代码+同一日期出现两次或以上。

### 6.2 去重键定义

| 数据类型 | 去重键 | 说明 |
|:--------|:------|:-----|
| Quote | Code | 每只股票在同一时刻只有一条行情 |
| KLine | Code + Date | 每只股票每天只有一条日K线 |
| Financial | Code + NOTICE_DATE | 每只股票每个报告期只有一条 |
| Sector | SectorCode | 每个板块只有一条排行数据 |
| FundFlow | Code + Date | 每只股票每天一条资金流向 |
| SectorFundFlow | SectorCode | 每个板块一条 |
| Research | Code + publishDate + orgName | 同一机构同一天对同一只股票只出一份报告 |

### 6.3 重复检测流程

```
1. 按去重键分组
2. 统计每组记录数
3. 记录数 = 1：正常
4. 记录数 > 1：重复 → 
   a. 如果是K线数据：保留时间戳最新的那条
   b. 如果是财务数据：保留NOTICE_DATE最新的那条
   c. 如果是行情数据：这是一个严重问题——同一时刻不应有两条不同行情
      → 保留最后获取的，触发P2告警"行情数据重复，可能缓存写入冲突"
```

### 6.4 重复阈值

- 重复率 = 重复的记录数 / 总记录数 × 100%
- 0%：正常
- 0% < 重复率 <= 1%：P4信息（少量重复，已自动去重）
- 1% < 重复率 <= 5%：P3注意（可能数据采集脚本重复运行）
- 重复率 > 5%：P2警告（数据采集流程可能存在问题）

## 七、维度6：有效性（Validity）

### 7.1 定义

有效性衡量数据是否符合业务规则约束。即使字段非空、数值准确，也可能违反业务逻辑。

### 7.2 通用业务规则

| 规则编号 | 规则描述 | 违反后果 |
|:------:|:--------|:--------|
| V-R01 | 收盘价必须在[最低价, 最高价]区间内 | P2 — 数据严重错误 |
| V-R02 | 最高价 >= 最低价 | P2 — 数据严重错误 |
| V-R03 | 开盘价必须在[最低价, 最高价]区间内 | P3 — 极端情况下开盘价可以等于涨跌停价，可能略超 |
| V-R04 | 非停牌日成交量必须 > 0 | P2 — 除非确认停牌 |
| V-R05 | 涨停日涨幅约等于板块涨跌幅上限 | P3 — 正常现象，非数据错误（但需标记） |
| V-R06 | 跌停日跌幅约等于板块涨跌幅下限 | P3 — 正常现象，非数据错误（但需标记） |
| V-R07 | 前收盘价不能为0 | P2 — 数据错误（除权除息日除外） |
| V-R08 | 可转债/ST股票的价格和涨跌幅规则不同 | P3 — 标记"特殊品种，标准规则不适用" |

### 7.3 涨停/跌停特殊处理

```
函数 IsLimitUp(code, changePct, prevClose):
  有效涨幅上限 = GetChangePctUpperBound(code)
  if changePct >= 有效涨幅上限 - 0.5%:
    返回 True  (触及涨停)
    进一步检查：涨停价 = Round(prevClose * (1 + 有效涨幅上限/100), 2)
    如果 Price == 涨停价：标注"封涨停"
    如果 Price < 涨停价：标注"触及涨停后回落"

函数 IsLimitDown(code, changePct, prevClose):
  有效跌幅上限 = GetChangePctUpperBound(code)  (取正数)
  if changePct <= -(有效跌幅上限 - 0.5%):
    返回 True  (触及跌停)
    进一步检查：跌停价 = Round(prevClose * (1 - 有效跌幅上限/100), 2)
    如果 Price == 跌停价：标注"封跌停"
```

### 7.4 财务数据业务规则

| 规则编号 | 规则描述 | 违反后果 |
|:------:|:--------|:--------|
| V-F01 | 营业总收入 > 0（正常经营公司） | 如果为0或负，标注"异常：营收为零或负" |
| V-F02 | 毛利率应在合理范围内（-50% ~ 95%） | 超出范围标注"异常毛利率" |
| V-F03 | 基本每股收益(BASIC_EPS)不能同时与净利润符号相反 | P3 — 检查数据正确性 |
| V-F04 | 净资产收益率(ROE)与EPS符号应一致（同为正或同为负） | P3 — 检查数据正确性 |
| V-F05 | 报告期应在12月/3月/6月/9月 | 否则标注"非标准报告期" |

### 7.5 K线数据有效性

| 规则编号 | 规则描述 | 违反后果 |
|:------:|:--------|:--------|
| V-K01 | K线日期必须单调递增 | P2 — 数据排序错误 |
| V-K02 | K线数据不应有未来日期 | P1 — 严重数据问题 |
| V-K03 | 除权除息日（如有）价格跳空不是数据错误 | 正常现象，不需告警 |
| V-K04 | 前复权K线的历史价格会变动 | 正常现象，标注"使用前复权数据" |

## 八、综合质量评分

### 8.1 单条数据质量评分

每次巡检后，对每条数据计算质量分：

```
质量分 = 100 - 扣分项合计

扣分项：
- 完整性：每个必填字段缺失 -5分
- 准确性：每个值域异常字段 -10分
- 时效性：TTL超标 -20分（过期不严重）/ -50分（严重过期）
- 一致性：跨源差异超警告阈值 -10分
- 唯一性：重复记录 -5分/条
- 有效性：每条业务规则违反 -15分

最低0分，最高100分
```

### 8.2 整体数据质量评级

| 质量分范围 | 评级 | 决策链允许度 |
|:--------:|:----:|:----------:|
| 95-100 | A 优秀 | 全部可用 |
| 85-94 | B 良好 | 可用，标注低分字段 |
| 70-84 | C 一般 | 可用，降级风险需标注 |
| 50-69 | D 差 | 仅做参考，决策需降级 |
| <50 | F 不可用 | 禁止进入决策链 |

### 8.3 质量趋势监控

玉夜应追踪以下趋势，当趋势恶化时提前告警：

```
监控指标（每日记录，取30日滚动窗口）:
1. API平均响应时间趋势（连续5日上升 → P4信息）
2. 字段非空率趋势（连续3日下降 → P3注意）
3. 缓存命中率趋势（从>90%降至<60% → P2警告）
4. 跨源差异率趋势（差异持续扩大 → P3注意）
5. 降级路径触发频率（从0次/周升至>3次/周 → P2警告）
```
