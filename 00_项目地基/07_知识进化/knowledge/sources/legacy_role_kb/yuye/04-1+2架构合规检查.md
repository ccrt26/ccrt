## 一、1+2架构定义

铁律量化项目强制要求每个数据字段必须按**三级降级链路**获取：

```
正常路径：   主API[1]  ──成功──▶  返回数据，写入缓存
              │
              │ 失败/超时/异常
              ▼
降级Level 1： 备API[B]  ──成功──▶  返回数据，写入缓存，标记[B]
              │
              │ 失败/超时/异常
              ▼
降级Level 2： 缓存[C]   ──可用──▶  返回数据，标记[C]+过期时间
              │
              │ 不可用
              ▼
降级Level 3： 缺失告警 ─────────▶  返回null，标注"数据不可获取"
```

### 1.1 架构原则

| 原则 | 说明 |
|:----|:-----|
| 必须尝试主源 | 每次数据请求必须先调用主API，不得跳过直达备源或缓存 |
| 失败记录可追溯 | 每次主/备/缓存切换必须有日志记录，含时间戳和失败原因 |
| 缓存不替代采集 | 缓存仅作兜底，不能因为"缓存有数据"而跳过API调用 |
| 恢复后自动切回 | 主API恢复正常后应自动切回主源，不能长期使用备源 |
| 独有源声明 | 无备源的数据必须在报告中标注"仅供参考" |

## 二、切换触发条件矩阵

### 2.1 主API→备API切换条件

以下任一条件满足时，触发从主API切换到备API：

| 编号 | 触发条件 | 判定标准 | 示例 |
|:---:|:--------|:--------|:-----|
| T01 | 超时 | 响应时间 > TimeoutSec | 腾讯行情>5s无响应 |
| T02 | HTTP错误 | 状态码 4xx/5xx | 503 Service Unavailable |
| T03 | 连接失败 | DNS解析失败/连接拒绝/网络不可达 | 服务器不可达 |
| T04 | 返回空数据 | Content为空字符串或null | qt.gtimg.cn返回空 |
| T05 | 格式异常 | JSON解析失败/字段结构不符合预期 | 返回HTML而非JSON |
| T06 | 全部字段为空 | 返回了数据结构但所有关键字段为null/0 | 全0行情数据 |
| T07 | 数据明显异常 | 主源数据与常识严重不符 | 贵州茅台PE=0.01 |
| T08 | API频率限制 | 返回错误码或空字符串，疑似被限流 | 东方财富空响应 |

### 2.2 备API→缓存切换条件

备API失败的条件与主API相同（T01-T08）。此外：

| 编号 | 额外条件 | 判定标准 |
|:---:|:--------|:--------|
| T09 | 备源不存在 | 该数据类型配置中无备源（如北向资金、研报、融资融券） |
| T10 | 备源版本不兼容 | 同花顺THS版本<1.18.63/akshare未安装 |

### 2.3 缓存→缺失告警切换条件

| 编号 | 触发条件 | 说明 |
|:---:|:--------|:-----|
| T11 | 缓存文件不存在 | 首次获取该数据且之前从未成功写入缓存 |
| T12 | 缓存已过期 | Age > TTL |
| T13 | 缓存文件损坏 | JSON解析失败、字段结构异常 |
| T14 | 缓存数据异常 | 缓存内容全null/全0/格式错误 |

## 三、当前实现的降级路径

### 3.1 完整路径配置

来自 `stock_data_fetcher.psm1` 的实际实现：

```
数据类型         主源                  备源                缓存TTL
──────────────────────────────────────────────────────────────
Quote          腾讯qt.gtimg.cn       新浪hq.sinajs.cn     1h
Quote(批量)     腾讯qt.gtimg.cn(批量)  逐只回退Get-StockQuote  1h
KLine          新浪money.finance     腾讯web.ifzq.gtimg    24h
Financial      东方财富datacenter     同花顺THS(akshare)    168h
Sector         东方财富push2          同花顺THS             6h
SectorConst.   东方财富push2          — (无备源)            6h
FundFlow(个)    东方财富push2          同花顺THS             6h
FundFlow(行)    东方财富push2          同花顺THS             6h
Northbound     东方财富datacenter     — (独有源)            168h
Research       东方财富reportapi      — (独有源)            24h
Margin         东方财富datacenter     — (独有源)            24h
PEPercentile   本地计算(依赖KLine+Fin) —                    168h
技术指标        本地计算               —                    实时计算
```

### 3.2 降级路径中的特殊处理

**批量行情降级**：当腾讯批量行情API失败时，不直接走缓存，而是逐只回退到单只的 `Get-StockQuote`，每只再走完整的「腾讯→新浪→缓存」链路。这意味着批量失败不等于整个行情获取失败。

**财务数据降级**：东方财富失败后，调用 `Invoke-ThsFallback -Action "financial"` 走THS桥接，所有THS调用出错会 Write-Warning 并继续尝试缓存。

**板块/资金流向降级**：东方财富失败后同样走THS桥接（sector_ranking / sector_fund_flow），THS输出与东方财富字段名不同但已做对齐。

## 四、合规检查清单

每次数据请求后，玉夜应自动检查以下项目。此清单是红线 §4 要求在数据层面的具体化。

### 4.1 逐请求合规检查

```
□ 本次数据请求使用的是什么数据类型？（Quote/KLine/Financial/...）
□ 实际使用的数据源是什么？（腾讯/新浪/东方财富/同花顺THS/缓存）
□ 是否尝试了主源？
  □ 是 → 主源成功/失败原因是什么？
  □ 否 → 为什么跳过主源？（红线违规，除非有明确的技术理由记录在案）
□ 如果使用了备源：
  □ 主源失败的原因是什么？（超时/错误码/空数据/格式异常）
  □ 是否记录了切换时间？
  □ 是否在返回数据中标记了[B]？
□ 如果使用了缓存：
  □ 备源失败的原因是什么？
  □ 缓存的时间戳是什么时候？
  □ 缓存是否在TTL内？
  □ 是否在返回数据中标记了[C]和过期时间？
□ 如果返回了null：
  □ 三级链路全部失败的原因分别是什么？
  □ 是否在报告中标注了"数据不可获取"？
```

### 4.2 合规状态追踪

玉夜应维护一个合规状态表：

| 数据类型 | 当前活跃源 | 主源状态 | 备源状态 | 最后一次切换时间 | 合规 |
|:--------|:--------:|:------:|:------:|:------------:|:---:|
| Quote | 腾讯 | 正常 | 正常 | — | ✅ |
| KLine | 新浪 | 正常 | 正常 | — | ✅ |
| Financial | 东方财富 | 正常 | 正常 | — | ✅ |
| Northbound | 东方财富 | 正常 | — | — | ⚠️ 独有源 |

### 4.3 严重违规识别

以下情况视为严格违规，需立即在报告中标注：

| 违规类型 | 严重度 | 判定标准 | 示例 |
|:--------|:----:|:--------|:-----|
| 跳过主源 | P1 | 直接使用缓存或备源且无记录的主源尝试 | 直接读缓存不调API |
| 长期使用备源 | P2 | 主源恢复正常后连续3次以上仍使用备源 | 新浪已恢复但一直用缓存 |
| 降级未标注 | P2 | 使用了备源/缓存但报告中未标注[B]/[C] | 报告写"数据来源：腾讯"实际用的缓存 |
| 缓存TTL配置错误 | P2 | 缓存TTL明显不符合数据特征 | 行情TTL=168h(7天) |
| 独有源未声明 | P3 | 使用了无备源的数据但未标注"仅供参考" | 北向资金数据未声明独有源 |

## 五、切换日志格式规范

### 5.1 标准切换日志条目

每次数据源切换发生时，应生成一条日志：

```json
{
  "Timestamp": "2026-05-23T09:35:00+08:00",
  "DataType": "Quote",
  "StockCode": "600036",
  "PrimarySource": "腾讯",
  "PrimaryResult": "Timeout-5s",
  "FallbackSource": "新浪",
  "FallbackResult": "Success",
  "CacheUsed": false,
  "DegradationLevel": 1
}
```

### 5.2 字段说明

| 字段 | 类型 | 说明 |
|:----|:----|:-----|
| Timestamp | ISO 8601 | 切换发生时间 |
| DataType | string | 数据类型（Quote/KLine/Financial等） |
| StockCode | string | 涉及的股票代码（如适用） |
| PrimarySource | string | 主源名称 |
| PrimaryResult | string | 主源结果：Success / Timeout-Xs / HTTP-XXX / Empty / ParseError / NetworkError |
| FallbackSource | string | 实际使用的源 |
| FallbackResult | string | 降级源结果 |
| CacheUsed | bool | 是否使用了缓存 |
| DegradationLevel | int | 降级等级：0=正常/1=备源/2=缓存/3=缺失 |
| CacheAge | string | 缓存年龄（仅在CacheUsed=true时） |
| Notes | string | 补充说明 |

### 5.3 日志存储位置

- 运行时日志：`$script:SourceUsed` 哈希表（内存中，进程级别）
- 持久化建议：每个交易日写入 `每日荐股/运营记录/source_switch_log_YYYYMMDD.json`

## 六、恢复检测机制

### 6.1 主API恢复检测

当主API处于异常状态、系统使用备源时，需定时检测主API是否恢复：

```
检测策略：
1. 每30分钟（非每次请求）对故障的主API发送一次探测请求
2. 探测请求使用轻量级查询（如行情API查询单只股票）
3. 连续3次探测成功后，判定主API已恢复
4. 自动切回主API（下一次数据请求即使用主源）
5. 记录恢复时间到日志

冷却期：恢复后5分钟内不重复切回（防止频繁切换）
```

### 6.2 恢复条件

| 主源故障类型 | 恢复判定条件 |
|:----------|:----------|
| 超时 | 连续3次探测均在TimeoutSec内响应 |
| HTTP错误 | 连续3次探测返回200 |
| 连接失败 | 连续3次探测连接成功 |
| 返回空数据 | 连续3次探测返回有效数据 |
| 格式异常 | 连续3次探测JSON/格式解析成功 |

### 6.3 恢复检测例外

以下情况不执行恢复检测：
- 非交易日（节假日、周末）
- 交易日的非交易时段（11:30-13:00午休）
- 已知的API维护窗口（如事先公告的东方财富维护时间）

## 九、玉夜执行1+2合规检查的操作指南

### 9.1 日常检查（自动化+人工复审）

```
1. 从 stock_data_fetcher.psm1 的 $script:SourceUsed 读取当前源状态
2. 如无法直接读取（不在同一PowerShell进程），检查 data_cache/ 文件的时间戳推断
3. 生成合规报告（使用第七章模板）
4. 如有P1/P2违规 → 在巡检报告的"阻断级"部分优先展示
5. 如有独有源未声明 → 在巡检报告的"提示级"部分提醒
```

### 9.2 不执行的操作

玉夜**不修复**1+2架构的代码问题（如修改stock_data_fetcher.psm1中的优先级配置），仅报告。修复指令交给Claude执行。

### 9.3 修复指令格式

当发现架构合规问题时，玉夜应输出可操作的修复指令：

```
问题：[严重度] 数据类型 X 已连续N次未尝试主源Y
影响：该类型数据完全依赖备源/缓存，违反红线§1.1
修复指令：请Claude运行 stock_data_fetcher.psm1 的 Test-AllDataSources
         检查主源Y的连通性，必要时重启PowerShell会话清除限流状态
```
