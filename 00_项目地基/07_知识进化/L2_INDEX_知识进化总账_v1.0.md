## 1. 五层知识结构

金融团队的知识体系分为五个层次，稳定性从左到右递减，更新频率从左到右递增：

| 层级 | 名称 | 回答的问题 | 稳定性 | 典型落点 |
|:-----|:-----|:-----------|:-------|:---------|
| L-K1 | 角色核心知识库 | 这个角色本来应该懂什么 | 高 | `.claude/agents/*-知识库/` |
| L-K2 | 场景适配器 | 角色知识在周报、日报、荐股、模拟交易中怎么输出 | 中 | `00_项目地基/07_知识进化/scenario_adapters/` |
| L-K3 | 后评估进化库 | 这次判断错了，应该生成什么更新候选 | 中 | `00_项目地基/07_知识进化/evolution_candidates/` |
| L-K4 | 反例库 | 哪些失败样本证明规则不能泛化 | 中高 | `00_项目地基/07_知识进化/counterexamples/` |
| L-K5 | 参数库 | 哪些阈值、窗口、权重需要版本化校准 | 中 | `00_项目地基/07_知识进化/parameters/` |

### 1.1 五层核心原则

| 原则 | 说明 |
|:-----|:-----|
| 稳定层不频繁改 | 东睦、周报、日报的单次变化不得直接冲击角色核心知识库 |
| 应用层可多场景适配 | 同一角色知识可以在周报、日报、荐股、模拟交易中有不同输出格式 |
| 学习层先收候选 | 后评估只能生成候选，不能直接写入核心规则 |
| 反例优先于硬改规则 | 单次失败先进入反例库；多次重复、跨样本成立，才考虑改规则 |
| 参数优先于逻辑重写 | 若问题是阈值过紧/过松，先修参数，不重写分析逻辑 |

### 1.2 五层关系图

```
                     ┌──────────────────────┐
                     │  L-K1 角色核心知识库  │  ← 稳定层
                     │  .claude/agents/     │  ← 角色确认后才能修改
                     └────────┬─────────────┘
                              │ 引用
              ┌───────────────┼───────────────┐
              │               │               │
     ┌────────▼──────┐ ┌─────▼──────┐ ┌──────▼───────┐
     │ L-K2 场景适配器│ │ L-K4 反例库│ │ L-K5 参数库  │  ← 应用层/数据层
     │ 报告怎么用    │ │ 失败在哪里 │ │ 阈值需校准  │
     └────────┬──────┘ └─────┬──────┘ └──────┬───────┘
              │               │               │
              └───────────────┼───────────────┘
                              │
                     ┌────────▼────────────┐
                     │ L-K3 后评估进化库    │  ← 学习层
                     │ KnowledgeUpdateCands │  ← 仅产出候选，不直接修改
                     └─────────────────────┘
```

## 3. KnowledgeUpdateCandidate 最小字段

正式 schema 见 `L2_SCHEMA_KnowledgeUpdateCandidate_v1.0.md`。此处为概览摘要：

| 字段 | 必填 | 说明 |
|:-----|:----:|:-----|
| candidate_id | 是 | 全局唯一 ID，建议 `KUC-YYYYMMDD-ROLE-XXXX` |
| source_type | 是 | weekly_report / daily_report / stock_pick / sim_trade / eval |
| source_ref | 是 | 来源文件、baseline、EvalHook 或报告路径 |
| stock_code | 否 | 涉及单一标的时填写 |
| scenario | 是 | 周报/日报/荐股/模拟交易/后评估 |
| owner_role | 是 | 首要确认角色 |
| related_roles | 否 | 需要联审的角色 |
| attribution_type | 是 | 数据/参数/权重/证据等级/分析逻辑/展示/执行/策略环境变化 |
| observed_failure | 是 | 后评估观察到的问题 |
| proposed_update | 是 | 建议更新内容 |
| target_layer | 是 | core / adapter / evolution / counterexample / parameter |
| confidence | 是 | low / medium / high |
| evidence_refs | 是 | 数据、公告、报告、后评估记录 |
| risk_if_applied | 是 | 若采纳可能造成的副作用 |
| risk_if_ignored | 是 | 若忽略可能重复发生的问题 |
| decision_status | 是 | proposed / role_review / approved / final_review / applied / rejected / parked / superseded / closed |
| final_decision_ref | 否 | 角色确认或审计记录 |

## 4. 候选状态机

```
                    ┌───────────┐
                    │ proposed  │  ← 后评估或人工提出候选
                    └─────┬─────┘
                          │
              ┌───────────┼───────────┐
              │           │           │
     ┌────────▼────┐    ╔══╧══╗    ┌─┴─────────┐
     │ role_review │    ║ REJ ║    │  parked   │
     │  角色评审中  │    ╚═════╝    │ 暂存待样本 │
     └────────┬────┘               └─────┬─────┘
              │                           │
     ┌────────┼──────────┐               │
     │        │          │               │
   ┌─▼──┐  ┌──▼───┐  ╔══╧══╗         │
   │APP │  │REJ   │  │park │         │
   └─┬──┘  └──────┘  └─────┘         │
     │                                │
   ┌─▼──────────┐                    │
   │final_review│  ← 腰子终审       │
   └─┬──────────┘                     │
     │                                │
   ┌─┼──────────┬─────────┐          │
   │ │          │         │          │
 ┌─▼──┐  ╔══╧══╗  ┌──▼───┐       │
 │app │  ║SUP  ║  │park  │       │
 └─┬──┘  ╚═════╝  └──────┘       │
   │                               │
 ┌─▼──┐                          │
 │clo │  ← 流程关闭              │
 └────┘                          │
                                  │
                                  │
 ┌─────────────────────────────────┘
 │ superseded → closed（被新候选替代）
```

| 状态 | 含义 | 允许下一步 | 负责角色 |
|:-----|:-----|:-----------|:---------|
| proposed | 后评估或人工提出候选 | role_review / rejected / parked | 提案者（执行模型/对应角色） |
| role_review | 对应角色评审中 | approved / rejected / parked | owner_role |
| approved | 角色确认可更新 | final_review | owner_role |
| final_review | 腰子终审（或阿黑终审非金融项） | applied / rejected / parked | 腰子 |
| applied | 已写入目标库并记录版本 | closed | 情墨 |
| rejected | 明确不采纳 | closed | 裁决者 |
| parked | 暂存，等待更多样本 | role_review / superseded | owner_role |
| superseded | 被新候选替代 | closed | — |
| closed | 流程关闭 | 不再流转 | 旧影审计确认 |

## 5. 流转规则

### 5.1 自动建议允许范围

系统或执行模型可以自动生成：

1. KnowledgeUpdateCandidate 草案。
2. 反例库候选条目。
3. 参数偏差统计。
4. 字段缺失、延迟、口径冲突提示。
5. 日报指令执行率统计。
6. 用户摘要返工模式统计。

### 5.2 必须人工确认范围

以下内容必须由对应角色确认，金融相关内容最终由腰子终审：

1. 核心知识库新增、删除、改写。
2. 状态机规则变化。
3. 否决项、降级项、恢复条件变化。
4. 信号升权、降权或移除。
5. 数据可用等级或权威源变化。
6. M 层宏观覆写阈值变化。
7. 场景适配器影响用户摘要或动作边界的变化。

### 5.3 腰子终审范围

| 终审范围 | 说明 |
|:---------|:-----|
| 核心知识库入库 | 金融规则、状态机、结论强度口径 |
| 参数库中涉及风控边界、否决项的参数 | 需要腰子和流金双签 |
| 证据等级规则变化 | 需要信鸽和腰子双签 |
| K-L2 适配器中涉及金融结论强度的描述 | 需要腰子确认 |
| 跨角色共识规则 | 腰子作为最终裁决 |

### 5.4 旧影审计范围

| 审计项 | 说明 |
|:-------|:-----|
| 来源检查 | 每个候选必须有 source_ref 和 evidence_refs |
| 分层检查 | target_layer 必须是五层之一 |
| 角色检查 | owner_role 必须与归因类型匹配 |
| 单次入库检查 | 单次报告结论不得直接进入核心知识库 |
| 签字检查 | 不得用执行模型代签角色确认 |
| 版本检查 | applied 后必须记录 final_decision_ref |
| 回溯检查 | 下次报告引用时必须能追到候选来源 |

## 6. 禁止自动写入（⛔ 红线）

任何自动流程都不得直接写入：

1. `.claude/agents/*-知识库/` 的核心知识文件。
2. 正式报告模板。
3. 正式风控规则。
4. 评分权重。
5. 否决项红线。
6. 生产调度入口。
7. 数据库、baseline、sidecar、eval records（不写真实数据）。

违反本条视为 P0 违规，自动触发旧影审计。
