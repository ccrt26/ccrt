# 重点股票产品化后评估与回测系统架构方案 v0.1

> 日期：2026-06-16
> 阶段：G2 架构方案候选
> 目标：把重点股票的深度分析、日报、后评估、回测、规则迭代，从“靠文档提醒”升级为“靠程序执行”的产品化闭环。
> 边界：本文是下一会话执行落地的设计输入，不直接修改生产规则，不直接放行任何回测结论。
> 外部建议吸收：已纳入豆包关于量化弱规则、单规则试点、数据可见性快照、事件型缺失、时间分层回测、动态样本门槛、角色交叉验证、极端行情切片、告警分级、规则可程序化分级、MVP核心子集等建议。架构层全部考虑，第一阶段按优先级落地。

---

## 1. 一句话定位

重点股票系统的完整产品链路应是：

```text
深度分析定规则
  -> 日报看变化
  -> 预测账本记录判断
  -> 特征服务读取当时可见数据
  -> 历史回测体检
  -> 前向后评估验证
  -> 偏差归因
  -> 专项回测验证新规则
  -> 规则候选进入治理
  -> 灰度/放行后反哺下一轮分析
```

核心原则：后评估和回测复盘的是“分析逻辑本身”，不是事后评价某只股票涨跌对不对。

## 2. 当前已有能力

### 2.1 已有业务能力

| 能力 | 当前状态 | 说明 |
|:--|:--|:--|
| 深度分析 | 已有 | v1.5 已经输出 baseline、signals、risk_flags、反证条件、日报承接字段 |
| 日报 | 已有 | v3.6 已经形成 baseline -> delta -> trigger 的日报结构 |
| 分层数据架构 | 已有 | 已经存在大量 K 线、财务、资金、事件、baseline 等数据资产 |
| 后评估方法文档 | 已有但偏旧 | 深度后评估 v1.0 仍偏“报告完整性打分”，未完全适配 v1.5 |
| 后评估脚本雏形 | 已有 | `代码文件/深度分析/*DeepEval*` 已有解析、计算、报告生成骨架 |

### 2.2 当前最大缺口

当前系统最缺的不是更多 Markdown 规则，而是程序化能力：

1. 预测判断没有统一结构化入账。
2. 回测和后评估缺统一特征服务层。
3. 缺历史回测体检和专项回测的统一引擎。
4. 每个环节缺程序化质量闸门、自动修复和主动告警。
5. 后评估发现还不能稳定生成 RuleUpdateCandidate，并进入治理流程。
6. 用户缺一个产品化驾驶舱，不应该靠翻审计报告发现问题。

## 3. 业务架构

### 3.1 业务层闭环

```text
深度分析：回答“这家公司中期怎么看、哪些条件会改变判断”
日报：回答“今天相对 baseline 发生了什么变化”
预测账本：记录“当时系统到底说过什么”
回测：回答“这类规则在历史上是否站得住”
前向后评估：回答“这套规则现在是否仍然有效”
偏差归因：回答“错在哪里，是数据、规则、假设、市场噪音还是承接错误”
规则候选：回答“是否值得提出规则修改，但不直接改规则”
治理灰度：回答“新规则是否经过回测、灰度、前向验证，能否放行”
```

### 3.2 角色分工

| 角色 | 职责 | 禁止事项 |
|:--|:--|:--|
| 阿黑 | 调度、派单、依赖检查、进度汇总 | 不做金融结论，不决定回测方法，不放行规则 |
| 青山 | 回测方法、因子评估、样本设计、统计方法、RuleUpdateCandidate 初稿 | 不直接修改规则资产 |
| 玉夜 | 数据口径、披露日、缺失、降级、未来函数检查 | 不用不可追溯数据支撑正式结论 |
| 流金 | 风险指标、回撤、止损、仓位影响、极端行情压力测试 | 不只看收益忽略风险 |
| 山猫 | 市场状态、政策周期、行业状态分层 | 不把单一市场状态结论泛化到全部市场 |
| 信鸽 | 公告、新闻、催化剂、事件数据结构化与来源验证 | 不把未验证事件当事实 |
| 腰子 | 金融业务总审，判断结论是否可进入规则候选 | 不跳过回测/灰度直接改规则 |
| 旧影 | 独立审计流程、证据、角色边界、结论越界 | 不代替业务角色做金融判断 |
| 红结/执行模型 | 代码实现、测试、运行证据 | 不签署 G5/G6 结论 |

### 3.3 角色交叉验证

回测不是阿黑单点调度，也不是单一角色闭门完成。每次正式回测必须形成角色交叉验证链：

| 发起/设计 | 必须交叉验证 | 硬条件 |
|:--|:--|:--|
| 青山设计回测方法 | 玉夜核对数据口径、披露日、未来函数 | 数据闸门不过不得运行正式回测 |
| 青山设定样本和统计方法 | 山猫核对市场/行业分层 | 无市场状态分层时不得下全局结论 |
| 流金设定风险指标 | 山猫核对牛熊震荡中的回撤标准 | 极端行情切片必须单独列示 |
| 信鸽提供事件数据 | 玉夜核对来源、时间戳、结构化字段 | 无来源/时间戳的事件不得进入正式统计 |
| 腰子判断规则候选 | 必须绑定回测质量闸门 PASS + 偏差归因明确 | 不允许主观绕过回测/灰度 |
| 旧影审计流程 | 检查角色越界、证据缺失、结论过度 | 审计不是业务放行，但可 BLOCK 越界流程 |

## 4. 系统架构

### 4.1 核心模块

| 模块 | 作用 | 程序化要求 |
|:--|:--|:--|
| 资产盘点器 | 扫描现有数据、规则、报告、脚本、baseline | 输出机器可读 inventory JSON |
| 预测账本 | 结构化记录深度分析和日报中的可验证判断 | 写入 EvalHook/PredictionLedger，不靠 Markdown 翻查 |
| 特征服务层 | 基于现有分层数据，按股票+日期返回标准特征 | 不重建数据仓库，只做统一口径计算与快照 |
| 历史回测引擎 | 启动体检回测和专项规则回测 | 同一引擎两种模式，避免两套口径 |
| 前向后评估引擎 | 自动检查到期预测并回填结果 | 按 T+1/T+5/T+20/T+60/T+120 滚动验证 |
| 偏差归因器 | 判断错误来源 | 输出数据/规则/假设/噪音/承接错误分类 |
| 数据需求闭环 | 缺数据时主动生成数据需求单 | 不直接放弃，也不乱抓未授权数据 |
| 规则候选生成器 | 后评估和回测触发规则候选 | 只生成候选，不直接改规则 |
| 质量闸门与自修复 | 每步输入/过程/输出检测，失败自动修复 | 3 次修复失败主动 BLOCK 告警 |
| 调度编排器 | 定时触发 + DAG 依赖启动 | 时间唤醒，依赖决定是否继续 |
| 产品驾驶舱 | 给用户看系统状态、风险、待处理事项 | 不要求用户翻审计报告找问题 |

### 4.1.1 资产盘点必须做规则可程序化分级

资产盘点不只列文件，还要把现有 Markdown 和脚本里的规则分成三类，决定第一阶段优先级：

| 分级 | 定义 | 示例 | MVP策略 |
|:--|:--|:--|:--|
| 完全可程序化 | 有明确字段、阈值、触发条件、验证标签 | MA20 破位、RSI 阈值、止损触发、质押比例 | 第一阶段优先落地 |
| 半可程序化 | 部分字段可抽取，但需要事件/语义判断 | 并购催化剂、订单超预期、政策强度 | 先做结构化入账和半定量分层 |
| 不可程序化 | 强依赖主观金融判断和文本推理 | 公司叙事、竞争格局长期变化 | 进入案例库，不作为第一阶段回测主对象 |

第一阶段禁止卡在半可程序化和不可程序化规则上。先跑通完全可程序化规则的产品闭环。

### 4.2 不再依赖 Markdown 执行

Markdown 只保留三类用途：

1. 方案接力和阶段记录。
2. 人读版报告。
3. 审计证据归档。

真正执行必须依赖：

1. JSON schema。
2. 程序入口。
3. 数据契约。
4. 自动质量闸门。
5. 可复现运行日志。
6. 驾驶舱状态输出。

### 4.3 预测账本判断类型

“可验证判断”必须按股票分析实操拆分类型，不能混在一个字段里。

| 判断类型 | 后评估口径 | 示例 | 最低字段 |
|:--|:--|:--|:--|
| 方向性判断 | T+N 收益符号、超额收益、是否跑赢基准 | 看多，T+20 目标收益 5% | direction、horizon、benchmark、confidence |
| 区间判断 | 价格是否落在预测区间，是否触及支撑/压力 | 支撑 10 元、压力 12 元 | lower_bound、upper_bound、touch_rule |
| 触发条件判断 | 条件是否触发，触发后收益/风险是否符合预期 | MA20 破位则止损 | trigger_condition、expected_action、post_trigger_window |
| 风险预警判断 | 风险灯触发后是否出现回撤/跑输/流动性恶化 | 质押黄灯后 T+20 跑输 | risk_flag、severity、risk_metric |
| 事件判断 | 事件是否落地、落地强度、落地后收益分布 | 并购落地、订单超预期 | event_type、event_stage、event_strength |

预测账本必须保存 `source_report_path`、`baseline_id`、`rule_version`、`data_snapshot_id`，否则后评估只能标为 WARN，不得进入规则候选。

## 5. 数据与特征设计

### 5.1 不重建数据仓库

“历史数据/特征库”不是单独再建一套数据仓库，而是在现有分层式数据架构上增加“特征服务层”。

```text
现有分层数据
  -> 标准特征计算
  -> 特征快照/索引
  -> 后评估/回测/驾驶舱调用
```

### 5.2 特征服务必须能回答的问题

按 `stock_code + trade_date + as_of_date` 返回：

| 类型 | 示例字段 |
|:--|:--|
| 技术特征 | MA5/MA20/MA60、RSI、MACD、布林、成交量、换手率 |
| 价格标签 | T+1/T+5/T+20/T+60 收益、最大回撤、是否触发止损 |
| 相对表现 | 相对沪深300、相对行业指数、相对重点股票池 |
| 风险特征 | 质押、解禁、股东人数、两融、北向、risk_flags |
| 财务特征 | 当时可见 EPS、ROE、毛利率、披露日、数据源 |
| baseline 特征 | baseline_id、关键支撑、压力、止损、valid_until |
| 事件特征 | 公告、订单、并购、政策、催化剂状态 |

### 5.2.1 第一阶段特征核心子集

第一阶段不追求一次覆盖所有数据。MVP 先做核心子集：

| 优先级 | 特征类别 | 是否进入第一阶段 | 理由 |
|:--|:--|:--:|:--|
| P0 | 技术特征 | 是 | MA20、RSI、MACD、成交量最容易标准化 |
| P0 | baseline 特征 | 是 | 深度分析和日报承接的核心 |
| P0 | risk_flags 基础特征 | 是 | 风控规则需要先验证 |
| P1 | 财务特征 | 延后 | 披露日、修正公告、口径复杂 |
| P1 | 事件特征 | 延后但先入账 | 先做半定量分层，不作为第一阶段主回测 |
| P2 | 拥挤度特征 | 延后 | 需要额外代理指标和方法校准 |

### 5.2.2 数据可见性快照库

为防隐性未来函数，特征服务必须建设“每日数据可见性快照库”。

快照库记录某个交易日盘后系统实际可获取的数据，而不是事后回补后的完美数据。

最低字段：

```text
snapshot_id
trade_date
generated_at
stock_code
available_sources
freshness_status
financial_data_available_as_of
event_data_available_as_of
northbound_status
margin_status
baseline_id
data_lineage_refs
```

回测时默认使用历史快照。若历史快照不存在，只能进入“重建快照”流程，并标记 `reconstructed_snapshot=true`，不得伪装为原始可见数据。

### 5.2.3 信息滞后参数

`get_features` 不只接受 `as_of_date`，还要区分数据可见和市场消化：

```text
get_features(stock_code, trade_date, as_of_date, market_lag_days=0)
```

| 参数 | 含义 |
|:--|:--|
| `trade_date` | 被分析的交易日 |
| `as_of_date` | 当时系统可见数据截止日 |
| `market_lag_days` | 市场消化延迟，适用于财报/重大公告后的 D+1/D+2 验证 |

注意：`market_lag_days` 不能替代披露日。先判断数据是否可见，再判断市场是否已消化。

### 5.3 数据科学底线

| 底线 | 说明 |
|:--|:--|
| 防未来函数 | 判断日只能使用当时已披露、已可见的数据 |
| 披露日优先 | 财务数据必须按披露日，不按报告期偷看 |
| 复权一致 | K 线回测统一复权口径 |
| 交易日历 | T+N 必须按真实交易日计算 |
| 停牌处理 | 停牌日不填虚假价格 |
| 幸存者偏差 | 尽量包含历史退市/ST/曾经在池股票 |
| 数据血缘 | 每个结论可追溯到数据源、快照、规则版本 |

## 6. 回测设计

### 6.1 两种回测模式

| 模式 | 触发 | 目的 |
|:--|:--|:--|
| 启动体检回测 | 阶段性主动运行 | 批量检查现有规则哪些天生弱 |
| 专项规则回测 | 后评估发现问题后触发 | 验证某个新规则候选是否值得灰度 |

两者必须使用同一套回测引擎和特征服务，避免口径分裂。

### 6.1.1 MVP 单规则试点

第一阶段不直接批量铺开，先选 1-2 个规则跑通全链路。

建议试点：

| 规则 | 类型 | 选择理由 |
|:--|:--|:--|
| MA20 破位止损 | 完全可程序化技术/风控规则 | 数据易得、触发明确、验证窗口清楚 |
| 质押/解禁 risk_flags 预警 | 风险规则 | 能验证风控规则是否真的有提前提示价值 |

试点必须跑通：

```text
资产盘点 -> 规则分级 -> 预测账本 -> 特征服务 -> 快照库 -> 回测 -> 弱规则量化结论 -> 告警分级
```

### 6.2 适合标准回测的数据

| 类别 | 示例 |
|:--|:--|
| 技术信号 | MA、RSI、MACD、布林、成交量、换手率 |
| 风控规则 | 支撑位、压力位、止损位、ATR 止损、MA20 破位 |
| 评分体系 | 六维评分、综合评分、评分阈值 |
| risk_flags | 质押、解禁、两融、北向、股东人数、大宗交易 |
| 仓位规则 | 风险灯与仓位折扣 |

### 6.3 更适合事件研究的数据

| 类别 | 方法 |
|:--|:--|
| 并购催化剂 | 事件日前后 T+5/T+20/T+60 表现 + 同行业对照 |
| 订单公告 | 公告落地状态、超预期/低预期、后续收益分布 |
| 政策利好 | 政策日期、行业指数、相关公司对照 |
| 公司叙事 | 案例库归因，不直接硬量化 |
| 竞争格局 | 定期复盘 + 事件研究，不做单一胜率结论 |

### 6.3.1 事件研究半定量分层

事件类规则不能只写案例描述，需要半定量分层，作为后续规则候选证据。

| 事件类型 | 分层字段 | 统计口径 |
|:--|:--|:--|
| 并购 | 意向/预案/过会/落地；金额占市值 >5% 或 <=5% | T+5/T+20/T+60 超额收益、回撤、落空率 |
| 订单 | 金额占营收比例、客户等级、是否超预期 | 事件后收益分布、同业对照 |
| 政策 | 全行业/细分赛道；征求意见/正式发布/补贴落地 | 行业指数 + 相关股票超额收益 |
| 产能 | 拿地/开工/投产/满产 | 事件链条阶段收益和证据等级变化 |

样本不足时只标 `OBSERVE`，不得写“事件规则无效”。

### 6.4 科学方法论

每次正式回测必须满足：

1. 先写假设，再跑数据。
2. 有训练集/验证集，优先 walk-forward。
3. 有对照组：沪深300、行业指数、未触发组。
4. 有市场状态分层：牛市、熊市、震荡市。
5. 同时看收益和风险：胜率、平均收益、超额收益、最大回撤、盈亏比。
6. 样本量不足不下确定性结论：小于 20 只/次只标观察。
7. 防过拟合：不追求孤立最优参数，优先稳定区间。
8. 输出失败样本，不只输出均值。
9. 固定规则版本和数据版本，保证可复现。
10. 按近 3 年、近 1 年、近 6 个月滚动窗口分层，识别规则时效性衰减。
11. 对极端行情单独切片，不能用常态均值掩盖极端失效。

### 6.4.1 时间分层回测

默认输出三层窗口：

| 窗口 | 目的 |
|:--|:--|
| 近 3 年 | 判断跨市场环境稳定性 |
| 近 1 年 | 判断当前市场阶段适配性 |
| 近 6 个月 | 判断近期是否衰减 |

若全历史有效但近 6 个月失效，规则不得进入“有效”清单，只能标为“历史有效、近期衰减”。

### 6.4.2 极端行情切片

回测引擎必须支持极端行情切片：

| 切片 | 用途 |
|:--|:--|
| 2015 股灾 | 检查趋势/止损规则在流动性冲击中的表现 |
| 2020 疫情冲击 | 检查突发事件和停牌/跳空处理 |
| 2022 加息/成长股杀估值 | 检查高估值成长股风险规则 |
| 项目运行期内单日极端波动 | 检查当代市场结构下的规则适配 |

极端切片结论不直接否定常态规则，但必须进入风险说明和仓位折扣建议。

### 6.4.3 动态样本门槛

样本量门槛按规则类型区分：

| 规则类型 | 最低样本 | 正式结论建议 | 额外要求 |
|:--|:--:|:--|:--|
| 技术信号 | >=20 | 初步可判 | 样本需跨至少 2 个月 |
| 风控规则 | >=20 | 初步可判 | 必须看最大回撤和止损后反向收益 |
| 评分维度 | >=60 | 较可靠 | 需要 IC/ICIR 或分层收益 |
| 事件规则 | >=10 | 仅半定量观察 | 必须按事件类型分层 |
| 财务规则 | >=20 个披露样本 | 初步可判 | 必须按披露日可见 |

若样本集中在单一月份或单一市场状态，即使数量达标也标 `OBSERVE_DISTRIBUTION_RISK`。

### 6.4.4 弱规则量化标准

弱规则清单必须有量化阈值，不允许只写“感觉弱”。

第一版建议阈值如下，后续应配置化：

| 规则类型 | 弱规则候选条件 |
|:--|:--|
| 技术规则 | 胜率 <40%，或 T+20 超额收益 <= -5%，或 IC <0 且样本达标 |
| 风控规则 | 止损触发后 T+5/T+20 反向收益 >8%，说明止损过紧或假破位多 |
| 支撑/压力规则 | 触及支撑后继续下跌概率 >60%，或触及压力后突破概率 >60% |
| risk_flags | 触发后未跑输基准且无更大回撤，连续样本达标后标为低预测力 |
| 事件规则 | 样本 <10 或收益分布无显著规律，只能标 OBSERVE，不标弱 |
| 评分规则 | 高分组 <= 低分组，或近 6 个月分层收益单调性失效 |

“弱”是进入复核和专项回测的起点，不等于立刻删除规则。

### 6.5 回测质量闸门

回测结果进入规则候选前，必须通过质量闸门：

| 检查项 | 失败处理 |
|:--|:--|
| 数据范围是否足够 | 不足则 OBSERVE，不生成规则候选 |
| 是否有未来函数 | BLOCK |
| 是否按披露日取财务数据 | BLOCK |
| 是否有对照组 | WARN 或 BLOCK，取决于规则影响 |
| 是否市场分层 | WARN，正式放行前必须补齐 |
| 是否样本量标注 | BLOCK |
| 是否可复现 | BLOCK |
| 是否记录失败样本 | WARN |
| 是否记录规则版本 | BLOCK |
| 是否做时间分层 | WARN，正式规则候选前必须补齐 |
| 是否做样本时间分布检查 | WARN |
| 是否输出弱规则量化原因 | BLOCK |

## 7. 数据缺失处理

数据缺失时不直接放弃，也不盲目下载。采用四段闭环：

```text
查本地已有数据
  -> 自动修复/重建
  -> 尝试已批准备用源
  -> 仍缺失则生成数据需求单
```

### 7.1 缺失分级

| 等级 | 示例 | 动作 |
|:--|:--|:--|
| 可自动补齐 | K 线缓存缺一天、特征快照缺失 | 自动重建 |
| 可备用源补齐 | 主源失败，备用源/本地历史可用 | 自动补齐并标记降级 |
| 无稳定来源 | 历史龙虎榜、历史质押明细、结构化公告事件 | 生成数据需求单 |
| 关键且不可替代 | 披露日财务、交易日历、复权价格 | BLOCK，不允许硬跑 |

### 7.1.1 事件型缺失与延迟验证

停牌、复牌、财报未披露、公告未落地，不等同于普通缺字段。

| 场景 | 处理 |
|:--|:--|
| 停牌 | 后评估窗口改为复牌后 T+N，并标记 `validation_delayed_by_suspension` |
| 复牌跳空 | 单独记录复牌首日跳空，不与普通日收益混算 |
| 财报未披露 | 未披露前标 `PENDING_DISCLOSURE`，不 BLOCK；最晚披露日 +1 后仍缺失再告警 |
| 事件未落地 | 标 `PENDING_EVENT`，按事件窗口继续追踪，不判错 |
| 数据源延迟 | 标 `STALE_SOURCE`，触发备用源或延后验证 |

### 7.2 数据需求单字段

数据需求单必须写清：

1. 缺什么数据。
2. 用于验证哪个规则。
3. 缺失影响哪些结论。
4. 需要多长历史。
5. 需要日频、周频、财报频还是事件级。
6. 是否必须带披露日。
7. 推荐 API 或数据源候选。
8. 是否需要 token/付费/授权。
9. 是否有可接受替代指标。
10. 不补数据时哪些回测只能 OBSERVE，不能 PASS。

## 8. 质量闸门、自动修复与主动告警

### 8.1 每个环节都要检测

| 环节 | 输入检查 | 过程检查 | 输出检查 |
|:--|:--|:--|:--|
| 数据入库 | 文件/接口/日期/字段 | 去重、交易日、复权 | schema、freshness、血缘 |
| 特征服务 | 数据是否可见 | 计算口径、未来函数 | 特征快照、缺失率 |
| 预测账本 | 报告/sidecar 是否存在 | 字段抽取、窗口生成 | EvalHook schema |
| 回测 | 样本、标签、对照组 | 分层、统计、过拟合 | 质量闸门、结果 JSON |
| 后评估 | 到期判断、数据标签 | 命中/偏离/无法判断 | 归因、状态、证据 |
| 规则候选 | 触发条件 | 回测/灰度证据 | RuleUpdateCandidate |
| 驾驶舱 | 全链路状态 | 聚合异常 | COMPLETE/AUTO_REPAIRING/BLOCK |

### 8.1.1 告警分级

用户侧告警分三级，不把所有问题都打成 BLOCK。

| 级别 | 含义 | 示例 | 用户动作 |
|:--|:--|:--|:--|
| WARN | 需关注，不影响主链路继续 | 样本量不足、非关键字段缺失、事件待验证 | 通常无需处理 |
| ALERT | 需干预或持续观察，系统可先自动修复 | 数据源降级、特征快照缺失、自动修复 1 次失败 | 观察或确认备用源 |
| BLOCK | 必须暂停下游 | 未来函数风险、关键数据缺失、修复 3 次失败、规则版本缺失 | 需要用户/API/权限或人工决策 |

驾驶舱仍可聚合为 COMPLETE/AUTO_REPAIRING/BLOCK，但详情里必须保留 WARN/ALERT/BLOCK。

### 8.2 自动修复规则

| 问题 | 自动修复 |
|:--|:--|
| 缓存缺失 | 重建缓存 |
| 特征快照缺失 | 重新计算 |
| 日期非交易日 | 按交易日历修正 |
| 非关键字段缺失 | 标记 WARN 并降级 |
| 主源失败 | 尝试备用源 |
| 输出 JSON 格式坏 | 重新生成 |
| 账本重复 | 幂等合并，不生成重复记录 |

自动修复最多 3 次。3 次仍失败，进入 BLOCK，主动告警并暂停下游依赖。

### 8.3 主动告警内容

BLOCK 告警必须包含：

1. 卡在哪个任务。
2. 哪个股票/日期/字段出错。
3. 已尝试哪些修复。
4. 哪些下游任务被暂停。
5. 是否需要用户确认数据源/API。
6. 最小恢复动作是什么。

不允许用“有审计报告”代替主动告警。

## 9. 调度与依赖

### 9.1 调度原则

采用“定时唤醒 + DAG 依赖编排”：

1. 定时任务负责唤醒。
2. 依赖检查决定是否继续。
3. 上游 BLOCK 时下游必须暂停。
4. 节假日、停牌、API 延迟由交易日历和 freshness gate 控制。

### 9.2 任务类型

| 类型 | 示例 |
|:--|:--|
| 定时任务 | 盘后行情入库、每日特征快照、日报生成、T+1 评估、周度深度分析、月度总结 |
| 依赖启动 | 数据入库 PASS 后算特征、日报 PASS 后写预测账本、窗口到期后触发后评估 |
| 事件触发 | 后评估发现问题触发专项回测、数据缺失触发数据需求单 |

### 9.3 时间通盘考虑

必须与全系统数据获取节奏统一：

1. 收盘数据稳定前不跑正式评估。
2. 北向、两融、财务延迟时不能当作 0。
3. 财报没披露不验证 EPS。
4. 行情接口失败不允许下游拿旧数据冒充新数据。
5. 周度深度分析生成后，自动排入 T+5/T+20/T+60 验证窗口。

## 10. 产品驾驶舱

驾驶舱不是审计报告，而是用户每天打开就能看懂的系统状态页。

### 10.1 必须展示

| 区块 | 内容 |
|:--|:--|
| 今日待看 | 哪些股票触发风险、反证、升级/降级 |
| baseline 状态 | 快过期、已过期、未承接、承接异常 |
| 到期评估 | 今天哪些 T+1/T+5/T+20/T+60 到期 |
| 规则健康 | 哪些规则胜率下降、IC 反向、样本不足、近期衰减、拥挤度升高 |
| 回测队列 | 启动体检、专项回测、数据缺口、BLOCK |
| 数据健康 | freshness、缺失字段、自动修复次数 |
| 告警中心 | WARN、ALERT、BLOCK、AUTO_REPAIRING、需要用户确认 |
| 规则候选 | 候选状态：待回测、待灰度、待审核、已驳回 |

### 10.1.1 规则拥挤度指标

拥挤度第一阶段不做完整模型，但驾驶舱要预留字段。

第一版可用代理指标：

| 指标 | 含义 |
|:--|:--|
| 同日触发数量 | 同一规则在重点股票池中触发的股票数量 |
| 同板块触发比例 | 同板块内触发同类信号的比例 |
| 连续触发天数 | 同一规则持续触发的天数 |
| 触发后成交放大 | 规则触发同时出现成交拥挤 |

拥挤度只作为风险提示，不作为第一阶段规则放行条件。

### 10.2 用户可见状态

只暴露三类总状态：

| 状态 | 含义 |
|:--|:--|
| COMPLETE | 当前链路完成，无需用户动作 |
| AUTO_REPAIRING | 系统正在自动修复，用户只需观察 |
| BLOCK | 多次修复失败或需要用户/API/权限决策 |

## 11. 落地步骤

### Step 1：资产盘点与入口冻结

目标：程序扫描现有数据、报告、baseline、脚本、规则入口，形成 inventory。

输出：

1. `keystock_system_inventory.json`
2. 可复用脚本清单
3. 缺口清单
4. 不改生产证明

验收：

1. 能列出深度分析、日报、baseline、数据源、现有后评估脚本。
2. 能标识哪些规则仍藏在 Markdown 中。
3. 能把规则分成完全可程序化、半可程序化、不可程序化。
4. 能给出第一阶段候选试点规则。

### Step 2：预测账本最小闭环

目标：深度分析和日报中的关键判断自动结构化入账。

输出：

1. PredictionLedger schema。
2. EvalHook 写入程序。
3. 去重和幂等逻辑。

验收：

1. 给定一份深度分析和一份日报，能生成 T+1/T+5/T+20/T+60 待验证记录。
2. 重跑不重复入账。
3. 能区分方向性判断、区间判断、触发条件判断、风险预警判断、事件判断。

### Step 3：特征服务层

目标：基于现有分层数据，按股票+日期返回标准特征和未来标签。

输出：

1. FeatureSnapshot schema。
2. `get_features(stock_code, as_of_date)` 程序入口。
3. freshness 和未来函数检查。

验收：

1. 能返回 MA/RSI/MACD、收益标签、risk_flags、baseline 信息。
2. 财务数据按披露日可见性处理。
3. 能读取或重建数据可见性快照。
4. 第一阶段只要求技术 + baseline + risk_flags 核心子集通过。

### Step 4：历史回测体检

目标：先完成单规则试点，再批量验证现有标准化规则。

输出：

1. backtest engine。
2. 启动体检报告 JSON/HTML。
3. 弱规则清单。
4. 单规则试点结果。

验收：

1. 先跑通 MA20 破位止损或质押/解禁 risk_flags 任一试点。
2. 通过回测质量闸门。
3. 样本不足项只标 OBSERVE，不下结论。
4. 弱规则清单必须带量化原因。
5. 输出近 3 年、近 1 年、近 6 个月分层结果。

### Step 5：前向后评估

目标：每天/每周自动回填到期判断。

输出：

1. due_eval scanner。
2. outcome backfill。
3. hit/deviation/insufficient 判定。

验收：

1. 到期任务自动发现。
2. 数据不足主动标注，不伪造结果。
3. 结果写回账本。

### Step 6：偏差归因与规则候选

目标：把“错了”拆成可处理原因，并生成规则候选。

输出：

1. attribution schema。
2. RuleUpdateCandidate schema。
3. 触发专项回测队列。

验收：

1. 能区分数据/规则/假设/噪音/承接错误。
2. 不能直接修改规则资产。

### Step 7：专项回测、灰度与驾驶舱

目标：新规则进入专项回测和灰度；用户看驾驶舱即可知道系统状态。

输出：

1. 专项回测模式。
2. 灰度验证记录。
3. 驾驶舱数据 API 或静态页面。

验收：

1. 后评估触发的问题能自动排队专项回测。
2. 驾驶舱能展示 COMPLETE/AUTO_REPAIRING/BLOCK。
3. 需要用户确认的数据源/API 会主动提示。

建议第一期只做到：

```text
资产盘点
```

第一阶段暂缓：

1. 完整财务特征回测。
2. 完整事件研究体系。
3. 完整拥挤度模型。
4. 全量驾驶舱 UI。
5. 规则正式放行。

## 14. 用户可见结论

本方案的核心是把重点股票系统升级为产品化流水线：

```text
程序记录判断
程序加工特征
程序执行回测
程序做后评估
程序自动修复
程序主动告警
角色参与方法与结论
```

目标不是多写文档，而是让系统长期为用户服务，并且能证明自己为什么可信。

## 15. 进一步补充：容易遗漏的系统工程问题

以下问题不一定都进入第一阶段实现，但必须进入总体架构视野。否则系统从原型走向产品时容易出隐性故障。

### 15.1 状态机与幂等

每个任务必须有明确状态机：

```text
PENDING -> RUNNING -> PASS/WARN/ALERT/BLOCK -> RETRYING -> RESOLVED/SUPERSEDED
```

要求：

1. 同一任务重复运行不生成重复账本。
2. 同一股票、同一日期、同一规则版本只能有一个权威结果。
3. 自动修复不能覆盖原始失败证据，只能追加修复记录。
4. 支持 replay：给定数据快照和规则版本，可重放当时结果。

### 15.2 存储与保留策略

需要区分短期缓存、权威快照、长期归档：

| 类型 | 用途 | 保留策略 |
|:--|:--|:--|
| 原始数据缓存 | API 原始返回、临时补数 | 可滚动清理 |
| 数据可见性快照 | 防未来函数、回测复现 | 长期保留 |
| 特征快照 | 回测/后评估标准输入 | 至少保留到相关规则退役后 |
| 预测账本 | 历史判断证据 | 长期保留，不删除，只 supersede |
| 回测结果 | 规则候选证据 | 长期保留 |
| 驾驶舱聚合 | 用户状态展示 | 可按月归档 |

### 15.3 API 权限、成本与限频

数据补齐不能只考虑“能不能取”，还要考虑权限、成本和稳定性。

必须记录：

1. API 来源和授权状态。
2. token/secret 是否就绪。
3. 调用频率限制。
4. 单次回填成本。
5. 失败重试策略。
6. 是否允许自动大批量下载。

涉及付费、敏感 token、批量下载的新数据源，必须进入用户确认或权限审批，不得静默接入。

### 15.4 安全与密钥管理

系统不得把 token、cookie、付费 API key 写入报告、日志或 Markdown。

要求：

1. 密钥统一走 secret loader 或环境配置。
2. 日志自动脱敏。
3. 驾驶舱只显示数据源状态，不显示密钥。
4. 数据源 BLOCK 时提示“缺授权/缺 token”，不泄露具体值。

### 15.5 测试体系

程序化系统必须有测试，不靠人工看报告。

最低测试分层：

| 测试 | 目的 |
|:--|:--|
| schema test | 输入输出字段正确 |
| unit test | 单个特征、指标、收益标签计算正确 |
| golden sample | 固定样例重跑结果不变 |
| synthetic case | 人造极端样本测试止损、停牌、缺失、未来函数 |
| integration test | 资产盘点 -> 账本 -> 特征 -> 回测 全链路 |
| regression test | 改代码后旧结果不无故漂移 |
| negative test | 故意缺字段/错日期，必须 WARN/ALERT/BLOCK |

第一阶段至少要有 schema test、golden sample、negative test。

### 15.6 LLM/文本解析风险

深度分析和日报目前大量信息在 Markdown 中，解析可能依赖正则或模型。

风险：

1. 正则漏提。
2. 模型误提。
3. 报告格式稍变导致字段消失。
4. 同一句话被解析成多个判断。

处理原则：

1. 能用 sidecar/schema 输出的字段，不从正文猜。
2. 正文解析只作为过渡能力。
3. 每条解析结果要带 confidence 和 source_span。
4. 低置信度字段进入 WARN，不进入正式回测。

### 15.7 股票标识与历史变更

需要处理：

1. 股票简称变化。
2. ST/*ST 状态变化。
3. 退市、暂停上市。
4. 复权因子变化。
5. 行业分类变更。
6. 重点股票池纳入/移出历史。

回测时不能只看当前股票池，否则会产生幸存者偏差。

### 15.8 交易成本与滑点

如果回测结论用于操作规则、止损、仓位折扣，就必须考虑交易成本。

最低需要：

1. 佣金/印花税估算。
2. 涨跌停无法成交处理。
3. 开盘跳空导致止损成交价偏离。
4. 停牌无法执行。
5. 大幅低开时的滑点。

纯分析规则可以先不做交易成本，但涉及“买/卖/止损/仓位”的规则必须至少标注是否已考虑交易成本。

### 15.9 配置与规则注册表

所有阈值都应配置化，不应散落在脚本里。

例如：

1. 弱规则阈值。
2. 样本量门槛。
3. T+N 验证窗口。
4. 告警等级。
5. 自动修复次数。
6. 规则试点清单。
7. 数据源优先级。

规则注册表必须带版本号、适用范围、生效日期、废止日期。

### 15.10 回滚、灰度和撤销

规则变更必须支持回滚。

要求：

1. 新规则先 shadow，不影响正式结论。
2. 灰度期新旧规则并行输出。
3. 灰度失败自动撤销候选。
4. 正式规则变更必须记录旧版本、原因、证据。
5. 回滚后能重放旧规则结果。

### 15.11 观测指标与SLO

产品化系统要有运行指标：

| 指标 | 用途 |
|:--|:--|
| 数据新鲜度 | 判断数据是否可用 |
| 任务成功率 | 判断流水线健康 |
| 自动修复次数 | 发现隐性不稳定 |
| BLOCK 数量 | 用户需要处理的压力 |
| 回测可复现率 | 判断科学可信度 |
| 预测账本覆盖率 | 判断分析是否被结构化记录 |
| 到期评估完成率 | 判断后评估是否按时执行 |
| 规则候选通过率 | 判断迭代质量 |

### 15.12 用户偏好与人工覆盖

系统为用户服务，需要支持少量人工偏好，但必须可追溯。

例如：

1. 用户不想看某类告警。
2. 某些股票临时提高关注优先级。
3. 用户临时要求某规则不参与操作建议。
4. 用户确认接入某个 API。

人工覆盖必须写入 override log，带时间、原因、影响范围和过期时间。

### 15.13 法务与数据授权边界

数据源接入需要注意授权和使用边界：

1. 不明来源数据不得进入正式回测。
2. 付费数据不得随报告明文外传。
3. 外部 API 的使用条款需留存摘要。
4. 生成报告时不得泄露原始授权数据。

### 15.14 第一阶段新增非功能验收

第一阶段除了业务验收，还要补充非功能验收：

1. 重跑同一任务结果一致。
2. 缺关键字段能主动 BLOCK。
3. 缺非关键字段能 WARN。
4. 自动修复失败 3 次后主动告警。
5. 不写入密钥。
6. 输出结果可追溯到数据快照和规则版本。
7. 至少一个 golden sample 可稳定复现。
