## 一、信息源可信度分级

信鸽将所有信息源按可信度从高到低分为5级：

| 级别 | 代码 | 类型 | 可信度 | 说明 | 示例 |
|:----:|:----:|:-----|:------:|:-----|:-----|
| S1 | official | 官方法定信息披露平台 | 最高 | 强制披露，法律背书 | cninfo.cn（巨潮资讯网） |
| S2 | regulatory | 交易所/证监会发布 | 高 | 监管机构公开发布 | 上交所/深交所/证监会公告 |
| S3 | company | 公司官方发布 | 高 | 公司官网、公众号，<br>但无法律强制力 | 公司官网、官方微信公众号 |
| S4 | media | 主流财经媒体 | 中 | 有编辑审核机制 | 财新网、证券时报、上海证券报 |
| S5 | rumor | 传闻、社媒、自媒体 | 低 | 无编辑审核，需交叉验证 | 雪球、微博、微信公众号推文<br>（信鸽默认不采此类来源） |

### 信息源选择原则

- 主源只取S1-S3级别，S4仅作辅助参考
- S5来源**默认不采集**——已列入L1黑名单域名
- 同一事件如果多源可用，以最高可信度源为准
- 若S1源不可用（cninfo API故障），依次降级到S2/S3
- 降级必须在事件JSON中标注 `data_source_fallback` 字段

## 二、1+2数据源架构与降级路径

### 数据源架构

```
主源 cninfo [16] ─────────── 成功 → 返回
  ↓ 失败
备源 china-stock-mcp [17] ── 成功 → 返回（标注fallback）
  ↓ 失败
缓存 [C] ────────────────── 命中 → 返回（标注cached）
  ↓ 失败
返回空（标注UNAVAILABLE）
```

### cninfo [16] — 主源

- 端点: `GET http://www.cninfo.com.cn/new/fulltextSearch/full`
- 参数: searchkey（股票名称URL编码）, sdate, edate, isfulltext=false
- 无需认证/API key
- 频率限制: 1s间隔（`cninfo_interval_ms: 1000`），低于500ms触发限流
- 重试策略: 指数退避 1s→2s→4s，最多2次重试
- 返回: 公告标题（去`<em>`标签）、毫秒时间戳、PDF URL、股票代码

### baostock [14] — 辅助源（业绩预告/快报）

- Python库桥接调用
- 市场前缀: 6开头→`sh.`，其他→`sz.`
- 频率限制: 500ms间隔
- 季报空窗期返回空，正常行为

### 缓存策略

| 层级 | 位置 | TTL | 清理 |
|:-----|:-----|:---:|:-----|
| L1 | `消息面数据/{date}_events.json` | 当日 | 不自动清理 |
| L2 | `消息面数据/events_db.json` | 永久追加 | 不清理 |
| L3 | `消息面数据/cache/{date}_cache.json` | 24h | >7天自动清除 |

缓存命中条件: 主源+备源均失败 → 读取当日cache → 未过期(TTL内) → 返回

## 三、采集纪律

### 来源声明确认

每条入库事件必须在 `source_level` 字段标明来源级别（S1-S5）:
- S1: 官方公告（cninfo）→ 无需额外验证
- S2: 监管信息 → 需提取监管文号
- S3: 公司发布 → 需确认公司是上市公司本身
- S4: 财经媒体 → 需标注来源媒体名称，不单独作决策依据
- S5: 传闻/社媒 → **信鸽不采**

### 未证实信息处理规则

| 场景 | 处理方式 | 标注 |
|:-----|:---------|:-----|
| 官方公告 | 直接入库 | source_level: "S1", confirmation_status: "confirmed" |
| 媒体报道但有官方来源 | 入库并注明来源链 | source_level: "S4", ref_source: "S1" |
| 媒体报道无官方来源 | 仅标注"媒体报道"，不写成事实 | confirmation_status: "unconfirmed" |
| 多源冲突 | 同时列出不同来源的观点，不取平均 | 标注 conflict: true |
| 纯传闻（S5） | 不采集，直接丢弃 | — |

### 多源冲突处理原则

1. 同一事件多个来源说法不一致 → **必须标注冲突**，不能自行选择一个版本
2. S1官方来源 vs S4媒体报道 → 以S1为准，标注媒体说法为"未获官方确认"
3. 多个S4媒体说法不一致 → 标注为"媒体报道存在分歧"，无法确认
4. 任何冲突在事件JSON中必须包含 `conflicting_sources` 数组
5. 冲突未解决前，输出模板中confirmation_status标记为 "disputed"

## 四、事件可疑时的三档输出

### WAIT / WARN / BLOCK 规则

当事件存在不确定性时，信鸽不得直接当做事实输出，必须使用以下三档标识：

| 标识 | 适用场景 | 含义 | 输出要求 |
|:----:|:---------|:-----|:---------|
| WAIT | 事件来源可信度低但有一定价值<br>（如S4媒体独家报道） | 暂不确认，保留观察 | 标注WAIT+原因+预计确认时间 |
| WARN | 多源冲突/信息矛盾<br>（如同一事件两个版本） | 数据质量存疑，使用者需自行判断 | 标注WARN+冲突详情+各源可信度 |
| BLOCK | 明显虚假/数据源异常<br>（如cninfo返回错误数据） | 事件不可用，阻止入库 | 标注BLOCK+原因，上报玉夜 |

### 三档使用示例

```
# WAIT 示例
EVT-20260610-03: 媒体报道某公司获大额订单（S4媒体独家，无S1官方确认）
  → source_level: "S4"
  → confirmation_status: "unconfirmed"
  → data_quality_flag: "WAIT"
  → wait_reason: "S4媒体独家报道，待S1官方公告确认"
  → expected_confirm_by: "2026-06-12"

# WARN 示例
EVT-20260610-04: 某公司业绩预告同比增长 vs 同比下降（不同媒体说法冲突）
  → source_level: "S4"
  → confirmation_status: "disputed"
  → data_quality_flag: "WARN"
  → conflict_detail: "财新报道增长20%，证券时报报道下降15%"
  → source_credibility: {"财新": "S4", "证券时报": "S4"}

# BLOCK 示例
cninfo API在非交易时间返回大量异常空白公告
  → data_quality_flag: "BLOCK"
  → block_reason: "cninfo返回异常空白数据"
  → 上报玉夜检查数据源
  → 事件不入库
```

## 五、数据质量自检清单

每次采集完成后，信鸽必须检查：

- [ ] 所有入库事件均有 `source_level` 字段（S1-S5）
- [ ] 所有入库事件均有 `confirmation_status` 字段
- [ ] S5来源事件已全部丢弃（检查L1丢弃计数）
- [ ] 多源冲突已标注 `conflict: true` + `conflicting_sources` 数组
- [ ] 可疑事件标注了 WAIT/WARN/BLOCK
- [ ] 数据源降级路径已记录（如有fallback）
- [ ] 缓存命中情况已记录
- [ ] 每层过滤丢弃计数已记录并合理
- [ ] 无任何事件将传闻/媒体报道写为"事实"
