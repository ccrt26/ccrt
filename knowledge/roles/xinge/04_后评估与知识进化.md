# 04 — 后评估与知识进化

> 知识库版本: v1.0 | 2026-06-10
> 关联: 03_输入证据与可信度规则.md, 02_核心判断框架.md, registry.json
> ⛔ 后评估是知识进化的核心机制。不评估，不进化。

---

## 一、为什么需要后评估

信鸽的采集和过滤规则不是一成不变的。随着市场环境变化、新的噪音模式出现、新的数据源接入，采集规则需要持续迭代。

后评估机制回答三个问题：
1. 信鸽之前的判断是否准确？（误报/漏报/过度解读）
2. 信息源的可信度判断是否需要调整？
3. 过滤规则（L1-L4）是否有盲区或过宽？

## 二、后评估类型

### 2.1 事后验证（常规）

**触发条件**: 事件发生T+N天后，由青山回填T+N excess_return数据

| 信鸽输出 | 事后实际结果 | 结论 |
|:---------|:-------------|:-----|
| 利好事件, probability=1.0 | 股价显著上涨 | 正确判断 |
| 利好事件, probability=1.0 | 股价下跌 | 判断偏差（可能是市场因素，不一定是信鸽问题） |
| 未采集到事件（漏报） | 发生了有影响的事件 | 漏报，需检查采集 |

**信鸽动作**: 阅读青山回填数据 → 标记事后验证结果 → 判断是否需要调整规则

### 2.2 误报 — 信鸽判断错误但事后证明是错的

| 场景 | 例子 | 根因排查 | 改进方向 |
|:-----|:-----|:---------|:---------|
| L2五问法误通过噪音 | 技术分析类标题含"MACD"被放行 | 检查黑名单关键词<br>MACD已在黑名单但regex未命中 | 扩展现有黑名单关键词 |
| L4误分事件类型 | 将"回购股份注销"分为"股东行为"而非"业绩" | 标签器优先级有问题 | 调整标签器匹配规则 |
| impact_score过高 | 例行公告分值过高 | weight或probability判断有误 | 调整权重/确定性判断 |
| P0误标 | 普通问询函被标为P0 | P0关键词regex过宽 | 缩小P0关键词范围 |

**信鸽动作**: 确认误报 → 记录反例 → 调整规则 → 验证

### 2.3 漏报 — 信鸽遗漏了重要事件

| 场景 | 例子 | 根因排查 | 改进方向 |
|:-----|:-----|:---------|:---------|
| L1黑名单误拦截 | 含"暴跌"关键词但实际是正式公告 | 黑名单关键词过宽 | 细化黑名单或调整regex |
| L2五问法未匹配 | 公告标题不含Q1-Q5任何关键词 | 检查被滤标题 | 扩展Q1-Q5的regex |
| 数据源异常 | cninfo当天返回为空 | 检查数据源状态 | 降级到备源或缓存 |
| 时间窗口不够 | 事件发生在3天前以外 | 检查lookback_days设置 | 调整窗口或补采 |
| 非重点股票 | 事件发生在非重点股票上 | 非信鸽采集范围 | 经腰子审批后加入股票池 |

**信鸽动作**: 确认漏报 → 记录反例 → 判断是否属于信鸽采集范围 → 调整规则

### 2.4 过度解读 — 信鸽给了过高权重

| 场景 | 例子 | 根因排查 | 改进方向 |
|:-----|:-----|:---------|:---------|
| impact_score过高 | 例行监管问询给分8.0 | category_weight或probability判断有误 | 降低对应子类权重 |
| 方向误判 | 将"计提减值准备"判为利好 | direction关键词有歧义 | 修正方向判断regex |
| 模式识别过度 | 非共振事件被标为板块共振 | pattern条件过宽 | 收紧模式触发条件 |

**信鸽动作**: 确认过度解读 → 记录反例 → 调整分值与规则

## 三、信息源可信度动态调整

### 调整原则

1. **单次事件不能直接升级或降级一个信息源的可信度级别**
   - 例: 某S4媒体独家准确报道了一件事 → 不能直接升级为S3
   - 例: 某S1源一次API异常 → 不能直接降级

2. **多次验证后进入候选列表**
   - 同一信息源被验证准确 >= 3次 → 进入"可信度升级候选"
   - 同一信息源被验证错误 >= 3次 → 进入"可信度降级候选"

3. **升级/降级需信鸽确认 → 腰子终审 → 旧影审计**
   - 信鸽整理升级/降级理由和数据
   - 提交腰子终审批准
   - 旧影在每周审计中检查变更记录
   - 变更后更新 registry.json 中的 source_level

### 可信度升降级条件

| 动作 | 条件 | 审批 |
|:-----|:------|:----|
| 升级 S4→S3 | 同一S4媒体连续5次以上准确报道（经事后验证），且无不实记录 | 腰子 |
| 升级 S3→S2 | S3来源持续30天以上稳定提供S1/S2级别独有信息 | 腰子+玉夜会审 |
| 降级 S3→S4 | S3来源连续3次失实或不准确 | 腰子 |
| 降级 S1→S2 | S1源持续异常/数据质量问题，需连续3天以上 | 腰子+玉夜+旧影会审 |
| 新增来源 | 新数据源引入 | 腰子终审 |
| 移除来源 | 来源失效/不再可信 | 腰子确认 |

## 四、反例库机制

### 反例登记格式

每次发现误报/漏报/过度解读，必须按以下格式记录：

```json
{
  "counterexample_id": "CE-{YYYYMMDD}-{序号}",
  "type": "false_positive|false_negative|over_interpretation",
  "date": "YYYY-MM-DD",
  "event_title": "事件标题",
  "stock_code": "600114",
  "expected": "预期应该发生/不应该发生什么",
  "actual": "实际发生了什么",
  "root_cause": "根因分析",
  "rule_impacted": "受影响的规则（如L1黑名单/L2 Q1-Q5/L4标签/P0判定/pattern）",
  "action_taken": "修复措施",
  "verified_by": "验证人",
  "status": "open|fixed|verified|closed"
}
```

### 反例存放位置

- 当前: 在知识库中引用反例ID
- 长期: 统一存放在独立的反例数据库（待Phase 2实现）

### 反例回顾周期

- 每周由旧影审计时检查本周新增反例及修复状态
- 每月由腰子主持召开反例回顾会，评估整体采集质量趋势

## 五、过滤规则迭代流程

### L1黑名单新增流程

```
发现新噪音模式
  ↓
检查是否可能误杀正式公告 → 可能误杀 → 暂缓，写入待定列表
  ↓
不误杀 → 新增到黑名单关键词/域名
  ↓
运行测试（回测历史数据检查误杀率）
  ↓
误杀率 <= 5% → 提交变更
误杀率 > 5% → 重新设计关键词
```

### L2 Q1-Q5扩展流程

```
收到误标反馈（L2应过未过 或 L2不应过却过了）
  ↓
分析被滤标题特征
  ↓
判断是否属于现有regex盲区
  ↓
是 → 扩展regex → 回测验证 → 提交变更
  ↓
否 → 误操作为"有意排除", 记录理由
```

### L4标签器调整流程

```
收到分类错误反馈
  ↓
检查标签器匹配优先级链
  ↓
确定问题来源（关键词缺失/优先级错误/新子类需要）
  ↓
修复 → 回测验证 → 提交变更
```

## 六、知识进化审批流程

所有知识变更（过滤规则、信息源可信度、标签体系等）必须经过以下审批链路：

```
信鸽确认 → 腰子终审 → 旧影审计
```

### 变更类型与审批

| 变更类型 | 信鸽 | 腰子 | 旧影 | 备注 |
|:---------|:----:|:----:|:----:|:-----|
| 黑名单新增关键词 | 自主 | — | 审计时检查 | 确认后即时生效 |
| Q1-Q5 regex扩展 | 自主 | — | 审计时检查 | 需附回测验证 |
| 标签器关键词补充 | 自主 | — | 审计时检查 | 需附回测验证 |
| 信息源可信度调整 | 建议 | 终审 | 审计 | 信鸽整理数据，腰子签批 |
| P0定义标准变更 | 建议 | 终审 | 审计 | 涉及风控，须流金会签 |
| impact_score权重 | 建议 | 终审 | 审计 | 需青山提供验证数据 |
| 新数据源引入 | 建议 | 终审 | 审计 | 需玉夜合规评估 |
| 重点股票池变更 | 不参与决策 | 终审 | 审计 | 信鸽仅执行采集 |

## 七、知识进化周期

| 周期 | 动作 | 负责人 |
|:-----|:------|:-------|
| 每次采集后 | 自查: 检查当日采集日志是否有异常 | 信鸽 |
| 每周 | 回查: 结合青山T+N验证数据，检查是否有误报/漏报 | 信鸽+青山 |
| 每月 | 回顾: 反例汇总、信息源可信度评估、规则迭代建议 | 腰子主持，全团 |
| 按需 | 紧急修复: 发现重大漏报或系统性问题 | 信鸽+腰子 |

### registry.json 同步

每次知识条目变更（新增/修改/废弃）后，必须同步更新 registry.json：
- 新增条目: 新增 entry + 更新 meta.total_entries
- 修改条目: 更新 review_date + status
- 废弃条目: 设置 status 为 "deprecated" + 记录 deprecation_reason + 更新 valid_until
- 升级条目: 更新 upgrade_condition + status
