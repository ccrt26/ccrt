# 角色知识库与六库融合规则 v1.0

> **本政策定义角色知识库与六库（信号胜率库/后评估库/反例库/参数库/来源等级库/模板污染库）的职责分工与协作规则。**
> 核心原则：角色知识库保存稳定认知，六库保存学习证据和质检记录。
> 生效日期：2026-06-10
> 维护人：青山 | 审计人：旧影

---

## 1. 核心分工

### 1.1 角色知识库（L-K1）
**定位**：角色的当前稳定认知
**内容**：
- 该角色领域的专业方法论
- 已验证的信号和因子知识
- 角色职责和边界
- 输出模板和表达约束
- 经过知识进化流程升级的成熟内容

**特征**：
- 是角色启动时的默认读取范围
- 是角色做出判断的主要依据
- 不能绕过六库自我改写
- 修改须经知识进化流程

### 1.2 六库（L-K2 ~ L-K5 的辅助记录）
**定位**：角色的学习账本和质检系统
**包含**：
| 库名 | 用途 | 负责人 |
|------|------|--------|
| 信号胜率库 | 记录信号实际表现，服务青山 | 青山/腰子 |
| 后评估库 | 记录判断之后的事实反馈 | 玉夜/腰子 |
| 反例库 | 记录失败案例，防止单次失败直接改核心规则 | 旧影/青山 |
| 参数库 | 记录可调整的阈值、窗口、权重、证据有效期 | 青山/腰子 |
| 来源等级库 | 判断知识来源是否可靠 | 青山/旧影 |
| 模板污染库 | 检查角色输出是否过度表达、空话、强结论、动作越界 | 旧影 |

**特征**：
- 记录学习证据、错误、参数和质检结果
- **不直接替代角色知识库**
- **不自动修改角色核心知识**
- 不作为角色启动上下文的默认全量加载内容
- 通过知识进化流程与角色知识库协作

## 2. 六库使用规则

### 2.1 角色启动时
- 角色默认读取：角色知识库（本目录 `knowledge/roles/<角色名>/`）
- 六库不作为角色自动启动加载内容
- 特定任务需要查阅六库时，按 README 中的任务类型路由读取对应模块

### 2.2 六库与角色知识库的读/写关系
| 操作 | 可读写六库 | 可读写角色知识库 |
|------|-----------|----------------|
| 日常运行（判断/输出） | 读（查阅参考） | 读（判断依据） |
| 出现分析偏差 | 写（记录偏差） | 不可直接写 |
| 完成一次后评估 | 写（记录结果） | 不可直接写 |
| 参数需要调整 | 写（参数候选） | 不可直接写 |
| 发现新型失败模式 | 写（反例候选） | 不可直接写 |
| 信号胜率明显变化 | 写（更新记录） | 不可直接写 |
| 知识进化候选确认（多次验证后） | 读（查阅记录） | 写（升级核心知识） |

**核心规则**：角色在运行过程中发现新证据时，先写入六库；六库中的多个一致证据积累到门槛后，通过知识进化流程升级进角色知识库。

### 2.3 知识进化流程（六库 → 角色知识库）
```
[后评估/复盘/分析偏差] → 写入六库记录
       ↓
积累多次一致证据（≥阈值）
       ↓
青山评估 → 提出知识更新候选
       ↓
角色确认（青山自评或跨角色讨论）
       ↓
腰子终审（涉及动作支持或战略变化时）
       ↓
旧影审计（独立审计）
       ↓
更新角色知识库
       ↓
registry.json 更新
```

**阈值参考**（以信号胜率为例）：
- 信号类型确认：≥20条
- 参数候选确认：≥8个样本
- 失败模式确认：≥3次同类失败
- 核心知识升级：≥5次一致正反馈或无反对票

## 3. 六库内容升级条件

### 3.1 信号胜率记录 → 青山信号知识

| 条件 | 说明 |
|------|------|
| 样本量达标 | 信号类型确认≥20条 |
| 胜率稳定 | 累计胜率方向一致且无明显震荡 |
| 无反例 | 在同类型失败模式中无反向证据 |
| 后评估确认 | 至少3次后评估为正 |
| 腰子审批 | 提升来源等级须腰子终审 |

### 3.2 后评估记录 → 青山规则调整

| 条件 | 说明 |
|------|------|
| 失败模式可归因 | 明确归因到分析逻辑/参数/外部环境 |
| 同类失败≥3次 | 单次失败不进规则调整 |
| 有修正候选 | 青山提出具体调整方案 |
| 模拟验证正反馈 | 调整后模拟表现改善 |
| 腰子审批 | 涉及输出强度或动作支持时 |

### 3.3 反例 → 青山知识

| 条件 | 说明 |
|------|------|
| 同类型反例≥3次 | 单次反例不直接改核心规则 |
| 归因清晰 | 明确是角色知识问题而非外部偶发 |
| 有修正方案 | 青山提出如何避免再次出现 |
| 正面验证 | 修正后未见该类反例 |

### 3.4 参数记录 → 青山参数知识

| 条件 | 说明 |
|------|------|
| 参数调整使改善持续 | 连续≥5次正向差异 |
| 回撤不增加 | 参数调整未引入额外风险 |
| 腰子审批 | 参数变更涉及阈值调整 |

## 4. 禁入规则

以下内容**不得**直接进入角色知识库：
1. 大模型临时推理结果（除非经过来源补强和角色确认）
2. 外部文献原文（必须浓缩并标注来源）
3. 六库原始记录（必须经过知识进化流程）
4. 单次后评估结果（单次失败/成功不直接改核心规则）
5. L5-seed 的知识以 core 状态入库（L5-seed 只能为 reference 或 candidate）
6. 未经角色确认的外部资料引用
7. 未经腰子审批的动作支持规则
8. 未经旧影审计的知识升级

## 5. 角色知识库与六库的映射关系

角色知识库中的每条知识，都应在 registry.json 中标注：
- `related_six_library`：关联的六库记录路径（可选）
- `upgrade_condition`：从六库升级到核心知识的条件（如适用）

六库中的每条记录，最终升级进角色知识库时：
- 保留原始六库记录作为审计追溯
- 在 registry.json 中标记 related_old_files
- 在 deprecated_refs.md 中记录旧文件引用关系

## 6. 六库不被合并为角色知识的声明

### 6.1 为什么六库不能作为角色知识库
1. **定位不同**：六库是学习账本，记录的是过程中的证据和错误；知识库保存的是稳定认知。
2. **内容性质不同**：六库包含大量低置信度、未验证、临时性的记录；知识库需要高置信度和稳定性。
3. **更新机制不同**：六库是日常写入的日志系统；知识库是经过审批的稳定系统。
4. **上下文成本**：六库全量加载到角色上下文中将造成大量 token 浪费，且其中大部分是低价值参考信息。
5. **审计追溯**：将学习过程记录与稳定知识分离，有利于审计和错误定位。

### 6.2 六库的正确效用
- 让青山知道自己在哪些信号上有持续成功的记录
- 让青山知道自己在哪些情况下犯过系统性错误
- 让青山知道哪些参数曾经有效、哪些无效
- 让青山知道当前知识的来源可靠性
- 让旧影检查青山是否有过度表达或空话

六库的作用是**帮助青山变得更聪明**，而不是**替代青山现有的知识**。

---

## 7. 一句话总结

> **角色知识库保存稳定认知；六库保存学习证据和质检记录；知识进化流程负责把六库中的成熟学习成果升级进角色知识库。**
