## 一、问题诊断

### 1.1 当前架构反模式

```
当前状态：双轨混杂，无统一编排

crontab (macOS)                  Claude scheduled_tasks
     │                                    │
45 9 * * 1-5                      ┌─ 9:17 周一 玉夜巡检提醒
sim_orchestrator.py               │─ 15:37 周一至五 日报(10只股票全团咨询)
                                  │─ 20:30 周五 深度分析(10只股票)
                                  │─ 每小时 git自动清扫
                                  └─ 9:35 周一至五 模拟交易引擎
```

**五个核心缺陷**：

| # | 缺陷 | 严重度 | 影响 |
|:--:|:-----|:------:|:-----|
| D1 | Claude Code = 调度平台 + 分析工具，角色冲突。Claude退出→5个任务静默丢失 | P1 | 日报/深度分析/git清扫全部停摆，无告警 |
| D2 | 无数据就绪前置检查。日报15:37盲跑，若收盘数据未刷新则用缓存兜底 | P2 | 报告数据可能不是最新收盘价 |
| D3 | 任务间无显式依赖。深度分析20:30不检查信鸽19:00采集是否完成 | P2 | 事件面章节数据缺失 |
| D4 | 千光知识库设计(Windows Task Scheduler + daily_workflow.ps1)与Mac实现(crontab + Claude tasks)已分叉，无文档记录 | P2 | 设计和实现不一致 |
| D5 | 无心跳监控。任何环节失败都静默 | P1 | 失败不可观测 |

### 1.2 反模式匹配

- **AP-04 静默失败**（匹配）：Claude退出→任务全部丢失，无告警
- **AP-06 设计-实现分叉**（匹配）：千光DAG vs 实际crontab配置
- **AP-03 上帝模块**（部分匹配）：Claude Code承载了调度+分析+通知三种职责

## 二、设计方案

### 2.1 核心原则：调度与分析分离

```
┌─ L0 系统调度层 (crontab) ─────────────────────────────┐
│  职责：触发、监控、告警                                  │
│  机制：crontab + bash/Python轻量脚本                     │
│  不依赖Claude Code                                      │
│                                                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │          daily_orchestrator.py (统一入口)          │  │
│  │                                                  │  │
│  │  交易日检测 → 数据就绪检查 → 任务DAG执行           │  │
│  │  超时控制 + 重试 + 降级 + 日志 + 锁                │  │
│  └──────────────────────────────────────────────────┘  │
│                         │                              │
│         ┌───────────────┼───────────────┐              │
│         ▼               ▼               ▼              │
│  ┌────────────┐ ┌────────────┐ ┌────────────┐         │
│  │ L1 计算层  │ │ L1 计算层  │ │ L2 分析层  │         │
│  │ Python脚本 │ │ Python脚本 │ │ ClaudeCode │         │
│  │ 数据/评分  │ │ PDF/git    │ │ AI判断     │         │
│  └────────────┘ └────────────┘ └────────────┘         │
│                                                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │          scheduler_health_check.py (心跳监控)      │  │
│  │          每30分钟检查 → 异常写日志                  │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

### 2.2 分层职责

| 层 | 负责 | 机制 | 可靠性 | 任务 |
|:--:|:-----|:-----|:------|:-----|
| L0 | 系统调度 | crontab | 极高（OS级） | 触发、心跳监控 |
| L1 | 确定性计算 | Python脚本 | 高（无AI依赖） | 数据拉取、评分、PDF生成、git清扫、信鸽采集 |
| L2 | AI判断 | Claude Code API | 中（取决于API） | 日报人话结论、深度分析、全团咨询 |

## 三、接口契约

### 3.1 daily_orchestrator.py

```
输入:
  --date YYYYMMDD          当日日期（默认当天）
  --mode daily|deep|all    执行模式
  --skip-data-check        跳过数据就绪检查（测试用）

输出:
  exit 0  全部成功
  exit 1  部分失败（降级完成）
  exit 2  全部失败（需人工介入）

日志:
  每日荐股/运营记录/orchestrator_YYYYMMDD.log

依赖脚本（调用，不修改）:
  - 代码文件/tools/batch_gen_daily_pdfs.py
  - 代码文件/tools/batch_gen_keystock_pdfs.py
  - 代码文件/tools/health_check.py (数据就绪检查)
  - 代码文件/信鸽信息采集/pigeon_collector.py (事件采集)

锁文件:
  每日荐股/运营记录/.locks/daily_orchestrator.lock
  超时: 3600s (1小时)
```

### 3.2 scheduler_health_check.py

```
输入: 无

输出:
  exit 0  健康
  exit 1  警告（写日志）
  exit 2  异常（写日志+标记）

检查项:
  1. 最近一次日报PDF生成时间 < 24h（交易日）
  2. 最近一次git自动清扫成功时间 < 2h
  3. 磁盘剩余空间 > 1GB
  4. crontab条目数 >= 预期值
  5. 数据缓存文件最近修改时间 < 24h（交易日）

日志:
  每日荐股/运营记录/health_check_YYYYMMDD.log
```

### 3.3 数据就绪检查（内嵌于daily_orchestrator）

```
检查逻辑:
  1. 选取3只代表性股票（600114东睦股份, 601727上海电气, 002230科大讯飞）
  2. 调用腾讯API [1] 获取最新价
  3. 对比缓存中的上一日收盘价
  4. 若3只中有>=2只价格与缓存不同 → 数据已刷新
  5. 若未刷新 → 等待900s (15min) 后重试，最多重试4次 (到16:30)
  6. 最终仍未刷新 → 标记[C]降级，继续执行

API调用间隔: >= 0.3s (红线§3.2)
```

## 四、Token影响评估

### 4.1 当前Token消耗（估算）

| 任务 | 频率 | 单次Token | 月Token |
|:-----|:----:|:---------:|:-------:|
| 日报(10只股票全团咨询) | ~22天/月 | ~80K | ~1,760K |
| 深度分析(10只股票) | ~4次/月 | ~200K | ~800K |
| git自动清扫 | ~720次/月 | ~2K | ~1,440K |
| 模拟交易引擎 | ~22天/月 | ~10K | ~220K |
| **合计** | | | **~4,220K/月** |

### 4.2 优化后Token消耗（估算）

| 任务 | 频率 | 单次Token | 月Token | 变化 |
|:-----|:----:|:---------:|:-------:|:----:|
| 日报(Python生成骨架+Claude做人话结论) | ~22天 | ~30K | ~660K | -62% |
| 深度分析(Claude全量，但串行可靠) | ~4次 | ~200K | ~800K | 不变 |
| git自动清扫(Python脚本，不进Claude) | ~720次 | 0 | 0 | -100% |
| 模拟交易引擎 | ~22天 | ~10K | ~220K | 不变 |
| **合计** | | | **~1,680K/月** | **-60%** |

### 4.3 Token节约机制

1. **git自动清扫**：从Claude scheduled_task迁移到crontab+Python脚本，零token消耗
2. **日报**：盘面数据/信号变化/基本面数据由Python脚本填入模板，Claude Code仅做人话结论+策略判断+情景应对（约40%的原token量）
3. **数据就绪检查**：Python脚本执行，不进Claude Code

## 五、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|:-----|:----:|:----:|:-----|
| crontab条目配置错误 | 低 | 高 | 红枫部署时逐条验证，保留旧配置备份 |
| daily_orchestrator.py脚本bug | 中 | 中 | 影子运行一周，与当前系统并行对比 |
| Claude Code API调用失败 | 中 | 中 | L1脚本生成完整MD骨架，API失败时MD仍可用，标记[AI分析未完成] |
| 信鸽采集crontab触发但脚本失败 | 低 | 中 | orchestrator启动前检查events_db新鲜度，过期则重试采集 |
| crontab与Claude scheduled_tasks同时触发 | 低 | 低 | 迁移时先删Claude任务，再添加crontab |
| 机器休眠/重启导致错过的任务 | 低 | 中 | @reboot crontab触发补跑检查（后续迭代） |

## 六、与千光知识库的对齐

千光知识库 `02-定时任务编排.md` 中的DAG设计是本次设计的参照基准，差异如下：

| 维度 | 千光设计 | 本次设计 | 原因 |
|:-----|:---------|:---------|:-----|
| 调度器 | Windows Task Scheduler | macOS crontab | 实际运行环境是Mac |
| 调度脚本 | daily_workflow.ps1 | daily_orchestrator.py | Python跨平台，Mac原生支持更好 |
| 评分引擎 | 在调度链路中 | 不在本次范围 | 评分引擎已有独立调度 |
| 盘前巡检 | 08:00触发 | 不在本次范围 | 当前日报/深度分析是盘后任务 |
| 三层分离 | 概念层 | 物理层 | 本次显式分离L0/L1/L2，千光设计中隐含 |
