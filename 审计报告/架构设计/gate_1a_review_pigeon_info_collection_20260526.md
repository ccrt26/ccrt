## 全团咨询记录

### ① 山猫 — 宏观/政策/情绪判断

**评估结论**: ✅ PASS

- 数据源方案认可：行业政策层信息由WebFetch采集(每周2次)，频率合理
- L3增量性检查设计正确：与我之前提出的"增量性+可传导性+时效窗口"三标准一致
- L3中对研报"无评级调整+无盈利预测修正→丢弃"的规则，建议补充：首次覆盖研报即使无调整也应保留（首次覆盖本身是信号）
- 建议：L3去重相似度阈值从80%调为70%，避免遗漏同一事件的跟进公告（如收购从"预案"→"草案"→"注册稿"，标题相似但内容增量不同）

### ② 玉夜 — 数据可用性/1+2合规

**评估结论**: ✅ PASS (有建议)

- cninfo JSON API作为新主源[16]：需补充具体的重试策略和超时参数（设计中已有，确认OK）
- 1+2架构完整：cninfo[16]主→china-stock-mcp[17]备→缓存[C]兜底
- baostock[14]业绩预告/快报复用：现有桥接脚本已验证可用
- 建议：cninfo API频率限制目前未知（设计假设1s间隔），Phase 1前5个交易日需实测记录实际限速阈值
- 建议：china-stock-mcp 50次/天配额分配需写入配置（6股×4类=24次，+备源5次，余21次给其他用途）
- ⚠️ 数据源全景(01)和频率限制表(07)需更新，新增[16][17]

### ③ 流金 — 风险评估/红线边界

**评估结论**: ✅ PASS

- P0事件强制入库机制设计正确，四类事件（立案/ST/全部质押/重组失败）覆盖了最高风险场景
- 每日每只股票≤5条上限合理，防止消息过载导致AI误判
- ⚠️ 建议增加一条红线：P0事件入库后，必须在当日操作简报中强制显示，不能被"≤5条上限"挤出
- 黑名单域名设计正确，guba/雪球/贴吧等噪音源已封堵
- 建议：L4 impact_score算法需要明确权重分配，避免主观打分。建议公式：`impact_score = category_weight × probability × freshness`，其中category_weight在config中预定义

### ④ 青山 — 策略/因子维度

**评估结论**: ✅ PASS

- 输出JSON Schema对齐腰子知识库/18 §五的事件记录格式，可以直接接入事件数据库
- Phase 3的事后IC验证设计正确，T+1/T+3/T+5收益回填是标准做法
- ⚠️ 建议：在events_db.json中预留 `actual_return_T1/T3/T5` 和 `market_return_T1/T3/T5` 字段（用于计算超额收益），当前Schema只有事件记录没有回测字段
- 建议：3个月后首次IC实证时，按事件类别分组统计——不同事件类型的IC差异可能很大（学术研究表明并购类IC~0.08，研报类IC~0.01）
