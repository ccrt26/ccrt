## 五、四级审计 — 技术健康

### F1 (FAIL, P1) — 闸门1缺少腰子确认检测

与新安 B1 为同一问题。闸门1定义要求：
```
情墨设计 → 腰子确认 → 新安审查 → 流入编码
```

引擎§六闸门1只检测「设计文档存在」+「pipeline_stage: complete 标记」，未检测腰子确认环节。引擎可能在腰子未确认的情况下自动推进到②。

**修复指令**:
- 文件: `代码文件/监督机制/pipeline_engine.ps1`（新建时）
- 位置: `-Validate` 函数，Stage 1 检测逻辑
- 操作: 增加 `finance_confirmed` 标记检测
- 具体: 扫描设计文档 frontmatter 或末尾是否含 `finance_confirmed: true`（YAML/JSON均可）；或检测独立确认文件 `审计报告/架构设计/design_*.confirmed` 是否存在
- 未检测到时: 引擎设 `next_action="stop_l3"`, `l3_reason="闸门1: 等待腰子确认金融意图"`

### F2 (WARN, P2) — ScheduleWakeup 可靠性未覆盖

设计依赖 ScheduleWakeup 实现跨轮次自动续跑。但 ScheduleWakeup 默认 `durable=false`（会话级），会话结束即丢失。如果流程在非 /loop 模式下执行，会话断开后流程永久卡住。

**修复建议**:
- 引擎在 `-Status` 时检测自身状态：若 `active==true` 且距 `updated` 超过 30 分钟无进展 → 设 `next_action="stop_l3"`, `l3_reason="流程超时未推进，可能会话中断"`
- 阿黑启动流程时设置 durable CronCreate 作为心跳兜底（每10分钟检查一次流程状态）

### F3 (WARN, P2) — 阶段③完成信号过于宽松

引擎§三.2 阶段③（红结编码）检测条件：「有新commit或staged files，路径在代码文件/」。任何人在代码文件/下的任何改动都会触发 PASS，可能误判。

**修复建议**:
- 阶段③检测增加「变更文件列表与设计文档 §八 需求→代码核对清单中的文件匹配度 ≥ 80%」
- 匹配逻辑：设计文档声明要改的文件列表 vs git diff 实际变更列表

### F4 (INFO, P3) — 错误处理规范缺失

设计未定义引擎自身故障时的行为规范（git 不可用、文件权限错误、JSON 损坏等）。

**修复建议**: 引擎每个操作前检测前置条件（git可用性、文件可读写），失败时输出结构化错误 JSON 而非裸 exit code。
