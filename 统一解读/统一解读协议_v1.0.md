# 项目统一解读协议 v1.0

> 版本 v1.0 | 生效日期 2026-06-02 | 情墨起草，腰子+旧影联审
> 本文档是铁律量化项目所有分析产出的解释层统一标准。所有日报/深度分析/每日荐股/模拟交易/保护机制/临时分析必须遵守本协议。

---

## 一、总则

### 1.1 什么是"统一解读"

统一解读是项目内所有分析的**底层解释对象层**。每一份分析报告、每一个交易建议、每一次风控判断，都必须生成结构化解释对象（interpretation object），而非自然语言段落。

### 1.2 核心原则

> **从数据到动作，每一步都必须可审计、可追溯、可后评估。**

```
数据事实 → 投资含义 → 动作建议 → 审计闸门 → 后评估 → 规则进化
```

### 1.3 适用范围

| 场景 | 是否覆盖 | 说明 |
|:-----|:--------|:-----|
| 日报 | 覆盖 | 每只股票的每日操作简报必须生成解释对象 |
| 深度分析 | 覆盖 | 每份九章报告必须逐章生成解释对象 |
| 每日荐股 | 覆盖 | 每只荐股必须生成解释对象 |
| 模拟交易 | 覆盖 | 每笔交易决策必须生成解释对象 |
| 保护机制 | 覆盖 | 每次保护触发/解除必须生成解释对象 |
| 临时个股分析 | 覆盖 | 任何临时分析请求必须生成解释对象 |

## 二、统一解读链路

### 2.1 六段链路

```
[1] 数据事实 ──→ [2] 投资含义 ──→ [3] 动作 ──→ [4] 审计(U-9/U-10) ──→ [5] 后评估(eval_hooks) ──→ [6] 规则进化
```

| 段 | 名称 | 责任人 | 输入 | 输出 |
|:--|:-----|:------|:-----|:-----|
| 1 | 数据事实 | 玉夜(数据)+山猫(宏观)+信鸽(事件) | 原始数据 | data_fact（禁止含结论） |
| 2 | 投资含义 | 青山(信号)+山猫(宏观)+腰子(综合) | data_fact | interpretation_hypothesis + supporting/counter_evidence |
| 3 | 动作 | 腰子(裁决)+流金(边界) | investment_implication | action_bias + trigger + invalidation |
| 4 | 审计 | 旧影(U-9)+流金(U-10) | 解释对象 | PASS/WARN/BLOCK |
| 5 | 后评估 | 青山(设计)+玉夜(数据) | eval_hook | 命中/部分命中/失败/不可评估/数据不足 |
| 6 | 规则进化 | 腰子(审批)+青山(提案) | 后评估结果 | rule_update_candidate |

### 2.2 链路不可断裂

- 缺数据事实 → BLOCK：不得凭空解释
- 缺反证 → BLOCK：不得选择性呈现
- 缺投资含义 → BLOCK：不得只有数据没有判断
- 缺失效条件 → BLOCK：不得给出不可证伪的结论
- 缺后评估挂钩 → BLOCK：不得产出无法验证的结论

## 三、角色边界

### 3.1 金融线角色在解读链中的定位

| 角色 | 在解读链中的职责 | 输出物 | 禁止 |
|:-----|:----------------|:------|:-----|
| **玉夜** | 提供数据事实包，标注数据新鲜度/缺失/降级/异常 | data_fact | ⛔ 在数据段写"建议"/"看好"等投资含义 |
| **山猫** | 提供宏观/政策事实，判断市场状态，标注对板块/风格影响 | macro_fact | ⛔ 做个股推荐 |
| **信鸽** | 提供事件事实，标注事件等级/兑现状态/催化方向 | event_fact | ⛔ 据事件调整评分 |
| **青山** | 提供信号胜率数据，标注适用/失效环境 | signal_assessment | ⛔ 对单票下结论（小样本<20日） |
| **流金** | 提供风险边界、仓位约束、U-10动作审计 | risk_boundary + U-10结果 | ⛔ 替代腰子做投资判断 |
| **腰子** | 综合全部输入，裁决投资含义和动作建议 | yaozi_integration | ⛔ 跳过任何角色、编造数据 |

### 3.2 工程线角色在解读链中的定位

| 角色 | 在解读链中的职责 |
|:-----|:----------------|
| **情墨** | 维护解释对象schema、闸门接口、接入架构 |
| **红结** | 实现schema对应的代码和脚本 |
| **千光** | 将闸门接入CI/CD流水线 |
| **新安** | 测试闸门有效性、验证样例 |
| **旧影** | U-9审计、模板污染检查、流程合规审计 |

## 四、解释对象格式

### 4.1 标准解释对象 (interpretation object)

每个分析结论必须生成一个结构化解释对象，格式由 `interpretation_schema.json` 定义。必填字段：

| 字段 | 类型 | 说明 | 空值处理 |
|:-----|:-----|:-----|:--------|
| interpretation_id | string | 唯一标识 | 不可为空 |
| scene | enum | 日报/深度分析/每日荐股/模拟交易/保护机制/临时分析 | 不可为空 |
| stock_code | string | 股票代码 | 不可为空（非个股场景填"MARKET"） |
| trade_date | date | 交易日期 | 不可为空 |
| role | string | 生成角色 | 不可为空 |
| data_fact | object | 数据事实包 | 为空→BLOCK |
| interpretation_hypothesis | string | 投资含义假说 | 不可为空 |
| supporting_evidence | array | 支持证据 | 至少1条 |
| counter_evidence | array | 反证 | 为空→BLOCK |
| investment_implication | string | 投资含义 | 为空→BLOCK |
| action_bias | enum | BUY/HOLD/SELL/WATCH/NEUTRAL | 不可为空 |
| confidence | enum | HIGH/MEDIUM/LOW | 不可为空 |
| invalidation_condition | string | 失效条件 | 为空→BLOCK |
| eval_window | object | 后评估窗口 {t1,t3,t5} | 不可为空 |
| rule_refs | array | 引用的铁律规则编号 | 至少1条 |
| knowledge_refs | array | 引用的知识库条目 | 可空 |

### 4.2 硬规则（闸门级，不可绕过）

| # | 规则 | 违规处理 |
|:--|:-----|:--------|
| R1 | 缺 data_fact | BLOCK |
| R2 | 缺 counter_evidence | BLOCK |
| R3 | 缺 investment_implication | BLOCK |
| R4 | 缺 invalidation_condition | BLOCK |
| R5 | 强动作(BUY/SELL)但无触发条件 | BLOCK |
| R6 | 低置信(LOW)强动作(BUY/SELL) | BLOCK |
| R7 | data_fact 中含投资结论性语言 | WARN，退回重写 |
| R8 | 反证仅有一条且为套话（如"市场风险"） | WARN，要求补充具体反证 |

## 五、腰子整合单格式

### 5.1 整合单结构

腰子整合单是腰子汇集全团输入后的统一输出，格式如下：

```json
{
  "integration_id": "string",
  "interpretations": ["interpretation_id_1", "interpretation_id_2"],
  "consensus": "string (全团一致意见)",
  "divergence": "string (分歧点，无分歧填NONE)",
  "ruling": "string (腰子裁决理由)",
  "final_investment_implication": "string",
  "action": {
    "bias": "BUY|HOLD|SELL|WATCH",
    "trigger_condition": "string (具体触发条件)",
    "price_range": "string (价格区间)",
    "position_limit": "string (仓位上限)",
    "time_window": "string (时间窗口)"
  },
  "invalidation": "string (失效条件)",
  "eval_hooks": ["eval_hook_id_1", "eval_hook_id_2"],
  "u9_result": "PASS|WARN|BLOCK",
  "u10_result": "PASS|WARN|BLOCK",
  "signatures": {
    "山猫": "signed|rejected|no_response",
    "信鸽": "signed|rejected|no_response",
    "玉夜": "signed|rejected|no_response",
    "流金": "signed|rejected|no_response",
    "青山": "signed|rejected|no_response",
    "腰子": "signed"
  }
}
```

## 六、U-9/U-10 闸门

### 6.1 U-9 事实审计（旧影负责）

检查项：
1. 事实和观点是否分开
2. 是否引用不存在的数据
3. 是否从单一信号推出强结论
4. 是否缺反证
5. 是否缺失效条件
6. 是否把相关性写成因果

结果：PASS(通过) / WARN(允许观察不允许强动作) / BLOCK(禁止发布)

### 6.2 U-10 动作审计（流金负责）

检查项：
1. 动作是否可执行
2. 是否有触发条件
3. 是否有仓位/价格/时间窗口
4. 是否与风险等级匹配
5. 是否低置信强动作
6. 是否出现空泛套话

结果：PASS(允许输出正式动作) / WARN(允许观察/等待，不允许强动作) / BLOCK(禁止发布正式分析)

## 七、六库责任

| 库 | 负责人 | 内容 | 来源等级要求 | 更新规则 |
|:---|:------|:-----|:-----------|:--------|
| 统一解读规则库 | 腰子 | ≥30条解读规则 | L1-L5 | 双周review |
| 信号胜率库 | 青山 | 信号→历史胜率映射 | L1-L3 | 每20个新样本更新 |
| 后评估库 | 青山 | eval_hooks模板+回填格式 | L1-L3 | 月度review |
| 错误反例库 | 旧影 | ≥20条解读反例 | L4-L5(种子) | 发现新反例即追加 |
| 模板污染检查库 | 旧影 | 禁用表达+替代表达 | — | 发现新套话即追加 |
| 角色知识库升级 | 各角色 | 补齐来源等级L1-L5 | L1-L5 | 按需更新 |

每个库必须具备：负责人、来源等级、适用范围、更新规则、审计规则、入库标准、废弃标准。七项缺一视为未完成。

## 八、禁止事项

1. 禁止只写规划不落地
2. 禁止只改日报不覆盖全项目
3. 禁止只有自然语言没有 schema
4. 禁止有库无负责人
5. 禁止有规则无来源等级
6. 禁止有解释无反证
7. 禁止有动作无触发条件
8. 禁止有强动作无 U-10
9. 禁止有最终结论无 eval_hooks
10. 禁止旧影只审格式不审推理
11. 禁止 data_fact 中含投资结论
12. 禁止跳过任何角色输出最终结论
13. 禁止低置信(LOW)给出强动作(BUY/SELL)
14. 禁止使用模板污染库中的禁用表达

---

## 九、验收标准

阿黑最终验收时，按以下10条逐项判定，任一不满足即判定未完成：

1. 是否有统一解读协议 ✓（本文档）
2. 是否有解释对象 schema
3. 六个库是否都有负责人和初版内容
4. 每个角色是否有解释包模板
5. 腰子整合单是否存在
6. U-9/U-10 是否能给 PASS/WARN/BLOCK
7. 日报/深度分析/每日荐股是否都接入
8. eval_hooks 是否能进入后评估
9. 模板污染是否能拦截套话
10. 是否有 3 个样例跑通
