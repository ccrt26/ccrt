## 一、运行调度

### 1.1 eval_hook 生成时机
每个解释对象生成后立即创建对应 eval_hook，初始状态为"待评估"

### 1.2 回填时间表
| 节点 | 触发时间 | 执行人 | 动作 |
|:-----|:--------|:------|:-----|
| T+1 | 次日 09:00 | 玉夜(数据)+青山(判定) | 回填 t1_check |
| T+3 | T+3日 15:30 | 青山 | 回填 t3_check |
| T+5 | T+5日 15:30 | 青山+旧影 | 回填 t5_check + 综合判定 + 失败归因 |

### 1.3 自动化调度
千光在 cron 中注册：
```
# T+1 回填 (每个交易日盘前)
7 9 * * 1-5 python3 scripts/eval_backfill.py --window t1

# T+3/T+5 回填 (每日收盘后)
37 15 * * 1-5 python3 scripts/eval_backfill.py --window t3
37 15 * * 1-5 python3 scripts/eval_backfill.py --window t5
```

## 二、综合判定规则

### 2.1 判定矩阵

| T+1 | T+3 | T+5 | 综合判定 |
|:-----|:-----|:-----|:--------|
| 命中 | 命中 | 命中 | **命中** |
| 命中 | 命中 | 部分命中 | **部分命中** |
| 命中 | 命中 | 失败 | **部分命中** (短期有效，中期失效) |
| 命中 | 失败 | 失败 | **失败** (仅T+1有效=噪音) |
| 失败 | — | — | **失败** (首日即失败) |
| 部分命中 | 部分命中 | 部分命中 | **部分命中** |
| 数据不足 | 数据不足 | 数据不足 | **不可评估** |

### 2.2 特殊场景

| 场景 | 处理 |
|:-----|:-----|
| 标的停牌 | T+1/T+3/T+5均标注"不可评估-停牌"，不计入胜率 |
| 涨跌停限制 | 若连续涨跌停导致无法交易→标注"不可评估" |
| 重大事件冲击 | 记录事件，归因标记"市场突变"，不影响规则 |
| 保护机制触发 | 若保护触发导致未执行动作→标注"不可评估-保护" |

## 三、失败归因规则

### 3.1 归因决策树

```
eval_hook判定=失败
  ├─ 数据回填时发现原始数据有误? → 数据问题
  ├─ 信号胜率明显偏离历史? → 规则问题
  ├─ 某角色输出被后续事实证明错误? → 角色问题
  ├─ 多信号综合时权重分配明显失当? → 腰子整合问题
  ├─ 置信度与动作明显不匹配? → 动作过强
  ├─ T+1窗口内发生不可预见重大事件? → 市场突变
  └─ 无法明确归因 → 标注"待进一步分析"
```

### 3.2 归因→修正映射

| 归因 | 修正动作 | 责任人 | 时限 |
|:-----|:--------|:------|:-----|
| 数据问题 | 修正数据采集/清洗流程 | 玉夜 | 次日 |
| 规则问题 | 标记信号胜率库待review，连续2次→重新计算胜率 | 青山 | 周度 |
| 角色问题 | 对应角色review知识库，找出错误原因 | 对应角色 | 3天 |
| 腰子整合问题 | 调整多信号整合权重 | 腰子 | 周度 |
| 动作过强 | 收紧U-10对应检查项阈值 | 流金 | 周度 |
| 市场突变 | 不调整规则，记录事件 | 旧影(归档) | 即时 |

## 四、规则进化触发

### 4.1 rule_update_candidate=true 条件
1. 同类型解释连续2次失败且归因相同（非市场突变）
2. 同一信号连续3次失败（任意归因）
3. 某角色连续3次被归因"角色问题"
4. 青山发现信号胜率连续20个样本低于历史胜率-15%

### 4.2 规则修正流程
```
eval_hook.rule_update_candidate = true
  → 青山提案（说明修正理由+数据支撑）
  → 腰子召集全团咨询
  → 全团通过 → 更新对应知识库 + 铁律（如需要）
  → 旧影记录规则变更历史
```
