# 一、数据真实性铁律（最高优先级）

## 1.1 绝对禁止

所有出现在报告中的数字，必须来自真实数据源。

**允许：**
- 从腾讯行情API、新浪财经、东方财富API等接口获取的真实数据
- 基于真实数据的本地计算（移动均线、RSI、MACD、量比等）
- 标注为[季报数据，非实时]的财报数据

**禁止：**
- 在没有数据时凭空赋值或编造任何数字
- 用AI模型推断缺失的财务指标
- 使用无法通过截图或链接验证的"听说"数据

## 1.3 PE(TTM) 计算红线

禁止直接使用腾讯行情API提供的静态PE作为否决依据。

```
PE(TTM) = 当前价[1] / TTM_EPS[3]
TTM_EPS = 最新年报EPS - 去年同季EPS + 最新季报EPS
```


## 1.6 CHANGELOG 与代码变更一致性规则（v1.5新增）

> **背景**：2026-05-23 审计发现 CHANGELOG v2.4.1 条目记录了"已移除 VetoedStocks 字段"等声明，但实际代码中从未执行对应修改。本文旨在杜绝"计划当完成"的虚假陈述。

### 1.6.1 CHANGELOG 真实性

- CHANGELOG 只记录**已完成且已验证**的改动
- 禁止先写 CHANGELOG 条目再补代码，禁止将"计划实施"记录为"已完成"
- 所有声称"已修改/已移除/已新增"的具体内容，必须在对应的代码或文档中有明确可查的对应修改
- **违反后果**：虚假 CHANGELOG 条目必须立即修正并在条目末尾标注更正声明

### 1.6.2 "已修复"声明的证据链要求

当 AI 对用户说"X已修复"时，必须同时附带以下信息中的至少一项：
- 修改的文件路径 + 行号 + 改动内容摘要
- 或 git diff / git show 的输出片段
- "已同步文档"等声明同样适用此规则

### 1.6.3 提交前验证

- 每次准备 commit 前，必须运行 `version_supervisor.ps1 -CrossCheck` 验证 CHANGELOG 条目与代码事实的一致性
- CrossCheck 失败时禁止提交，必须修正后再提交

### 1.6.4 适用范围

本规则适用于铁律量化项目下**所有**文档的 CHANGELOG 记录，包括但不限于：
- 每日荐股分析逻辑白皮书
- 次日后评估白皮书
- 重点股票跟踪分析逻辑白皮书
- 重点股票次日后评估白皮书
- 分析的规则红线（本文档）

# 二、资源节约铁律

## 2.1 核心原则

Token是付费资源。能用本地或免费资源完成的工作，禁止用AI Token完成。免费公开API抓取 -> 本地计算处理 -> AI分析。

| 层级 | 成本 | 承担工作 |
|:----|:----:|:---------|
| 数据获取层 | 零Token | API调用/数据格式化/缓存读写 — 由代码执行，AI不参与 |
| 分析决策层 | 消耗Token | 评分判断/否决判定/报告文本生成 — AI参与 |
| 校验层 | 少量Token | 交叉验证/异常检测 — AI参与，原始数据比对由代码完成 |

## 2.2 Token使用边界

**允许：**
- AI处理分析逻辑判断/规则解读/报告文本生成
- AI对比多个数据源做一致性校验
- AI根据评估结果提出规则优化建议

**禁止：**
- 让AI用自然语言估算已有API可获取的数据
- 无谓的重复调用
- 把原始数据全文喂给AI做阅读理解

# 三、API调用纪律与缓存策略

## 3.1 数据分层与缓存

所有数据获取函数内置本地缓存层，API成功调用后自动写入缓存，API失败时自动读取缓存兜底。

| 层级 | 数据 | 主源 | 备源 | 缓存TTL | 缓存文件 |
|:----|:-----|:-----|:-----|:--------|:--------|
| 实时 | 当前价/涨跌幅/换手率/PE | 腾讯[1] | 新浪[1B] | 1h | Quote_{Code}.json |
| 日更 | 120日日K线(OHLCV) | 新浪[2] | 腾讯[2B] | 24h | KLine_{Code}_240.json |
| 日更 | 技术指标(均线/RSI/MACD/布林) | 本地计算[5] | — | 基于K线实时 | — |
| 日更 | 板块行业TOP | 东方财富[7] | — | 6h | Sector_{Top}.json |
| 日更 | 个股资金流向 | 东方财富[9] | — | 6h | FundFlow_{Code}_{Days}.json |
| 日更 | 行业资金流向 | 东方财富[10] | — | 6h | SectorFundFlow_{Top}.json |
| 日更 | 研报/评级 | 东方财富[11] | — | 24h | Research_{Code}_{Count}_{DaysBack}.json |
| 日更 | 融资融券 | 东方财富[12] | — | 24h | Margin_{Code}_{Days}.json |
| 季度 | 财务数据(EPS/ROE/营收) | 东方财富[3] | — | 168h(7天) | Financial_{Code}.json |
| 低频 | PE百分位 | 本地计算(K线+EPS) | — | 168h(7天) | PEPercentile_{Code}.json |
| 低频 | 北向资金持股 | 东方财富[8] | — | 168h(7天) | Northbound_{Code}.json |

**缓存读写规则：**
- 写：API返回有效数据后立即写入 `Save-DataCache -Key "类型_标识" -Data $result`
- 读：API全部失败后 `Load-DataCache -Key "类型_标识" -TTLHours N`，缓存过期不读取
- 缓存目录：`股票分析/data_cache/`，自动创建，归入gitignore不进版本控制

## 3.2 防封禁规则

- 每次API调用后强制间隔 >= 0.3秒
- 每10次调用后额外休息 >= 2秒
- 财务数据仅在缓存过期时重新拉取（每7天1次）
- 禁止在短时间内(<5分钟)重复拉取同一只股票的同一类数据
- 同一数据类别内，主源失败→备源时，间隔 >= 1秒再试

## 3.3 降级路径

| 主数据源 | 备数据源 | 缓存兜底 | 报告中标注 |
|:---------|:---------|:---------|:----------|
| 腾讯行情[1] | 新浪行情[1B] | 缓存[C] | 备源/缓存 |
| 新浪K线[2] | 腾讯K线[2B] | 缓存[C] | 备源/缓存 |
| 东方财富财务[3] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富板块[7] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富资金[9][10] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富北向[8] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富研报[11] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富融券[12] | — | 缓存[C] | 缓存数据，可能滞后 |

> **独有数据说明：** 资金流向[9][10]、北向资金[8]、研报[11]、融资融券[12]为东方财富垄断数据，无免费备API。1+2架构中备源为缓存兜底，数据可用性依赖本地缓存。发现可用的免费备API后必须补充。

## 3.4 调用监控与告警

以下情况必须告警并暂停分析：
- 单次分析API调用失败率 > 20%
- 同一类数据主API+备API(如有)+缓存全部失败
- 腾讯/新浪API响应时间异常(单次 > 3秒)
- 降级路径连续2次以上仍不可用
- 东方财富接口连续返回空数据或异常数据带有相同特征

格式 `v<MAJOR>.<MINOR>.<PATCH>`，遵循语义化版本（SemVer 2.0.0）。

| 层级 | 变更类型 | 示例 | 审批要求 |
|:----|:---------|:------|:--------:|
| **MAJOR** 主版本 | 评估维度重构、核心方法论变更、不兼容的规则变更 | v1.5.0 → v2.0.0 | 人审批 |

**过渡规则：** 现有 `vX.Y` 视同为 `vX.Y.0`，下一次 PATCH 修正为 `vX.Y.1`，MINOR 变更为 `vX.Y+1.0`。

### 5.4.3 CHANGELOG 规范

每个白皮书目录下的 `*_CHANGELOG.md` 必须遵循以下规范。

#### 5.4.3.1 条目格式

每个版本条目按以下结构组织，变更类型采用 Keep a Changelog 六类标记：

```markdown
## [vX.Y.Z] - YYYY-MM-DD

### 负责人
- 修改：<人名>（<角色>）
- 审批：<人名>（仅 MAJOR/MINOR）
- 依据：<来源说明>

### Added
- 新增内容 1 — 说明

### Changed
- 修改内容 1 — 说明前后对比

### Deprecated
- 即将废弃的功能

### Removed
- 已移除的内容

### Fixed
- 修复的问题

### Security
- 安全修复（如有）
```

#### 5.4.3.2 规则

1. **倒序排列**：最新版本在最上方
2. **责任人**：每个版本必须有明确的修改人和审批人
3. **关联文件**：每次变更必须列出受影响的文件清单
4. **[Unreleased]** 占位：文档顶部保留 `## [Unreleased]` 段

### 5.4.4 文档与代码同步规则

- **.md 是唯一源文件**，禁止直接编辑 .docx
- 每次 .md 版本变更后必须同步重新生成 .docx
- 版本一致性必须满足：

| 检查项 | 验证方式 |
|:-------|:---------|
| 文件名版本号 = 文档头版本号 | 人工/AI 检查 |
| CHANGELOG 最新条目版本 = 文档当前版本 | version_supervisor.ps1 [1/7] |
| 对应的 .docx 存在且版本号匹配 | version_supervisor.ps1 [4/7] |
| 文档版本索引 > 当前版本一致 | version_supervisor.ps1 [7/7] |

### 5.4.5 版本发布流程

```
Phase 1: 提案
  发现修改需求 → 记录到改进日志.md（含证据/原因/修改方案）
  → AI 向人提交修订提案

Phase 2: 确认
  人审查提案 → 决定：采纳 / 修改后采纳 / 拒绝
  → 如采纳，确定版本层级（MAJOR / MINOR / PATCH）

Phase 3: 执行
  升版本号 + 更新文档头日期 → 修改文档正文
  → 更新版本历史表 → 按 5.4.3 更新 CHANGELOG.md
  → 重新生成 .docx → 更新文档版本索引
  → 运行 version_supervisor.ps1 验证一致性
  → git commit（message 标注版本号）→ git tag 标注
```

### 5.4.6 版本载体

| 载体 | 位置 | 用途 | 保留期限 |
|:-----|:-----|:------|:---------|
| 文档头 | 第 1-3 行 | 当前版本和更新日期 | 随文档更新 |
| 版本历史表 | 文档开头表格 | 快速回顾，保留最近 10 条 | 保留所有 |
| CHANGELOG.md | 同目录独立文件 | 永久记录，含责任人+文件清单 | 永久 |
| git tag | git tag | 发布标记，便于回溯 | 永久 |
| 文档版本索引.md | 规则红线\ | 全局版本概览 | 随索引更新 |

### 5.4.7 归档策略

- 每个版本独立文件：`白皮书名称_vX.Y.Z.md` + `.docx`

## 6.5 样式违规处理

1. 立即停止当前报告生成任务
2. 识别修改来源（脚本文件变更位置）
3. 对照样式基线文档确认差异
4. 回滚未经授权的样式修改
5. 如需正式变更，走 6.3 变更流程
