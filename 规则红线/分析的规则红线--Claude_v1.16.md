### 1.2.1 数据访问分层策略（缓存优先原则）

> **核心原则**：数据一旦落地（本地缓存），后续所有运算优先使用本地数据。数据的可变性决定访问顺序——收盘后不可变的数据走「缓存优先」，盘中实时变化的数据走「API优先」。

```
┌─────────────────────────────────────────────────────────────┐
│  Tier 1 — 实时可变数据        API优先 → 缓存兜底            │
│  Quote(行情)                                                 │
│  特征：每秒变化 | TTL: 1h                                    │
│  策略：先打API，失败才读缓存。因为盘中价格每时每刻在变。     │
├─────────────────────────────────────────────────────────────┤
│  Tier 2 — 日频不可变数据      缓存优先 → API补充             │
│  KLine(日线) / FundFlow(资金流向) / Margin(两融) /          │
│  Northbound(北向) / Research(研报)                           │
│  特征：收盘后确定，永不变化 | TTL: 24h                       │
│  策略：先检查本地缓存，24h内新鲜直接返回 [C]；过期才拉API。  │
│  落地即事实源：昨天的K线数据今天不会变，重复拉取是浪费。     │
├─────────────────────────────────────────────────────────────┤
│  Tier 3 — 低频不可变数据      缓存优先 → 过期才拉            │
│  Financial(财务季报) / PEPercentile(PE百分位) /              │
│  SectorConstituents(板块成分股)                              │
│  特征：季度/月度更新 | TTL: 168h(7天)                        │
│  策略：缓存新鲜直接返回 [C]，不碰API。                       │
│  季报3个月才更新一次，7天内重复拉取是浪费。                  │
├─────────────────────────────────────────────────────────────┤
│  Tier 4 — 半可变数据          盘中API优先 / 盘后缓存优先      │
│  Sector(板块排行) / SectorFundFlow(行业资金)                 │
│  特征：盘中变化，盘后固定 | TTL: 6h                          │
│  策略：交易时段API优先；盘前/盘后走缓存。                    │
└─────────────────────────────────────────────────────────────┘
```

**分层依据（三原则）**：

| 原则 | 内容 | 落地方式 |
|:----:|:-----|:---------|
| ① 频率分类 | 所有数据按更新频率分为：盘中实时/每日/每周/每月/每季/半年/每年 | 每个缓存键标注更新周期 + TTL |
| ② 落地本地优先 | 数据一旦从API拉取并写入 `data_cache/`，后续所有计算优先读缓存 | Tier 2/3 函数顶部加缓存检查，命中直接返回 |
| ③ 补拉机制 | 因关机/限流未拉取的数据，下次开机自动检测并回填；回填落地后同② | `catchup_launcher.ps1` v2：P1(KLine)→P2(资金/两融/北向)→P3(研报) 逐级回填 |

**缓存标注规则**：
- 使用缓存命中时，`$script:SourceUsed["DataType"] = "缓存"` 自动标注 `[C]`
- API双源均失败时，使用过期缓存兜底（TTL=720h/30天）并标注 `[C]-过期`
- 独有数据源（北向[8]/研报[11]/融资融券[12]）缓存命中时标注"仅供参考"

**实现文件**：`stock_data_fetcher.psm1` (8个函数已实现缓存优先) | `catchup_launcher.ps1` v2 (多日离线补偿)

## 1.3 PE(TTM) 计算红线

禁止直接使用腾讯行情API提供的静态PE作为否决依据。

```
PE(TTM) = 当前价[1] / TTM_EPS[3]
TTM_EPS = 最新年报EPS - 去年同季EPS + 最新季报EPS
```

## 1.6 CHANGELOG 与代码变更一致性规则（v1.5新增）

> **背景**：2026-05-23 审计发现 CHANGELOG v2.4.1 条目记录了"已移除 VetoedStocks 字段"等声明，但实际代码中从未执行对应修改。本文旨在杜绝"计划当完成"的虚假陈述。

### 1.6.1 CHANGELOG 真实性

- CHANGELOG 只记录**已完成且已验证**的改动
- 禁止先写 CHANGELOG 条目再补代码，禁止将"计划实施"记录为"已完成"
- 所有声称"已修改/已移除/已新增"的具体内容，必须在对应的代码或文档中有明确可查的对应修改
- **违反后果**：虚假 CHANGELOG 条目必须立即修正并在条目末尾标注更正声明

### 1.6.2 "已修复"声明的证据链要求

当 AI 对用户说"X已修复"时，必须同时附带以下信息中的至少一项：
- 修改的文件路径 + 行号 + 改动内容摘要
- 或 git diff / git show 的输出片段
- "已同步文档"等声明同样适用此规则

### 1.6.3 提交前验证

- 每次准备 commit 前，必须运行 `version_supervisor.ps1 -CrossCheck` 验证 CHANGELOG 条目与代码事实的一致性
- CrossCheck 失败时禁止提交，必须修正后再提交

### 1.6.4 适用范围

本规则适用于铁律量化项目下**所有**文档的 CHANGELOG 记录，包括但不限于：
- 每日荐股分析逻辑白皮书

- 分析的规则红线（本文档）

# 二、资源节约铁律

## 2.1 核心原则

Token是付费资源。能用本地或免费资源完成的工作，禁止用AI Token完成。免费公开API抓取 -> 本地计算处理 -> AI分析。

| 层级 | 成本 | 承担工作 |
|:----|:----:|:---------|
| 数据获取层 | 零Token | API调用/数据格式化/缓存读写 — 由代码执行，AI不参与 |
| 分析决策层 | 消耗Token | 评分判断/否决判定/报告文本生成 — AI参与 |
| 校验层 | 少量Token | 交叉验证/异常检测 — AI参与，原始数据比对由代码完成 |

## 2.2 Token使用边界

**允许：**
- AI处理分析逻辑判断/规则解读/报告文本生成
- AI对比多个数据源做一致性校验
- AI根据评估结果提出规则优化建议

**禁止：**
- 让AI用自然语言估算已有API可获取的数据
- 无谓的重复调用
- 把原始数据全文喂给AI做阅读理解

## 2.3 Token预算门禁（强制）

> 本节将Token使用原则量化为可测量的预算指标。预算超标由pre-commit hook自动阻断，由Proof周度审计追踪。

| 文件类别 | 行数上限 | 大小上限 | 审批超标者 |
|:---------|:------:|:------:|:---------|
| Agent定义文件（.claude/agents/*.md） | 250行 | 12KB | Arch |
| Command文件（.claude/commands/*.md） | 40行 | 2KB | Arch |
| Python核心脚本stdout输出（正常模式） | 20行 | — | Arch |
| AI直接读取的大文件（>500KB原始数据） | — | 禁止读取 | — |

**预算等级**：
- 警告阈值：Agent定义>250行或>12KB，stdout>8个print()，不阻断提交但记录日志
- 阻断阈值：Agent定义>300行或>15KB，stdout>12个print()，拒绝提交（需Arch审批豁免，72h内修复）
- 知识库文件（-知识库/*.md）和白皮书不设上限（仅按需加载，不参与基础上下文消耗）

**禁止AI直接读取的文件**：data_full.json、data_scored.json、score_history.jsonl 等>500KB的原始/中间数据文件。AI应通过脚本查询或解析JSON摘要获取所需信息，不得全文读取。

## 2.4 三层Token防护机制

| 防线 | 机制 | 执行者 | 频率 |
|:-----|:-----|:-----|:----:|
| 第1层：创建时约束 | 文件大小预算（§2.3），超标不允许创建 | 所有角色自检 | 每次 |
| 第2层：提交时门禁 | pre-commit hook Check E自动检查 | Forge（门禁实现） | 每次git commit |
| 第3层：定期审计 | Proof周检R13 Token预算合规 + Arch月检趋势 | Proof + Arch | 每周/每月 |

**责任归属**：Proof主执行（R13回归检查），Forge实现门禁（Check E），Arch定义预算阈值和审批豁免，阿黑月度问责。

**Pre-commit hook 检查清单**：

| Check | 检查内容 | 阻断级别 |
|:------|:---------|:--------:|
| A | 数据源1+2架构合规（check_redlines.ps1） | 阻断 |
| B | 版本号一致性（version_supervisor.ps1） | 阻断 |
| C | CHANGELOG CrossCheck（version_supervisor.ps1 -CrossCheck） | 阻断 |
| D | 报告样式合规（check_report_style.ps1 -Quick） | 阻断 |
| E | Token预算门禁（Agent≤250行/12KB，stdout≤20行） | 阻断 |

# 三、API调用纪律与缓存策略

## 3.1 数据分层与缓存

所有数据获取函数内置本地缓存层，API成功调用后自动写入缓存，API失败时自动读取缓存兜底。数据源编号、缓存TTL、缓存文件详见 **§1.2 数据源编号表**（已合并）。

**缓存读写规则：**
- 写：API返回有效数据后立即写入 `Save-DataCache -Key "类型_标识" -Data $result`
- 读：API全部失败后 `Load-DataCache -Key "类型_标识" -TTLHours N`，缓存过期不读取
- 缓存目录：`股票分析/data_cache/`，自动创建，归入gitignore不进版本控制

## 3.2 防封禁规则

- 每次API调用后强制间隔 >= 0.3秒
- 每10次调用后额外休息 >= 2秒
- 财务数据仅在缓存过期时重新拉取（每7天1次）
- 禁止在短时间内(<5分钟)重复拉取同一只股票的同一类数据
- 同一数据类别内，主源失败→备源时，间隔 >= 1秒再试

## 3.3 降级路径

| 主数据源 | 备数据源 | 缓存兜底 | 报告中标注 |
|:---------|:---------|:---------|:----------|
| 腾讯行情[1] | 新浪行情[1B] | 缓存[C] | 备源/缓存 |
| 新浪K线[2] | 腾讯K线[2B] | 缓存[C] | 备源/缓存 |
| 东方财富财务[3] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富板块[7] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富资金[9][10] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富北向[8] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富研报[11] | — | 缓存[C] | 缓存数据，可能滞后 |
| 东方财富融券[12] | — | 缓存[C] | 缓存数据，可能滞后 |

> **独有数据说明：** 资金流向[9][10]、北向资金[8]、研报[11]、融资融券[12]为东方财富垄断数据，无免费备API。1+2架构中备源为缓存兜底，数据可用性依赖本地缓存。发现可用的免费备API后必须补充。

## 3.4 调用监控与告警

以下情况必须告警并暂停分析：
- 单次分析API调用失败率 > 20%
- 同一类数据主API+备API(如有)+缓存全部失败
- 腾讯/新浪API响应时间异常(单次 > 3秒)
- 降级路径连续2次以上仍不可用
- 东方财富接口连续返回空数据或异常数据带有相同特征

2. **责任人**：每个版本必须有明确的修改人和审批人
3. **关联文件**：每次变更必须列出受影响的文件清单
4. **[Unreleased]** 占位：文档顶部保留 `## [Unreleased]` 段
5. **条目格式**：采用 Keep a Changelog 六类标记（Added/Changed/Deprecated/Removed/Fixed/Security），详细模板见版本管理操作规程

### 5.4.4 文档与代码同步规则

- **.md 是唯一源文件**，禁止直接编辑 .docx
- 每次 .md 版本变更后必须同步重新生成 .docx
- 版本一致性必须满足：

| 检查项 | 验证方式 |
|:-------|:---------|
| 文件名版本号 = 文档头版本号 | 人工/AI 检查 |
| CHANGELOG 最新条目版本 = 文档当前版本 | version_supervisor.ps1 [1/7] |
| 对应的 .docx 存在且版本号匹配 | version_supervisor.ps1 [4/7] |
| 文档版本索引 > 当前版本一致 | version_supervisor.ps1 [7/7] |

> 📋 **详细操作规程**（CHANGELOG模板、发布流程、版本载体、归档策略）见 **[版本管理操作规程.md](版本管理操作规程.md)**。

3. **CHANGELOG**：名册版本变更须在本文档 CHANGELOG 中记录
4. **文档版本索引同步**：名册版本变更须同步更新 `规则红线/文档版本索引.md`

6. **一致性验证**：`version_supervisor.ps1` 检查项覆盖团队名册版本号
7. **规则-监督器同步**：§5.4 新增纳入版本管理的文件类型时，须在同一 commit 中更新 `version_supervisor.ps1` 增加对应检查项，并在提交前运行验证通过。禁止规则上架而监督器留空——规则和监督器同 commit，不允许分拆。

5. **提交规则**：.md 和 .xlsx 须在同一 commit 中提交，禁止分拆提交

## 5.5 样本外验证(OOS)规则（v1.11新增）

> ⛔ **红线**：所有涉及评分权重、否决阈值、选股逻辑、交易规则的变更，必须经过样本外验证后方可正式上线。此规则响应豆包建议「过拟合风险」——规则变更须经OOS验证，胜率提升≥3%方可上线。

### 5.5.1 适用范围

| 变更类型 | OOS要求 | 最低样本量 |
|:---------|:--------|:----------:|
| 评分权重调整 | 必须OOS | 近6个月数据 |
| 否决阈值变更 | 必须OOS | 近6个月数据 |
| 新增/删除评分因子 | 必须OOS | 近6个月数据 |
| 交易规则变更(开仓/出场/仓位) | 必须OOS | 近6个月数据 |
| 数据源切换(主备互换) | 建议OOS | 近3个月数据 |
| 错别字/格式修正 | 无需OOS | — |

### 5.5.2 验证标准

变更必须同时满足以下条件方可正式上线：

1. **胜率提升 ≥ 3%**：新规则相对旧规则的胜率提升不低于3个百分点
2. **最大回撤不恶化**：新规则的最大回撤不超过旧规则的110%
3. **样本量充足**：OOS测试覆盖至少6个月（约120个交易日）的样本外数据
4. **统计显著性**：若样本量充足(≥60笔交易)，胜率差异的p值 < 0.1

### 5.5.3 验证流程

```
提出规则变更 → 确定OOS范围(6个月样本外数据)
  → 在样本外数据上分别运行旧规则+新规则
  → 对比胜率/回撤/夏普比率
  → 满足§5.5.2标准 → 标记"OOS通过" → 按§5.3执行变更
  → 不满足 → 记录不通过原因 → 回退至改进日志待重新设计
```

### 5.5.4 豁免条件

以下情况可豁免OOS验证（须人审批）：
- 修复明确的Bug（如除零错误、计算逻辑错误）
- 紧急风控规则上线（如API被封导致无法获取数据时的降级规则）
- 数据源新增（不改变现有逻辑，仅新增备源）

## 5.6 紧急豁免条款（v1.14新增）

> 当系统异常或市场极端情况发生时，可临时绕过非安全红线。豁免须人审批，事后72h内补齐合规流程。

| 场景 | 可豁免规则 | 不可豁免规则 |
|:-----|:----------|:-----------|
| API大面积故障 | §3.2防封禁间隔、§5.5 OOS | §1.1编造数据、§1.7 PDF保护 |
| 市场剧烈波动需紧急风控 | §5.5 OOS、§5.4版本流程 | §1.1、§1.3 PE计算 |
| 系统故障导致缓存全失效 | §3.1缓存TTL | §1.1、§1.7 PDF保护 |

**豁免记录要求**：所有豁免须记录到改进日志.md（场景+豁免规则+审批人+补齐期限）。同一规则连续豁免3次以上须启动规则修订。
