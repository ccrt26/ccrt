## 一、系统概述

### 1.1 定位

模拟交易系统是铁律量化重点股票分析体系的交易验证层。其核心定位为：

- 将每日分析报告中的评分、预判、信号转化为可量化的模拟买卖操作
- 实时跟踪组合净值、胜率、最大回撤等绩效指标
- 积累交易级数据，为策略迭代优化提供依据
- 在不占用真实资金的前提下，验证分析逻辑的有效性

### 1.2 目标

1. **信号至交易闭环**：每日分析输出自动触发模拟开仓/平仓，消除人工决策随意性
2. **绩效量化**：以精确的数字衡量每笔交易、每个信号的真实价值
3. **归因分析**：识别哪些评分维度、哪些预判方向真正贡献了正收益
4. **策略迭代**：通过回测数据驱动分析逻辑和交易规则的持续优化

### 1.3 适用股票范围

系统固定跟踪以下 6 只重点股票，不扩展、不缩减：

| 代码 | 名称 | 所属板块 |
|:----:|:----|:---------|
| 603019 | 中科曙光 | 计算机 |
| 601689 | 拓普集团 | 汽车零部件 |
| 600114 | 东睦股份 | 金属新材料 |
| 301075 | 多瑞医药 | 医药 |
| 000967 | 盈峰环境 | 环保 |
| 600036 | 招商银行 | 银行 |

### 1.4 非目标

- 不接入真实交易接口
- 不做日内高频交易
- 不做融资融券模拟
- 不修改现有系统的任何文件
- 不新增外部 API 依赖

## 二、交易规则

### 2.1 开仓条件

开仓需同时满足以下全部条件：

| 序号 | 条件 | 规则 | 数据来源 |
|:----:|:-----|:-----|:---------|
| 1 | 方向 | Short 预测为"看多"或"偏多" | 评估数据.Prediction.Short |
| 2 | 趋势健康 | TrendHealth.Label 不为"危险"且不为"数据不足" | 评估数据.TrendHealth.Label |
| 3 | 未持仓 | 该股票当前无持仓 | positions.json |
| 4 | 仓位上限 | 总持仓数量不超过 MaxPositions(默认3只) | sim_config.json |
| 5 | 止损冷却期 | 该股票过去 CooloffPeriodDays(默认5日)内未触发止损 | positions.json.LastStopLossDate |
| 6 | 止盈冷却期 | 该股票过去 FullTakeProfitCooldownDays(默认3日)内未触发 P4 全部止盈 | positions.json.LastFullTakeProfitDate |
| 7 | 未涨停 | 今日开盘未涨停(涨跌幅 < 9.4%) | 腾讯行情 API 开盘价 vs 前日收盘 |
| 8 | StopLoss 合理 | StopLoss < 当前价 | 评估数据.KeyLevels.StopLoss |

> **冷却期设计理由**：止损后 5 日冷却防止 whipsaw（反复打脸），避免同一只股票刚止损又买入导致连续亏损。全部止盈后 3 日冷却避免在短期超买状态下追高。

### 2.2 多股选股优先级

当同时满足开仓条件的股票数量超过最大持仓限制(3只)时，按以下优先级依次选取：

| 优先级 | 因子 | 规则 |
|:------:|:-----|:-----|
| P1 | CompositeScore | 评分高者优先 |
| P2 | Confidence | 同分时，"高置信度" > "中" > "低" |
| P3 | ShortBull Score | 同分同置信度时，短期看多强度高者优先 |
| P4 | 代码顺序 | 以上均相同的，按代码排序取前 N 只 |

**Confidence 字段映射规则**：

| 原始值 | 排序数值 |
|:-------|:---------|
| 高(>70%) | 3 |
| 中(50-70%) | 2 |
| 低(<50%) | 1 |
| 无法识别或空值 | 0(排最后) |

### 2.3 仓位管理

#### 2.3.1 仓位档位

仓位比例根据 CompositeScore 分档确定：

| CompositeScore 区间 | 仓位比例 | 说明 |
|:-------------------:|:--------:|:-----|
| >= 80 | 25% | 强烈关注，重点配置 |
| >= 65 | 20% | 关注，正常配置 |
| >= 45 | 10% | 观察，轻仓试探 |
| >= 30 | 5% | 谨慎，极轻仓 |
| < 30 | 0% | 回避，不参与 |

#### 2.3.2 仓位计算规则

- 仓位比例 = 占**当前现金**的百分比（非总资产）
- 买入股数向下取整到 100 股（一手）
- 单只股票买入金额不超过总资产的 SingleStockLimitPct(默认 30%)
- 若计算所得股数不足 100 股，跳过该股开仓

#### 2.3.3 边界说明

仓位比例在阈值边界存在阶梯跳跃（例如 Score=64 时为 10%，Score=65 时跳至 20%）。引擎按配置如实执行此阶梯，评估阶段再审视是否需要平滑处理。

### 2.4 入场价格

#### 2.4.1 价格确定

1. **优先使用开盘价**：读取腾讯行情 API 返回的当日开盘价(parts[5])
2. **兜底方案**：若开盘价无法获取（API 降级等），使用评估数据的 Price 字段（即昨日收盘价）
3. **滑点**：在最终入场价上乘以 (1 + SlippagePct)，默认 0.1%，买卖双向均适用

#### 2.4.2 引擎运行时序

```
T日 15:00   -> 市场收盘
T日 20:00   -> 生成评估数据_T.json（已有流程）
T+1日 09:25 -> 集合竞价结束，开盘价确定
T+1日 09:35 -> 运行模拟交易引擎（开盘5分钟后，确保行情API已稳定返回）
```

- 引擎固定于每个交易日 09:35 触发
- 若超过 09:45 仍未运行（如系统故障），当日跳过不开新仓，仅执行止损检查（用最新价代替开盘价）
- 节假日或停市日引擎静默跳过，不报错中断

### 2.5 出场规则

#### 2.5.1 出场优先级总览（P1 至 P5）

出场条件按优先级逐级检查，同一交易日即使同时触发多个条件，仅执行优先级最高的一个。

| 优先级 | 出场原因 | 条件 | 操作 |
|:------:|:---------|:------|:-----|
| P1 | 止损 | 当前价 <= KeyLevels.StopLoss | 全部卖出 |
| P2 | 趋势恶化 | TrendHealth 变为"危险" | 全部卖出 |
| P3 | 预判转空 | Short 从入场时的值变为"中性"或"看空" | 全部卖出 |
| P4 | 全部止盈 | 当前价 >= R3（独立于 Short 方向） | 全部卖出 + 进入 3 日止盈冷却期 |
| P5 | 止盈减仓 | 当前价 >= R2 | 卖出 50% 持仓（向下取整到 100 股） |

> **优先级设计理由**：止损(P1)永远优先于止盈——截断亏损比锁定利润更重要。趋势恶化(P2)和预判转空(P3)作为风控补充，在止损未触发但基本面/趋势已变化时主动退出。全部止盈(P4)在股价达到目标后全额退出，止盈减仓(P5)在达到中间目标时锁定部分利润。

#### 2.5.2 P1 止损（v1.5: ATR动态止损）

> **v1.5 升级**：从固定比例止损(-8%)升级为 ATR 动态止损。

**公式**：

```
StopLoss = EntryPrice - N × ATR(14)

其中:
  N = 2.5  (EntryScore >= 78)
  N = 2.0  (EntryScore >= 65)
  N = 1.5  (EntryScore < 65)

硬帽规则:
  - 宽松侧: StopLoss 不得低于 EntryPrice × 0.92（即最大止损距离 = -8%）
  - 收紧侧: StopLoss 不得高于 EntryPrice × 0.97（即最小止损距离 = -3%）
  - 无 ATR 数据时: 兜底使用固定 -8%
```

**设计理由**：
- 高分股票置信度高，给予更宽止损空间（N=2.5），避免被正常波动震出
- 低分股票置信度低，收紧止损（N=1.5），控制单笔亏损
- -8% 硬帽防止极端波动时单笔亏损过大
- -3% 硬底防止止损过紧（尊重A股日常波动）
- ATR 随市场波动率自适应：高波动期止损自动放宽，低波动期止损自动收紧

- **触发条件**：当前价 <= StopLoss（按上述公式计算）
- **操作**：全部卖出，记录止损日期以触发冷却期
- **跌停处理**：若止损日该股跌停（涨跌幅 <= -9.4%），标记为"未成交"，持续跟踪至恢复流动性后卖出（见第六章节）

#### 2.5.3 P2 趋势恶化

- **触发条件**：TrendHealth.Label 变为"危险"
- **操作**：全部卖出
- **警戒状态**：TrendHealth 变为"警戒"时不触发自动卖出，仅输出黄旗警告并标记该持仓进入关注名单。警戒恢复为健康后自动从关注名单移除。

#### 2.5.4 P3 预判转空

- **触发条件**：最新评估数据的 Prediction.Short 从入场时的值变为"中性"或"看空"
- **操作**：全部卖出
- **滞后说明**：此条件存在至少 1 个交易日的固有滞后（详见 2.5.6 节）

#### 2.5.5 P4 全部止盈 / P5 止盈减仓

R2 和 R3 的计算方式（方案B，即插即用，不改数据源）：

```
R2 = EntryPrice x (1 + FixedPct1 / 100)   默认 FixedPct1 = 5.0
R3 = EntryPrice x (1 + FixedPct2 / 100)   默认 FixedPct2 = 10.0
```

- P4 触发条件仅依赖于价格到达 R3，**不依赖** Short 方向
- P5 减仓卖出当前持仓的 50%，向下取整到 100 股；若 50% 不足 100 股则全额卖出
- P4 触发后进入 3 日止盈冷却期，期间该股票不可开新仓

#### 2.5.6 预判转空的滞后处理

预判转空存在至少 1 个交易日的固有滞后：

```
T日 收盘   -> 生成评估数据_T.json（含 Short="看多"）
T+1 09:35  -> 引擎运行，只能读到评估数据_T.json，Short 仍为"看多" -> 不触发
T+1 收盘   -> 股价已下跌，生成评估数据_T+1.json（Short 变为"中性"）
T+2 09:35  -> 引擎比对两份数据，发现 Short 变化 -> 触发卖出（滞后 1 日）
```

**实现方案**：

1. 每个持仓记录中保存 `EntryShortPrediction` 字段，记录入场时的 Short 值
2. 每次引擎运行时，用**最新评估数据**的 Short 值与 `EntryShortPrediction` 比对
3. 若 Short 变为"中性"或"看空"，触发卖出
4. 若无新的评估数据，跳过此检查，正常处理其他出场条件

> 此滞后属于系统固有局限（每日评估数据仅在收盘后生成），无法在现有架构下消除。绩效报告中应标注"预判转空出口存在 >= 1 日滞后，实际效果弱于理论设计"。

### 2.6 交易费用

费用计算采用 A 股真实费率标准：

| 费用类型 | 费率 | 收取方向 | 说明 |
|:---------|:----|:---------|:-----|
| 佣金 | 万分之 2.5 | 买卖双向 | 按成交金额计算 |
| 印花税 | 千分之 1 | 仅卖出时收取 | 按卖出成交金额计算 |
| 最低佣金 | 5 元/笔 | 买卖双向 | 计算佣金不足 5 元时按 5 元收取 |

**费用计算示例**：

买入 1300 股，成交价 72.05 元：
```
成交金额 = 1300 x 72.05 = 93,665.00
佣金 = 93,665 x 0.00025 = 23.42（>= 5 元，按实际收取）
总成本 = 93,665 + 23.42 = 93,688.42
```

卖出 1300 股，成交价 71.50 元：
```
成交金额 = 1300 x 71.50 = 92,950.00
佣金 = 92,950 x 0.00025 = 23.24（>= 5 元，按实际收取）
印花税 = 92,950 x 0.001 = 92.95
净收入 = 92,950 - 23.24 - 92.95 = 92,833.81
```

## 三、数据流

### 3.1 每日运行流程

```
步骤 0: 检测当日是否为交易日（节假日/周末自动跳过）
步骤 1: 读取 sim_config.json 配置
步骤 2: 读取 positions.json 当前持仓
步骤 3: 读取 评估数据_YYYYMMDD.json
步骤 4: 执行数据质量检查（检查通过方可继续）
步骤 5: 调用腾讯行情 API 获取 6 只股票实时行情（含开盘价/现价/涨跌幅）
步骤 6: 检查除权除息配置，计算调整因子
步骤 7: 执行出场检查（按优先级 P1 -> P5）
   P1: 止损（当前价 <= StopLoss）
   P2: 趋势恶化（TrendHealth = 危险）
   P3: 预判转空（Short 变为中性/看空）
   P4: 全部止盈（当前价 >= R3）
   P5: 止盈减仓（当前价 >= R2，卖出50%）
步骤 8: 应用出场交易（更新现金、持仓数量、冷却期标记）
步骤 9: 执行开仓检查
   筛选满足全部开仓条件的股票
   按多股选股优先级排序
   按可用仓位数量依次开仓
步骤 10: 写入交易流水 transactions.csv
步骤 11: 更新持仓文件 positions.json
步骤 12: 计算组合净值 -> 写入每日快照 snapshot_YYYYMMDD.json
步骤 13: 更新绩效汇总 perf_summary.json
步骤 14: 写入运行日志
```

### 3.2 文件格式

#### 3.2.1 positions.json

当前持仓快照。记录现金余额、总资产、每只持仓股的成本、入场日期、入场预判、冷却期标记等。

```json
{
  "Cash": 872345.67,
  "TotalValue": 985432.10,
  "LastUpdated": "20260522",
  "Positions": {
    "601689": {
      "Code": "601689",
      "Name": "拓普集团",
      "Shares": 1300,
      "AvgCost": 72.05,
      "CurrentPrice": 72.05,
      "EntryDate": "20260522",
      "EntryShortPrediction": "看多",
      "LastStopLossDate": null,
      "LastFullTakeProfitDate": null,
      "Support": 64.73,
      "Resistance": 61.77,
      "StopLoss": 60.20,
      "UnrealizedPnL": 0,
      "UnrealizedPnLPct": 0
    }
  }
}
```

**持仓字段说明**：

| 字段 | 类型 | 说明 |
|:-----|:-----|:-----|
| Cash | number | 当前现金余额 |
| TotalValue | number | 总资产 = 现金 + 持仓市值 |
| LastUpdated | string | 最后更新日期 (yyyyMMdd) |
| Positions | object | 持仓股票字典，key 为股票代码 |
| Code | string | 股票代码 |
| Name | string | 股票名称 |
| Shares | int | 持仓股数 |
| AvgCost | number | 平均成本价（含佣金） |
| CurrentPrice | number | 当前市价 |
| EntryDate | string | 入场日期 |
| EntryShortPrediction | string | 入场时的 Short 预测值 |
| LastStopLossDate | string|null | 最近止损日期(用于冷却期检查)，未止损过为 null |
| LastFullTakeProfitDate | string|null | 最近全部止盈日期(用于冷却期检查)，未触发为 null |
| Support | number | 入场时记录的支撑位 |
| Resistance | number | 入场时记录的阻力位 |
| StopLoss | number | 入场时记录的止损位 |
| UnrealizedPnL | number | 浮动盈亏金额 |
| UnrealizedPnLPct | number | 浮动盈亏百分比 |

#### 3.2.2 transactions.csv

完整交易流水，永不清除。每笔买卖操作记录为一行。

```
date,code,name,action,price,shares,amount,commission,stamp_tax,total_cost,reason,entry_prediction
20260522,601689,拓普集团,BUY,72.05,1300,-93665,-23.42,0,-93688.42,开仓_看多_健康,看多
20260522,601689,拓普集团,SELL,71.50,1300,92950,23.24,92.95,92833.81,止损_StopLoss,看多
```

**字段说明**：

| 字段 | 说明 |
|:-----|:-----|
| date | 交易日期 (yyyyMMdd) |
| code | 股票代码 |
| name | 股票名称 |
| action | 操作类型：BUY(买入) / SELL(卖出) / SELL_HALF(减仓) |
| price | 成交价格 |
| shares | 成交股数 |
| amount | 成交金额(买入为负值，卖出为正值) |
| commission | 佣金费用（绝对值） |

**保守估计价定义**（三重回退）：

```
第1优先: min(昨日收盘, 前日收盘)
```

> 设计原则：API 全挂属于极端情况，止损检查宁严勿松。保守估计价使用历史最低价，确保不遗漏真实止损信号。

## 四、绩效指标

### 4.1 核心指标

| 指标 | 计算公式 | 说明 |
|:-----|:---------|:-----|
| 总收益率 | (当前净值 / 初始资金 - 1) x 100% | 衡量整体盈利水平 |
| 日收益率 | (当日净值 / 前一交易日净值 - 1) x 100% | 衡量每日波动 |
| 最大回撤 | min(当日净值 / 前期最高净值 - 1) x 100% | 衡量组合风险水平 |
| 胜率 | 盈利交易数 / 总交易数 x 100% | 已完整平仓的交易统计 |
| 连续失败次数 | 连续净盈亏 <= 0 的交易笔数 | 连败次数可触发预警 |
| 夏普比率 | 预留（详见 4.2） | 风险调整后收益 |
| 超额收益 | 组合总收益率 - 基准总收益率 | 相对沪深300的表现 |

### 4.2 夏普比率

夏普比率基于日频收益率计算，其生效条件如下：

- **生效条件**：至少需要 20 个交易日样本
- **前 20 个交易日内**：SharpeRatio 字段显示 `null`，不触发任何预警
- 计算公式（预留，待样本充足后启用）：

```
SharpeRatio = (日均收益率 - 无风险利率) / 日收益率标准差 x sqrt(252)
```

### 4.3 基准比较

- **基准标的**：沪深 300 指数（代码 000300.SH）
- **数据获取**：每天 09:35 从腾讯行情 API 获取沪深 300 最新值
- **初始值**：首次运行引擎时记录 09:35 的沪深 300 值作为基准初始值
- **日收益率计算**：使用 09:35 截面数据，保持与组合净值同口径
  - 基准日收益率 = (T 日 09:35 基准值 / T-1 日 09:35 基准值) - 1
- **超额收益率** = 组合总收益率 - 基准总收益率

### 4.4 自动预警条件

| 条件 | 动作 |
|:-----|:------|
| 最大回撤 > 8% | 红旗警告，建议暂停开仓 |
| 连续亏损交易 >= 5 笔 | 红旗警告，建议审视信号有效性 |
| 单笔亏损 > 总资产 2% | 黄旗警告，标记该交易 |
| 胜率 < 40% 且总交易 >= 10 | 黄旗警告，建议审视开仓条件 |

### 4.5 连续亏损计数器规则

- 单笔完整平仓（全部卖出）后判断：
  - **净盈亏 > 0**：计数器重置为 0（记为"成功"）
  - **净盈亏 <= 0**：计数器 +1（记为"失败"，包含保本交易）
- P5 止盈减仓（SELL_HALF）不计入连续亏损统计
- 仅完整平仓时才结算盈亏，防止减仓动作干扰预警准确性

## 五、冷却期规则

### 5.1 止损后冷却期（5 个交易日）

- **触发场景**：P1 止损、P2 趋势恶化、P3 预判转空导致全部卖出
- **冷却时长**：5 个交易日
- **计算方式**：从 `LastStopLossDate` 日期起算，至当日间隔 < 5 个交易日则禁止开仓该股票
- **设计目的**：防止 whipsaw（反复打脸），避免同一只股票刚止损又买入导致连续亏损
- **冷却期期满后**：正常参与开仓检查

### 5.2 止盈后冷却期（3 个交易日）

- **触发场景**：P4 全部止盈导致全部卖出
- **冷却时长**：3 个交易日
- **计算方式**：从 `LastFullTakeProfitDate` 日期起算，至当日间隔 < 3 个交易日则禁止开仓该股票
- **设计目的**：P4 全部止盈后股价往往处于短期超买状态，立即重新入场可能追高。3 日冷却期既避免追高，又不至于错过趋势延续
- **冷却期期满后**：正常参与开仓检查

### 5.3 冷却期字段标记

- `LastStopLossDate`（string | null）：未止损过的为 null，止损后标记当日日期
- `LastFullTakeProfitDate`（string | null）：未触发 P4 的为 null，触发后标记当日日期
- 两个字段独立维护，互不干扰

## 六、特殊处理

### 6.1 涨跌停处理

#### 6.1.1 涨停（不开仓）

- **检测条件**：当日开盘涨跌幅 >= 9.4%（考虑 A 股 10% 涨跌停限制的误差）
- **处理方式**：跳过该股当日开仓，日志记录"涨停，跳过"
- **设计理由**：涨停时无法以开盘价成交，且涨停后次日大概率高开，追涨风险大

#### 6.1.2 跌停（不卖出，标记未成交）

- **检测条件**：触发出场检查时，当日涨跌幅 <= -9.4%
- **处理方式**：标记该笔卖出为"未成交"，持续保留持仓，等待后续交易日恢复流动性后再执行卖出
- **日志标记**：记录"触发止损但跌停，标记未成交"
- **设计理由**：A 股有涨跌停限制，跌停时卖单无法成交，模拟交易不应记录虚假成交

### 6.2 除权除息处理

#### 6.2.1 调整因子方案

采用调整因子法处理除权除息，而非暂停止损检查。

**调整因子定义**：

```
Ratio = 除权后开盘价 / 除权前收盘价
```

**调整对象**：将该股票的所有 KeyLevels 等比调整：

```
调整后 StopLoss    = StopLoss    x Ratio
调整后 Support     = Support     x Ratio
调整后 Resistance  = Resistance  x Ratio
```

**调整时机**：引擎每日运行时，检查 `ex_dividend_dates.json` 中当日是否有持仓股除权除息。

#### 6.2.2 ex_dividend_dates.json 配置格式

```json
{
  "20260528": [
    { "Code": "601689", "Name": "拓普集团", "Type": "cash_dividend", "Ratio": 0.98 },
    { "Code": "600036", "Name": "招商银行", "Type": "cash_dividend", "Ratio": 0.97 }
  ]
}
```

| 字段 | 说明 |
|:-----|:-----|
| 日期 key | 除权除息日 (yyyyMMdd) |
| Code | 股票代码 |
| Name | 股票名称 |
| Type | 类型：cash_dividend(现金分红) / stock_dividend(送股) |
| Ratio | 调整因子 = 除权后开盘价 / 除权前收盘价 |

> **说明**：Ratio < 1 表示除权后价格下降（现金分红或送股），> 1 的情况极少（配股等），引擎一并支持。若无配置则不做调整，跳过该日。此配置文件需每月初手动更新。

### 6.3 Support / Resistance 倒挂处理

#### 6.3.1 问题描述

现有评估数据中，部分股票的 Support 值大于 Resistance 值（传统技术分析中 Support 应低于 Resistance），表明数据可能存在异常。

#### 6.3.2 处理方式

引擎不阻塞运行，但执行以下措施：

1. **前置校验**：数据质量检查阶段检测到 `Support >= Resistance` 时，输出 `RED WARNING` 日志
2. **跳过质量校验**：对该股票跳过第 6.5 节数据质量检查中的 Support/Resistance 合理性校验项（`Support < Price x 1.5` 和 `Resistance > Price x 0.5`）
3. **不受影响的部分**：
   - R2/R3 使用方案B（EntryPrice x 固定倍数），不依赖 KeyLevels，不受影响
   - P1 止损依赖 StopLoss，该字段独立于 Support/Resistance，不受影响
4. **其他股票**：不受影响，正常执行全部检查

### 6.4 涨跌停无法成交处理

前述跌停场景的补充说明：

- 触发止损当日若该股跌停，记录"未成交"标记
- 持续跟踪，在后续交易日继续尝试卖出
- 绩效报告中标注"模拟滑点未含涨跌停无法成交风险"

### 6.5 数据质量检查

每次运行引擎前，对评估数据执行以下质量检查。检查不通过则当日跳过该股开仓，但已有持仓的止损检查不受影响。

| 检查项 | 规则 | 失败处理 |
|:------|:-----|:---------|
| KeyLevels 完整性 | Support / Resistance / StopLoss 均存在且为正数 | 跳过当日开仓 |
| Support vs Price 合理性 | Support < Price x 1.5 | 记录警告日志，仍执行已有持仓止损检查 |
| Resistance vs Price 合理性 | Resistance > Price x 0.5 | 记录警告日志，仍执行已有持仓止损检查 |
| StopLoss 合理性 | StopLoss < Price | 跳过该股开仓 |
| CompositeScore 范围 | 0 ~ 100 之间 | 跳过该股开仓 |
| 必要字段存在 | Prediction.Short / TrendHealth.Label / Price / Code 均存在 | 跳过该股 |

> **设计理由**：输入数据异常时，宁可跳过也不能让引擎基于错误数据做交易决策。已有持仓的止损保护是最高优先级，不受数据质量问题影响。

## 八、风险说明

### 8.1 模拟交易与实盘差异

模拟交易系统虽然是按真实 A 股费率标准设计，但与实盘存在以下本质差异：

| 差异项 | 模拟交易 | 实盘 |
|:-------|:---------|:-----|
| 成交确定性 | 假定按指定价格全额成交 | 可能部分成交、无法成交或滑点超预期 |
| 流动性约束 | 不考虑盘口深度 | 大单可能拉抬/打压股价 |
| 时间粒度 | 每日 09:35 单次运行 | 可实时监控、随时操作 |
| 止损执行 | 仅检查日频收盘附近价格 | 可设置条件单自动触发 |
| 涨跌停处理 | 标记未成交，后续跟踪 | 可能连续跌停无法卖出 |
| 心理因素 | 无 | 恐惧/贪婪影响实际决策 |
| 现金管理 | 闲置资金无收益 | 可做逆回购或货基 |

### 8.2 已知限制

以下限制在 v1.0 中不做修改，但作为已知风险记录：

| 风险 | 说明 | 影响 |
|:-----|:------|:-----|
| 盘中止损盲区 | 引擎每日 09:35 仅运行一次，盘中价格若跌破 StopLoss 后反弹，止损不会触发 | 实际止损效果弱于理论，最大回撤可能放大 |
| 预判转空滞后 | 评估数据仅在收盘后生成，预判转空检查存在 >= 1 日滞后 | 实际反应速度比理论慢 1 个交易日 |
| 单股止损距离差异大 | 不同股票止损幅度差异显著(4% ~ 16%)，宽止损股放大最大回撤 | 最大回撤可能超过预期 |
| 初期现金闲置 | 满足开仓条件的股票可能仅 1-2 只，仓位比例低，初期大量现金闲置 | 收益曲线对少数交易高度敏感 |
| 除权除息依赖人工配置 | 需手动维护 ex_dividend_dates.json，漏配导致 KeyLevels 未调整 | 漏配时止损价可能永久高于现价，保护失效 |
| 组合净值波动 | 模拟交易组合仅含 1-3 只股票，集中度高，单只股票波动对净值影响大 | 净值波动大于分散化投资组合 |

## 九、策略优化与迭代管理

### 9.1 核心理念

模拟交易系统的根本目的是**用数据驱动策略优化**。每次交易、每个信号、每笔盈亏都是策略迭代的输入。为此建立三级响应机制，按变更的影响范围和风险等级分级管理，确保迭代过程有章可循。

策略迭代所需的数据分析（交易归因、信号有效性统计、误判分类）来源于[次日后评估白皮书](../每日荐股/事后评估/次日后评估白皮书_v1.5.md)的输出，二者形成"数据输入→策略迭代→规则验证"的完整闭环。

### 9.2 三级响应机制

#### 第一级：日常微调（不影响逻辑）

| 项目 | 说明 |
|:-----|:------|
| **适用范围** | sim_config.json 中的参数数值调整（费率、冷却期天数、止盈倍数等纯数值参数） |
| **白皮书更新** | 不修改白皮书正文。白皮书仅记录设计原则，具体数值以 sim_config.json 为准 |
| **记录方式** | 在当日运行日志 `sim_YYYYMMDD.log` 中记录变更内容和理由 |
| **审批** | 无需审批，分析师自行决定 |
| **示例** | 将 FixedPct2 从 10.0 改为 8.0、将 CooloffPeriodDays 从 5 改为 3 |

> **理由**：配置参数本质是策略的超参数，需要通过回测不断调优找到最优值。如果每次修改参数都更新白皮书，白皮书的版本将频繁变更，反而失去作为权威参考文档的意义。

#### 第二级：规则迭代（逻辑变更，不改方法论）

| 项目 | 说明 |
|:-----|:------|
| **适用范围** | 交易规则的增减、出场优先级的调整、开仓条件的修改、仓位档位调整等逻辑层面的变更 |
| **白皮书更新** | 需更新白皮书对应章节内容，并在版本历史表中记录变更日期、变更内容、变更理由 |
| **触发条件** | 满足以下任一条件即可发起： |
| | ① 连续亏损 >= 5 笔触发红旗预警后，经复盘确认规则缺陷 |
| | ② 单只股票累计亏损 >= 总资产 3%，经归因分析发现规则漏洞 |
| | ③ 胜率 < 40% 且总交易 >= 10 笔，经统计分析确认规则需要调整 |
| | ④ 分析师基于交易数据复盘提出明确的规则改进方案 |
| **记录方式** | ① 在白皮书版本历史表中新增一行 |
| | ② 在当日运行日志中记录规则变更内容和决策依据 |
| **审批** | 需至少两名分析师确认（防止单人主观判断偏差） |
| **示例** | 新增"开盘 5 分钟内不卖出规则"、修改"P3 优先级高于 P2"、增加"N 连败后暂停该股交易" |

> **数据驱动决策原则**：规则迭代不应凭"感觉"或"直觉"进行。每次规则变更必须基于实际交易数据的统计归因——找到具体的交易记录、具体的信号、具体的数字作为变更依据。没有数据支撑的规则变更，不予执行。

#### 第三级：方法论重构（核心方法论变更）

| 项目 | 说明 |
|:-----|:------|
| **适用范围** | 评分体系重构、信号计算逻辑变更、新增或移除核心交易策略等影响系统根基的变更 |
| **白皮书更新** | 发布新版白皮书（v2.0、v3.0 等）。旧版白皮书归档保留，附版本对照表说明变更要点 |
| **触发条件** | ① 累计亏损达到初始资金 10%，确认当前方法论存在系统性缺陷 |
| | ② 胜率 < 30% 且总交易 >= 20 笔，确认信号系统失效 |
| | ③ 最大回撤连续超过预警线(8%)达 3 次，确认风控体系不足 |
| | ④ 市场结构发生重大变化（如交易规则变更、涨跌幅限制调整等） |
| | ⑤ 积累 >= 60 个交易日数据后，系统性审视全部规则并进行版本升级 |
| **记录方式** | ① 发布新版白皮书，在 §一 中说明版本变更的核心差异 |
| | ② 旧版白皮书移至 `归档/` 目录，按 `模拟交易白皮书_v1.0.md` 格式保留 |
| | ③ 版本历史表记录本次重构的触发原因和主要变更清单 |
| **审批** | 集体决策，记录每位参与者的意见和最终结论 |

### 9.3 三级响应流程图

```
                              策略改进建议
                                    |
                                    v
                    ┌────────────────┴────────────────┐
                    │         判断变更类型              │
                    └───────┬───────────────┬──────────┘
                            │               │
                    数值参数调整          逻辑规则变更
                            │               │

                    ┌──────────────┐  ┌──────────────────┐
                    │  第一级      │  │ 影响底层方法论？ │
                    │  日常微调    │  └──┬───────────────┘
                    │  (不改白皮书) │     │              │

                    └──────────────┘     │              │
```

### 9.4 触发条件的量化基线

| 指标 | 第一级触发 | 第二级触发 | 第三级触发 |
|:-----|:----------|:----------|:----------|
| 连续亏损 | 3 笔 | >= 5 笔 | >= 8 笔 |
| 最大回撤 | > 3% | > 5% | > 8%（连续 3 次超预警线） |
| 胜率（交易 >= 10） | < 50% | < 40% | < 30% |
| 单股累计亏损 | > 1% 总资产 | > 3% 总资产 | — |
| 累计净值亏损 | — | — | > 10% |
| 数据积累 | — | >= 20 笔交易 | >= 60 个交易日 |

> **说明**：以上基线为默认值，团队可根据实际情况调整。基线数据随策略迭代同步更新。

**自动化状态**：
- Tier 1 检测已由 `check_tier_triggers.ps1` 实现自动化
- 每次引擎运行（sim_trading.ps1）结束后自动调用检测器，结果写入当日日志

### 9.4.1 多级触发冲突处理

当多个响应级别的触发条件同时满足时，按以下规则处理：

| 并发情况 | 处理规则 |
|:---------|:---------|
| 第二级与第三级条件同时满足 | 执行第三级（方法论重构），第三级涵盖第二级的所有变更 |
| 同一级别多个触发条件同时满足 | 满足其一即可发起，无需等待全部条件触发。记录最先达到的触发条件作为发起依据 |
| 第一级微调累计触发第二级基线 | 当月第一级微调变更超过 3 次，或连续 2 个月均有第一级微调，自动升级为第二级规则迭代审查 |
| 新数据与现有规则冲突 | 优先保护已有持仓（执行止损/止盈检查），再评估规则变更 |

**升级自动触发机制**：当第一级微调的频率或累计影响达到第二级基线时，应自动发起规则迭代审查，防止"微调过多、积小变为大变"。

### 9.5 评分反馈闭环

模拟交易的止损记录通过 trade_to_score_feedback.py 反馈到评分系统：

1. **止损归因**: 读取 transactions.csv 的 P1 止损记录
2. **维度分析**: 回溯对应日期的评分明细，识别误判维度
3. **调整建议**: 生成"调高某维度及格线"或"观察某维度可靠性"的建议
4. **人工确认**: 建议经人工确认后，更新 scoring_engine_v2.py 参数

此闭环打通了模拟交易与每日评分系统的双向数据流动。

### 9.6 复盘周期

| 周期 | 频率 | 内容 | 输出 |
|:-----|:-----|:------|:------|
| 日复盘 | 每个交易日 | 检查当日交易是否按规则执行、有无异常 | 日志 |
| 周复盘 | 每周五收盘后 | 归因分析：本周盈亏从何而来、哪些信号有效 | 周报 |
| 月复盘 | 每月最后一个交易日 | 完整绩效分析：胜率、回撤、信号有效性统计，触发条件检查；汇总当月所有第一级微调变更清单 | 月报 + 变更清单 + 白皮书更新评估 |
| 季复盘 | 每季度 | 系统性审视全部规则，评估三级响应触发状态 | 季度报告 + 版本规划 |

### 9.7 版本管理规范

| 版本号 | 对应级别 | 说明 |
|:-------|:---------|:------|
| v1.x | 第二级 | 规则迭代，x 为迭代次数（v1.1、v1.2...） |
| v2.0+ | 第三级 | 方法论重构，主版本号递增 |

- 第一级（日常微调）不改变版本号
- 第二级（规则迭代）每次更新需在版本历史表中记录变更日期、变更内容、变更理由
- 第三级（方法论重构）发布新主版本，旧版本归档

**与 version_supervisor 联动**：

- 白皮书版本变更时，必须同步更新 `代码文件/监督机制/version_supervisor.ps1` 中的 `$WHITEPAPERS` 哈希表，注册新版本号及文件路径
- CHANGELOG.md 独立记录每次变更，不再合并到版本历史表中
- 每次提交前运行 `version_supervisor.ps1 -CrossCheck` 验证版本一致性

### 9.8 长期积累与系统性审视

当系统运行满 60 个交易日或积累 30 笔以上完整交易后，应主动发起一次全面的方法论审视。届时需：

1. 汇总全部交易数据，按股票、信号方向、评分段等维度分组统计
2. 识别哪些规则有效、哪些规则形同虚设、哪些规则产生了负贡献
3. 评估三级响应中各触发条件的状态，判断是否需要升级响应级别
4. 将系统性审视结论写入白皮书附录，作为下一版本的决策依据

## 十、v1.5 新增功能（2026-05-24）

### 10.1 大盘系统性熔断（Sentinel设计）

每日引擎运行时检查沪深300实时涨跌幅，触发大盘级别保护：

| 级别 | 条件 | 操作 |
|:----:|:-----|:-----|
| 熔断 | CSI300 跌幅 > 5% | 强制减仓50% + 停开仓3个交易日 |
| 警告 | CSI300 跌幅 > 3% | 当日不开新仓 |
| 流动性枯竭 | 全市场成交额 < 5000亿 连续2日 | 开仓金额减半 |

**数据来源**: 腾讯行情API `qt.gtimg.cn/q=sh000300`，计算 `(当前/昨收-1)×100` 作为涨跌幅。

**实现位置**: `risk_framework.ps1` → `Get-MarketCircuitBreaker`，两套模拟系统共用。

### 10.2 两赛道共享冷却期（Vega设计）

两套模拟交易系统（重点股票 + 每日荐股）通过共享文件同步冷却期状态：

```
模拟交易/共享模块/shared/cooldowns.json
```

**同步触发点**:
- 止损/止盈卖出后 → 写入共享冷却期
- 开仓前冷却期检查 → 三层查找：当前持仓 → 本系统持久化冷却期 → 跨系统共享冷却期

**设计理由**: 一只股票在每日荐股赛道止损后，重点股票赛道也应避免同日重新买入——两赛道面对同一市场，信号不应相互矛盾。

### 10.3 数据质量降级机制（Pulse设计）

`check_data_quality.ps1` 独立于引擎运行，检查API连通性、文件新鲜度、推荐数下限、null穿透、缓存TTL。

| 质量标记 | 含义 | 引擎行为 |
|:-------:|:-----|:---------|
| normal | 所有数据源正常 | 正常开仓(100%仓位) |
| degraded | 部分数据源降级/文件过时 | 仓位降至80% |
| cached | 全部API不可用/全部使用缓存 | 当日不开新仓 |

**输出格式**: JSON → stdout → `sim_trading_daily.ps1` Step 4 捕获。

### 10.4 板块相位持仓检查（Sentinel设计）

每日引擎运行时检查已有持仓的板块健康状态：

| 条件 | 动作 | 级别 |
|:-----|:-----|:----:|
| 持仓板块Phase退入"衰退期" | 输出警告日志 | 黄旗 |
| 板块主线置信度 < 40 | 强制减仓 | 红旗 |

**实现**: `risk_framework.ps1` → `Get-SectorPhaseAlerts`。

### 10.5 行业集中度限制（Vega设计）

每日荐股赛道新增行业集中度控制：同一申万一级行业最多持有 2 只股票。

**实现**: `risk_framework.ps1` → `Get-IndustryConcentration`。

**违规处理**: 当日不开该行业新仓，已有持仓不受影响。

### 10.6 周度反馈链路（Alpha设计）

每周一 09:00 自动运行 `weekly_feedback_loop.ps1`：

```
后评估 issues.csv → 检测14天内异常 → 计算周度趋势 → 生成FB001-003自动建议 → 腰子审核
```

**输出**: `模拟交易/每日荐股赛道/周报/feedback_recommendations_YYYYMMDD.md`

**周度因子归因**: `weekly_factor_attribution.py` 同步运行，计算 Spearman(评分,收益) + 板块阶段胜率。

### 10.7 月度相位折扣校准（Alpha设计）

每月第一个周一 10:00 自动运行 `monthly_phase_calibration.ps1`：

```
上月交易数据 → 逐相位统计胜率&盈亏 → 搜索最优折扣系数(±0.10, 步长0.05) → 生成校准建议书
```

**输出**: `模拟交易/每日荐股赛道/月报/phase_calibration_YYYY-MM.md`

**流程**: Alpha自动生成 → 腰子审核 → 更新白皮书§二十二 → 更新评分引擎 `phase_penalty_map` → 灰度3天 → 正式上线

### 10.9 每日荐股赛道 ATR 动态止损

> 详见 `每日荐股模拟交易白皮书` §2.5.1
