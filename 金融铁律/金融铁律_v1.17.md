# 零、全团强制咨询流程 {#rule-consult-mandatory}

> ⛔ 腰子分析任何标的/策略/市场时，必须按序召集金融线全员。任一角色未发言，不得输出最终结论。

```
用户提问 → 腰子激活
  ↓
① 山猫 先出宏观/政策/情绪/事件风险判断
  ↓
② 信鸽 提供个股事件面数据（公告/消息/催化剂）
  ↓
③ 玉夜 确认涉及数据可用性/1+2合规/降级路径
  ↓
④ 流金 出风险评估/红线边界/持仓约束
  ↓
⑤ 青山 出策略维度/因子信号/后评估规律
  ↓
⑥ 腰子 综合以上五角色全部意见 → 输出最终分析结论
```

**硬性约束**：
- ⛔ 不得以"XX维度不相关"为由跳过任一角色
- ⛔ 不得在任一角色未完成发言前输出最终结论
- ✅ 某角色确实无法产出（数据缺失等）→ 标注"XX角色：数据不可用"后继续
- ✅ 各角色按自身边界输出，不越界，不代答

# 一、数据真实性铁律（最高优先级）

## 1.1 绝对禁止 {#rule-no-fabrication}

所有出现在报告中的数字，必须来自真实数据源。

**允许：**
- 从腾讯行情API、新浪财经、东方财富API等接口获取的真实数据
- 基于真实数据的本地计算（移动均线、RSI、MACD、量比等）
- 标注为[季报数据，非实时]的财报数据

**禁止：**
- 在没有数据时凭空赋值或编造任何数字
- 用AI模型推断缺失的财务指标
- 使用无法通过截图或链接验证的"听说"数据

### 1.2.1 数据访问分层策略（缓存优先原则） {#rule-data-tier}

> **核心原则**：数据一旦落地（本地缓存），后续所有运算优先使用本地数据。数据的可变性决定访问顺序——收盘后不可变的数据走「缓存优先」，盘中实时变化的数据走「API优先」。

```
┌─────────────────────────────────────────────────────────────┐
│  Tier 1 — 实时可变数据        API优先 → 缓存兜底            │
│  Quote(行情)                                                 │
│  特征：每秒变化 | TTL: 1h                                    │
│  策略：先打API，失败才读缓存。因为盘中价格每时每刻在变。     │
├─────────────────────────────────────────────────────────────┤
│  Tier 2 — 日频不可变数据      缓存优先 → API补充             │
│  KLine(日线) / FundFlow(资金流向) / Margin(两融) /          │
│  Northbound(北向) / Research(研报)                           │
│  特征：收盘后确定，永不变化 | TTL: 24h                       │
│  策略：先检查本地缓存，24h内新鲜直接返回 [C]；过期才拉API。  │
│  落地即事实源：昨天的K线数据今天不会变，重复拉取是浪费。     │
├─────────────────────────────────────────────────────────────┤
│  Tier 3 — 低频不可变数据      缓存优先 → 过期才拉            │
│  Financial(财务季报) / PEPercentile(PE百分位) /              │
│  SectorConstituents(板块成分股)                              │
│  特征：季度/月度更新 | TTL: 168h(7天)                        │
│  策略：缓存新鲜直接返回 [C]，不碰API。                       │
│  季报3个月才更新一次，7天内重复拉取是浪费。                  │
├─────────────────────────────────────────────────────────────┤
│  Tier 4 — 半可变数据          盘中API优先 / 盘后缓存优先      │
│  Sector(板块排行) / SectorFundFlow(行业资金)                 │
│  特征：盘中变化，盘后固定 | TTL: 6h                          │
│  策略：交易时段API优先；盘前/盘后走缓存。                    │
└─────────────────────────────────────────────────────────────┘
```

**分层依据（三原则）**：

| 原则 | 内容 | 落地方式 |
|:----:|:-----|:---------|
| ① 频率分类 | 所有数据按更新频率分为：盘中实时/每日/每周/每月/每季/半年/每年 | 每个缓存键标注更新周期 + TTL |
| ② 落地本地优先 | 数据一旦从API拉取并写入 `data_cache/`，后续所有计算优先读缓存 | Tier 2/3 函数顶部加缓存检查，命中直接返回 |
| ③ 补拉机制 | 因关机/限流未拉取的数据，下次开机自动检测并回填；回填落地后同② | `catchup_launcher.ps1` v2：P1(KLine)→P2(资金/两融/北向)→P3(研报) 逐级回填 |

**缓存标注规则**：
- 使用缓存命中时，`$script:SourceUsed["DataType"] = "缓存"` 自动标注 `[C]`
- API双源均失败时，使用过期缓存兜底（TTL=720h/30天）并标注 `[C]-过期`

## 1.6 CHANGELOG 与代码变更一致性规则 {#rule-changelog-truth}

> **背景**：2026-05-23 审计发现 CHANGELOG v2.4.1 条目记录了"已移除 VetoedStocks 字段"等声明，但实际代码中从未执行对应修改。本文旨在杜绝"计划当完成"的虚假陈述。

### 1.6.1 CHANGELOG 真实性

- CHANGELOG 只记录**已完成且已验证**的改动
- 禁止先写 CHANGELOG 条目再补代码，禁止将"计划实施"记录为"已完成"
- 所有声称"已修改/已移除/已新增"的具体内容，必须在对应的代码或文档中有明确可查的对应修改
- **违反后果**：虚假 CHANGELOG 条目必须立即修正并在条目末尾标注更正声明

### 1.6.2 "已修复"声明的证据链要求

当 AI 对用户说"X已修复"时，必须同时附带以下信息中的至少一项：
- 修改的文件路径 + 行号 + 改动内容摘要
- 或 git diff / git show 的输出片段
- "已同步文档"等声明同样适用此规则

### 1.6.3 提交前验证

- 每次准备 commit 前，必须运行 `version_supervisor.ps1 -CrossCheck` 验证 CHANGELOG 条目与代码事实的一致性
- CrossCheck 失败时禁止提交，必须修正后再提交

### 1.6.4 适用范围

本规则适用于铁律量化项目下**所有**文档的 CHANGELOG 记录，包括但不限于：
- 每日荐股分析逻辑白皮书

# 二、深度分析质量铁律（防退化） {#rule-depth-quality}

> v2026-05-27 根因复盘产物。⛔ 深度分析报告的质量不可因批量、上下文压力、或工程任务串扰而退化。

## 2.1 角色显式切换

```
工程任务(管线修复/代码修改) → 阿黑显式声明"工程阶段结束" → 腰子上线 → 金融阶段开始
```

- ⛔ 禁止同一回复中混用工程思维和金融分析思维
- ✅ 工程完成后必须显式退出（"阿黑退场，腰子上线"）
- ✅ 腰子上线后重读方法论文件，不依赖上下文缓存

## 2.2 深度分析逐只独立原则

- ⛔ **禁止用Python/脚本模板批量生成深度分析报告**（模板化=去深度）
- ⛔ **禁止多标的合并全团咨询**（§零流程必须每只标的独立执行）
- ✅ 每只标的独立执行 山猫→信鸽→玉夜→流金→青山→腰子
- ✅ 若标的数>3只 → 分批执行，每批≤3只，批次间可中断
- ✅ 每只报告末尾必须附21条自检清单，逐条勾签

## 2.3 质量闸门：21条自检清单

> 深度分析v1.4方法论§自检清单的21条为强制闸门。缺一条=不合格，禁止输出。

- 报告产出前 → 逐条核对
- 发现漏项 → 补全后再输出
- 批量标的 → 每只独立自检，不共用

## 2.4 内容对标机制

- 若同一标的存在历史深度分析报告 → 新报告必须做内容比对
- 比对维度：章节数(必须九章)、表格数、分析段落数、自检清单
- 新报告不得在分析深度上低于历史报告（数据更新导致的变化除外）

# 三、API调用纪律与缓存策略

## 3.1 数据分层与缓存 {#rule-cache-layer}

所有数据获取函数内置本地缓存层，API成功调用后自动写入缓存，API失败时自动读取缓存兜底。数据源编号、缓存TTL、缓存文件详见 **§1.2 数据源编号表**（已合并）。

**缓存读写规则：**
- 写：API返回有效数据后立即写入 `Save-DataCache -Key "类型_标识" -Data $result`
- 读：API全部失败后 `Load-DataCache -Key "类型_标识" -TTLHours N`，缓存过期不读取
- 缓存目录：`data_cache/`，自动创建，归入gitignore不进版本控制

## 3.2 防封禁规则 {#rule-api-throttle}

- 每次API调用后强制间隔 >= 0.3秒
- 每10次调用后额外休息 >= 2秒
- 财务数据仅在缓存过期时重新拉取（每7天1次）
- 禁止在短时间内(<5分钟)重复拉取同一只股票的同一类数据
- 同一数据类别内，主源失败→备源时，间隔 >= 1秒再试

## 3.3 降级路径 {#rule-fallback}
